# evoxc-compiler — the native builder and transform engines

## Intent

`evoxc-compiler` is the single native home of graph construction and graph-to-graph transformation: the mutable `Builder`, the `vectorize`/`vmap` engine with the builtin batching rules, the AD engines (`jvp`/`vjp`/`grad`) with the builtin derivative rules, the extension-rule inlining bridge, and the `batch_functions` population-merge engine — the sixth builtin graph transform.
`batch_functions` merges N programs with identical input/output signatures but different bodies onto ONE program whose leading axis is a STATIC length-N function axis; `evoxc/transforms/batch_functions.py` is its Python frontend (validation, native call, `Graph` reconstruction), and the merge logic itself is `./src/batch_functions/`.
It mirrors, op for op and error for error, the Python authority — `evoxc/transforms/vectorize.py`, `vmap.py`, `batching.py`, `rules.py`, `autodiff.py`, `grad.py`, `jvp.py`, `vjp.py` and `evoxc/ir/builder.py` — with one deliberate exception: `vmap`'s non-leading `out_axes` rearrangement is implemented here ahead of the Python path (which still defers those entries).
The binding FFI and wire format are `../../native/CONTEXT.md`; the core API this crate builds on is `../evoxc-core/CONTEXT.md`; this file refines crate internals and changes neither.
Python keeps the public frontend surface (decorators, pytrees, static values, reconstruction metadata); this crate sees only an `evoxc-native-ir` `Program` plus a typed config, and it holds no Python objects.

## API Surface

### Crate entry points

- `transform(kind, &Program, &TransformConfig, Option<&dyn ExtensionRule>) -> Result<TransformOutput>` — the one entry point the PyO3 binding calls; it dispatches to `vectorize::vectorize_graph`, `vmap::vmap_graph`, `ad::grad_graph`, `ad::jvp_graph` or `ad::vjp_graph`.
- `transform` always uses the process-wide builtin registry (`builtin_registry()`); a caller-supplied registry is reachable only through those module-level functions with an explicit `TransformEnv`.
- `TransformKind { Vectorize, Vmap, Grad, Jvp, Vjp }` with `as_str()` (the wire/error spelling) and `parse()` (an unknown name is a `TransformError` listing the five kinds).
- `TransformConfig { axes, input_axes, out_axes, batch_dim_name, argnums, tangent_inputs, cotangent_inputs }` — one typed config struct, each field used by the kinds in the table below.
- `TransformOutput { program, output_ids, input_ids, batch_dim }` — the transformed module (entry = its first function), the return operands in order, the function's block arguments in order, and the fresh batch `Dim` name (`None` for every AD kind).
- `OutAxes { All(Option<i64>), PerOutput(Vec<Option<i64>>) }` with `resolve(outputs, transform)` normalizing one entry per output.
- `ExtensionRule` (trait) with `call(&self, &ExtensionRequest) -> Result<Option<ExtensionResponse>>`; `Ok(None)` means "no rule" and the engine raises its ordinary `TransformError`, an `Err` propagates verbatim.
- `ExtensionKind { Batching, Jvp, Vjp }` with `as_str`/`parse` (`batching`, `jvp`, `vjp`).
- `ExtensionRequest { kind, op_name, rule_key, attributes, operand_types, result_types, axes, tangents, cotangent_type }`, built with `new(kind, &RuleOp)` and refined by `with_axes` / `with_tangents` / `with_cotangent_type`.
- `ExtensionResponse { module, entry, output_ids, output_axes }`, built with `new(module, entry, output_ids)` and refined by `with_output_axes`; `output_ids` is `Vec<Option<ValueId>>`, where `None` is a structurally-zero dual (`Dual::ZeroTangent`) and is legal only for `jvp`/`vjp` responses (a batching response needs a real value per result).
- `Registry { batching, jvp, vjp }` with `new()` / `register_builtins()`; `builtin_registry() -> &'static Registry` is the `OnceLock` singleton the FFI path reads.
- `batching::builtin_rule_keys() -> Vec<String>` (re-exported as `builtin_rule_keys`) is read-only introspection over that singleton's batching keys — sorted, builtin-only (never `block:*`/`external:*`/`sparse_*`), and the source of the FFI `batching_rule_keys()`.
- `TransformEnv<'a> { registry: &'a Registry, extension: Option<&'a dyn ExtensionRule> }` with `builtin()`, `with_registry(&Registry)` and `with_extension(&dyn ExtensionRule)`.
- `VERSION` (the crate version marker).

### Per-kind config usage

| kind | fields |
|---|---|
| `vectorize` | `input_axes` and/or `axes` (every input needs an entry: `Some(0)` maps the leading axis, `None` shares the input), optional `batch_dim_name` |
| `vmap` | the `vectorize` fields plus `out_axes` (default `All(Some(0))`; any integer entry or `null` per output, negative entries resolve like Python indices) |
| `grad` | `argnums` over the flattened tensor inputs (absent = every input in input order; an explicit list keeps its own order) |
| `jvp` | `tangent_inputs` (required; the flattened input indices that get an explicit tangent block argument) |
| `vjp` | `cotangent_inputs` (required; the flattened output indices that get an explicit cotangent block argument) |

### Batch functions

- `batch_functions::batch_functions(programs: &[Program], config: &BatchFunctionsConfig) -> Result<BatchOutput>` — merges N same-signature programs onto one STATIC length-N function axis (row `i` evaluates program `i`), under the process-wide builtin registry (`TransformEnv::builtin()`).
- `batch_functions::batch_functions_with_env(programs, config, env)` — the same engine with an explicit `TransformEnv`: a caller-supplied rule registry plus the optional host extension bridge, so `sparse_*` / `dense_dot_sparse` / `block:*` / `external:*` keys answer through their registered rules.
- `BatchFunctionsConfig { axes: Vec<Option<i64>>, out_axes: Vec<Option<i64>>, switch_ops: SwitchOps, bands: Bands, alignment: Alignment }` with `Default` (`axes`/`out_axes` empty — missing trailing entries default to `Some(0)` — `switch_ops = SwitchOps::None`, `bands = Bands::Flat`, `alignment = Alignment::Variant`); the config carries already-normalized per-tensor-leaf entries.
- `out_axes` entries are validated against the PER-FUNCTION output rank, except that a rank-0 output accepts the mapped entry `0` because the merged value carries the static function axis as its leading dim (`(N,)`); every other out-of-range entry is an explicit `TransformError` (`axes=0` on a rank-0 input stays out of range).
- `SwitchOps { None, Default, Groups(Vec<MergeGroupSpec>) }` with `Default` = `None` and `From<bool>` (`true` → `Default`); `Default` means the `elementwise` + `comparison` schema-category pair.
- `MergeGroupSpec { Category(String), Ops(Vec<String>) }` — one explicit merge group: every op of an IR category, or this set of IR op names; declaration order decides the first match.
- `canon::parse_switch_groups(&SwitchOps) -> Result<Vec<MergeGroup>>` validates the selection into groups (the `Default` pair, or one `MergeGroup { kind, category, names, label }` per explicit spec; an empty group, an unknown category or an unknown op name is a `TransformError`).
- `Bands { Flat, Explicit(usize), Auto }` (`Default` = `Flat`) and `Alignment { Variant, Occurrence, Auto }` (`Default` = `Variant`) with `Alignment::parse(&str)` / `Alignment::as_str()` (`"variant"` / `"occurrence"` / `"auto"`); `Bands` and `SwitchOps` spellings are parsed by the FFI layer.
- `BatchOutput { program: Program, output_ids: Vec<ValueId>, input_ids: Vec<ValueId>, report: BatchReport }` — the merged entry module, its `return` operands in order, its entry block arguments in order, and the merge report.
- `BatchReport` holds exactly the twelve Python `BatchReport.as_dict()` keys: `n_functions`, `value_classes`, `shared_classes`, `switched`, `stacked_constants`, `output_muxes`, `emitted_ops`, `bands`, `band_sizes`, `band_strategy` (`"flat"` / `"explicit"` / `"auto"`), `cost_estimate`, `flat_cost_estimate`.
- `switched` is a `Vec<SwitchRecord>` with the nested keys `group`, `variants`, `rows_per_variant`; `BatchReport::to_json() -> serde_json::Value` renders the identical payload (tuples become arrays, a cost estimate a JSON number or `null`), which is what the FFI returns as `batch_report`.
- Validation is one ordered pipeline: a non-empty program list → program shape (exactly one function, one entry block, a `return`, one block argument per declared input) → cross-program contract (identical input/output counts, dtype via `DTypeError`, shape via `ShapeError`) → per-op batchability (a `TransformError` naming the op, checked before any banding decision) → `axes` normalization → `out_axes` normalization → the `Explicit(k)` range check and `switch_ops` parsing → the non-flat `out_axes = None` check → the partition → flat or banded emission.

### Rule surface

- `RuleCtx<'a> { builder, batch_dim }` with `new(builder)` (AD rules) and `with_batch_dim(builder, name)` (`vectorize`/`vmap` rules).
- `RuleCtx` type readers: `ty`, `dtype`, `rank`, `shape`.
- `RuleCtx` emission: `op`/`op1`/`call`/`unary`/`binary`/`ternary`/`constant`/`scalar`/`scalar_i64`/`arange_i64`, structural `reshape`/`broadcast`/`transpose`/`slice`/`pad`/`concatenate`/`gather`/`scatter`, reductions `reduce`/`reduce_sum`/`reduce_prod`/`reduce_mean`/`reduce_max`/`reduce_min`, `argmax`/`argmin`, `cast`/`select`/`dot`/`conv`/`solve`/`tril`/`triu`/`cumsum`/`cumprod`/`stop_gradient`.
- Every `RuleCtx` emission re-validates and re-infers through the native schema table, exactly like the frontend.
- `RuleOp { name, attributes, original_operand_types, original_result_types, operands, operand_types, results, result_types, location }` — one op as a rule sees it, captured with `from_source(&Program, &Op)` and refined by `bind_operands(&Builder, &[ValueId])` / `bind_results(&Builder, &[ValueId])`.
- `RuleOp` accessors: `rule_key()` (`block:<name>`, `external:<name>` or the op name), `display()`, `original_operand(i)`, `original_result(i)`, then `int`/`opt_int`/`ints`/`opt_ints`/`bool`/`str`/`dtype`/`shape_attr`/`float`/`nested_ints`/`any`.
- `ConvParams { strides, padding, input_dilation, kernel_dilation, feature_group_count, batch_group_count }` with `from_op(&RuleOp)` (validated read) and `to_attrs()` (IR rebuild).
- `MappedAxes` (batching metadata) and `Dual { ZeroTangent, Value(ValueId) }` (AD metadata), both `Copy`.
- `BatchingRule = fn(&mut RuleCtx, &RuleOp, &[MappedAxes]) -> Result<(Vec<ValueId>, Vec<MappedAxes>)>`, `JvpRule = fn(&mut RuleCtx, &RuleOp, &[Dual]) -> Result<Vec<Dual>>`, `VjpRule = fn(&mut RuleCtx, &RuleOp, &[Dual]) -> Result<Vec<Dual>>`.
- Builtin coverage: 61 batching keys (40 pointwise — 28 `ELEMENTWISE_OPS` + the 12 non-differentiable pointwise ops — 7 reduction, 8 structural, 6 linalg) and 60 JVP plus 60 VJP keys (27 pointwise, 5 reduction, 7 structural, 14 non-differentiable zero rules plus `stop_gradient`, 6 linalg).

### Builder

- `Builder { program, function, block }` — a mutable builder that appends to ONE open block of ONE function of a program; there is no insertion cursor.
- `new(module_name)` / `with_metadata(module_name, metadata)` start an empty module; `resume(program, function, block)` continues an existing one (allocators reseeded above every live id, missing function = `TransformError`).
- `open_function(name, input_types)` creates the entry block arguments and the function; `set_function_metadata`, `program`, `block`, `function_name`, `block_arguments`, `value_type(s)`, `block_op_ids`, `block_op_len`, `terminator_operands` read the state under construction.
- `emit`/`emit_typed`/`emit_typed_one`/`unary`/`binary`/`ternary`/`constant` write ops; `set_terminator` writes the `return`; `take_terminator` removes it again; `set_op_location` stamps a location on an emitted op; `set_op_location_from(start, location)` stamps it on every op appended since the `block_op_len()` snapshot `start` (an index-range write over the open block — no op-id clone, no membership scan); `push_op_with` is the explicit-location form of `emit`.
- `inline_function(sub, entry, arg_values)` splices a straight-line subgraph with SSA remapping and returns the sub-value → new-value map.
- `finish()` rebuilds the use lists, refreshes every function's `output_types` from its terminator, and returns the `Program`.
- Free helpers: `declared_attrs(&OpSchema)` / `result_text(&OpSchema)` (message rendering), `scalar_payload(dtype, value)` (re-exported from `emit`), `emit::dims_i64`, `emit::i64_vector_payload`, `emit::f32_to_f16_bits`.

## Constraints

- Dependencies are `evoxc-core` and `serde_json` only; no `pyo3`, no Python, no `evoxc-runtime` and no backend/compiler knowledge.
- Builtin inference and builtin rules live here (and in `evoxc-core`), never as a second Python-side implementation; the Python graph path is the parity oracle, never the other way round.
- Rules never touch a `Program` directly: they read `RuleOp` and emit through `RuleCtx`, which goes through schema validation + `infer_op` on every op.
- No rule ever falls back to a Python loop, a silent pass-through or a guessed shape; a missing rule is an explicit `TransformError` naming the op (and the registration call to add one).
- User errors are `Result` values with `Error::transform` / `Error::shape` / `Error::verification`; rule code uses guarded accessors instead of indexing, and no `unwrap`/`expect` on user input.
- Messages carry the transform prefix (`vectorize:`, `vmap:`, `jvp:`, `vjp:`, `grad/vjp:`) and reuse `format_shape` so the dims render like the Python tuples.
- The transform never mutates its input `Program`: a fresh module is built from `Builder::with_metadata(&program.name, program.metadata)` (+ `batch_depth` metadata preserved for `vectorize`), and op order, locations and attributes are carried forward.
- Ids are fresh and allocated by the program's reserved allocators; decoded ids are never renumbered and `Builder::resume` reseeds first.
- Every emission is statically typed: shapes are `Dim`s, symbolic dims are handled where the rules say so and rejected with an explicit `TransformError` everywhere else.
- `src/ad/reduction_structure.rs` is the only source file still above the ~1000-line guideline (`batching/structure.rs` sits just under it); `src/ad/mod.rs` and `src/ad/engine.rs` are both under it, split into the frontend surface and the sweep engine along the module's existing boundary — split further only along the existing per-category rule boundaries.

## The mappedness model

- `MappedAxes` is a leading-batch-axis COUNT (`MappedAxes::new(count)`, `UNMAPPED`, `count()`, `is_mapped()`, `axis()` → `Some(0)`/`None`), because mapped axes are always a contiguous prefix of the shape.
- v1 maps exactly the leading axis: `MappedAxes::from_axis` maps `Some(0)` to count 1 and `None` to 0, and any other axis value is rejected during input-axis normalization (`must be 0 (the leading axis) or None in v1`).
- Nesting accumulates counts through rule results (a second pass sees count 1 and returns count 2); a rule result is rejected when `count > rank`.
- One fresh `Dim` per pass: `batch_dim_name` uses `config.batch_dim_name` when non-blank, else the module metadata key `batch_depth` (`batch` at depth 0, `batch_1`, `batch_2`, …).
- All mapped inputs of one pass share that single `Dim`, so same-level batch extents unify by construction and `is_batch_dim` recognizes only an UNSIZED named dim of that name (or `max` of two such dims).
- `resolve_input_axes` requires an entry per input (from `input_axes` positionally, overridden by the value-id-keyed `axes`), errors on an entry naming a non-input value id, and errors when an input has no entry at all.
- Rule-result validation is one value plus one `MappedAxes` per source result, with counts not exceeding the produced rank; a mismatch is a `TransformError` naming the op.
- `vmap` then normalizes `out_axes` per output (`OutAxes::resolve`; a bare `All` entry on a graph with more than one tensor output is rejected), then against the output rank `r`: a negative entry is `k + r`, and an entry `< -r` or `>= r` is a `TransformError` naming the output index, the entry and the rank (a rank-0 output accepts only `0`).
- A mapped output with entry `k` moves its leading batch axis to position `k` with one `transpose` (permutation `[1..k, 0, k+1..r-1]`, so output axis `j < k` reads input axis `j+1`, axis `k` reads `0`, `j > k` reads `j`); `k == 0` emits nothing.
- An unmapped output with entry `k` inserts a size-one axis at `k` with one `reshape` and, when the pass resolved at least one mapped input (a real runtime batch extent), broadcasts that axis to `Dim::named(<batch_dim_name>)`; with no mapped input only the size-one insertion is emitted, and `k == 0` keeps the size-one leading axis without a broadcast.
- `null` requires a proved-unmapped output — a mapped output with `null` is a `TransformError` (a batch axis is never silently dropped) — and emits nothing.
- With `out_axes = 0` on every mapped output, `vmap` emits nothing extra — the IR is identical to plain `vectorize`.
- Every rearrangement op is spliced immediately before the `return` (`Builder::resume` / `take_terminator` / `RuleCtx` / `set_terminator`), one `transpose` or `reshape`(+`broadcast`) per changed output.

## The Builder contract

- Every op goes through the same door: `schema::require(name)` (unknown op = `VerificationError`), the declared arity check, an unknown-attribute check against `OpSchema`, `Attrs::with_defaults` + `validate_attrs`, then `infer_op` for the result types.
- Emitted ops carry the schema defaults filled by `attrs.with_defaults(schema)`, with nullable attributes stored as `AttrValue::Null`; core inference reads an absent attribute and `AttrValue::Null` alike as `None` and `envelope::validate_attrs` / the encoder render the `Null` as JSON `null`.
- `result_types` is an override reserved for op-specific ops (`constant`, `if`, `runtime_call`, `block_call`, `external_call`, the shapeless `custom`-category callback ops `custom_call`/`inline_stablehlo`), the terminator (`Some(&[])`) and inlined extension subgraphs / swept ops whose types must be carried verbatim; everything else infers.
- Result count is validated against the schema, values are allocated from `Program::new_value_id`/`new_op_id`, and the op is appended to the open block (`push_op`).
- `require_open_block` forbids appending after a terminator (`the block already has a terminator`).
- `take_terminator` pops and removes the `return` op (returning its operands and location) so a transform can rewrite outputs and `set_terminator` again — the mechanism behind `vmap`'s output rearrangement and `grad`'s selective return.
- `inline_function` requires the named entry function, an argument-count match, and a straight-line block: a region-bearing sub-op, a sub-op reading an undefined value, or a wrong argument count is an explicit `TransformError`; each inlined op keeps its location and its declared result types.
- `finish()` rebuilds uses and refreshes `output_types`, so the returned module is shaped so that `evoxc_core::verify` accepts it — the engines never call `verify` themselves, the binding (or a caller) does.
- Because the builder only ever appends to the open block, "the ops this dispatch emitted" is exactly `ops[block_op_len ..]`: `vectorize` snapshots the length before a rule runs and stamps the range afterwards, so per-op cost is linear (the former `block_op_ids` + `contains` pair cloned the whole block twice per op).
- Sweeps emit with explicit `result_types` (`captured`/`captured_ir`) so a transform never changes a value's type and the constant payloads survive unchanged.

## The sweep contracts

- `Dual` is a real value or the structurally-zero `ZeroTangent` sentinel; zero is materialized (`zeros_of` = `multiply` by a zero constant of the primal's own dtype) only when a graph output must carry it — a zero that feeds only downstream rules stays structurally zero and emits no op, and an extension AD response may report a zero dual directly with a `null` output id.
- Forward sweep (`jvp`): rebuild the graph in program order and apply the op's JVP immediately, threading one `Dual` per new SSA value; `constant` results are `ZeroTangent` and need no rule.
- Reverse sweep (`vjp`): rebuild the whole graph first, seed the output cotangents, then walk the recorded ops backwards applying VJP rules and accumulating into the operand values with `add` (multiply-used values accumulate; `constant` ops are skipped).
- The output seed is the explicit cotangent block argument when the output is listed in `cotangent_inputs`, else an in-graph rank-0 scalar one — which is why an unlisted output must be rank 0 (`ShapeError` otherwise).
- Rule resolution order is: the registered rule, then — for `jvp` only — the adjoint trick over a registered VJP rule, then the host bridge for `block:*`/`external:*`/`sparse_*`, else an explicit `TransformError` naming the op.
- The adjoint trick calls the VJP rule with the op's own results as cotangents, records every op the rule emitted, marks the values on the op's path, then reverse-sweeps only that emitted subgraph (with the op's tangents as seeds) using the registry's VJP rules, and combines the accumulated terms.
- `jvp` requires `tangent_inputs`: the selected inputs get an explicit tangent block argument appended after the primals; unselected inputs use the zero tangent; the result function returns the primal outputs followed by one tangent per output.
- `vjp` requires `cotangent_inputs`: the selected outputs get an explicit cotangent block argument appended after the primals; the result function returns the primal outputs followed by one cotangent per input.
- `grad` is `vjp` with the scalar-one seed: exactly one tensor output, rank 0 (`ShapeError` with the shape in the message), `argnums` validated for range and duplicates, every selected input float or complex, then the swept module is resumed, its terminator taken, and only the selected gradients (in selector order) returned.
- `stop_gradient` and the 14 non-differentiable ops have explicit zero rules, so they contribute `ZeroTangent` instead of failing.
- The VJP extension request carries `cotangent_type` as the op's FIRST result type (the wire request shape holds one type); the JVP request carries one tangent flag per operand.
- Rule results are count-checked against the op's results (JVP) or operands (VJP) before they are threaded, with the transform's prefix in the error.

## The extension-rule inlining contract

- Only `block:*`, `external:*` and `sparse_*` keys are bridge-eligible (`extension_eligible`); a builtin rule always wins, and no other op may reach the host.
- The request is neutral JSON-shaped data: kind, op name, rule key, attributes as a JSON map, the operand/result types the rule must consume, plus `axes` (batching), `tangents` (jvp) or `cotangent_type` (vjp).
- The response carries an `evoxc-native-ir` envelope, its entry function name, the `output_ids` that become the rewritten results/contributions, and (batching only) optional `output_axes`.
- An `output_ids` entry is a value id or `null`: `null` means the rewritten result / spliced contribution is structurally zero (`Dual::ZeroTangent`), so the rule omits the zero-materialization op — legal only for `jvp`/`vjp` responses, where the engine materializes such a zero only if it reaches a graph output; a batching response with a `null` entry is an explicit `TransformError` naming the op and the output index.
- The subgraph entry block arguments are, in order, the op's rewritten operands — and, for `jvp`/`vjp`, one proxy value per result; batching subgraphs receive operands only.
- The engine decodes the envelope, `inline_function`s it, and maps each `Some` output id through the SSA remapping (a `None` entry becomes `Dual::ZeroTangent` with no lookup); an id that is not a value of the inlined entry is an explicit `TransformError`.
- Response arity is validated for the kind (results for batching/jvp, operands for vjp), including the `null` entries, and batching output axes must be `0` or `null`.
- Because `inline_function` ignores the subgraph's terminator, an AD response subgraph may `return` only its non-zero contributions; the envelope's declared `output_types` must still match those return operands (`evoxc_core::envelope::decode`), so the rule declares exactly the real values it splices.
- Without `output_axes`, batching mappedness is derived from the spliced values' leading dims named like the pass's batch `Dim` (all unmapped when the pass has no batch dim).
- No other Python callback may occur during a transform: the GIL crossing is once per transform plus once per extension-ruled op.

## The batch_functions contract

- Alignment is structural and occurrence-indexed: each op is keyed by a `Skeleton` = `(Identity, Vec<Slot>, Vec<ValueType>)`, where `Identity` is `Constant` for every `constant`, the `switch_ops` group key when a declared group covers the op (first match in declaration order), else the op's `VariantKey` = `(op name, canonical attributes sorted by name)`; `Slot::Input(leaf)` names a block argument and `Slot::Class { class_id, result_index }` an earlier class result, so identical computation positions across programs land in one congruence class.
- Attributes canonicalize deterministically (floats by `f64::to_bits`, arrays by `(dtype, static shape, payload bytes)` with the CONTENT part of the key, JSON in canonical order, tuples/lists as one `seq` form, `AttrValue::Null` as `none`), so equal attributes always share a class.
- One class with a single variant is rebuilt ONCE through `crate::batching::dispatch` with the operands' `MappedAxes`, so identical programs emit ZERO `select`s and one batched op per source op; rule-emitted ops inherit the contributing source op's `Location`.
- `switch_ops` (default groups = the `elementwise` + `comparison` schema categories, or explicit `Category`/`Ops` groups) merges a same-skeleton position whose op DIFFERS into one switch class: one op per variant over the SAME rewritten operand stack, each candidate aligned to `(N, 1…, *per_row)`, variant 0 as the accumulator and one static bool mask constant per extra variant (shape `(N,) + (1,)*(rank-1)`); conflicting candidate result types or a shape one `select` cannot mux is a `TransformError`, and a switch class is always mapped.
- A class holds at most one distinct variant per program and is only reused when it does not already hold the program, so contributors arrive in non-decreasing program order; `alignment` picks among the candidates — `Variant` (default: first a class already holding this variant), `Occurrence` (the occurrence bucket, the byte-stable legacy output) or `Auto` (variant-first, then any other free class of the skeleton) — a pure performance heuristic that never changes a number.
- Constants share ONE unmapped constant when every contributing payload is equal, else ONE stacked `(N, *payload_shape)` constant with row `i` the payload of program `i` (non-contributing rows repeat the lowest contributing program's payload); `stacked_constants` counts only the stacked case.
- Remaining divergence is `select`-muxed at the consumers and outputs: an output leaf with several distinct producing refs gets one broadcast/mux per distinct ref and a mask-cascade `select` (`output_muxes`), while different topologies stay separate classes.
- `bands` is a pure performance choice: `Flat` (also `Explicit(1)` and an auto-resolved single band) delegates to the flat emitter, `Explicit(K)` with `1 <= K <= N` splits into K contiguous bands as even as possible with the larger bands first (`even_partition`), and `Auto` prices candidates with the static cost model — flat, the structural fingerprint partition, that partition with every singleton bucket coalesced into one trailing misc band, and the geometric ladder `k in {2,4,8,16,32,64} ∩ 2..N-1` plus `k = N` — dropping duplicates and keeping the cheapest (earlier wins ties).
- The cost model (element-equivalents) charges `DISPATCH_COST = 512.0` per dispatch, `CONSTANT_COST = 128.0` per reachable constant class, `BAND_OVERHEAD = 8192.0` per band of a multi-band partition (`BAND_OVERHEAD * band_count`, the first band included, nothing for a single band — the formula is stated once in `./src/batch_functions/CONTEXT.md` "Banded merge"), and per-category op weights (`linalg 12`, `reduction 2`, `sorting 2`, `sparse 4`, otherwise 1); a class costs `DISPATCH_COST + op_work * rows` per distinct variant plus `DISPATCH_COST + result_elements * band_size` per extra variant, with `rows = band_size` when the variant is row-dependent and 1 otherwise, and a symbolic/dynamic dim counts as one element.
- Every band is merged independently over its own `MergeDag` into the SAME builder with band-local input views: a mapped input view is materialized once per `(band, leaf)` — a `slice` when the band is contiguous and every trailing dim is a static int, otherwise one `gather` with a cached int32 row-index constant — while an unmapped input uses the block argument itself.
- Band outputs are glued with one `concatenate` along axis 0 (an unmapped band output first broadcast to `(band_size, *shape)`), and when the partition's concatenation order is not `0…N-1` the rows are re-permuted once with one shared int32 inverse-index constant via `gather`.
- With several bands the per-class report counters are TOTALS across bands, and `SwitchRecord.rows_per_variant` always holds GLOBAL program indices.
- The merged graph is an ordinary graph of ordinary ops: it needs no new backend support, exports to StableHLO unchanged and compiles on every adapter that compiles its components.

### batch_functions v1 deferrals

- Any op without a batching rule is an explicit `TransformError` naming the op and the function index: region-bearing control flow (`cond`/`while_loop`/`scan`), `runtime_call`/`external_call` and block calls without their namespaced rules, the `custom`-category callback ops (`custom_call`/`inline_stablehlo`), the collectives, `rank`/`world_size`, `call`, the `random_*` ops, the 8 new IR ops of the 15-op batch (`sort`/`argsort`/`tile`/`flip`/`roll`/`diag`/`cumprod`/`nan_to_num`), `diagonal` and the linalg factorizations; `sparse_*` / `dense_dot_sparse` DO merge through the host bridge when one is present.
- A registered pytree OUTPUT node with static leaves is rejected at the FFI layer (a `Program` has already lost the pytree), so that check lives there, not in this crate.
- Non-zero `axes`/`out_axes` entries (v1 maps only the leading axis), an out-of-range entry for the tensor's rank, and `out_axes = None` on a mapped or muxed output are `TransformError`s (a rank-0 output accepts the mapped `out_axes` entry `0`, see above).
- Non-flat `bands` together with an `out_axes = None` entry is a `TransformError` (checked after op batchability and before the partition), and an `Explicit(K)` band count outside `1 <= K <= N` is a `TransformError` naming the accepted range.
- Program-shape violations (more than one function, a multi-block region, no `return`, a block-argument/input-count mismatch) and cross-program signature mismatches are likewise explicit (`TransformError`, `DTypeError`, `ShapeError`).

## Deviations from the Python engine

- Inputs are `Program`s, not `Graph`s: pytrees, static values, devices, `TensorSpec`s and source locations stay on the Python side, and the static-output-node check is an FFI-layer check; count/type validation stays here.
- `Bands`, `SwitchOps` and `Alignment` are typed enums, so string/JSON parsing (including the `switch_ops` spellings and the boolean form) belongs to the FFI layer; `Alignment::parse` exists here for the enum itself and `parse_switch_groups` still validates every group against the IR op registry.
- Helper ops the engine emits itself (masks, selects, broadcasts, band slices/indices, concatenations) carry no `Location`, because Rust has no frame-capture call site; rule-emitted ops carry the contributing op's location.
- `band_sizes` and `switched` are `Vec`s where Python uses tuples.
- The twelve report key names and the nested `SwitchRecord` keys are identical to `BatchReport.as_dict()`.

## v1 deferrals (explicit errors, never silent fallback)

- `vectorize`/`vmap` reject a module that is not exactly one single-block function (`entry_function`) and reject every region-bearing op (`if`/`while`/`scan`) with `cannot batch op '<op>': region-bearing control-flow ops … are not vectorizable in v1`.
- `vmap` defers a bare `out_axes` on a graph with more than one tensor output.
- Batching deferrals: `conv` with a mapped kernel (a symbolic `batch_group_count`), `conv` with `batch_group_count != 1`, `conv` over a dynamic batch dim or a rank-0 input; `gather` with mapped data but unmapped indices, with multiple `axes`, or with dynamic index dims; `scatter` with mapped data but unmapped indices/updates, or with indices and updates disagreeing on mappedness; `slice` with a dynamic batch dim or a symbolic per-axis limit; `concatenate` with no operand carrying all mapped axes; `solve` with `left_side = false`; per-axis int attributes whose length disagrees with the per-row rank.
- AD deferrals: `conv` VJP (the IR has no transposed-convolution op); `reduce_mean` over a symbolic reduced dim (the count is unknown); `gather` with multiple axes in both sweeps; a `slice` VJP with strided entries on more than one axis, or over a symbolic dim; a `pad` VJP over a symbolic dim; a `concatenate` VJP with symbolic dims; `solve` with `left_side = false` in both sweeps; a `conv` with `batch_group_count != 1`.
- Ops with NO batching rule at all (a `TransformError` naming the op): `acos`/`ceil`/`floor`/`round`, `cumprod`, `bitwise_left_shift`/`bitwise_right_shift`, `sort`/`argsort`/`tile`/`flip`/`roll`/`diag`/`nan_to_num`, `diagonal`, the linalg factorizations (`cholesky`/`eigh`/`matrix_exp`/`matrix_rank`/`qr`/`svd`), the `random_*` ops, the collectives (`all_reduce`/`all_gather`/`reduce_scatter`/`all_to_all`/`broadcast_collective`/`collective_permute`), `rank`/`world_size`, control flow, `call`, `runtime_call` and the `custom`-category callback ops `custom_call`/`inline_stablehlo`. Every sparse op reaches the host bridge instead — the `sparse_*` family plus `dense_dot_sparse`, the one sparse op whose IR name carries no `sparse_` prefix (the eligibility gate names it explicitly) — and fails only when the host has no rule.
- Ops with NO derivative rule at all (a `TransformError` naming the op and the registration call): `acos`/`ceil`/`floor`/`round`, `cumprod`, `sort`/`argsort`/`tile`/`flip`/`roll`/`diag`/`nan_to_num`, `diagonal`, the linalg factorizations, `random_*`, the collectives, `rank`/`world_size`, control flow, `call`, `runtime_call`, the `custom`-category callback ops `custom_call`/`inline_stablehlo`, and every sparse op (bridge only — `sparse_*` plus `dense_dot_sparse`).
- Frontend compositions need no rule of their own: `eye`/`linspace` become `constant` payloads, and `matmul`/`topk`/`stack`/`clamp`/`isnan`/`mean`/`std`/`var`/`median`/`norm` expand onto ruled IR ops — so their transformability follows their components (`topk` needs `sort`/`argsort`, which have no rule).
- `constant` needs no rule in either sweep (special-cased), `return` is never dispatched, and `block_call`/`external_call`/`sparse_*` are never "missing" while the bridge answers for them.

## Known gaps / notes for agents

- Where the source carried `null` (the frontend always serializes those attributes as `null`) the value arrives as `AttrValue::Null`, `with_defaults` skips it and `envelope::validate_attrs` accepts it, so a rebuild of a decoded op is fine too.
- `ConvParams::to_attrs` omits `strides`/`input_dilation`/`kernel_dilation` when the source did not carry them; `Builder::emit` fills the schema defaults via `Attrs::with_defaults`, so the omission is harmless.
- Frontend-vs-IR differences every rule must respect: `ops.slice` takes SIZES in Python while the IR `slice` carries `start_indices`/`limit_indices` (+ optional `strides`); `ops.gather(axis=a)` is the IR `gather` with `axes = [a]`; `ops.scatter(axis=a)` is the IR `scatter` with a scalar `axis`; `reduce_*` requires the `reduce_op` attribute (the frontend sugar sets it, hand-built attrs must too); `transpose`'s `permutation: null` means full reversal; `padding_config` is one `(low, high)` (or bare int) pair per axis.
- Batching rules see the op's REWRITTEN operands and an EMPTY `results`/`result_types` (`RuleOp::from_source(...).bind_operands(...)`), so a batching rule must never read a rewritten result.
- AD rules see both: the rewritten operands (the primals of the output module) and the rebuilt `results` (which is what the Python rules receive as `primals`).
- `lib.rs` owns `test_support` (a `#[cfg(test)] pub(crate)` module with `f32_ty` and `add_program`), which the module test modules share — a new test module should import from there rather than redefining helpers.
- `gather.axes` and `scatter.axis` are optional in the schema, so the rules read them with the schema defaults (`[0]` / `0`) instead of requiring them.
- `src/batching/elementwise.rs` holds both the pointwise family and the `_reduction_batching` port (`reduction_rule`): `REDUCTION_OPS` by exact IR name plus `ARG_REDUCTION_OPS`, with the `axis = None`/empty-axes cases handled per the Python (reduce over the per-row axes, `argmax`/`argmin` flatten through a `reshape` to `prod(dims)`; a runtime-dynamic dim is an explicit `TransformError`). The bare `sum`/`max`/`min`/`mean`/`prod` frontend aliases are compositions, not IR ops, so they are deliberately unregistered.
- This crate contains no Python, no device, no backend and no runtime code; it never edits `../evoxc-core/`, the Python packages or the PyO3 crate.

### The Python-driven differential parity harness (`./tests/`)

- `./tests/parity_transform/convert.py` is the envelope bridge: `to_native(module)` turns `evoxc.ir.serialize_module` output into the native `evoxc-native-ir` envelope (the `constants` table inlined as `{"dtype","shape","data_b64"}` with base64 raw C-order little-endian bytes, `format`/`version` set, `sha256` dropped) and `from_native(envelope)` reverses it (inline payloads hoisted into a fresh `constants` table as `np.save` bytes, the canonical `sha256` recomputed, `evoxc.ir.deserialize_module` re-verifying). It loads the extension with `importlib.util.spec_from_file_location("evoxc._evoxc_native", <repo>/evoxc/_evoxc_native.abi3.so)` — never a plain `import`.
- The converter passes `{"__evoxc_tuple__": [...]}` attribute markers through VERBATIM (no flattening, `any` attributes and nested tuple structures included), so the harness exercises `evoxc-core`'s tag-directed tuple decoding (`ints`/`floats`/`strs`/`nested_ints`/`shape` → their sequence variants, `any` → `Tuple`) on the real wire format.
- `./tests/parity_transform/run_parity.py` is the corpus: traced graphs (`evoxc.trace(fn, *TensorSpec)`) → `to_native` → `evoxc._evoxc_native.transform(kind, envelope, config)` → `from_native` → a `Graph` around the native module reusing the Python graph's trees → both graphs evaluated through the explicit numpy pipeline (`lower` → `compile` → `load` → `run`) on identical seeded inputs (one `np.random.default_rng(seed)` per case, every fresh symbolic batch `Dim` fixed at `BATCH_EXTENT = 3`). - `./tests/parity_transform/batch_cases.py` is the `batch_functions` corpus: same-signature program populations (identical bodies, divergent topology, `switch_ops` off/`Default`/explicit groups, shared vs stacked constants, `bands` None/1/K/auto, the three alignments) plus the deferral cases.
- `./tests/parity_transform/run_batch_parity.py` is the differential runner for the FFI `evoxc._evoxc_native.batch_functions(list_of_envelopes, config)`: it compares the native result against `evoxc.batch_functions` in three layers — a structural envelope comparison through a canonical id-remapped view, numerics through the numpy backend on seeded inputs, and the exact twelve-key `batch_report` dict — and prints `BATCH PARITY: <cases> cases, <checks> checks, <mismatches> mismatches` (exit 1 on a mismatch).
- With the extension built, `run_batch_parity.py` reports `BATCH PARITY: 25 cases, 87 checks, 0 mismatches`; it accepts `-k SUBSTRING` filters and leaves `run_parity.py` untouched.
- `./tests/batch_functions_parity.rs` is the cargo gate for that runner: it SKIPS with the missing-prerequisite message when `.venv/bin/python` or `evoxc/_evoxc_native.abi3.so` is absent, otherwise it runs the runner from the repository root with inherited stdout/stderr and fails on a non-zero status.
