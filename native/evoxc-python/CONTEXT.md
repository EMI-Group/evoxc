# evoxc-python — the PyO3 binding (`evoxc._evoxc_native`)

## Intent

The only crate that knows about Python: it exposes `evoxc._evoxc_native` as a thin adapter over `evoxc-core` (and, once wired, `evoxc-compiler`).
It holds **no** numerical semantics of its own — one envelope dict crosses the FFI per call, and every judgment (schemas, inference, error families) comes from the native authority.
`native/CONTEXT.md` is the binding contract; this file refines crate internals and never changes the wire format or the FFI names.
The built cdylib is `libevoxc_python.so`, installed by `scripts/build-native.sh` as `evoxc/_evoxc_native.abi3.so` for `evoxc/_native.py` to load — a build product, gitignored.

## Python-visible surface

| Name | Signature | Behavior |
|---|---|---|
| `version()` | `-> str` | `evoxc_core::VERSION` (`"0.1.0"`). |
| `__version__` | `str` | Same string; also appears in the generated `__all__`. |
| `infer(...)` | `(op_name: str, operand_types, attributes, result_types=None, module=None) -> list[dict]` | Native shape inference for one op; returns `[{"dtype": str, "shape": [dim, ...]}, ...]`. |
| `transform(...)` | `(kind: str, module: dict, config: dict) -> dict` | Signature final; every valid kind raises `TransformError` until the compiler engines are wired (see the gap below). |
| `NativeError` | exception class (`__module__` = `"evoxc._evoxc_native"`) | Every native failure; `.kind` names the public family, `.message` equals `str(exc)`. |
| `__all__` | frozen list | Generated by `#[pymodule]` from the module content — do not add it by hand (it would appear twice). |

`operand_types` / `result_types` accept a list **or** a tuple of type dicts; `attributes` is a dict of op attributes (`None` is accepted as `{}`); `module` is an `evoxc-native-ir` envelope dict (`None` unless the op needs one).
`infer` never mutates an argument and never executes user Python: a non-data Python object (a `set`, a generator, a numpy array, a complex number) is a `TypeError` naming its path (`attributes.axes[1]`).

## Envelope conversion rules (`src/convert.rs`)

- Python → JSON accepts exactly the JSON data model plus tuples: `None`, `bool`, `int`, `float`, `str`, `dict` (str keys), `list`, `tuple`.
- `bool` is tested before `int` (it is an `int` subclass in Python) so `True` never becomes `1`.
- Integers keep their integer-ness: `i64` then `u64`; anything outside that range is a `TypeError` (the envelope has no big-integer form).
- Non-finite floats (NaN/∞) are a `TypeError` — they have no JSON form; they belong inside an ndarray attribute payload.
- `dict` keys must be `str`; a non-string key is a `TypeError` naming the path.
- JSON → Python rebuilds `dict`/`list`/`str`/`bool`/`int`/`float`/`None` only (never a wrapper object), and an `i64`/`u64` JSON number becomes a Python `int`.
- One conversion per call, in one reused path buffer: a per-node Python callback is explicitly rejected by the contract (it would cross the GIL once per op and tie the native dispatch loop to Python object lifetimes).
- Conversion failures are `TypeError`s; envelope/schema/inference failures are `NativeError`s from `evoxc_core::Error`.

## GIL discipline

`infer` and `transform` in `src/module_ops.rs` convert while holding the GIL, run all native work inside `Python::detach` (pyo3 0.30's name for the old `allow_threads`; the closure captures only plain Rust data), then re-acquire the GIL for encoding.
No `Bound<PyAny>` crosses into native code and no native type is captured from a Python reference across the boundary.

## Error mapping

| Native `ErrorKind` | `NativeError.kind` | Origin |
|---|---|---|
| `Trace` | `TraceError` | `evoxc_core::Error::trace` |
| `Shape` | `ShapeError` | inference shape/axis conflicts |
| `Transform` | `TransformError` | unknown transform kind, unwired engine |
| `Backend` | `BackendError` | (none from this crate yet) |
| `Persistence` | `PersistenceError` | envelope format/version/id violations |
| `Device` | `DeviceError` | (none from this crate yet) |
| `DType` | `DTypeError` | unknown dtype name |
| `Verification` | `VerificationError` | unknown op, arity, attribute schema, op-specific result rules |
| `General` | `EVOXCError` | wrapped Python-object failure (`object_error`) |

`ErrorKind::as_str()` is the authority; `error::KINDS` is the closed set and a test asserts every family is present.
`error::from_core` copies the family and message verbatim; `error::type_error` builds a plain `TypeError` for argument-shape problems; `error::object_error` wraps a Python-object failure as `EVOXCError` and chains the original as `__context__` — nothing panics or `unwrap`s across the FFI boundary.

## Known gap: `transform` is not wired

`transform` validates its signature (`kind` ∈ `vectorize`/`vmap`/`grad`/`jvp`/`vjp`, else `TransformError` naming the kind; `module`/`config` must be dicts, else `TypeError`) and then raises `TransformError: native transform '<kind>' is not wired in this build`.
The `evoxc-compiler` engines are a parallel workstream; wiring them is meant to be a one-function change in `module_ops::transform` (decode `module` with `evoxc_core::envelope::decode`, call the engine under `detach`, encode the result envelope).
`evoxc-compiler` and `evoxc-runtime` are declared dependencies for that follow-up; this crate currently uses only `evoxc-core`.

## Cargo features (test linkage)

`Cargo.toml` deliberately does **not** use `pyo3.workspace = true`: the workspace entry hard-enables `extension-module`, and an extension-module build links no libpython, so a `cargo test` binary that touches the Python API cannot link.
`default = ["extension-module"]` keeps `scripts/build-native.sh` and `cargo build -p evoxc-python` on the cdylib path; `auto-init` (`pyo3/auto-initialize`) is the test-only alternative that links libpython and initializes an interpreter.
`pyo3` is pinned to `0.30` with `macros` + `abi3-py311` explicitly (default features off, since `default-features = false` must be compensated for `macros`).

## Module map

| Path | Area |
|---|---|
| `./src/lib.rs` | `#[pymodule] _evoxc_native`: `version`/`infer`/`transform` wiring, `__version__`, `NativeError` registration (`__module__` rewritten to `evoxc._evoxc_native`). |
| `./src/module_ops.rs` | The `infer`/`transform` entry points: argument decoding, `Python::detach` boundary, result encoding; `TRANSFORM_KINDS`. |
| `./src/convert.rs` | Python ⇄ envelope JSON conversion (one pass per call, path-tagged `TypeError`s, number/`bool` fidelity). |
| `./src/error.rs` | `NativeError` (`create_exception!`), `KINDS`, `raise`/`from_core`/`type_error`/`object_error`. |
| `./Cargo.toml` | cdylib crate, the `extension-module`/`auto-init` feature split. |

## Test strategy

`cargo test --manifest-path native/Cargo.toml --workspace` is the always-on gate: it compiles this crate with `extension-module` and runs the interpreter-free tests (the error-family closure and the transform-kind list).
`cargo test --manifest-path native/Cargo.toml -p evoxc-python --no-default-features --features auto-init` runs the interpreter-backed tests (12 total): scalar/bool/int/float fidelity, nested dict/list/tuple round trips, ndarray-payload base64 through `wire::array_from_json`, out-of-range ints, NaN, non-string keys, unsupported-type and index path messages, `NativeError` kind/message/`str`, `from_core` family preservation and `object_error` context chaining.
End-to-end verification is `source scripts/dev-env.sh && scripts/build-native.sh [--debug]` (builds the cdylib, installs it into `evoxc/` and smoke-tests `version()` through `.venv/bin/python`), then loading the installed `.so` with `importlib.util.spec_from_file_location("evoxc._evoxc_native", "evoxc/_evoxc_native.abi3.so")` — that avoids `import evoxc`, which would pull the whole Python frontend.
No test needs a GPU, the network, or (for the always-on gate) a linked libpython.
