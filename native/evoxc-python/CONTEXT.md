# evoxc-python — the PyO3 binding (`evoxc._evoxc_native`)

## Intent

The only crate that knows about Python: it exposes `evoxc._evoxc_native` as a thin adapter over `evoxc-core` (schemas, envelope codec, inference, error families), `evoxc-compiler` (the five transforms and the `batch_functions` merge) and `evoxc-cpu` (the native CPU plan + interpreter).
It holds **no** numerical semantics of its own — one envelope dict crosses the FFI per call, and every judgment (schemas, inference, error families) comes from the native authority.
`native/CONTEXT.md` is the binding contract; this file refines crate internals and never changes the wire format or the FFI names.
The built cdylib is `libevoxc_python.so`, installed by `scripts/build-native.sh` as `evoxc/_evoxc_native.abi3.so` for `evoxc/_native.py` to load — a build product, gitignored.

## Python-visible surface

| Name | Signature | Behavior |
|---|---|---|
| `version()` | `-> str` | `evoxc_core::VERSION` (`"0.1.0"`). |
| `__version__` | `str` | Same string; also appears in the generated `__all__`. |
| `infer(...)` | `(op_name: str, operand_types, attributes, result_types=None, module=None) -> list[dict]` | Native shape inference for one op; returns `[{"dtype": str, "shape": [dim, ...]}, ...]`. `module` accepts a full envelope **or** a signature-only callee context ("The `infer` module argument" below). |
| `transform(...)` | `(kind: str, module: dict, config: dict) -> dict` | Runs `evoxc_compiler::transform` (all five kinds); returns the transformed `evoxc-native-ir` envelope plus `"transform": {"kind", "output_ids", "input_ids", "batch_dim"}`. Config keys and accepted shapes: `native/CONTEXT.md` "Transform configs" + "Config decoding" below. |
| `batch_functions(...)` | `(programs: list[dict], config: dict) -> dict` | Runs `evoxc_compiler::batch_functions::batch_functions_with_env`; returns `{"module": <merged evoxc-native-ir envelope>, "batch_report": <12-key report>}`. Config keys (`axes`/`out_axes`/`switch_ops`/`bands`/`alignment`/`extension_rule`) and shapes: "`batch_functions`" below. |
| `batching_rule_keys()` | `-> list[str]` | Read-only introspection: `evoxc_compiler::builtin_rule_keys()` — the sorted rule keys of the compiled-in builtin batching registry (the ops the native engines can map); never `block:*`/`external:*`/`sparse_*`, which come from the host bridge. |
| `native_compile(envelope: dict)` | `-> NativeProgram` | Decodes an `evoxc-native-ir` envelope and compiles it with `evoxc_cpu::plan::compile`; a non-dict is a `TypeError`, envelope violations keep their native family, an op without a native kernel is `BackendError` at compile time. |
| `NativeProgram` | class | Immutable compiled native CPU program: `entry()`, `plan_text()`, `stats()`, `output_types()`, `required_ops()`, `run(flat_inputs, resolver=None)`, plus a `__repr__`. |
| `NativeError` | exception class (`__module__` = `"evoxc._evoxc_native"`) | Every native failure; `.kind` names the public family, `.message` equals `str(exc)`. |
| `__all__` | frozen list | Generated by `#[pymodule]` from the module content — do not add it by hand (it would appear twice). |

`operand_types` / `result_types` accept a list **or** a tuple of type dicts; `attributes` is a dict of op attributes (`None` is accepted as `{}`); `module` is an `evoxc-native-ir` envelope dict or a signature-only callee context (`None` unless the op needs one).
`infer` never mutates an argument and never executes user Python: a non-data Python object (a `set`, a generator, a numpy array, a complex number) is a `TypeError` naming its path (`attributes.axes[1]`).

## The `infer` module argument

`infer`'s `module` supplies the callee signatures `call` resolves against (`evoxc_core::infer_op` reads `module.function(callee)?.output_types`), and it is decoded by `infer_context::decode_module` into a `Program`. Two shapes are accepted:

* **A full `evoxc-native-ir` envelope** — recognized by its `"format"` key and decoded by `evoxc_core::envelope::decode`, unchanged (`PersistenceError`/`VerificationError` diagnostics keep their `module:` context).
* **A signature-only context** — a dict whose `"functions"` is a list of function signatures; one body-less `Function` per entry is synthesized into a `Program` named `"signature-context"`, so every downstream `call` path is untouched:
  * `[name, [output types]]` (2-element: no input types are claimed),
  * `[name, [input types], [output types]]` (3-element),
  * `{"name": ..., "input_types": optional, "output_types": ...}` (an unknown dict key is a `TypeError`).

Types are the same `{"dtype": str, "shape": [dim, ...]}` dicts as `operand_types` (both go through `evoxc_core::wire`), so symbolic `Dim`s, `DimExpr`s and `None` dims work identically. An empty `"functions"` list is a valid callee-less module (a later `call` then fails naming its callee).

An unknown callee stays an explicit `VerificationError` (`no function named 'x' in module 'signature-context'`); a malformed type is the type decoder's own family (`DTypeError`/`VerificationError`) tagged with its path (`module.functions[0] types: ...`).
Argument-shape problems are plain `TypeError`s (never a silent fallback to "no module"): a non-dict module, a dict with neither `"format"` nor `"functions"`, a `"functions"` value that is not a list, an entry that is neither list nor dict, a wrong element count (not 2/3), a non-string or empty name, a dict entry missing `"name"`/`"output_types"`, or an unknown dict key.
The JSON walk (`decode_module_json`/`signature_program`/`signature_entry`) is interpreter-free and unit-tested in the always-on gate; only the final `ContextError -> PyErr` mapping (`Shape` -> `TypeError`, `Core` -> `NativeError`) needs the GIL.

## Envelope conversion rules (`src/convert.rs`)

- Python → JSON accepts exactly the JSON data model plus tuples: `None`, `bool`, `int`, `float`, `str`, `dict` (str keys), `list`, `tuple`.
- `bool` is tested before `int` (it is an `int` subclass in Python) so `True` never becomes `1`.
- Integers keep their integer-ness: `i64` then `u64`; anything outside that range is a `TypeError` (the envelope has no big-integer form).
- Non-finite floats (NaN/∞) are a `TypeError` — they have no JSON form; they belong inside an ndarray attribute payload.
- `dict` keys must be `str`; a non-string key is a `TypeError` naming the path.
- JSON → Python rebuilds `dict`/`list`/`str`/`bool`/`int`/`float`/`None` only (never a wrapper object), and an `i64`/`u64` JSON number becomes a Python `int`.
- One conversion per call: a per-node Python callback is explicitly rejected by the contract (it would cross the GIL once per op and tie the native dispatch loop to Python object lifetimes).
- Conversion failures are `TypeError`s; envelope/schema/inference failures are `NativeError`s from `evoxc_core::Error`.

### Outbound object sharing (what the returned envelope aliases)

A transform returns tens of thousands of small Python objects and almost all of them are repeats, so `py_from_json` runs with a per-call `PyCache` (dropped when the call returns; nothing is shared across calls or with the input envelope):

| Cache | Sharing rule | Why it is unobservable |
|---|---|---|
| strings | one `PyString` per spelling, dict keys and string values alike | `str` is immutable; the shared object is also where `PyDict_SetItem` finds the hash it caches |
| ints | one `PyInt` per value in `0..8192` (CPython's own `-5..=256` singletons are used as-is and never enter the table) | Python `int`s are immutable |
| type dicts | one `{"dtype": …, "shape": […]}` dict per distinct native type, keyed by a content fingerprint (FNV-64, collisions resolved by comparing the JSON) | only reached from `Type` positions (`results[].type`, `block.arguments[].type`, `function.input_types`/`output_types`); `evoxc.ir` reads `dtype`/`shape` by field into its own `ValueType` |
| location dicts | one `{"file","line","col","code_snippet"}` dict per distinct location | same: `_decode_location` reads the four fields |

Every `dict`/`list` **other** than those records is allocated per node — a caller may mutate a container in the returned envelope, so aliasing one would be observable. That is also why empty `attributes`/`regions`/`metadata` containers are **not** shared: `evoxc.ir` can hold a decoded attribute mapping, so one shared empty dict would let one op's mutation reach every other op.
A shared record is only ever handed out at a *record* position: `is_type_object`/`is_location_object` require the exact two-/four-key record shape, so an arbitrary payload that happens to sit under a `"type"` or `"location"` attribute key is converted (and kept distinct) like any other dict.

### Inbound path rendering

The `attributes.axes[1]` path in a `TypeError` is a parent-linked `Path` chain (one stack frame per recursion level), rendered exactly once and only on failure. It used to be written into a reused `String` at every key and element — tens of thousands of `write!` calls per transform for a message that almost never renders.

## GIL discipline

`infer`, `transform`, `batch_functions`, `native_compile` and `NativeProgram.run` convert while holding the GIL, run all native work inside `Python::detach` (pyo3 0.30's name for the old `allow_threads`), then re-acquire the GIL for encoding.
The closure captures only `Send` data: the decoded `Program`, the typed `TransformConfig`, the `Arc<evoxc_cpu::plan::Plan>`, the input `Vec<Buffer>`, and (when one was supplied) a `PyExtensionRule` / `PyCallbacks` holding `Py<PyAny>` — `Py<T>` is `Send + Sync`, and each bridge re-attaches with `Python::attach` instead of carrying the `Python` token across the boundary.
No `Bound<PyAny>` crosses into native code and no native type is captured from a Python reference across the boundary.

## The native CPU engine (`native_compile` / `NativeProgram`, `src/cpu.rs`)

`native_compile(envelope)` decodes with `evoxc_core::envelope::decode` (GIL held), times and runs `evoxc_cpu::plan::compile(&program)` detached, and returns an immutable `NativeProgram` owning the `Program`, the `Arc<Plan>` and the measured `compile_ms: f64`.
`entry()` is the plan's entry function name and `plan_text()` is `Plan::text()`; `output_types()` is `evoxc_core::wire::value_types_to_json(plan.entry_function().output_types)` through `py_from_json`; `stats()` and `required_ops()` build one `serde_json` object each and return it through `py_from_json`.
`stats()` has exactly `ops`, `dispatched_ops` (equal to `ops` — this engine dispatches every planned op), `blocks` (`plan.block_count`), `plan_entries` (`plan.op_count`, the planned step count), `compile_ms`, `unsupported` (`plan.unsupported`, the dense ops the engine does not implement), `required_blocks`, `required_external` and `required_runtime`; `required_ops()` has `blocks`, `external` and `runtime_calls`.
`run(flat_inputs, resolver=None)` converts the flat numpy inputs while holding the GIL, preflights the resolver, runs `evoxc_cpu::run_program(program, &plan, inputs, RunOptions::default(), callbacks)` detached, then builds fresh numpy arrays with the GIL re-acquired.
Input arity/dtype/shape are validated by the engine at the run boundary (`BackendError`/`DTypeError`/`ShapeError`); an op without a native kernel is the plan's own `BackendError` at compile time.

### numpy interop

Arrays cross through the `numpy` 0.30 crate as TYPED payloads (`numpy = { version = "0.30", features = ["half"] }` + `ndarray = "0.17"`): numpy 0.30 pairs with this crate's pyo3 0.30, and its C-API is imported lazily on the first array use, so `import evoxc` still touches neither numpy nor the crate.
`half` and `num-complex` stay direct dependencies because they type the `Storage` variants — the same crates and semver numpy and `evoxc-cpu` use, so `f16`/`Complex<f32>`/`Complex<f64>` are the very types numpy expects.
There is no `PyBuffer` byte marshalling, no `numpy.ascontiguousarray` call, no `numpy` Python-module import outside the tests, and no `unsafe` of the crate's own; the per-direction design is "Buffer hand-off (native CPU engine)" below.

### Host callbacks (the `resolver`)

`block_call` / `external_call` / `runtime_call` reach Python through `PyCallbacks`, a `evoxc_cpu::Callbacks` implementation over one `Py<PyAny>` resolver that re-attaches per call.
Preflight (GIL held, before the detach) requires `resolver` whenever `plan.required_blocks`/`required_external`/`required_runtime` is non-empty and requires it to expose a callable method of the matching name (`call_block` / `call_external` / `call_runtime`); otherwise the run raises a `BackendError` naming the required methods and what the plan needs.
Call shape is `call_block(name, args)` plus — when the engine's `static_args` is non-null and non-empty — the static args payload as a third positional argument (converted with `crate::convert::py_from_json`); `call_external(name, args)` and `call_runtime(name, args)` always take exactly two arguments.
`args` is a Python list of numpy arrays and the answer must be a list/tuple of numpy arrays (converted back through the same array→`Buffer` path).
A resolver exception, an un-iterable answer or an unconvertible array becomes `BackendError("resolver.<method>(<name>) raised: <interpreter text>")`; nothing panics and nothing is silently skipped.

## Buffer hand-off (native CPU engine)

`src/cpu.rs` moves tensor payloads as raw little-endian bytes in one pass per direction — a marshalling copy, never an element-at-a-time conversion through intermediate Python objects.

### Inbound (Python → engine)

`decode_inputs` walks the `flat_inputs` sequence and hands each element to `array_to_buffer(py, obj, path)` with `path = "flat_inputs[<index>]"`, so every inbound failure names the input index.
`array_to_buffer` validates an array once: `dtype.name` → `DType::parse` (the 14 evoxc dtypes), `dtype.isnative` (a swapped byte order is an explicit `BackendError` naming the path, because those raw bytes would otherwise be read as little-endian), `shape` → `Vec<usize>` (a negative extent is a `ShapeError` naming the path), and `flags.c_contiguous`; a non-array argument is a `TypeError` (`<path>: expected a numpy array, got <type>`).
A C-contiguous array is used as-is, while a strided view is first copied by `numpy.ascontiguousarray` into a contiguous temporary — copied, never misread, and the caller's object is only borrowed.
`byte_view` takes `array.data.cast("B")` and wraps it as a `PyBuffer<u8>`, and `borrowed_bytes` turns that into a borrowed `&[u8]` through `PyBuffer::as_slice_ptr()` — a pointer/slice view, not a byte copy; a buffer numpy will not hand out contiguously is an explicit `BackendError` naming the path.
The borrow is valid only while the `view` owned by `array_to_buffer` is alive and no Python code runs meanwhile (a Python call could resize the exporting array).
`decode_bytes(dtype, bytes, split_threads(bytes.len()))` decodes the borrowed slice straight into the typed `evoxc_cpu::Storage` variant — `bool` as `word[0] != 0`, `float16` via `f16::from_bits`, complex as an `re`/`im` pair, every other dtype via `from_le_bytes` — with no intermediate `Vec<u8>`.
A byte count that disagrees with `shape` × `dtype.itemsize()` is an explicit `VerificationError` naming the path, and `Buffer::new` re-checks dtype and dims before the run starts.
The caller's array is borrowed for the duration of the conversion and never mutated (`the_returned_array_is_fresh_writable_and_does_not_alias_the_input` writes into the result and asserts the input's bytes are unchanged).

### Outbound (engine → Python)

`buffer_to_array` allocates the destination ONCE with `numpy.empty(shape, dtype.name())` — it therefore owns writable, C-contiguous bytes — and fills it with one bulk copy of the whole payload.
`storage_bytes_le` hands out the storage's own bytes as a borrowed `&[u8]` (a shared `&[T]` reinterpreted over exactly `size_of_val`), which on a little-endian target already IS the numpy layout for all 14 dtypes (`f16` as its 2-byte bit pattern, `Complex` as `repr(C) {re, im}`, `bool` as one byte holding 0 or 1).
The little-endian gate is `cfg!(target_endian = "little")`: on a little-endian host `fill_bytes` is fed that borrowed view with no flattening, and on a big-endian host `storage_to_bytes` first flattens the payload elementwise (`to_le_bytes`; `f16::to_bits`; `bool` as `0x00`/`0x01`; complex as interleaved real/imaginary) into a `Vec<u8>`.
`fill_bytes` copies with `PyBuffer::copy_from_slice` when the split is a single thread and otherwise writes through the destination's `as_slice_ptr()`; a non-contiguous destination or a byte-count mismatch is an explicit `PyBufferError`.
The result shares nothing with the engine, so writing into it never reaches a caller's input array.

### Wide copies (one size threshold, at most four threads)

`split_threads(bytes)` is the single threshold: below `SPLIT_MIN_BYTES` (`1 << 20`, 1 MiB) a copy runs on the calling thread, and at or above it the thread count is `std::thread::available_parallelism()` clamped to `1..=SPLIT_MAX_THREADS` (4) and then capped by `bytes / SPLIT_PER_THREAD` (`1 << 19`, 512 KiB per extra thread).
So a wide copy never uses more than 4 threads, and the threshold exists because a scoped spawn costs ~12 µs here — spawning for a smaller payload loses more than it gains.
`copy_bytes(dst, src, threads)` splits `dst` with `chunks_mut(len.div_ceil(threads))`, spawns one scoped thread per trailing chunk over that chunk's disjoint destination range with the matching `src` window, and copies the leading chunk on the calling thread instead of idling.
`decode_words` (the inbound decode) splits the same way: `chunk = count.div_ceil(threads.max(1))`, one scoped thread per trailing index range, the leading range on the calling thread, and `set_len(count)` only after the join.
Both paths are value-identical to the single-threaded copy, which `large_payloads_take_the_threaded_path_bit_identically` asserts bit-for-bit.

### `unsafe` surface

The crate's `unsafe` is confined to this marshalling code in `src/cpu.rs`; everything else is PyO3's own FFI glue, and no SIMD intrinsics are used (`std::arch` and `core::simd` appear nowhere).
`borrowed_bytes`'s pointer→slice view carries the SAFETY argument that the pointer addresses the buffer's own `item_count()` bytes, that `view` keeps them exported for the slice's lifetime, that `u8` has no validity or alignment requirement, and that nothing writes through the shared slice.
`fill_bytes`'s bytes→destination copy carries the SAFETY argument that `dest` is the `B`-cast view of an array this call just allocated with `numpy.empty` and has not returned or shared, so an exclusive borrow of its `bytes.len()` bytes cannot alias anything, that no Python code runs while it lives, and that `copy_bytes` splits it into disjoint chunks.
`storage_bytes_le`'s `view` carries the SAFETY argument that a shared, initialized `&[T]` reinterpreted as a `&[u8]` of exactly its bytes is sound because `u8` has no validity or alignment requirement and the lifetime is the source's.
The threaded decode adds the raw-pointer writes: `OutPtr<T>`'s `unsafe impl Send`/`Sync` are justified by `decode_words` handing out disjoint output ranges only, `OutPtr::write` documents that its index is inside the allocation and written by exactly one thread, and `decode_words`'s own block documents that the allocation is exclusively ours, that writing through the raw pointer into uninitialized memory is fine for a `Copy` type, and that `set_len` runs only after the join.

### Measured FFI floor

A round trip is two passes over the payload — the inbound decode and the outbound bulk copy — plus the Python-side `numpy.empty` allocation: a measured ~0.20 ms for an 8 MB payload on this host.
A small-graph `run` is therefore dominated by the kernels and the plan dispatch, not by marshalling.
`run`'s per-call cost is O(input bytes + output bytes) and INDEPENDENT of op count: every input array is decoded into a fresh typed `Storage` once per call, outputs are bulk-copied once each, and no Python code runs during the planned loop (the GIL is released at `cpu.rs:186`), so a performance gap that scales with op count is inside `evoxc_cpu::run_program`, never in this seam.
`stats()['compile_ms']` times ONLY `evoxc_cpu::plan::compile` — the timer starts after `json_from_py` and `envelope::decode` (`src/cpu.rs:100-108`) — so a `native_compile` wall time is decode + plan compile (at 2000 ops: 5.421 ms of envelope decode/FFI vs 0.860 ms of engine compile, `../CONTEXT.md` "Known gap (CPU FFI)").
`NativeProgram` keeps the decoded `Program` and the compiled `Arc<Plan>` across calls, so a repeated run pays only input validation + marshalling + execution, never a re-compile or a re-decode.

### Inbound integer attributes (`convert.rs`)

`encode_value` tests `bool` before `int` (`bool` is an `int` subclass, so `True` never becomes `1`) and then takes a `PyInt` as `i64` first and as `u64` second.
An unsigned 64-bit attribute above `i64::MAX` therefore encodes verbatim — `random_key_mix`'s splitmix64 salt `0x9E3779B97F4A7C15` (11400714819323198485) reaches the envelope as exactly that number — and only an integer that fits neither is rejected, with a `TypeError` naming the attribute path and "the envelope's 64-bit number range".
Negative values keep their sign (the `i64` arm), and `number_to_py` on the way back returns a Python `int` for every `i64`/`u64` (`as_i64` first, then an unsigned value above `i64::MAX` as the Python `int` of that value), so a 64-bit unsigned attribute round-trips exactly.

## Error mapping

| Native `ErrorKind` | `NativeError.kind` | Origin |
|---|---|---|
| `Trace` | `TraceError` | `evoxc_core::Error::trace` |
| `Shape` | `ShapeError` | inference shape/axis conflicts |
| `Transform` | `TransformError` | unknown transform kind, transform-engine diagnostics, malformed config/extension response |
| `Backend` | `BackendError` | `evoxc-cpu` compile/run diagnostics, the resolver preflight and the host-callback bridge |
| `Persistence` | `PersistenceError` | envelope format/version/id violations |
| `Device` | `DeviceError` | (none from this crate yet) |
| `DType` | `DTypeError` | unknown dtype name |
| `Verification` | `VerificationError` | unknown op, arity, attribute schema, op-specific result rules |
| `General` | `EVOXCError` | wrapped Python-object failure (`object_error`) |

`ErrorKind::as_str()` is the authority; `error::KINDS` is the closed set and a test asserts every family is present.
`error::from_core` copies the family and message verbatim; `error::type_error` builds a plain `TypeError` for argument-shape problems; `error::object_error` wraps a Python-object failure as `EVOXCError` and chains the original as `__context__` — nothing panics or `unwrap`s across the FFI boundary.

## `transform` is wired to `evoxc-compiler`

`module_ops::transform` validates `kind` with `TransformKind::parse` (unknown → `TransformError` naming the kind and the accepted set), requires `module`/`config` to be dicts (`TypeError`), decodes `module` with `evoxc_core::envelope::decode`, decodes the config with `parse_config`, and runs `evoxc_compiler::transform(kind, &program, &config, extension)` inside `Python::detach`.
The transformed `Program` is encoded with `evoxc_core::envelope::encode` and the envelope gains one top-level `"transform"` object: `kind`, `output_ids` (the transformed return operands), `input_ids` (the transformed block arguments) and `batch_dim` (the fresh batch `Dim` name, `null` for the AD transforms).
Engine `Error` kinds map to `NativeError.kind` verbatim, so e.g. `grad`'s non-scalar-output diagnostic stays `ShapeError` and every transform-engine diagnostic stays `TransformError`.

## Config decoding

The config dict accepts exactly the keys of `native/CONTEXT.md`; an unknown key is a `TransformError` naming it and the accepted set (typos are never ignored), and a missing/inapplicable key falls through to the engine's own diagnostics.

* `axes` — a dict of value-id → `int | null` (keys are ints or decimal strings; a JSON map is sorted by value id), a list of `[value_id, axis]` pairs, or a list of per-input-position `int | null` entries (the pair form and the positional form are distinguished by whether every list entry is itself a sequence). The first two fill `TransformConfig.axes`, the third fills `input_axes`.
* `batch_dim_name` — `str | null`; `out_axes` — `int | null` (`All(None)` when explicitly `None`) or a list of `int | null` (`PerOutput`); `argnums` / `tangent_inputs` / `cotangent_inputs` — lists of non-negative ints.
* `extension_rule` — a Python callable (any other non-`None` value is a `TypeError`); it becomes a `PyExtensionRule` handle moved into the detached transform.

All JSON-shaped decoding lives in `src/transform_config.rs` and is unit-tested without an interpreter; only the dict/pair walk and the callable handle touch Python.

## `batch_functions` is wired to `evoxc-compiler`

`batch_ops::batch_functions` is the population-merge sibling of `transform`: `programs` is a list/tuple of `evoxc-native-ir` envelopes (one per function, decoded by `evoxc_core::envelope::decode` with a `programs[i]` context), the config dict is decoded with `transform_config::parse_batch_config`, and `evoxc_compiler::batch_functions::batch_functions_with_env` runs inside `Python::detach` with the SAME extension-rule bridge `transform` builds (`extension_rule_from_value` + `PyExtensionRule`), so `sparse_*` / `block:*` / `external:*` rules participate exactly as in a transform.
The result is `{"module": <merged evoxc-native-ir envelope>, "batch_report": <BatchReport::to_json()>}` — the shape `native/evoxc-compiler/tests/parity_transform/run_batch_parity.py` drives (`convert.from_native(result["module"])`, `_normalize_report(result["batch_report"])`).
The `BatchReport` object has exactly the 12 documented keys: `n_functions`, `value_classes`, `shared_classes`, `switched` (group/variants/rows_per_variant), `stacked_constants`, `output_muxes`, `emitted_ops`, `bands`, `band_sizes`, `band_strategy`, `cost_estimate`, `flat_cost_estimate`.

Config keys (an unknown key is a `TransformError` naming it and the accepted set; `extension_rule` accepts a callable or `None`):

* `axes` / `out_axes` — `int | null` (broadcast to every tensor leaf) or a list of `int | null` (one entry per tensor input / output leaf, in order). Absent or an empty list means the engine default (`Some(0)`, the leading function axis); an explicit `null` means "unmapped". Both expand to the engine's `Vec<Option<i64>>` using the entry function's leaf counts; non-leading entries fall through to the engine's own `TransformError`.
* `switch_ops` — `null`/`false` (none), `true` (the default `elementwise` + `comparison` groups) or a list of merge groups (a category-name string, or a list of op-name strings). Unknown categories/op names are the engine's `TransformError`.
* `bands` — `null` (flat), an int `K >= 1` (`explicit`; `K > N` is the engine's out-of-range `TransformError`), or `"auto"`; a bool is a `TransformError`.
* `alignment` — `null` (the `variant` default) or `"variant" | "occurrence" | "auto"`, normalized trimmed + case-insensitive like the Python frontend; anything else is a `TransformError`.

The five data keys are decoded interpreter-free by `transform_config::{batch_axes_from_json, switch_ops_from_json, bands_from_json, alignment_from_json, parse_batch_config}` (unit-tested without Python); `batch_ops` only walks the Python dict, converts each value to JSON and extracts the callable.

## Extension-rule bridge

`PyExtensionRule` implements `evoxc_compiler::ExtensionRule` over the `Py<PyAny>` callable.
The engine runs detached, so `call` re-attaches with `Python::attach` for the duration of one rule call only.
The request is encoded as the neutral dict of `native/CONTEXT.md` (`kind`, `op_name`, `rule_key`, `attributes`, `operand_types`, `result_types`, `axes`, `tangents`, `cotangent_type`) via `py_from_json`.
The callback's answer is read back with `json_from_py`: Python `None` → `Ok(None)` (the engine then raises its ordinary `TransformError` naming the op), a dict → `ExtensionResponse` with `module`/`entry`/`output_ids`/`output_axes` decoded by `transform_config::response_from_json`.
`output_ids` accepts an int/string value id or `null` per entry: `null` parses to `None`, the structurally-zero dual (`Dual::ZeroTangent`) of a `jvp`/`vjp` response (batching rejects it), so the Python bridge can send `None` for every `autodiff.ZeroTangent`/`None` dual slot and omit the `autodiff._materialize` zero values — the scratch subgraph then returns only its non-zero contributions, and the engine materializes zeros only where a zero dual reaches a graph output.
A malformed response is a `TransformError` naming the op and the field (unknown response keys and a non-id, non-null `output_ids[i]` included); a Python exception is a `TransformError` preserving the interpreter's message text and naming the op.

## Cargo features (test linkage)

`Cargo.toml` deliberately does **not** use `pyo3.workspace = true`: the workspace entry hard-enables `extension-module`, and an extension-module build links no libpython, so a `cargo test` binary that touches the Python API cannot link.
`default = ["extension-module"]` keeps `scripts/build-native.sh` and `cargo build -p evoxc-python` on the cdylib path; `auto-init` (`pyo3/auto-initialize`) is the test-only alternative that links libpython and initializes an interpreter.
`pyo3` is pinned to `0.30` with `macros` + `abi3-py311` explicitly (default features off, since `default-features = false` must be compensated for `macros`).

## Test strategy

`cargo test --manifest-path native/Cargo.toml --workspace` is the always-on gate: it compiles this crate with `extension-module` and runs the interpreter-free tests (32: the error-family closure, the transform-kind list, the whole `transform_config` decode/encode surface — axes shapes, `out_axes`, batch-dim name, index lists, the `batch_functions` config (axis broadcast/per-leaf, every `switch_ops`/`bands`/`alignment` form, unknown-key rejection), request JSON, response parsing and its malformed-response diagnostics — the `infer` module-argument decoding: full envelope, signature-only `call` resolution in all three entry forms, unknown callee, every malformed argument shape, and a malformed type; `batch_ops::arity`; and the `cpu` helpers — the 14-dtype name round trip, `storage_to_bytes` for integers/floats/bool/f16/complex, a bad envelope discriminator surfacing `PersistenceError`, and an empty module decoding).
`cargo test --manifest-path native/Cargo.toml -p evoxc-python --no-default-features --features auto-init` runs that same set plus the 25 interpreter-backed tests (57 total): scalar/bool/int/float fidelity, nested dict/list/tuple round trips, ndarray-payload base64 through `wire::array_from_json`, out-of-range ints, NaN, non-string keys, unsupported-type and index path messages, `NativeError` kind/message/`str`, `from_core` family preservation, `object_error` context chaining, `parse_config` for every key and both `axes` shapes, unknown-key/non-callable rejection, the `PyExtensionRule` bridge (`None` / dict response / exception text), the end-to-end `infer` module contexts (signature-only 2-tuple + full envelope resolve `call`, an unknown callee and the malformed-context `TypeError`s), the `batch_functions` argument-shape rejections (`programs[i]` / `config` non-dict, unknown config key), and the shared-int table's band boundaries (`-8` … `i64::MIN`, `256`/`257`, `i64::MAX`, and identity of an in-band value), and the `cpu::marshalling` numpy hand-off suite (bit-identical round trips for all 14 dtypes, bool normalization, the threaded large-payload path, freshness/non-aliasing, a strided input copied contiguous, 0-d and empty arrays, and the `split_threads` threshold).
The interpreter-backed set needs `numpy` importable by the linked interpreter (the `cpu::marshalling` helpers build their arrays with `numpy.frombuffer`).
End-to-end verification is `source scripts/dev-env.sh && scripts/build-native.sh [--debug]` (builds the cdylib, installs it into `evoxc/` and smoke-tests `version()` through `.venv/bin/python`), then loading the installed `.so` with `importlib.util.spec_from_file_location("evoxc._evoxc_native", "evoxc/_evoxc_native.abi3.so")` — that avoids `import evoxc`, which would pull the whole Python frontend.
No test needs a GPU, the network, or (for the always-on gate) a linked libpython.

## Manual harnesses

`./verify_infer_parity.py` is the FFI-level **inference parity** harness: it replays 11 `infer` module-argument cases through the extension (signature-only 2-element/3-element/dict entries and a full envelope resolving `call`, plus the unknown-callee `VerificationError` and the `TypeError` argument-shape rejections — they need no `evoxc` import, so they always run), and imports the installed extension with `import evoxc._evoxc_native`, replays the committed differential fixture `../evoxc-core/tests/parity/cases.json` (518 cases over all 113 shape-function ops) through `infer(op_name, operand_types, attributes, result_types=None, module=None)`, and compares every answer with `expected.json` — exact dtype name plus the full shape JSON for a success (symbolic `Dim` with/without `size`, `DimExpr` op/operand structure, dynamic `None`), and the exact `NativeError.kind` family for a rejection.
It also re-derives **every** successful case from the live authority (`evoxc.ir.op_defs.opdef(op).shape_fn(operand_types, effective_attrs)`, the same call `parity/generate.py` makes, defaults layered under the case's explicit attributes) and compares that answer with the native one, so a stale fixture fails too.
A rejection whose family differs from the record is only accepted as a *documented divergence* when the record still matches the live `shape_fn` AND either the live pipeline (`evoxc.ir.builder.Builder.create` — the layer native `infer` mirrors) raises the native family, or the recorded family is not an EVOXC family while the message is identical; everything else is a mismatch (exit 1). A missing extension prints a skip naming `scripts/build-native.sh` and exits 2 (0 with `--allow-missing`).
Run it with `source scripts/dev-env.sh && scripts/build-native.sh --debug && .venv/bin/python native/evoxc-python/verify_infer_parity.py` (flags: `--allow-missing`, `--verbose`, `--fixture-dir`, `--min-cross-check`).
Result on the committed fixture: **529 cases (518 fixture + 11 module-context), 529 passed, 0 mismatches, 461 live cross-checks, 2 documented layered family divergences, exit 0** — `random_uniform#2` (fixture records the `shape_fn`'s plain `ValueError`, which no `NativeError.kind` can express; native `VerificationError` carries the identical message) and `sparse_concatenate#2` (fixture records the `shape_fn`'s `ShapeError`; both native `infer` and the authority's own `Builder.create` raise `VerificationError` on the 2-operand arity first).
No binding-side conversion bug was exposed by this fixture (every dtype, symbolic dim, `DimExpr` and `None` dim round-trips exactly); the two divergences are authority-record layering, not port defects.
`./verify_transform.py` is the sibling manual harness for the five transforms, the extension-rule bridge and the config diagnostics (same build, `.venv/bin/python native/evoxc-python/verify_transform.py`).
