# evoxc documentation site — compiler.evox.group

## Intent

The public documentation site for **EvoX Compiler** (`evoxc`), published at **https://compiler.evox.group**.
It is a Nimbus (Astro) static site deployed as a Cloudflare Worker and built by the shared reusable workflows in `EMI-Group/evox-docs-infra`.
Every factual claim here is derived from this repository's contracts — the root `../CONTEXT.md`, `../evoxc/CONTEXT.md`, the per-module `CONTEXT.md` files, `../README.md`, `../RELEASING.md` — and never invented.
Measured numbers may only be copied from those files or from a committed bench record (`../evoxc/bench/`).
The site documents the public API; it never documents private modules (`evoxc._native`, `evoxc._inspect`, …) or promises an implementation detail the contracts mark as deferred.
It carries two kinds of page: 28 hand-written `.mdx` pages (the guides and the reference prose) and 439 generated `.md` pages (the Python API reference under `src/content/docs/api/`, which is COMMITTED).

## Authoring rules (binding for every page)

- Frontmatter: `title` (required, unique), `description` (one sentence, used for meta/OG/search), `sidebar.order` (group pages also set `sidebar.group.label`, page order ascending).
- The page H1 comes from `title`: never repeat it as a `#` heading in the body — start at `##`.
- Markdown-first: `##`/`###` headings, fenced code blocks with a language (`python`, `sh`, `text`, `toml`, `yaml`, `json`), tables for reference data, `<Aside>` for caveats.
- Components usable in `.mdx` without any import (registered in `src/components.ts`): `Aside`, `Card`, `CardGrid`, `PackageManagers`, `Step`/`Steps`, `Tabs`/`TabItem`, `Render`.
  `<Aside type="note|tip|caution|danger" title="…">` is the callout form — those are the only types `ui/aside/Aside.astro` styles, so any other value renders as a Note.
- Internal links are absolute site paths with a trailing slash, e.g. `/guides/graph-transforms/`.
  The `nimbus/internal-link` rule is an error, so a link to a page that does not exist fails the `npx @cloudflare/nimbus-docs check` preflight for `.mdx` sources (the Astro build itself still passes; `.md` pages are not linted — see Known issues).
- Every `/api/…` deep link must name a page that exists in the committed tree; derive it from the file on disk (`ls`/`find` under `src/content/docs/api/`) or from the grouped index `src/content/docs/api/index.md`, never by lowercasing a Python name by hand.
- Code examples must call the real public API exactly as `../evoxc/CONTEXT.md` defines it — real names, real keyword arguments, no invented parameters or return shapes.
- A page is finished when no `TODO`, placeholder or authoring note remains, every link target exists, and both `npx @cloudflare/nimbus-docs check` and `npm run build` pass.
- Prefer explaining *why* a design is the way it is (explicitness, no hidden tracing, physical devices) over restating an API signature that the generated reference already shows; link a symbol at its first mention and leave the signature to `/api/`.
- Never hand-edit a page under `src/content/docs/api/`: it is regenerated and its marker comment means so. A wrong generated page is a docstring bug (or a `../docs-infra.yml` bug).

## Build and verification

```sh
npm ci                                          # once
npx @cloudflare/nimbus-docs check               # build-free preflight: structure, authoring, types
npm run build                                   # astro build → dist/ (467 pages: 28 hand-written + 439 generated)
```

`check` reports Environment, Migrations and Types green, Structure and Authoring "partly checked" — the computed `sidebar` needs a real build, and the authoring rules read `.mdx` only, so the 439 generated `.md` pages are never linted.
The build therefore validates the generated pages structurally (every page renders, the strict `docs` frontmatter schema accepts it), and `nimbus/internal-link` covers the hand-written `.mdx` links into `/api/`.
Links *inside* a generated page are not link-checked by either tool: to verify them, scan the built output (every `href`/`src` starting `/` must resolve to a file or `<path>/index.html` in `dist/`).
The current tree resolves 233,419 internal `href`/`src` targets across `dist/` (467 HTML files) with 0 missing.

## The generated Python API reference (committed)

`src/content/docs/api/` is the Python API reference of BOTH distributions, generated by the `docs-infra python-api` command from the repo-root `../docs-infra.yml` (`python_api` is a list: the `evoxc` package with 17 modules and NO `exclude` list, and the separate `evoxc_hf` package with 11 modules at `source_path: evoxc_hf/src`).
It is **committed**, not git-ignored: 439 markdown files — 410 symbol pages, 28 module `index.md` pages (17 `evoxc` + 11 `evoxc_hf`), and one root `api/index.md`.
Each page carries `title` and `description` frontmatter, the `<!-- Generated by docs-infra Python API -->` marker, a `python` fenced signature, a `Part of [module]` backlink, RST `Parameters`/`Returns`/`Raises` sections rendered as bullets (a wrapped `Returns` is ONE bullet, `x`/``x`` literals become single-backtick code spans, section underlines become headings), and a `View Python source` link.
The source links use the stable `revision: main` from `../docs-infra.yml`, so a page only changes when its docstring changes — never pin the generation to a commit SHA.

A page's URL is its public name with dots turned into directories, each segment lowercased and `_` → `-`: `evoxc.pipeline.compile` → `src/content/docs/api/evoxc/pipeline/compile.md` → `/api/evoxc/pipeline/compile/`.
The package `evoxc_hf` maps to the single segment `evoxc-hf` (`/api/evoxc-hf/load/load-hf/`).
A module index page lives at the module URL itself (`/api/evoxc/ops/`) and is the sidebar "Overview" of its group.
A symbol exported by two listed modules gets a page under each (e.g. `Executable` at `/api/evoxc/backends/executable/` and `/api/evoxc/pipeline/executable/`).
A name a same-named submodule shadows is resolved to its own page: the generator walks the defining submodule too, so `evoxc.transforms.vmap`/`vectorize`/`grad`/`jvp`/`vjp`/`batch_functions`, `evoxc.trace.trace`, `evoxc.ir.verify` and `evoxc.ops.constant` are published even though `evoxc.transforms`, `evoxc.trace`, `evoxc.ir` and `evoxc.ops` are themselves modules.
Page paths are lowercased, so a class/function pair that differs only in case is disambiguated instead of aborting the run: the first name in SORTED order keeps the plain path and the later one gets a `-class`/`-function` suffix, which is why `evoxc.ir.OpDef` is `/api/evoxc/ir/opdef/` and `opdef()` is `/api/evoxc/ir/opdef-function/`, `evoxc.dist.Group` is `/api/evoxc/dist/group/` and `group()` is `/api/evoxc/dist/group-function/`, and the same split applies to `Dim`/`dim`, `Tensor`/`tensor` and `Defn`/`defn`.
Link a name only to the page whose title claims it: `core/tensor.md` is the `Tensor` CLASS, `core/tensor-function.md` the `tensor()` factory.
The root `api/index.md` (title `Python API reference`) is the grouped index — `## evoxc` / `## evoxc_hf`, one `### [module]` block each with one-line summaries — and is the authority for which deep link is valid.
There is no `api/evoxc/index.md`, so the `Evoxc` sidebar group is heading-only (no Overview link); the `evoxc_hf` group gets one because its package level generates `api/evoxc-hf/index.md` (title `evoxc_hf`); `/reference/api-overview/` is the human entry point.

### Regenerating

Run from the repository root (the config paths are root-relative). The toolkit's Node deps are not installed in this repo, so copy the checkout and install them there — never write inside the toolkit checkout:

```sh
TOOLKIT=<path-to>/evox-docs-infra          # the toolkit checkout
mkdir -p "$TMPDIR/toolkit"
cp -r "$TOOLKIT"/{bin,lib,python,package.json,package-lock.json} "$TMPDIR/toolkit/"
npm ci --prefix "$TMPDIR/toolkit" --ignore-scripts --no-audit --no-fund
node "$TMPDIR/toolkit/bin/docs-infra.mjs" python-api --root .
```

A fresh tree reports `Python API: 410 symbols, 439 changed, 0 removed`; a second run must report `0 changed, 0 removed` (the tree is idempotent, which is what makes committing it safe).
Griffe emits "No type or annotation for parameter …" notes for unannotated `evoxc_hf` helpers — they are informational, not failures.
The doc-site build workflow runs the same command before every build, so a docstring change lands in the tree on the next CI build; commit the regenerated pages with the change that caused them.
`src/content/docs/api/` must stay out of `.gitignore` — `./.gitignore` therefore anchors the build output as `/dist/` (not `dist/`), because an unanchored `dist/` also matches the generated `src/content/docs/api/evoxc/dist/` group and silently drops the `group-function.md` page; `git add -f` is only needed if the rule is ever widened again.

### Sidebar behaviour

The tree is a directory of the primary `docs` collection (not a separate `api` collection), so `sidebar.scope`/`isolate` cannot isolate it.
`astro.config.ts` keeps the group in its place between Reference and the HuggingFace page (`{ label: "Python API", autogenerate: { directory: "api" }, collapsed: true }`), so it starts closed.
Nimbus renders a nested group OPEN unless its `collapsed` is `true`, and the generated pages carry no `sidebar` frontmatter, so `collapseApiGroups` in `src/pages/[...slug].astro` (passed as the `getSidebar` `transform`) collapses every group that hangs off `api/`.
The group holding the current page still opens, because `SidebarGroup.astro` treats an active descendant as open — on `/api/evoxc/ops/add/` the `Python API`, `Evoxc` and `evoxc.ops` groups are open and every sibling module group is closed.
Scoping the collapse to `api/` leaves the hand-written sections' rail expanded.
A hand-authored `src/content/docs/api/index.md` is overwritten by the generated root index (same path, and the generator owns it); a nested `api/<package>/index.md` has no generated counterpart and survives regeneration, while any other same-path collision now costs the later name a `-class`/`-function` suffix instead of aborting the run.

## Known issues

- The module-level registries `evoxc.transforms.batching_rules`, `jvp_rules` and `vjp_rules` are plain dicts, so they get no symbol page; the transform FUNCTIONS around them are all published (`/api/evoxc/transforms/<name>/`) and the guide names the registries in prose with no link.
- The `evoxc` package level has no index page (its `__all__` is computed at import time, so static analysis cannot build the package page), so the `Evoxc` sidebar group is heading-only (no "Overview" link); the `evoxc_hf` group has one from `api/evoxc-hf/index.md`. `/api/` (the grouped root index) is the module entry point, and `/reference/api-overview/` is the human one.
- `check` does not lint `.md` pages (the authoring rules read `.mdx`), so a broken link or bad frontmatter INSIDE a generated page is caught by neither `check` nor the Astro build. Verify generated links against `dist/` (see Build and verification) and treat any link-shape change as a toolkit/config question.
- A group index page must carry a `sidebar.order` strictly lower than every other page in its group — equal orders are not reliably broken — so `guides/index.mdx` uses `order: 0` and leads its group; `reference/index.mdx` sits at `order: 3` and its Overview link renders mid-group, after Op catalogue.
- Nimbus discovers `public/favicon.svg` before `public/favicon.ico`, so the head links the SVG and the `.ico` only answers a bare `/favicon.ico` request; both are the evoxc mark — regenerate the `.ico` from the SVG if the mark changes.
- The top-level `evoxc` namespace is not generated: its `__all__` is computed at import time, which Griffe's static analysis cannot evaluate, so `reference/api-overview.mdx` is hand-written and links into the definition pages.
- A new public top-level name therefore never appears without hand edits, and the transform inventory (`vectorize`/`vmap`/`grad`/`jvp`/`vjp`/`batch_functions` and the structural `split_by_inputs`/`analyze_inputs`) is duplicated in `reference/api-overview.mdx` (Transforms table), `reference/index.mdx` (pipeline chain), `reference/pipeline-objects.mdx` (the `Graph` producer diagram and "Produced by"), `reference/architecture.mdx` (layer diagram, crate table, the numeric-transform sentence and the "What stays Python" table), `guides/graph-transforms.mdx`, `guides/index.mdx`, `index.mdx`, `getting-started/quickstart.mdx`, `getting-started/install.mdx` and `development.mdx`; the sidebar needs no edit because `astro.config.ts` autogenerates every group by directory.
- The generated pages carry the toolkit's back-link and signature text verbatim; when a docstring changes the page changes too, so never patch a generated page — fix the docstring.
- `check` also lists two optional Nimbus starter upgrades (`starter-a11y-layout`, `theme-switch-no-fade`) as informational `nimbus/upgrade-optional` findings until `npx @cloudflare/nimbus-docs migrate --yes` records 0.20.2 as reviewed; they are not errors.
- `development.mdx` documents the regeneration recipe and the committed-tree status; keep it in step with this file when either changes.

## Notes for Agents

- Adding a public name is two jobs: an entry in the `__all__` of a module named in `../docs-infra.yml` (such as `split_by_inputs` in `evoxc/transforms/__init__.py.__all__`) reaches `/api/` automatically on the next generation run, but the top-level `evoxc.*` spelling is hand-maintained in `reference/api-overview.mdx` plus the transform enumerations listed under Known issues — no generator writes those.
- A split example in a guide or reference page must show the verified runtime call shapes: `evoxc.run(prepare, *fixed_args)` (the fixed arguments as separate arguments — `run(prepare, (params,))` raises `TraceError`) and `evoxc.run(apply, varying_tree, prepared_tuple)` (two arguments; nesting them as one raises `TraceError`), because `evoxc.run`'s root argument *is* the args tuple.
- `evoxc.build` refuses an already-traced `Graph`, so every split example stages with the explicit `lower` → `compile` → `load` chain.
- A split example may fix only some members of a plain tuple/list/dict input: those containers prune per tensor leaf (a partially pruned dict is rebuilt with just its surviving keys, a container whose subtree keeps no leaf is dropped from that half's signature), `prepare` keeps the fixed members while `apply` takes the varying ones plus the prepared tuple, and a namedtuple/dataclass/registered pytree node losing only some of its children is still a `TransformError`.
- The split section's figures (prepare 2 ops, apply 5 ops, one boundary value of 128 B for the `fitness(dataset, params, candidate)` example) come from `evoxc/transforms/CONTEXT.md`; re-verify the snippet and those numbers together if the example ever changes.
- Verify a Python sample against the tree before publishing it (`PYTHONPATH=. .venv/bin/python sample.py` after `scripts/dev-env.sh` — the generated pages and the site need no extension build).

## Deployment (read only by agents assigned to `./docs-site`)

- Worker name `evoxc-docs`, `workers_dev: false`, static assets `./dist`; the Custom Domain `compiler.evox.group` (zone `evox.group`) is attached to that Worker in the Cloudflare dashboard, not in `wrangler.jsonc`.
- The GitHub environment `docs-production` carries the `CLOUDFLARE_API_TOKEN` secret and the `CLOUDFLARE_ACCOUNT_ID` variable; the token needs Workers Scripts edit rights on this Worker.
- `../.github/workflows/docs-site.yml` calls `EMI-Group/evox-docs-infra/.github/workflows/{build,deploy}.yml@main` (pinned to the toolkit's `main` for the module-page, collision and stable-`revision` generator; move both pins to the next published tag) with `site_directory: docs-site`, `output_directory: docs-site/dist` and `wrangler_config: docs-site/wrangler.jsonc`: it builds on pull requests and deploys on pushes to `main`.
- That workflow regenerates `src/content/docs/api/` before each build, so CI's copy is always the current docstrings; a committed page that differs is a docstring change that has not been regenerated locally — the CI build does not fail on the difference, it just publishes the fresh one.
- The optional `DOCS_INFRA_READ_TOKEN` repository secret lets a private checkout of the toolkit be read; with the public toolkit the caller falls back to the job token.
- Local deploy: `npm run build` then `npx wrangler deploy` with `CLOUDFLARE_API_TOKEN` exported.
- Translations are not enabled (`../docs-infra.yml` has `locales: []`); enabling them means adding locale IDs there, registering a Nimbus `docs-<locale>` collection here, and adding the toolkit's `docs-translate.yml` caller.
- Upgrading the Nimbus starter follows `./AGENT.md` (`npx @cloudflare/nimbus-docs outdated`, `diff`, `migrate --dry-run`); keep `nimbus.json` committed and never edit it by hand.
