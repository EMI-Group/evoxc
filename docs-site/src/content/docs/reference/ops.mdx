Every numerical operation that can appear in an EvoXIR graph is a function in the frontend op namespace (`evoxc.ops`, re-exported at the top level of `evoxc`): `evoxc.ops.__all__` holds 104 names, plus [`evoxc.arange`](/api/evoxc/numpy/arange/) from `evoxc.numpy`, the eight `evoxc.random` functions, the `evoxc.dist` collectives and the `evoxc.sparse` surface.
This page groups them by area; exact signatures, defaults and per-op docstrings are in the generated Python API reference published at `/api/` on this site, which is built from those docstrings.

## How ops are called

An op function is a *builder*, never an executor: it appends one IR op to the active builder (obtained from the trace context) and returns a `SymbolicTensor` wrapping the result value, with its dtype and shape already computed at trace time.

| Call shape | What happens |
|---|---|
| `SymbolicTensor` operands | One IR op is created in the active builder; the result is a `SymbolicTensor` |
| Python scalar alongside a `SymbolicTensor` | The scalar is auto-promoted to a 0-d constant operand — transparent sugar |
| A concrete `Tensor` operand | `TraceError`: evoxc has no eager mode |
| Called outside a trace | `TraceError` naming `evoxc.trace`, `@evoxc.defn` and `evoxc.evaluate` |

```python
import evoxc

evoxc.add(evoxc.tensor([1.0, 2.0]), 1.0)   # no graph is active: TraceError
```

```text
evoxc.core.errors.TraceError: No active trace: tensor ops can only be called while
tracing a graph definition (inside an `@evoxc.defn` function traced via
`evoxc.trace`, or inside the callables of `evoxc.cond` / `evoxc.while_loop` /
`evoxc.scan`). Call `evoxc.trace(fn, *specs)` or `evoxc.evaluate(fn, *args)` …
```

Passing a concrete `Tensor` from inside a trace fails with the three sanctioned ways out: make it an explicit input, embed it with the warned `evoxc.constant`, or run the whole thing through `evoxc.evaluate`.

Every non-tensor parameter — an axis, a shape, a padding table, `k`, a dtype, a callback — is a **static Python value**. It specializes the graph: a different value is a different op in a different program, with no hidden guard and no recompile. Nothing in the op layer computes a result, caches data, or inspects a runtime value.

### Operator overloads

`SymbolicTensor` supports the ordinary Python operators. Each one dispatches through a handler that the op layer registers at import time, so the dunder is pure sugar over the named function — including the reflected forms, which pass the tensor as the first argument:

| Expression | Op |
|---|---|
| `x + y`, `x - y`, `x * y`, `x / y`, `x ** y`, `-x` | [`add`](/api/evoxc/ops/add/), [`subtract`](/api/evoxc/ops/subtract/), [`multiply`](/api/evoxc/ops/multiply/), [`divide`](/api/evoxc/ops/divide/), [`power`](/api/evoxc/ops/power/), [`negate`](/api/evoxc/ops/negate/) |
| `x @ y` | [`dot`](/api/evoxc/ops/dot/) (rank ≥ 2; use [`matmul`](/api/evoxc/ops/matmul/) for 1-D operands) |
| `x == y`, `x != y`, `x < y`, `x <= y`, `x > y`, `x >= y` | [`equal`](/api/evoxc/ops/equal/), [`not_equal`](/api/evoxc/ops/not-equal/), [`less`](/api/evoxc/ops/less/), [`less_equal`](/api/evoxc/ops/less-equal/), [`greater`](/api/evoxc/ops/greater/), [`greater_equal`](/api/evoxc/ops/greater-equal/) |
| `x[key]` | [`slice`](/api/evoxc/ops/slice/) / [`gather`](/api/evoxc/ops/gather/) for static keys |

`__eq__` on two symbolic values builds a graph comparison, not a Python boolean — that is why `if x > 0:` on a symbolic value fails instead of silently picking a branch.

## Dtype and shape rules that hold everywhere

- **Tensor ⨯ tensor promotes by `numpy.result_type`**, including its subtleties: `int8`+`uint8` → `int16`, `float32`+`int64` → `float64`, `float16`+`float16` → `float16`.
- **Python scalar ⨯ tensor follows NEP 50 weak promotion**, implemented explicitly so the behavior is identical on numpy 1.x and 2.x: `int` scalars promote down to a `float16`/`float32`/`float64` tensor when exactly representable, `float` scalars are weak toward every float/complex tensor, `complex` scalars toward `complex64`/`complex128` only.
- **Unary math** ([`sqrt`](/api/evoxc/ops/sqrt/), [`exp`](/api/evoxc/ops/exp/), [`log`](/api/evoxc/ops/log/), [`log1p`](/api/evoxc/ops/log1p/), trig, [`tanh`](/api/evoxc/ops/tanh/), [`sigmoid`](/api/evoxc/ops/sigmoid/), [`relu`](/api/evoxc/ops/relu/), [`gelu`](/api/evoxc/ops/gelu/), [`erf`](/api/evoxc/ops/erf/)) turns integer/bool input into `float64` and keeps a float dtype; **unary preserving** ([`abs`](/api/evoxc/ops/abs/), [`negate`](/api/evoxc/ops/negate/), [`square`](/api/evoxc/ops/square/), [`sign`](/api/evoxc/ops/sign/), [`floor`](/api/evoxc/ops/floor/), [`ceil`](/api/evoxc/ops/ceil/), [`round`](/api/evoxc/ops/round/)) keeps the dtype.
- **Broadcasting** aligns shapes right. Two concrete extents that disagree is a `ShapeError` at trace time — a statically known failure is never deferred; when a symbolic dim is involved the result dim is the `DimExpr.max` of the two, which is numpy's own result shape, and the runtime enforces exact compatibility.
- **Reductions** take `axes=None` (all axes), negative axes, or a tuple; `keepdims=True` leaves the reduced axes as extent 1. A rank-0 result is the scalar shape `()`.
- Shape arithmetic over symbolic dims uses `Dim`/`DimExpr`, so rank is always known at trace time even when extents are not.

## Backend support

| Backend | Coverage |
||---|---|
| `numpy` interpreter (default) | Every op — it is the reference implementation, and it supports symbolic shapes everywhere |
| `native` Rust engine | The dense operation set, at parity with the numpy reference (exact bool/integer paths, measured float tolerances); sparse ops are off |
| Compiler adapters (`iree`, `xla`, `tvm`) | The StableHLO-exportable subset; the rest raises an explicit `BackendError` at `lower()` |

The compiler-relevant deferrals today: [`tril`](/api/evoxc/ops/tril/), [`triu`](/api/evoxc/ops/triu/), [`cumsum`](/api/evoxc/ops/cumsum/), [`cumprod`](/api/evoxc/ops/cumprod/), [`flip`](/api/evoxc/ops/flip/), [`roll`](/api/evoxc/ops/roll/), [`nan_to_num`](/api/evoxc/ops/nan-to-num/), [`solve`](/api/evoxc/ops/solve/), [`erf`](/api/evoxc/ops/erf/) and [`gelu`](/api/evoxc/ops/gelu/) (there is no StableHLO error function, so GELU is deferred with it rather than approximated), [`diagonal`](/api/evoxc/ops/diagonal/), the factorizations [`cholesky`](/api/evoxc/ops/cholesky/)/[`qr`](/api/evoxc/ops/qr/)/[`matrix_rank`](/api/evoxc/ops/matrix-rank/)/[`svd`](/api/evoxc/ops/svd/)/[`matrix_exp`](/api/evoxc/ops/matrix-exp/), [`random_multinomial`](/api/evoxc/random/multinomial/), every `sparse_*` op (densify with `evoxc.sparse.to_dense` first), and the callback ops [`runtime_call`](/api/evoxc/ops/runtime-call/)/[`external_call`](/api/evoxc/ops/external-call/)/[`dist.rank`](/api/evoxc/dist/rank/)/[`dist.world_size`](/api/evoxc/dist/world-size/).
The frontend compositions below work through their components, so [`topk`](/api/evoxc/ops/topk/), [`stack`](/api/evoxc/ops/stack/), [`clamp`](/api/evoxc/ops/clamp/), [`matmul`](/api/evoxc/ops/matmul/), [`isnan`](/api/evoxc/ops/isnan/), [`eye`](/api/evoxc/ops/eye/) and [`linspace`](/api/evoxc/ops/linspace/) inherit the coverage of the ops they expand into.
[`diag`](/api/evoxc/ops/diag/) is a single IR op whose own v1 emission is a flatten-plus-gather (rank 2) or an iota mask plus [`select`](/api/evoxc/ops/select/) (rank 1), so it needs neither a separate mnemonic nor a composition.
The two escape hatches [`custom_call`](/api/evoxc/ops/custom-call/)/[`inline_stablehlo`](/api/evoxc/ops/inline-stablehlo/) are gated on the backend's `Capabilities.custom_ops`: the numpy interpreter and the native engine reject them explicitly and the compiler decides their validity.

## IR op or composition

Some frontend names are one IR op; others are documented compositions of ordinary ops. The difference is observable — it changes the op count in `graph.summary()`, the derivative rules that apply, and the compiler coverage — so it is worth knowing which is which.

| Kind | Names |
|---|---|
| One IR op each | the arithmetic, comparison, logical, bitwise and unary-math ops, [`cast`](/api/evoxc/ops/cast/), [`broadcast`](/api/evoxc/ops/broadcast/), [`reshape`](/api/evoxc/ops/reshape/), [`transpose`](/api/evoxc/ops/transpose/), [`slice`](/api/evoxc/ops/slice/), [`gather`](/api/evoxc/ops/gather/), [`scatter`](/api/evoxc/ops/scatter/), [`concatenate`](/api/evoxc/ops/concatenate/), [`pad`](/api/evoxc/ops/pad/), the `reduce_*` ops, [`argmax`](/api/evoxc/ops/argmax/)/[`argmin`](/api/evoxc/ops/argmin/), [`dot`](/api/evoxc/ops/dot/), [`conv`](/api/evoxc/ops/conv/), [`tril`](/api/evoxc/ops/tril/)/[`triu`](/api/evoxc/ops/triu/), [`diagonal`](/api/evoxc/ops/diagonal/), [`solve`](/api/evoxc/ops/solve/), the factorizations, [`sort`](/api/evoxc/ops/sort/)/[`argsort`](/api/evoxc/ops/argsort/), [`tile`](/api/evoxc/ops/tile/)/[`flip`](/api/evoxc/ops/flip/)/[`roll`](/api/evoxc/ops/roll/)/[`diag`](/api/evoxc/ops/diag/)/[`nan_to_num`](/api/evoxc/ops/nan-to-num/), [`stop_gradient`](/api/evoxc/ops/stop-gradient/), [`constant`](/api/evoxc/ops/constant/) |
| Composition over IR ops | [`sum`](/api/evoxc/ops/sum/)/[`max`](/api/evoxc/ops/max/)/[`min`](/api/evoxc/ops/min/)/[`mean`](/api/evoxc/ops/mean/)/[`prod`](/api/evoxc/ops/prod/) (shorthand for `reduce_*`), [`cumsum`](/api/evoxc/ops/cumsum/)/[`cumprod`](/api/evoxc/ops/cumprod/), [`matmul`](/api/evoxc/ops/matmul/), [`topk`](/api/evoxc/ops/topk/), [`stack`](/api/evoxc/ops/stack/), [`clamp`](/api/evoxc/ops/clamp/), [`isnan`](/api/evoxc/ops/isnan/), [`eye`](/api/evoxc/ops/eye/), [`linspace`](/api/evoxc/ops/linspace/), [`trace`](/api/evoxc/ops/trace/), [`norm`](/api/evoxc/ops/norm/), [`var`](/api/evoxc/ops/var/), [`std`](/api/evoxc/ops/std/), [`median`](/api/evoxc/ops/median/), [`nansum`](/api/evoxc/ops/nansum/), [`evoxc.arange`](/api/evoxc/numpy/arange/) |

A composition adds no new semantics: it is the same graph you would have written by hand, and its name in the catalogue is a convenience, not a backend feature.

<Aside type="tip" title="Each op exists in three places">
By contract a dense op lives in exactly three places: its schema and shape inference in the EvoXIR op registry (`evoxc/ir/op_defs/`), its reference kernel in the numpy interpreter (`evoxc/backends/numpy/`), and its fast kernel in the native CPU engine (`native/evoxc-cpu/`). A frontend op that works on one backend and not the other is a bug, not a tolerance.
The documented exceptions are the compiler escape hatches `custom_call`/`inline_stablehlo` (a schema, inference, export and deliberately **no** kernel anywhere), the frontend compositions (no IR op at all), and the sparse ops (numpy-backend-only in v1).
</Aside>

## Indexing, gather, scatter, slice and pad

| Op | Meaning | Notes |
|---|---|---|
| [`slice(x, start, lengths, strides=1)`](/api/evoxc/ops/slice/) | Static strided slice | Starts/strides must be static ints; lengths may be symbolic; shape is exactly `lengths` |
| [`gather(x, indices, axis=0)`](/api/evoxc/ops/gather/) | Take entries along an axis | `indices` must be `int32`/`int64` (else `DTypeError`); result shape is `x.shape[:axis] + indices.shape + x.shape[axis+1:]` |
| [`scatter(x, indices, updates, axis=0)`](/api/evoxc/ops/scatter/) | Update along an axis | Functional: `x` is never mutated, a copy is updated; `updates` is cast to `x.dtype` |
| [`pad(x, config, value=0)`](/api/evoxc/ops/pad/) | Constant padding | One entry per axis, each an `int` (symmetric) or a `(before, after)` pair; negative padding is a `ShapeError`; the fill value is cast to `x.dtype` |
| `x[key]` | `getitem` operator handler | Static ints and `slice` objects only → `slice`/`gather`; symbolic indices, masks, `None`/newaxis and ellipsis are `TraceError`s |

| [`sort(x, axis=-1, descending=False, stable=False)`](/api/evoxc/ops/sort/) | Sort values | Exports as v1 StableHLO (descending = reverse after the sort) |
| [`argsort(x, axis=-1, descending=False, stable=False)`](/api/evoxc/ops/argsort/) | Sort indices | Exports as v1 StableHLO |
| [`topk(x, k, axis=-1, largest=True)`](/api/evoxc/ops/topk/) | Top-`k` values **and** indices | Composition returning a pair; `k` is a static int ≤ the extent (a symbolic extent defers to run time); `k=1` uses an argmax/reduce fast path |

## Convolution and pooling

`conv` is the only spatial op in the frontend; there is no pooling op, and no `conv` VJP.
Windowed reductions are written out by the caller from `slice`, `reshape` and the `reduce_*` ops, exactly like softmax and layer norm, which are also explicit compositions rather than ops.

## Random

`evoxc.random` is key-based and functional: the algorithm is a static tag on the key, and the same key plus operands always produces bit-identical values.

| Op | Meaning | Notes |
|---|---|---|
| [`key(seed, algorithm="splitmix64")`](/api/evoxc/random/key/) | Create a key | The only polymorphic creator; accepts a name or an `Algorithm` member (`SPLITMIX64`, `THREEFRY2X32`, `PHILOX4X32_10`) |
| [`split(key)`](/api/evoxc/random/split/), [`split_n(key, n)`](/api/evoxc/random/split-n/) | Derive independent keys | Keys are never mutated, so splitting is how you get more of them |
| [`uniform(key, shape, low=0.0, high=1.0, dtype=float32)`](/api/evoxc/random/uniform/) | Uniform sample | The key's form determines the algorithm; a mismatched key is a `ShapeError`/`DTypeError` |
| [`normal(key, shape, mean=0.0, std=1.0, dtype=float32)`](/api/evoxc/random/normal/) | Normal sample | |
| [`randint(key, shape, low, high, dtype=int32)`](/api/evoxc/random/randint/) | Integer sample | |
| [`permutation(key, n, dtype=int32)`](/api/evoxc/random/permutation/) | Random permutation | |

## Control flow and graph annotations

| Op | Meaning | Notes |
|---|---|---|
| [`evoxc.cond(pred, true_fn, false_fn, *operands)`](/api/evoxc/trace/cond/) | Runtime branch | The two callables are traced into IR regions; both must return the same structure |
| [`evoxc.while_loop(cond_fn, body_fn, init)`](/api/evoxc/trace/while-loop/) | Runtime loop | The predicate and the carry must involve at least one symbolic value |

## Sparse ops

`evoxc.sparse` exposes 16 graph ops — [`sparse_from_dense`](/api/evoxc/sparse/from-dense/), [`sparse_to_dense`](/api/evoxc/sparse/to-dense/), the [`coo`](/api/evoxc/sparse/coo/)/[`csr`](/api/evoxc/sparse/csr/)/[`csc`](/api/evoxc/sparse/csc/) conversions, [`negate`](/api/evoxc/sparse/negate/), [`add`](/api/evoxc/sparse/add/), [`multiply`](/api/evoxc/sparse/multiply/), [`multiply_dense`](/api/evoxc/sparse/multiply-dense/), [`reduce_sum`](/api/evoxc/sparse/sum/), [`transpose`](/api/evoxc/sparse/transpose/), [`reshape`](/api/evoxc/sparse/reshape/), [`concatenate`](/api/evoxc/sparse/concatenate/) and the two `dot` variants — and they are **numpy-backend-only in v1**: a compiler backend raises an explicit `BackendError` suggesting `evoxc.sparse.to_dense`. Sparse tensors are pytree composites over ordinary tensor values, not a new IR value kind. See [sparse tensors](/guides/sparse-tensors/).

## Custom and escape-hatch ops

| Op | Meaning | Notes |
|---|---|---|
| [`custom_call(call_target_name, *operands, result=..., backend_config="", api_version=1, has_side_effect=False)`](/api/evoxc/ops/custom-call/) | Emit `stablehlo.custom_call @target` | The compiler validates the target and its configuration; numpy/native reject it |
| [`inline_stablehlo(body, *operands, result=..., has_side_effect=False)`](/api/evoxc/ops/inline-stablehlo/) | Splice a raw StableHLO snippet verbatim | Operand *i* is `%in<i>`, result *i* must be assigned as `%out<i>` exactly once; the snippet is static text |

Both are effect-`callback` opaque ops with no kernel anywhere. A user *kernel* does not go through them: it plugs in as `external_call` or a `block` with a portable decomposition, which both numpy and the compiler adapters accept.

## When an op fails

Every op validates eagerly, at construction time, and the failure class tells you who owns the problem:

| Failure | Raised as | Example |
|---|---|---|
| No active trace, a concrete `Tensor` operand, a symbolic index, two scalar operands | `TraceError` | calling `evoxc.add(x, 1.0)` outside a trace |
| A statically known shape/rank/axis/broadcast/padding conflict | `ShapeError` | `broadcast: operand dim 2 cannot expand to target dim 3` |
| A bad dtype for the op (non-bool logical, non-integer bitwise, non-integer gather indices, a bad `cast` target) | `DTypeError` | `cast: 'not-a-dtype' is not a valid dtype` |
| A malformed static parameter (a list where a tensor belongs, a non-int axis) | `TypeError` | a Python programming error, not a graph error |

A conflict that depends on a symbolic dim cannot be decided at trace time, so it is deferred: the numpy backend and the native engine enforce the exact compatibility check at run time and raise there.

Every op also records a call-site `Location` (file and line) unless capture is disabled with `EVOXC_DISABLE_LOCATIONS=1`, which is what lets an error quote `model.py:83` instead of a stack trace.

## Names that do not exist

Composing is the intended style, so a few names callers reach for are deliberately absent — and there is no silent alias for them:

- `rsqrt` — write `evoxc.divide(1.0, evoxc.sqrt(x))` or `evoxc.power(x, -0.5)`.
- `softmax`, `logsumexp`, `layer_norm`/`rms_norm` — explicit `exp`/`sum`/`reduce_*` compositions.
- `where` — the op is `evoxc.select`; `where` exists only as `evoxc.numpy.where`.
- `any`, `all`, `count_nonzero`, `allclose` — explicit reduce compositions, e.g. `evoxc.max(evoxc.isnan(x))` as a NaN guard.
- `einsum`, `tensordot`, `outer` — a batched `dot` plus `reshape`/`transpose`; an embedding lookup is `evoxc.gather(table, idx, axis=0)`.

Calling one of these is an ordinary Python `AttributeError` naming the missing attribute — evoxc never resolves an unknown frontend name to a different op.
