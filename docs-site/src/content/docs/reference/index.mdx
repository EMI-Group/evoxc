The reference section states what evoxc *is*, in the form you can check a program against: exact public names, the objects each pipeline stage hands you, the option surface every backend shares, and the things v1 refuses.
Every claim here is derived from the package contract, not from a single implementation detail — so if a page here and a docstring disagree about a signature, the generated API page wins (see below), and if they disagree about meaning, this section is the one to trust.

## What "reference" means here

These pages are **contract-level, not tutorial**:

- **Names are exact.** Every function, class and keyword argument shown exists with that spelling. There are no "approximately like this" snippets.
- **Stages stay distinct.** A page never shows a convenience call doing a step the explicit pipeline does not do; the [pipeline objects](/reference/pipeline-objects/) page names the producing function for every type.
- **Refusals are documented.** When v1 does not support something, the [deferrals](/reference/deferrals/) page states the behaviour that marks it — usually a typed error naming the op — because "it raised" is part of the contract, not an accident.
- **No invented numbers.** The only figures quoted are ones recorded in the repository's contracts or in a committed bench record.

Why a design is the way it is — why there is no eager mode, why devices are physical, why `vmap` is sugar over `vectorize` — belongs to the guides and to [Core concepts](/getting-started/core-concepts/).
This section answers "what exactly can I call, and what exactly comes back".

## A pipeline you can hold in your head

Every reference page is consistent with this one chain, and each arrow is a public function that returns a distinct public type:

| Hop | Function | Result |
|---|---|---|
| define | `evoxc.defn` | `Defn` |
| trace | `evoxc.trace` | `Graph` (EvoXIR) |
| transform (optional) | `evoxc.vectorize` / `vmap` / `grad` / `jvp` / `vjp` / `batch_functions` | `Graph` |
| transform (structural, optional) | `evoxc.split_by_inputs` | `SplitPlan` — a `prepare` / `apply` pair of `Graph`s |
| lower | `evoxc.lower` | `LoweredProgram` |
| compile | `evoxc.compile` | `CompiledArtifact` |
| load | `evoxc.load` | `Executable` |
| run | `evoxc.run` | `Tensor` tree |

`evoxc.build` composes trace → lower → compile → load, `evoxc.evaluate` adds a run, and `evoxc.build_cached` memoizes the build. Those three are documented shorthand and nothing more; every other reference claim is about one of the explicit hops.
`evoxc.split_by_inputs` is the structural exception in the transform row: it returns a `SplitPlan` holding two ordinary `Graph`s rather than one `Graph`, and each half then stages through the same explicit hops.

## How the reference relates to the generated Python API

The site ships two kinds of API material, and they answer different questions.

| Material | Question it answers | Where it comes from |
|---|---|---|
| These reference pages | What does this name *mean*, which stage does it belong to, what does it refuse? | This repository's contracts, maintained by hand |
| The generated tree under [`/api/`](/api/) | What is the exact signature, docstring and module path of this symbol? | Griffe reading the installed package's docstrings |

The generated tree ships two kinds of page. Every public symbol gets its own page, addressed by its public name split on dots with each segment lowercased and `_` written as `-` — `/api/evoxc/pipeline/compile/` is the page for `evoxc.compile`, and `/api/evoxc/pipeline/compile-text/` is the page for `evoxc.compile_text`. Every module also gets an index page listing what it exports, such as [`/api/evoxc/ops/`](/api/evoxc/ops/), [`/api/evoxc/core/`](/api/evoxc/core/) or [`/api/evoxc/pipeline/`](/api/evoxc/pipeline/), and the grouped index at [`/api/`](/api/) lists every page by module.
Start from that grouped index when you need a signature.

Two consequences worth knowing:

- **The top-level `evoxc` namespace is not generated.** `evoxc.__all__` is computed at import time from the module globals, which static analysis cannot evaluate, so no generator page exists for the namespace itself. [Python API at a glance](/reference/api-overview/) is the hand-written replacement, and it links into the per-module pages.
- **A generated page is never patched here.** If a docstring is wrong or unclear, the fix belongs in the docstring, and the page changes on the next build. That is also why signatures are linked to rather than restated: a hand-copied signature is a second source of truth, and it rots.

The practical rule: read a reference page to decide *which* symbol you want and what it guarantees, then open the `/api/` page for the argument list.

## Conventions used across these pages

- **Shapes** are written as tuples. An `int` is a static extent, `evoxc.dim("B")` is a named symbolic extent, and `None` is a runtime-dynamic extent the tracer does not check. Rank is always known at trace time.
- **Dtypes** are the numpy dtype objects exposed as `evoxc.float32`, `evoxc.int64`, … (see [Python API at a glance](/reference/api-overview/)). `bool_` keeps its underscore so it does not shadow the builtin.
- **"Documents-ignored"** means an option is accepted at that stage and deliberately has no effect — it is not an error, so one options dict can be forwarded across backends.
- **"Byte-identical"** means the option, left unset, derives no compiler flag or changes no emitted text: a program compiled without it is the same program as before the option existed.
- **Errors** are subclasses of `evoxc.EVOXCError`, except where a page says a plain `TypeError`, `NotImplementedError` or `ValueError` is raised — those mark Python-level argument misuse rather than a graph or backend problem. The full taxonomy is on [Python API at a glance](/reference/api-overview/).
- **Stage mismatch** is always loud: passing the wrong object type to a stage raises `TypeError` naming the expected type and the producing function.

## What "stable" means for a reference page

A name documented here is a name the project treats as public API — the kind of thing that needs a deprecation rather than a quiet rename.
Two caveats are deliberate:

- **A backend may refuse a public name.** `custom_call` is public and real, and the numpy interpreter rejects it with an explicit `BackendError`. Public does not mean "works on every backend"; [Options](/reference/options/) and the capability flags say which backend honours what.
- **A deferral is not an oversight.** Where v1 has no answer, the error is the answer, so a program that raises has not half-worked. The list is on [Limitations and deferrals](/reference/deferrals/).

If you are extending evoxc rather than using it, read [Architecture](/reference/architecture/) and the import-acyclicity rules there before adding a module: the layering is part of the contract, not a convention.

One more habit worth forming: when an example here and a guide disagree, treat the disagreement as a bug report rather than a choice.
Both are derived documents, so a contradiction means one of them has drifted from the contract — and the contract is the only thing that decides.
