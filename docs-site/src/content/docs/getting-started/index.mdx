evoxc — **EvoX Compiler** — is a minimal, explicit, compiler-neutral tensor graph compiler and runtime for Python.
You write a numerical program as a graph, you inspect it, you transform it, and then you hand it to a backend: the bundled NumPy interpreter, the in-process Rust CPU engine, or an external compiler (IREE, XLA via PJRT, TVM) that receives StableHLO.

Nothing in that sequence happens by accident, and nothing happens out of order.
Every stage is a public function with its own public result object, so you can stop after tracing, save a graph, load it back in another process, or swap backends without touching the program.

## What you need

- **Python 3.11 or newer.** The project's `requires-python` is `>=3.11`, and the released wheels are a single `cp311-abi3` build per platform, so one wheel covers every supported CPython version.
- **NumPy 1.24 or newer.** It is the only hard runtime dependency, and deliberately so: `evoxc.float32` and friends *are* NumPy dtype objects, and a host `Tensor` payload is an `np.ndarray`.
- **No GPU.** The reference backend is a CPU NumPy interpreter, the second backend is an in-process Rust CPU engine shipped inside the wheel, and every test in this repository runs on CPU. Accelerators are optional adapters.
- **A Rust toolchain and a C compiler — only when building from source.** Published wheels already contain the compiled Rust/PyO3 extension, so a normal `pip install evoxc` needs no compiler at all.

That list is the whole prerequisite set. There is no CUDA toolkit to install, no compiler to configure and no environment variable to set before your first graph runs. [Install](/getting-started/install/) has the extras table and the source-build path.

<Aside type="tip" title="Nothing to configure">
  The default backend is the NumPy interpreter, so `evoxc.build(fn, *specs)` without a `backend=` argument is a complete, working pipeline.
  Compiler backends are activated per call (`backend="iree"`) or by environment default (`EVOXC_BACKEND`), never by a global switch that changes the meaning of existing code.
</Aside>

## The mental model: the graph is the program

There are two things to internalise before the guides make sense, and they are both consequences of the same design choice.

**The graph is the program.** `@evoxc.defn` marks a *graph definition*, not a compiled function and not an eager function. Calling a `Defn` with concrete tensors is an error rather than a silent trace, because the library never guesses when you wanted a graph. You say so explicitly: `evoxc.trace(fn, *specs)` builds a `Graph` (EvoXIR, a region-based SSA module) and hands it back to you.

**Every stage is an explicit public function.** The pipeline is not a call graph hidden inside a decorator; it is a sequence of calls you can stop, inspect and resume:

```text
defn → trace → Graph → transform → Graph
     → lower → LoweredProgram → compile → CompiledArtifact
     → load → Executable → run → Tensor
```

Each arrow is one public function returning one public object type, and no function consumes an earlier-stage object and performs the missing steps.
[Core concepts](/getting-started/core-concepts/) tabulates which call produces which object; [Pipeline objects](/reference/pipeline-objects/) lists what each one exposes.

Convenience APIs exist, and they are documented compositions of exactly those stages — `evoxc.build`, `evoxc.evaluate`, `evoxc.build_cached` and `evoxc.vmap` add no semantics you could not have written yourself.

```python
import evoxc
from evoxc import TensorSpec

@evoxc.defn
def f(x, w):
    return evoxc.sum(evoxc.tanh(evoxc.dot(x, w)), axes=1)

spec_x, spec_w = TensorSpec((4, 8), evoxc.float32), TensorSpec((8, 4), evoxc.float32)
graph = evoxc.trace(f, spec_x, spec_w)          # Graph — nothing has run yet
print(graph.digest())                           # sha256 over the structural payload
print(graph.summary()["tensor_inputs"])         # path / shape / dtype of each input
```

That snippet is the entire idea: a Python function becomes data, and the data is what executes.

## Four words

The design is easiest to remember as four words — the same four the [landing page](/#the-four-defining-properties) opens with, each a constraint on what the library is allowed to do.

- **Simple.** Convenience APIs compose the pipeline and add no semantics: `vmap` uses `vectorize`, `bind` supplies arguments, `build` chains trace → lower → compile → load.
- **Minimal.** NumPy is the only runtime dependency. The package is a Python frontend, a NumPy interpreter and a compiled Rust extension; a prebuilt wheel runs graphs with no compiler toolchain installed.
- **Explicit.** Every pipeline stage is a public function with its own result type, and no stage runs on your behalf.
- **Compiler-neutral.** EvoXIR — a region-based SSA IR — represents the program. StableHLO connects it to IREE, XLA and TVM; which one you get is decided by `backend=`, not by the language you wrote.

What follows from those words — no eager mode, no implicit tracing, no hidden recompilation, no automatic device movement, no silent fallback — is spelled out in [Core concepts](/getting-started/core-concepts/).

## Backends in one paragraph

Two backends ship inside the wheel: the **NumPy interpreter**, which is the default and interprets EvoXIR with NumPy kernels, and the **`native`** backend, which runs the same EvoXIR on the in-process Rust CPU engine. Neither is a mode — you select one with `backend=` and the graph's meaning is unchanged; [Backends and options](/guides/backends/) is the full story.

Everything else is an optional adapter that receives StableHLO: **IREE** (llvm-cpu, CUDA, ROCm, Vulkan-SPIRV), **XLA** (through a PJRT C API plugin the adapter discovers) and **TVM**. Because the boundary is a compiler-neutral IR, choosing a backend is a deployment decision, not a rewrite — an absent or incapable backend raises `BackendError` instead of quietly doing something else, as [Compiler adapters](/guides/compiler-adapters/) records per adapter.

## Vocabulary

Five names recur in every page, so they are worth fixing now.

| name | one-line meaning |
|---|---|
| `Defn` | a Python callable marked as a graph definition — the input to `trace` |
| `Graph` | the traced program: EvoXIR plus input/output trees and snapshotted static values |
| `SymbolicTensor` | an SSA value inside a `Graph` — shape and dtype only, never storage |
| `Tensor` | materialized runtime data with a concrete shape and a physical device |
| `Executable` | a compiled artifact bound to a device; the thing `run` calls |
