A transform in evoxc takes a `Graph` and returns a `Graph`. It never runs anything, never asks a backend for help, and never leaves a marker op behind: the result is a program made of ordinary `evoxc.ops` ops with static shapes, so the NumPy interpreter, the native engine and every compiler adapter execute it without knowing a transform happened.
That is design principle 7, and it is why `vmap`-ed or differentiated code can be persisted, inspected and lowered exactly like the graph it came from.

## One Rust implementation, no fallback

`vectorize`, `vmap`, `grad`, `jvp`, `vjp` and the `batch_functions` merge are a single implementation in the Rust core, reached through the compiled `evoxc._evoxc_native` extension (`scripts/build-native.sh` builds it; `EVOXC_NATIVE_LIB` can point at a prebuilt library).
There is no Python fallback: if the extension is missing, the first transform call raises `ImportError` with the build instructions instead of silently taking a slower, subtly different path.

Python keeps only frontend duties — argument validation with fixed error wording, `TensorSpec`/pytree adaptation, `Graph` reconstruction, and the rules bridge.
That bridge is how custom `block` ops (`block:<name>`), external kernels (`external:<name>`) and sparse ops (`sparse_*`) contribute batching and derivative rules: their Python rules run inside the native rewrite and produce subgraphs that the engine splices in.
A backend therefore only ever sees plain ops — there is no "vectorized" or "autodiff" runtime support to implement anywhere.

## Graph in, graph out — or a callable of specs

Every transform accepts a traced `Graph` or a function/`Defn`.

```python
graph = evoxc.trace(fn, *specs)

batched = evoxc.vmap(graph, in_axes=(0, None))   # Graph → Graph
gw      = evoxc.grad(graph, argnums=(0,))        # Graph → Graph
```

A function cannot be transformed before its shapes are known, and `evoxc.transforms` may not import the pipeline, so a callable input returns a `TransformCallable`: call it with specs and it traces once and transforms.

```python
tf = evoxc.vmap(per_sample, in_axes=(None, 0))
graph = tf(w_spec, x_spec)          # a fresh Graph per call; tf.kind == "vmap"
```

Two rules follow from "transforms never execute":

- A `TransformCallable` rejects concrete `Tensor` arguments with `TraceError` ("never execute") — pass `TensorSpec`s.
- `evoxc.build` accepts a function or `Defn`, not a `Graph`; it raises `TypeError` telling you to use the explicit `lower`/`compile`/`load` pipeline. Stage a transformed graph the long way:

```python
exe = evoxc.load(evoxc.compile(evoxc.lower(graph)))
out = evoxc.run(exe, *args)
```

## `vectorize` — the batching primitive

```python
evoxc.vectorize(graph, axes) -> Graph
```

`axes` is an `int`, `None`, or a pytree of those over the input structure: `0` maps a tensor input's leading axis into a fresh batch dimension, and `None` leaves it unmapped (mandatory for a static input, since a static leaf has no axis).
Only leading axes are accepted in v1 — anything else is a `TransformError` naming the rule ("must be 0 (the leading axis) in v1").

`vectorize` is a graph→graph function and takes a traced `Graph` only; handing it a bare callable is a `TypeError` that points at `evoxc.vmap`.

## `vmap` — transparent sugar over `vectorize`

```python
evoxc.vmap(fn_or_graph, in_axes=0, out_axes=0) -> Graph | TransformCallable
```

`vmap` is `vectorize` plus output rearrangement, and the equivalence is tested, not asserted:

1. `vmap(graph, in_axes, out_axes=0)` produces the same IR as `vectorize(graph, in_axes)`.
2. `vmap(f)(*batched_specs)` produces the same IR as `vectorize(trace(f, *stripped_specs), in_axes)`, where `stripped_specs` drops the leading mapped dim of each mapped spec.
3. `out_axes` handling happens *after* the vectorize pass, as ordinary ops: a transpose for a mapped axis, a size-one axis insertion for an unmapped output. With `out_axes=0` on every mapped output, no extra op is emitted at all.
4. The wrapped function is traced exactly once per call.
5. Running the vectorized graph on a batch equals running the unvectorized graph per row and stacking.

`out_axes=None` requires the output to be unmapped; on a mapped output it raises `TransformError`, because a batch axis is never silently dropped.

```python
@evoxc.defn
def per_sample(w, x):
    """One sample in, one scalar out."""
    return evoxc.tanh(evoxc.dot(w, x))

B = evoxc.dim("B")
batched = evoxc.vmap(per_sample, in_axes=(None, 0))    # share w, map over samples
graph = batched(evoxc.TensorSpec((4,), evoxc.float32),
                evoxc.TensorSpec((B, 4), evoxc.float32))

exe = evoxc.load(evoxc.compile(evoxc.lower(graph)))
scores = evoxc.run(exe, W, X)          # X: (5, 4) → scores: (5,)
```

### Axis levels and the batch dimension

One batching pass creates **one** fresh batch `Dim` shared by all of its mapped inputs, named after the pass depth: `batch` at depth 0, `batch_1` at depth 1, and so on.
The name must be level-distinct because the NumPy interpreter binds symbolic dims by name: a mismatch then raises a clear `ShapeError` ("dimension 'batch' is already bound to 4, got 1") instead of silently broadcasting.

The depth counter follows `TransformCallable` composition, which is why `vmap(vmap(f))` and `vmap(grad(f))` nest cleanly.
`vectorize(vectorize(g))` on the Graph path runs both passes at depth 0 and yields same-named dims — a documented v1 fail-explicit: unequal extents raise `ShapeError`.

## `grad` — reverse mode

```python
evoxc.grad(fn_or_graph, argnums=None) -> Graph | TransformCallable
```

`grad` requires exactly one scalar tensor output (`ShapeError` otherwise) and returns one gradient per selected input, in selector order.
`argnums` indexes the **flattened tensor inputs**, not pytree positions, and `None` means all of them; a selected input that is not floating or complex raises `TransformError` ("cannot be differentiated").

```python
@evoxc.defn
def loss(params, x, y):
    pred = evoxc.dot(x, params["w"]) + params["b"]
    err = pred - y
    return evoxc.mean(err * err)

specs = ({"w": evoxc.TensorSpec((4,), evoxc.float32),
          "b": evoxc.TensorSpec((), evoxc.float32)},
         evoxc.TensorSpec((8, 4), evoxc.float32),
         evoxc.TensorSpec((8,), evoxc.float32))

graph = evoxc.trace(loss, *specs)
grads = evoxc.grad(graph, argnums=(0, 1))     # → Graph with TWO outputs
# flat tensor inputs are 0 = params["b"], 1 = params["w"], 2 = x, 3 = y
# (dict keys are sorted when flattened, so "b" precedes "w")

exe = evoxc.load(evoxc.compile(evoxc.lower(grads)))
d_b, d_w = evoxc.run(exe, params, X, Y)
```

Semantics worth knowing:

- Multiply-used values accumulate cotangents with `add`.
- `stop_gradient` yields a zero gradient in both directions.
- Ops that produce booleans or integers (`equal`, `less`, `argmax`, …) yield a **zero** tangent, documented, not an error.
- An op with no rule — `runtime_call`, a collective, an `external_call` with no rule and no portable decomposition — raises `TransformError` naming the op (and its rule key), never a silent fallback.

## `jvp` — forward mode

```python
evoxc.jvp(fn_or_graph, tangents) -> Graph | TransformCallable
```

`tangents` mirrors the **input** structure — same containers, with a `TensorSpec` at every position you want a tangent for and `None` where the tangent is zero. The result graph's inputs are the primal inputs followed by the tangent inputs, and its outputs are `(primal outputs, tangent outputs)`.

```python
tangents = ({"w": None, "b": None},                     # zero for both params
            evoxc.TensorSpec((8, 4), evoxc.float32),    # tangent for x
            None)                                       # zero for y
jac = evoxc.jvp(graph, tangents)
# inputs: params, x, y, dx      outputs: (loss, dloss)
```

When a VJP rule exists but no JVP rule does, the tangent is derived through the adjoint trick rather than raising — all-zero tangents short-circuit to zero without calling the rule.

## `vjp` — reverse mode with explicit cotangents

```python
evoxc.vjp(fn_or_graph, cotangents=None) -> Graph | TransformCallable
```

`cotangents` mirrors the **output** structure; the result graph's outputs are `(primal outputs, input cotangents)`.
The default `None` becomes an *explicit* scalar-one cotangent input, so `vjp(graph)` still requires a single scalar output — pass a `TensorSpec` per output when the function returns more than one value.

```python
back = evoxc.vjp(graph)                       # inputs: params, x, y, seed
# outputs: (loss, d(params["b"]), d(params["w"]), d(x), d(y))
# — one cotangent per flat tensor input, in that order
```

## `batch_functions` — one graph for a whole population

```python
evoxc.batch_functions(fns, axes=0, out_axes=0, *,
                      switch_ops=None, bands=None, alignment="variant")
```

`fns` is a non-empty sequence of same-signature programs — traced `Graph`s, or callables/`Defn`s (never mixed).
The result is **one** `Graph` whose leading axis is a static, length-N function axis: row `i` evaluates program `i`, bit for bit. A mapped input (`axes=0`) supplies its own row; an unmapped one (`axes=None`) is shared by every program.

Identical positions collapse into one batched op (the same per-op batching rules `vmap` uses), so identical programs emit zero `select`s; per-program constants stack into one `(N, …)` constant; every remaining divergence is `select`-muxed at its consumers and at the outputs, which is why *any* same-signature list merges correctly.

```python
@evoxc.defn
def prog_mul(x, c):
    return evoxc.tanh(evoxc.multiply(x, c))

@evoxc.defn
def prog_add(x, c):
    return evoxc.tanh(evoxc.add(x, c))

programs = [prog_mul, prog_add, prog_mul, prog_add]     # one program per row

specs = (evoxc.TensorSpec((4, 32), evoxc.float32),      # row i = program i's input
         evoxc.TensorSpec((1,), evoxc.float32))         # shared by every program

merged = evoxc.batch_functions(programs, axes=(0, None))(*specs)
report = merged.batch_report
print(report.n_functions, report.value_classes, report.emitted_ops)

exe = evoxc.load(evoxc.compile(evoxc.lower(merged)))
y   = evoxc.run(exe, X, c)          # y[i] is program i's own output
```

Two keyword-only knobs tune the merge, and neither can change a row's value:

- **`bands`** — `None` merges all N programs on one flat function axis; an `int K` merges K contiguous bands independently and concatenates their outputs; `"auto"` groups programs by structural fingerprint and lets a static cost model pick a partition. On divergent genetic-programming populations a NumPy evaluation with `bands="auto"` measured 2.6–10.7× faster than a flat merge, and it picks flat for identical programs. CPU guidance is `bands="auto"`; on an accelerator, dispatch is cheap, so `bands=16` (or `None`) is the data-supported choice.
- **`alignment`** — `"variant"` (default) sends a program's switched op into an existing class that already holds that variant; `"occurrence"` is the byte-stable legacy merge; `"auto"` is variant-first with an occurrence fallback.

`graph.batch_report` is documented transform metadata — value classes, shared and switched ops, output muxes, emitted ops, band sizes, cost estimates (12 keys, plus `as_dict()`); it is ignored by persistence and absent from a graph loaded from disk.
`switch_ops=True` opts into collapsing same-skeleton positions whose op differs; `switch_ops` should not be combined with banding.

## Splitting a program at its inputs

An outer loop — a genetic-programming population, an evaluation sweep, a fine-tuning harness — repeats one program many times, and most of its input is identical on every turn: a dataset, a trained parameter tree.
Only a small part changes per evaluation, such as one candidate.
Re-running the fixed half's subprogram and re-sending its data every turn is waste, because that half's contribution is the same program every time.

`split_by_inputs` turns that observation into an explicit structural boundary in the graph — one program for the fixed inputs, one for what varies — rather than a cache hidden behind a call.
That is design principle 3 in practice: caching and staging are operations you perform, never something the frontend does for you.

```python
evoxc.split_by_inputs(graph_or_fn, fixed=None, *, fixed_leaves=None)
# Graph → SplitPlan;  callable/Defn → SplitCallable
```

A callable or `Defn` input returns a `SplitCallable` for the same reason `vmap` does: the shapes must be known before the slice can be computed, and `evoxc.transforms` may not import the pipeline.
Call it with specs and it traces exactly once and returns a `SplitPlan`; concrete `Tensor` arguments raise `TraceError`, because a plan never executes anything.

This is the first structural — non-numeric — pass in `evoxc.transforms`: it only slices the graph data structure (no derivatives, no batching, no computation), so unlike `vectorize`, `vmap`, `grad`, `jvp`, `vjp` and the `batch_functions` merge it is a Python pass rather than part of the Rust engine, under the same import constraints: no backend awareness, no lowering.

### The two-graph contract

- `plan.prepare` maps the **fixed** inputs to a flat tuple of boundary tensors.
- `plan.apply` maps the **varying** inputs, plus that boundary tuple, to the source graph's output tree.

Both halves are ordinary `Graph`s of cloned ordinary ops, so every backend runs them with no split-specific support — a split graph is not a new kind of program.
The source graph is never mutated: its `digest()` is unchanged by a split, so you can keep using it directly alongside the plan.

One rule decides what crosses the boundary: a fixed-only value crosses only where a `return` operand *is* it or a mixed op consumes it.
A fixed-only value consumed only by fixed-only ops stays inside `prepare`, so the computed downstream value is what crosses, not its inputs; constants are re-cloned into `apply` instead of being shipped across the boundary.
`plan.boundary` lists the `BoundaryValue`s in `prepare`-output order, and `plan.boundary_specs` / `plan.boundary_bytes` describe their types and size.
A varying input the source never reads stays in `apply`'s signature for stability and is listed in `plan.unused_varying_leaves`.

The boundary is a **snapshot**, not a cache: neither graph carries state or invalidation logic, so when a fixed input changes you run `prepare` again — running `apply` on a stale boundary silently computes a stale answer.

`plan.verify()` checks the wiring law: that both halves are well formed and that the boundary tuple `apply` expects is exactly what `prepare` returns.
Alongside it, `plan.fixed_leaves` / `plan.varying_leaves` are flat **tensor-input** indices in ascending order, and `plan.summary()` is an 11-key dict (`fixed_leaves`, `varying_leaves`, `boundary_values`, `boundary_bytes`, `source_ops`, `prepare_ops`, `apply_ops`, `dropped_ops`, `unused_varying_leaves`, `prepare_digest`, `apply_digest`), with `as_dict()`, `text()`, `print()` and a one-line `__repr__` next to it.

### The mask, or the leaf index

There are two ways to name the fixed inputs, and they are mutually exclusive — passing both, or neither, is a `TypeError`.

- `fixed` is a pytree mask of bools and `None`s mirroring the graph's **input structure**: `True` keeps a tensor input in `prepare`, `False`/`None` moves it to `apply`. A bare bool broadcasts over every tensor leaf, and a non-`None` entry at a **static** leaf is a `TransformError`.
- `fixed_leaves` is a sequence of flat tensor-input indices, in `graph.tensor_specs` order.

The two axes are not the same axis: mask positions count static leaves too, while `fixed_leaves` counts tensor leaves only.
Both halves must be non-trivial — no fixed leaf, or every leaf fixed, is a `TransformError`.

### A worked example

```python
import evoxc

def fitness(dataset, params, candidate):
    return evoxc.sum(evoxc.tanh(evoxc.matmul(dataset * candidate, evoxc.tanh(params))))

graph = evoxc.trace(
    fitness,
    evoxc.TensorSpec((768, 32), evoxc.float32),   # dataset   (varies)
    evoxc.TensorSpec((32,), evoxc.float32),       # params    (FIXED)
    evoxc.TensorSpec((32,), evoxc.float32),       # candidate (varies)
)
plan = evoxc.split_by_inputs(graph, fixed=(False, True, False))
plan.verify()                                    # wiring law: check it once

def stage(half):                                 # evoxc.build refuses a Graph
    return evoxc.load(evoxc.compile(evoxc.lower(half, backend="numpy"), backend="numpy"),
                      backend="numpy")

prepare, apply = stage(plan.prepare), stage(plan.apply)
prepared = evoxc.run(prepare, params)                 # flat tuple of boundary tensors
score    = evoxc.run(apply, (dataset, candidate), prepared)
```

`prepare` holds 2 entry-block ops (`tanh`, `reshape`) and returns one boundary value of 128 B — `tanh(params)` reshaped to `(32, 1)` — while `apply` holds 5 (`multiply`, `dot`, `reshape`, `tanh`, `reduce_sum`).
So `plan.fixed_leaves == (1,)`, `plan.varying_leaves == (0, 2)`, `plan.boundary_bytes == 128`, and `repr(plan)` is `<SplitPlan fixed=1 varying=2 boundary=1 values / 128 B, prepare 2 ops, apply 5 ops>`.
The split result is numerically bit-identical to running the un-split graph on the NumPy backend.

The two runtime call shapes follow from `evoxc.run(exe, *args)` treating its **root** argument as the args tuple, and they are easy to get wrong:

- `prepare` takes exactly the fixed arguments as separate arguments — `evoxc.run(prepare, params)`, not `evoxc.run(prepare, (params,))`, which raises `TraceError`. A fixed dict input keeps its container (`evoxc.run(prepare, {"w": w, "b": b})`) and still returns a **flat** tuple of tensors.
- `apply` takes exactly two arguments: the varying input tree and the prepared tuple — `evoxc.run(apply, (dataset, candidate), prepared)`. Nesting them as one argument (`evoxc.run(apply, ((dataset, candidate), prepared))`) raises `TraceError`: "expected tuple of length 2, got tuple of length 1".

`evoxc.build` is not usable here for the same reason it is not usable on any transformed graph: it accepts a function or `Defn`, not a `Graph`, and raises `TypeError` pointing at the explicit pipeline.
Stage both halves with `lower`/`compile`/`load` once per shape set (see [Pipeline objects](/reference/pipeline-objects/)) and reuse the two executables across turns.

### `analyze_inputs` — choosing the boundary

```python
evoxc.analyze_inputs(graph) -> InputAnalysis
```

Which inputs are worth fixing is a structural question, and `analyze_inputs` answers it with the report the split itself would compute: it is derived from the same helpers the split uses, so the numbers cannot drift from what `split_by_inputs` actually does.
Per input it reports `index` (the flat tensor-input index — the axis `fixed_leaves` uses), `path` (the pytree path, such as `[0]` or `[0]['w']`), `spec`, `nbytes`, `direct_consumers`, `op_count` (the ops that transitively depend on it), `outputs` (the output indices it influences), and `boundary_bytes` / `boundary_count` — the cost of fixing *that input alone*.

```python
analysis = evoxc.analyze_inputs(graph)
analysis.print()                                 # or analysis.text()
info = analysis.inputs[1]                        # params: flat tensor input 1
info.op_count, info.outputs                      # dependent ops, influenced outputs
info.boundary_bytes, info.boundary_count         # the cost of fixing params alone
analysis.split(fixed_leaves=[1])                 # == split_by_inputs(graph, fixed_leaves=[1])
```

`.text()` prints a header line with the counts (tensor inputs, static values, entry-block ops, tensor outputs), a `splittable:` line, and one row per tensor input under the columns `idx`, `path`, `shape`, `dtype`, `bytes`, `consumers`, `ops`, `outputs`, `boundary(alone)`.
`InputAnalysis` also carries `source`, `inputs`, `op_count` (non-terminator entry-block ops), `output_count`, `splittable`, `blocked_reason` (the gate's own message when the graph cannot be split), `summary()` (five keys), `as_dict()` and `text()`.
`split(...)` is the sugar over `split_by_inputs` on the same graph and takes the identical `fixed` / `fixed_leaves` arguments.

### When to prefer it over `vmap` or `batch_functions`

| Transform | Axis it divides | What the work looks like |
|---|---|---|
| `split_by_inputs` | one program in **time** — fixed inputs vs per-call inputs | one call per turn at the same shapes; nothing is batched, and no op needs a batching rule |
| `vmap` / `vectorize` | one sample-level program across a leading **batch** axis | many rows in ONE call; every op in the body needs a batching rule |
| `batch_functions` | **different** same-signature programs | one graph with a static function axis — a merge, not a split |

The split replaces neither: it is the structural option when the axis of variation is *which inputs change between calls*, not *many samples at once*.

### v1 limits

| Situation | Error |
|---|---|
| Fixed or varying side reaches `cond` / `while_loop` / `scan` | `TransformError` naming the IR op — `op 'if' carries 2 nested region(s)` |
| An op whose effect is not `pure` or `read` — a `collective`, a `callback` or a `write` (collectives, `runtime_call`, `external_call`, `custom_call`, `inline_stablehlo`) | `TransformError` — "does not depend on the varying inputs" is not "safe to run once" |
| Both `fixed` and `fixed_leaves`, or neither | `TypeError` — exactly one argument form |
| No fixed leaf, or every leaf fixed | `TransformError` — each half must be non-trivial |
| A non-`None` mask entry at a static leaf | `TransformError` — a static leaf has no tensor to fix |
| A changed fixed input, expecting `apply` to notice | no error, and no protection: the boundary is a snapshot, so `prepare` must run again |

`block_call`, `rank` and `world_size` carry the `read` effect and are allowed; the refused effects are exactly the ones whose *running once* could differ from running per turn.
Region-bearing control flow is refused as a whole — a body that needs splitting has to be restructured before it enters the graph, as it does for the other transforms.
There is no per-turn state and no invalidation logic anywhere in the plan, and `apply`'s synthetic two-child signature `(varying inputs, prepared tuple)` is fixed.

## Composition

`vmap(vmap(f))` (nested batching) and `vmap(grad(f))` (per-sample gradients) compose, because a `TransformCallable` input is invoked at one deeper batch depth.
`vmap(vjp(f))` and `vmap(jvp(f))` are v1 deferrals: those callables produce extended input trees the outer axes normalization cannot address, so they raise `TransformError` instead of guessing.

## What refuses, and how

| Situation | Error |
|---|---|
| Vectorizing a graph containing `cond`/`while_loop`/`scan` | `TransformError` "cannot batch op 'if' … not vectorizable in v1" |
| An op with no batching rule (collectives, `random_*`, `sort`, `argsort`, `tile`, `flip`, `roll`, `diag`, `cumprod`, `nan_to_num`, the linalg factorizations…) | `TransformError` `no batching rule for op '<name>'` |
| An op with no VJP/JVP rule | `TransformError` `no VJP rule for op '<name>'` (extension keys add `(key 'external:<name>')` and a registration hint) |
| `conv` differentiated in reverse mode | `TransformError` — the IR has no transposed-convolution op (v1 deferral) |
| `mean`/`concatenate`/`pad` VJP over a symbolic dim | `TransformError`; static dims work |
| A non-leading `in_axes`/`out_axes` entry | `TransformError` "must be 0 (the leading axis) in v1" |
| `out_axes=None` on a mapped output | `TransformError` — a batch axis is never dropped |
| `grad` of a non-scalar output | `ShapeError` "requires a scalar output" |
| A `TransformCallable` given a concrete `Tensor` | `TraceError` — transforms never execute |
| Vectorizing a graph with no Python rule and no native rule | `TransformError` naming the op — no Python-loop fallback |

Region-bearing control flow is refused as a whole by the vectorizer and by the AD sweep: a `while` op is never walked, so a body that needs batching has to be restructured before it enters the graph.
For a custom op the fix is a rule, not a workaround: register a batching/derivative rule on the `block`, register an `external_call` rule or a portable decomposition, or register the rule directly in `evoxc.transforms`' public registries (`batching_rules`, `jvp_rules`, `vjp_rules`). See [Custom ops and kernels](/guides/custom-blocks/).

<Aside type="note" title="The result is an ordinary graph">
A transformed graph has no transform metadata in its ops — only `graph.batch_report` (in memory) records that a merge happened.
That is why a transformed graph can be saved, lowered to StableHLO, and compiled by IREE, XLA or TVM without any adapter support for `vmap` or autodiff; see [Backends and options](/guides/backends/) for the stage that consumes it.
</Aside>
