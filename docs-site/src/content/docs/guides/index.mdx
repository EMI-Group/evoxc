The guides are task-shaped: each page takes one job — trace a graph, differentiate it, put a loop inside it, move it to a device — and shows the exact calls that do it.
They spend most of their words on *why* the API is shaped the way it is, because every design decision here is load-bearing: the graph is the program, staging is explicit, and nothing happens behind your back.
The [reference](/reference/) pages carry the catalogue data instead: [pipeline objects](/reference/pipeline-objects/), the [op catalogue](/reference/ops/), the [option surface](/reference/options/) and the [v1 deferrals](/reference/deferrals/), with generated signatures indexed from [Python API at a glance](/reference/api-overview/).
When a guide and the reference appear to disagree, the reference and the generated API pages win — a guide never introduces a name the API does not have.

## The pipeline every guide returns to

Every page here is a variation on one loop: build a graph, transform it if you need to, hand it to a backend, run it.

```python
import evoxc

graph    = evoxc.trace(fn, *specs)   # Defn/function + TensorSpec tree → Graph
lowered  = evoxc.lower(graph)        # Graph → LoweredProgram
artifact = evoxc.compile(lowered)    # LoweredProgram → CompiledArtifact
exe      = evoxc.load(artifact)      # CompiledArtifact → Executable
out      = evoxc.run(exe, *args)     # Executable + tensors → Tensor tree
```

Each arrow is a public function with its own object type, and no stage silently performs the next one.
`evoxc.build` and `evoxc.evaluate` are documented shorthand for exactly those compositions, so you can switch between the explicit form and the shorthand without changing semantics.

## Your first five minutes

If evoxc is not installed yet, [Install](/getting-started/install/) covers PyPI, the source build and the extras. Then:

<Steps>

1. **Trace one graph.** Copy the snippet from [Quickstart](/getting-started/quickstart/) and print the module with `graph.print()`. You should see one `func @main` with one op per line and a `loc("…":line:col)` on the ops that were built from your source.

2. **Read the summary.** `graph.summary()` gives you the op count, the ops by category, and the tensor inputs and outputs as `{"path", "shape", "dtype"}` records — a compact description of the program you just wrote.

3. **Run it.** `evoxc.build(fn, *specs)` composes trace → lower → compile → load, and `evoxc.run(exe, *args)` executes. Both are shorthand for stages you can also call one at a time.

4. **Change one thing.** Add a `vmap`, a `grad`, or a `cond`, and trace again. Transforms return a `Graph`, so the rest of the pipeline is unchanged.

</Steps>

Nothing above caches, specializes or re-traces behind your back: two `evoxc.trace` calls are two graphs, even for the same function.

## The four value kinds, in one table

The guides assume this vocabulary throughout; [Core concepts](/getting-started/core-concepts/) is the long version.

| Kind | What it is | Has storage? | Where you meet it |
|---|---|---|---|
| Python/static value | `None`, bool, int, float, str, Enum, dtype, slice, `Dim`, `Device`, config objects | n/a | Evaluated at trace time, specializes the graph |
| `TensorSpec` | Describes a future runtime tensor | No | The arguments of `evoxc.trace` |
| `SymbolicTensor` | An SSA value inside a graph | No | `x` inside a `@evoxc.defn` body |
| `Tensor` | A materialized runtime tensor | Yes | `evoxc.constant`, `evoxc.run` outputs, creators |

The distinction that matters most: a static value is *Python*, so Python `if`/`for` over it runs once, at trace time, and bakes its outcome into the graph — while a `SymbolicTensor` is a *graph* value, so any decision on it must be `evoxc.cond`/`evoxc.while_loop`/`evoxc.scan`.

## Conventions in these pages

- **Backend.** Code examples run on the default NumPy interpreter unless the snippet names a backend. `backend="native"` selects the in-process Rust CPU engine; the compiler adapters need their own extra (see [Compiler adapters](/guides/compiler-adapters/)).
- **Specs.** `TensorSpec(shape, dtype)` describes a future runtime tensor and holds no data. `evoxc.dim("B")` is a named symbolic extent; a plain `int` is a static one.
- **Values.** Inside a traced function every graph value is a `SymbolicTensor`: it has a dtype and a shape, and no data. Concrete `Tensor`s only exist outside a trace.
- **Errors.** Every failure is a subclass of `evoxc.EVOXCError` — `TraceError`, `ShapeError`, `DTypeError`, `TransformError`, `BackendError`, `DeviceError`, `PersistenceError`, `VerificationError`, `BlockError`. Messages quote the source location of the op when a graph location exists.
- **Deferrals.** A feature that v1 refuses raises an explicit error naming the op or option. There is no silent fallback, so "it raised" is documentation too — see [Limitations and deferrals](/reference/deferrals/).

<Aside type="tip" title="Everything is inspectable">
No inspection call in evoxc traces, compiles, executes, transfers or mutates anything — `Graph.summary()`, `LoweredProgram.source_text()`, `Executable.summary()` and `Tensor.__repr__` are pure reads.
Reach for them first when a graph does not do what you expected; [Inspection and errors](/guides/inspection-and-errors/) walks through each stage.
</Aside>
