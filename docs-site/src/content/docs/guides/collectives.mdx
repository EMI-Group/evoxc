Communication in evoxc is a graph op, not a runtime service.
A collective appears in the program text exactly where you wrote it, with the group it operates over recorded as an attribute — so it is visible in `Graph.text()`, in the digest, and in the artifact.
A compiler may optimize a collective; it may never invent one, and no API inserts one for you.

```python
import evoxc

@evoxc.defn
def distributed_sum(x):
    grp = evoxc.dist.group("dp", (0, 1, 2, 3))
    return evoxc.dist.all_reduce(x, op="sum", group=grp)

evoxc.trace(distributed_sum, evoxc.TensorSpec((4, 8), evoxc.float32)).print()
#   %0 = evoxc.all_reduce(%arg0) attributes {group = "dp", group_size = 4, reduce_op = "sum"} : tensor<4x8xf32> loc("collectives.py":6:11)
```

The value model underneath is the same as everywhere else: a tensor is a **local** physical tensor, so a collective's result has your rank's local shape, and no global tensor type ever appears in the IR.

## Groups

A [`group`](/api/evoxc/dist/group/) is a static Python value — a named set of ranks that specializes the graph at trace time:

```python
dp = evoxc.dist.group("dp", (0, 1, 2, 3))
dp.name, dp.ranks, dp.size()        # "dp", (0, 1, 2, 3), 4
dp.is_world                         # False

everyone = evoxc.dist.WORLD_GROUP   # the default: group=None on every collective
```

- `ranks` must be non-empty, unique and non-negative integers (bools are rejected) — otherwise `ValueError`.
- `WORLD_GROUP` (name `"world"`) means *all ranks of the runtime execution context*: its membership is known only at run time, so its shapes stay runtime-dynamic where a shape depends on the group size.
- Groups are immutable and hashable, compared over `(name, ranks, backend)`.
- Collectives record the group **by name and size** (`group`, `group_size`; `None` for the world group), so artifacts stay self-describing with no Python objects inside.

## The six collectives

Every collective takes one `SymbolicTensor` and returns one `SymbolicTensor`; calling one with a concrete `Tensor`, or outside a trace, raises `TraceError` — there is no eager collective mode.

| Collective | Signature | Local effect |
|---|---|---|
| [`all_reduce`](/api/evoxc/dist/all-reduce/) | `all_reduce(x, op="sum", group=None)` | same shape; elementwise reduction across ranks |
| [`all_gather`](/api/evoxc/dist/all-gather/) | `all_gather(x, axis=0, group=None)` | `out[axis] = in[axis] × group_size` |
| [`reduce_scatter`](/api/evoxc/dist/reduce-scatter/) | `reduce_scatter(x, op="sum", axis=0, group=None)` | `out[axis] = in[axis] ÷ group_size` |
| [`all_to_all`](/api/evoxc/dist/all-to-all/) | `all_to_all(x, split_axis, concat_axis, group=None)` | split dim ÷ g, concat dim × g |
| [`broadcast`](/api/evoxc/dist/broadcast/) | `broadcast(x, src_rank=0, group=None)` | same shape; `src_rank`'s copy on every rank |
| [`collective_permute`](/api/evoxc/dist/collective-permute/) | `collective_permute(x, source_target_pairs, group=None)` | same shape; routed by the pair list |

`op` is one of `"sum"`, `"max"`, `"min"`, `"prod"`; anything else is a `ValueError`.
Axes normalize Python-style (negative wraps), and an out-of-range axis is a `ShapeError`.
For an explicit group, `reduce_scatter` and `all_to_all` check divisibility at trace time and raise `ShapeError` when the axis extent does not divide evenly — the world group cannot check that statically, so its axis dims stay `None` and the executor validates at run time.

Worked local shapes for `g = evoxc.dist.group("data", (0, 1, 2, 3))`:

| Call | Local input | Local output |
|---|---|---|
| `all_reduce(x, "sum", g)` | `(4, 8)` | `(4, 8)` |
| `all_gather(x, axis=0, group=g)` | `(256, 1024)` | `(1024, 1024)` |
| `all_gather(x, axis=1, group=g)` | `(256, 1024)` | `(256, 4096)` |
| `reduce_scatter(x, "sum", axis=0, group=g)` | `(1024, 1024)` | `(256, 1024)` |
| `all_to_all(x, 0, 1, g)` | `(512, 64)` | `(128, 256)` |
| `broadcast(x, src_rank=0, group=g)` | `(256, 1024)` | `(256, 1024)` |
| `collective_permute(x, ((0, 1), (1, 2), (2, 3), (3, 0)), g)` | `(256, 1024)` | `(256, 1024)` |

## `rank()` and `world_size()`

These are **graph scalars**, not Python ints: [`evoxc.dist.rank()`](/api/evoxc/dist/rank/) and [`evoxc.dist.world_size()`](/api/evoxc/dist/world-size/) each build a scalar `int64` op of shape `()` whose value comes from the execution context at run time.

```python
@evoxc.defn
def who_am_i(x):
    return x, evoxc.dist.rank(), evoxc.dist.world_size()
```

They carry a `read` effect rather than `pure`, so a backend must resolve them per execution and must not constant-fold them at lower or compile time.
Trying to use one as a Python control-flow value is not special-cased: it is a `SymbolicTensor`, so it fails the same way any symbolic value does in `if` — see [in-graph control flow](/guides/control-flow/).

## What the NumPy interpreter does

The NumPy interpreter installs a **single-process identity executor** at import: with one rank and a world size of one, every collective returns its input (a copy).
That is emulation, not parallelism — it keeps a distributed graph runnable and inspectable on one machine, and it is the one documented place where the backend layer reaches into `evoxc.dist` (to install the executor and to read the rank context).

The hook itself is public and process-global:

```python
evoxc.dist.set_collective_executor(my_executor)   # must satisfy the executor protocol
evoxc.dist.get_collective_executor()              # BackendError when nothing is installed
```

An executor implements one method per collective — `all_reduce`, `all_gather`, `reduce_scatter`, `all_to_all`, `broadcast`, `collective_permute` — each receiving the local concrete tensor, the graph-constant descriptors and returning the local result.
Executors may coordinate across ranks in-process (the multi-rank tests do) or delegate to a real transport.
`set_collective_executor(None)` resets the slot; a non-executor raises `TypeError`.

For multi-rank simulation on the NumPy interpreter, run the same executable once per simulated rank with a per-run rank context:

```python
ctx = evoxc.dist.RankContext(rank=1, world_size=4)     # frozen, validated
out = evoxc.run(exe, shard, rank_context=ctx)          # numpy interpreter only
```

The context is thread-local for the duration of that run, so `rank()`/`world_size()` resolve to the simulated values.

## Compiler adapters do not compile collectives in v1

`collectives` is `False` in every compiler adapter's `Capabilities`, and the capability pre-check rejects the op at `lower()` with a `BackendError` naming it — multi-rank runtime channels are simply not wired yet.
There is no fallback and no silent single-rank rewriting.
Practical consequence: a distributed graph runs on the NumPy interpreter (or the `native` engine, whose collectives are single-rank identity semantics), and only the per-rank compute graph goes to a compiler.

## A data-parallel step, end to end

The honest shape of multi-device work in v1: prepare each rank's local data explicitly, build one graph, and run it per device.

```python
import numpy as np
import evoxc

@evoxc.defn
def averaged_step(grad, weight):
    grp = evoxc.dist.group("dp", (0, 1, 2, 3))
    total = evoxc.dist.all_reduce(grad, op="sum", group=grp)
    return weight - 0.1 * (total / 4.0)

grad_spec = evoxc.TensorSpec((2, 4), evoxc.float32)
weight_spec = evoxc.TensorSpec((2, 4), evoxc.float32)
exe = evoxc.build(averaged_step, grad_spec, weight_spec)      # numpy interpreter

# Explicit data preparation: one local gradient per rank.
host_grads = evoxc.from_numpy(np.arange(32, dtype=np.float32).reshape(8, 4))
shards = evoxc.split_tensor(host_grads, 0, [evoxc.Device("cpu", 0)] * 4)
weights = evoxc.replicate_tensor(evoxc.zeros((2, 4), evoxc.float32),
                                 [evoxc.Device("cpu", 0)] * 4)

for rank, (grad, weight) in enumerate(zip(shards, weights)):
    ctx = evoxc.dist.RankContext(rank=rank, world_size=4)
    updated = evoxc.run(exe, grad, weight, rank_context=ctx)
```

Three things to notice:

- `split_tensor`/`replicate_tensor` only *prepare* data; they never move it. On a GPU you would follow them with an explicit `t.to(evoxc.Device("cuda", 0))` per rank.
- The graph contains one explicit `all_reduce` and nothing else — no implicit gradient synchronization, no sharding pass, no collective inserted by a builder.
- On the built-in single-process executor each rank gets its own local result back; the *same* graph, driven by a real multi-rank executor, computes the cross-rank average.

<Aside type="caution" title="Placement is physical">
A group names ranks; it does not place tensors.
Multi-device work therefore means **one executable per device**, data moved with `Tensor.to(device)`, and communication declared in the graph with `evoxc.dist.*`.
The run boundary rejects any input whose `device` differs from the executable's device with a `DeviceError`; placement rules live in [tensors and devices](/guides/tensors-and-devices/), and the compiler adapters own how a kind maps onto hardware — see [compiler adapters](/guides/compiler-adapters/).
</Aside>

For the surrounding machinery, see [tensors and devices](/guides/tensors-and-devices/) for placement and [backends and options](/guides/backends/) for choosing where each per-rank graph runs.
