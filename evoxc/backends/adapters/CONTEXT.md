# evoxc/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends for evoxc.
Each adapter consumes the SHARED StableHLO lowering produced by `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half: the optional dependency probe (`check_available` override — the shared base is a concrete no-op), `compile` (invoke the external compiler on the MLIR text), and `load` (rebuild the executable from the artifact — never recompiling).
Activation is register-on-first-use: `evoxc.backends.registry.get(name)` imports the adapter module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`; `import evoxc` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** evoxc depends directly on the ML compilers. The `jax` frontend package appears NOWHERE in `evoxc/`, and the xla adapter uses no jaxlib either.
- **xla** = the PJRT C API driven through pure-stdlib ctypes against a USER-PROVIDED plugin binary (a `.so` exporting `GetPjRtApi`). Plugin distribution is explicitly OUT of scope; no pip package provides one.
- **tvm** = `apache-tvm` + `jaxlib`, where jaxlib is used ONLY for its bundled LLVM MLIR python bindings (not the jax API), behind the `_mlir_bindings` seam. The vendored translator's `jax._src.interpreters.mlir` import is satisfied by an injected `sys.modules` shim.

Status: all three adapters are implemented and validated — iree end-to-end on llvm-cpu, CUDA, ROCm/HIP and Vulkan/SPIR-V (the Vulkan path validated on Mesa lavapipe, a SOFTWARE device — no GPU-Vulkan driver serves this host's GPU); xla against the test fake plugin AND the real `jax_cuda12_pjrt` (CUDA) and `jax-rocm7-pjrt` (ROCm) plugins; tvm on `apache-tvm` 0.26 + jaxlib (CPU, and ROCm compile-only).
**iree 3.13.0 re-validation (this host, MI300X VF / ROCm 7.1):** the extras now pin `>=3.13.0,<3.14` (Known Issue 5) and the llvm-cpu + ROCm/HIP legs were re-run on it — every flag the adapter emits still exists and none is deprecated, no runtime API the adapter uses drifted, and the default paths are warning-free (audit detail in Known Issues 2, 10, 13, 16 and 21).
The CUDA leg could not be re-exercised on this box (no NVIDIA GPU).
The Vulkan leg DOES run here: no GPU-Vulkan driver serves this host's GPU, but iree-base-runtime 3.13.0 enumerates the Mesa lavapipe (software Vulkan) device UNCONDITIONALLY — `iree.runtime.get_driver("vulkan").query_available_devices()` returns it with `VK_ICD_FILENAMES` UNSET (the 3.11 `llvmpipe` device-name denylist is gone), and all 6 device-guarded tests in `tests/backends/test_iree_vulkan_device_resident.py` pass with the variable unset.
The renamed-ICD `VK_ICD_FILENAMES` recipe is a 3.11-era fallback and a loader-pinning convenience (it keeps this host's loader away from its wedged radeon ICD), NOT a precondition for the suite seeing a device (Known Issue 16, "Device visibility").
Its 3.13 device→host readback is adapter-owned (Known Issue 21).
Measurements, probe narratives and the long procedural recipes live in `./PER-ADAPTER-NOTES.md` (the companion to this file) and the skill `evoxc-compiler-adapter-recipes`.

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes the same shape:
- `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`, `"xla"`, `"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), singleton `<name>_backend`, and a module-level `register()` (probes the dependency — `core.BackendError` with an actionable message when missing — then registers idempotently).
  Every compiler executable exposes `synchronize() -> None`: `IreeExecutable.synchronize` is a documented no-op because `run` already blocks on the device queue (the numpy executable has no such method — `pipeline.Executable.synchronize` is the no-op there), while `XlaExecutable.synchronize` awaits + destroys the `PJRT_Event*` device-complete handles of every earlier DEVICE-RESIDENT `run` (that `run` returns after ENQUEUE — Known Issue 17); `XlaExecutable.close` destroys any still-pending handles without awaiting.
  `register()` also installs the module-level `upload_tensor` into the PER-BACKEND device-transfer slots (`core.register_backend_device_transfer_provider`) — iree for kinds `"cuda"`/`"rocm"`/`"hip"`/`"vulkan"`, xla for every `_NON_CPU_KINDS` entry — so `Tensor.to(Device(kind, N))` resolves to the activated adapter. Per-backend slots mean activation order can never clobber another backend's provider or the flat DEFAULT slot. `"vulkan"` is the ONE exception to the per-backend-only rule: `register()` ALSO fills the FLAT DEFAULT slot for it, because `evoxc.backends` registers no vulkan thunk at import and no other backend serves a vulkan device — so `register()` is the only thing that serves `Tensor.to(Device("vulkan", N))`.
- `<name>_util.py` helpers: `xla_util.py` (PJRT C API driver: plugin discovery/loading, version gate, client/compile/execute/buffer/serialize plumbing), `tvm_util.py` (vendored-translator compat shim + jax `sys.modules` shim injection, op whitelist gate, translate/build/run/persist helpers).
- `_pjrt_c_api.py`: vendored ctypes translation of the Apache-2.0 PJRT C API header (header URL + commit recorded; offsets verified against a plugin compiled from the real header).
- `_mlir_bindings.py`: the MLIR binding-provider seam (jaxlib today; a standalone `mlir` package is a one-module swap).
- `__init__.py`: documentation only, imports nothing heavy.

The shared mechanism — per-stage `KNOWN_OPTIONS`, union-of-stages key validation, `validate_options`, `normalize_opt_level`/`normalize_bool_option`, the env table, and explicit > env > default precedence — is specified in `../CONTEXT.md` ("Backend options override") and implemented in `../options.py` + `evoxc/pipeline_options.py`; this file records only the per-adapter keys, defaults and conflict rules.

| all (iree/xla/tvm) | lower | `eigh_algorithm` (str) | `EVOXC_EIGH_ALGORITHM` | `"jacobi"`\|`"jacobi_batched"` (case-insensitive, whitespace-stripped), default = `CompilerBackend.default_eigh_algorithm` = `"jacobi_batched"` (all mutually disjoint rotations of one odd-even round-robin round per `stablehlo.while` iteration); `"jacobi"` is one (p,q) rotation per iteration. | iree/xla/tvm | run | — (none in v1) | — | non-empty run options → loud `BackendError` (by design) |

**Exporter-option plumbing (for adding new options):** no adapter overrides `lower()` — the shared `CompilerBackend.lower` validates keys and builds the export dict in `_exporter_options`, which forwards exactly `rng_bit_generator`, `sort_emission`, `while_init_rewrite`, `dot_precision`, `eigh_algorithm`, `split_reduction`.
`eigh_early_exit`, `split_reduction_threshold` and `split_reduction_non_exact` are writer-only options NOT plumbed through the adapter path — passing them to `evoxc.lower(..., backend="iree")` raises the unknown-key `BackendError`.
Env spellings exist only for the backend-agnostic reserved lower options `eigh_algorithm` (`EVOXC_EIGH_ALGORITHM`) and `split_reduction` (`EVOXC_SPLIT_REDUCTION`), registered for all three adapters at the lower stage.
A NEW exporter option requires three touches: add it to `_exporter_options`, declare it in each adapter's `KNOWN_OPTIONS["lower"]` (all three declare `rng_bit_generator`/`dot_precision`/`eigh_algorithm`/`split_reduction`; iree additionally `sort_emission`/`while_init_rewrite`), and consume it in the stablehlo Writer (sibling node).

## Adapter designs

### IREE (`iree.py`) — llvm-cpu, CUDA, ROCm/HIP and Vulkan/SPIR-V

- **compile:** `iree.compiler.compile_str(mlir_text, target_backends=..., input_type="stablehlo", extra_args=resolved_args)` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"`, keeping `mlir_text` + `entry_functions` + `target_backends`). Compiler diagnostics are re-raised as `core.BackendError` carrying them (never silent).
- **Compile flags are user-overridable** — the fixed defaults are minimal and documented: `_IREE_DEFAULT_COMPILE_ARGS = ("--iree-input-demote-f64-to-f32=false",)` (always — IREE otherwise demotes f64 to f32 silently, which evoxc's error strategy forbids), `_IREE_DEFAULT_LLVMCPU_ARGS = ("--iree-llvmcpu-target-cpu=generic", "--iree-llvmcpu-link-embedded=false")` (llvm-cpu only — the embedded `-nostdlib -static` link cannot resolve the libm symbols `log`/`cos`/`floor` that f64 math ops lower to), and the rocm-only `_IREE_DEFAULT_ROCM_ARGS_NAME = "--iree-rocm-target"` (see the ROCm section). The only other derived flags are the `opt_level`, `vulkan_target` and `dispatch_formation` translations (see the options table) — evoxc emits NO matmul/tiling/bufferization/codegen-quality flag and NO `--iree-opt-level` unless `opt_level` is set, so ROCm GEMV/matmul quality is entirely iree-compile's (measured O1 vs O3 on ROCm: 0.66–1.47×, i.e. opt level is never the cause of a large cross-backend gap — `../../../bench_logs/hf_bench_results.md` §5e). A same-NAME user flag drops the default; only the DENY list is rejected.
- **load/run — CPU** (device `None` or `Device("cpu", *)`) via `iree.runtime.get_driver("local-task")` + `driver.create_default_device()` + `load_vm_flatbuffer(flat, driver="local-task")`. Do NOT reintroduce `rt.system_setup(config=...)` — it intermittently fails with `TypeError: 'module' object is not callable` (submodule shadowing).
- **load/run — CUDA/ROCm** via `rt.get_driver("cuda"|"hip")` + **`driver.create_device(device_id=index + 1)`** — iree GPU device ids are **1-BASED** (device_id 0 raises `ValueError`, wrapped into `core.BackendError`) — plus `rt.Config(device=...)` → `rt.VmModule.copy_buffer(config.vm_instance, vmfb)` → `rt.load_vm_module(vm_module, config)`. `load_vm_flatbuffer`'s driver-name form always creates the DEFAULT device and cannot select an index. The CUDA HAL driver is compiled INTO the runtime wheel (no extra pip dependency). Vulkan takes the same `rt.Config(device=...)` module-load path but a DIFFERENT device-acquisition convention — see the Vulkan section.
- **Artifact↔device validation:** the payload's `target_backends` must include the target matching the device kind (`cuda` artifact ↔ cuda device, `rocm` ↔ rocm/hip, `vulkan-spirv` ↔ vulkan, `llvm-cpu` ↔ cpu) — ONE table, `_EXPECTED_TARGET_BY_KIND` via `_expected_target_for_kind`, shared by `IreeBackend.load` and `_load_segments` so the two gates cannot drift; absent `target_backends` means `["llvm-cpu"]`; a mismatch raises `core.BackendError` naming both.
- **Inputs (explicit placement — no implicit host↔device transfers):** an input already on the executable's device — an `IreeDevicePayload`-backed `core.Tensor` with matching kind+index, or a raw iree `DeviceArray` — passes through to the invoke with ZERO host round-trips. Every other input is rejected; plain cuda/rocm/vulkan runs NEVER stage host inputs. The pipeline run boundary raises its own `core.DeviceError` ("no implicit device", `t.to(`) first, and a GPU executable additionally enforces a defensive `core.DeviceError` for direct `exe.run([...])` calls. The single exception is an llvm-cpu executable, which accepts host ndarray-backed inputs via `rt.asdevicearray` (host→host ABI representation — the only plain-run host-input path).
- **Outputs (device-resident, all targets):** outputs are `core.Tensor`s wrapping the iree `DeviceArray`s in the PUBLIC `IreeDevicePayload`; `.device` is the run device. Host materialization is lazy and explicit: a cpu-kind output's `.numpy()` materializes a host copy on demand through the ADAPTER's own readback (`_readback_device_array` — a zero-copy mapping for mappable local-task buffers, an explicit staging `queue_copy` on device memory; Known Issue 21); a NON-cpu output's `.numpy()` raises `core.DeviceError` — read it back with `t.to(core.Device("cpu", 0)).numpy()`, or interop zero-copy with `torch.from_dlpack(t)` (the payload exports its HAL buffer as a DLPack capsule — no host round-trip; cpu-kind payloads keep the `.numpy()` path). The hot run path performs no host round-trip either way, and `core.Tensor` wrappers never alias or pin the HAL buffers.
- **Per-call run path — cached PLANS of static metadata, never values.** `IreeExecutable` derives ONE cached input plan from its signature (`_input_plan`: per-leaf `(dtype, shape, needs_dim_walk)`, where `needs_dim_walk` is True iff a declared dim is non-`int` — symbolic `Dim`/`DimExpr` or `None`) and ONE flat tuple of expected output dtypes (`_output_dtypes`); `run` compares the ACTUAL argument metadata against those plans on every call, so there is no skip-validation path and no cached tensor value.
  `run` performs ONE fused pass per input leaf — `isinstance(tensor, core.Tensor)` first, then dtype (`data.dtype` against the planned dtype, with a single `core.dtype(...)` normalization when the two are not already equal so a non-normalizable dtype still raises `core.DTypeError`), then shape (one tuple compare on the static steady-state path, else `_validate_input_shape`'s per-dim walk), then the HAL buffer build — filling a pre-sized `buffers = [None] * n_inputs` list by index instead of a second `_build_buffers` walk.
  The fused buffer branch order is `_build_buffers`'s: same-device payload / raw `DeviceArray` pass-through (ZERO `asdevicearray`/`numpy()` calls), `core.DeviceError` for a non-pass-through input on a cuda/rocm/vulkan executable (byte-identical text), `rt.asdevicearray(runtime_device, tensor.numpy())` for an llvm-cpu host input.
  `_build_buffers` therefore serves `_IreeSegmentExecutable` (and the external-call/segment path) only; the two forms are 1:1 in branch order, pass-through rule and errors, so a change to one must be mirrored in the other.
  Outputs are wrapped and dtype-checked in ONE pass over a pre-sized list (count check first, then `IreeDevicePayload` + `core.Tensor` + the planned-dtype compare, with `tensor.dtype` used only inside the byte-identical error text); the non-signature path wraps without validation.
  Work on a same-device input is METADATA-ONLY and independent of the input's BYTES — no copy, no re-layout, no contiguity/row-major fix and no host import exists anywhere in `run`, so a multi-GB packed weight tensor costs the same per call as a 1-element tensor (per-call cost tracks leaf COUNT, never leaf size); error wording and exception types are unchanged from the two-walk form (every message rebuilt on the failure path from the same `spec.dtype` / `tensor.dtype` / `tensor.shape` expressions).
- **Payload metadata comes from the HAL buffer view.** `IreeDevicePayload.__init__` caches `_shape`/`_dtype` ONCE (a `DeviceArray` is shape/dtype-immutable for its lifetime), resolving them from `array._buffer_view` — `tuple(view.shape)` (0.07 us) and `view.element_type` (0.04 us) through the module-level `_HAL_ELEMENT_DTYPES` memo filled by `_hal_element_dtype` (lazy `HalElementType.map_to_dtype`) — rather than the public `array.shape`/`array.dtype` accessors (~0.35 us + ~0.4 us: numpy `__array_function__` dispatch plus a nanobind dtype hop; that pair was the largest component of output wrapping).
  `array._override_dtype` is honored FIRST (it wins in `DeviceArray.dtype` too, and bool/relaxed-dtype results depend on it), and a runtime without the private buffer-view protocol falls back to `tuple(array.shape)`/`array.dtype` and caches whatever it got — the public payload protocol (`.shape` tuple of ints, `.dtype` numpy dtype, `.device_array`, `.device`, `to_host()`, `__array__`) and the constructor signature are unchanged, and the payload still retains nothing beyond the `DeviceArray` handle.
  `_runtime_modules()` memoizes the lazy `numpy` / `iree.runtime` imports for the run path (the heavy-import rule keeps them out of module top level; the memo avoids a per-call `sys.modules` lookup).
- **Explicit synchronization — `synchronize()` is a documented no-op:** `IreeExecutable.run` hands its inputs to the invoke and returns the invoke's output buffers, i.e. it already blocks on the device queue, so nothing is outstanding when it returns. The method exists only so every compiler executable exposes the same call shape (`exe.synchronize()`) and callers never need to know which backend they hold — it adds no per-call sync, flag or FFI call, and `run` is untouched by it. The xla adapter's device-resident `run` IS asynchronous (Known Issue 17).
- **External kernels (`external_call`):** graphs containing `external_call` are SPLIT at `lower()` by the shared `CompilerBackend` (`../compiler.py::_lower_external_segments` + `../external_split.py`) into ordered SEGMENT programs (plain graphs, each compiled to its own vmfb — payload `stablehlo-segments`, artifact `iree-vmfb-segments`, per-segment `target_backends`/`iree_compile_args`) plus a JSON-safe kernel-call PLAN persisted in the artifact. `IreeExternalExecutable` runs segments strictly in plan order and dispatches each boundary through `evoxc.external.get_external_kernel_entry(name, "iree")` (unknown name at run → `BackendError` naming the kernel; outputs validated count/dtype/shape).
  - **host mode** (default): operands staged to host numpy arrays, the kernel runs on host, results staged back as the next segment's inputs; the once-per-executable staging `UserWarning` fires only when a boundary actually stages.
  - **device-resident mode** (`device_resident=True`, explicit per-backend slot only): the kernel receives the boundary's device tensors DIRECTLY (never host-staged) and may return device tensors / duck payloads / raw `DeviceArray`s / DLPack-capable objects (a `torch.Tensor`) / numpy arrays / tuple-list mixes; results are validated METADATA-ONLY, and the next segment consumes device results through the same-device pass-through with ZERO host round-trips (numpy results stage back and mark the boundary staged). Kernel authors may isinstance-check `evoxc.backends.adapters.iree.IreeDevicePayload` (`.device_array`, `.shape`, `.dtype`, `.to_host()`, `.device`, and the DLPack export `__dlpack__`/`__dlpack_device__` reached through the wrapping `core.Tensor`) and run further vmfb modules on the SAME HAL device. **Zero-copy DLPack round trip:** `torch.from_dlpack(operand_tensor)` imports the operand's HAL buffer (the capsule is created by `HalDevice.create_dlpack_capsule` on the payload's own HAL device; device id = the 0-based `core.Device.index`, kind→code cuda 2 / rocm·hip 10 / vulkan 7), and a returned `torch.Tensor` is imported by `_wrap_device_result` via `HalDevice.from_dlpack_capsule` into an `IreeDevicePayload` on the run's device — its `__dlpack_device__` MUST equal the executable's device (else explicit `BackendError`), the imported buffer keeps the producer's memory alive, and the adapter adds NO fence (iree's HAL uses its own stream, so a kernel returning work still pending on torch's stream must synchronize it; the export direction is safe because `run` blocks). `copy=True` / a different `dl_device` / a dtype the HAL cannot express natively refuse the export with an explicit `core.DeviceError`.
  Carried plain values that are not kernel operands stay device-resident across segments. Lower-time restrictions (explicit `BackendError`, MODE-AWARE): no calls inside cond/while/scan bodies, ≥1 tensor operand, single-function graphs, and — HOST-mode boundaries only — STATIC integer result dims. DEVICE-RESIDENT boundaries allow symbolic/runtime-dynamic result dims (e.g. vmap/vectorize batch `Dim`s on a batched-variant kernel — the vmapped kernel receives the FULL batched stack, invoked once per run), validated metadata-only at run time with the ACTUAL shapes. Kernels are assumed PURE; segments run sequentially and preserve `callback` effect order.
- **Explicit placement — `Tensor.to(Device(kind, N))` → `upload_tensor`:** `core.Tensor.to` dispatches through the device-transfer provider registry. `evoxc.backends` pre-registers a LAZY `"cuda"` thunk in the flat DEFAULT slot at import (delegating to this module's `upload_tensor` by attribute lookup, so placement works before the adapter activates), and `register()` installs the DIRECT function under the per-backend slots plus — the ONE flat-slot exception — `"vulkan"` (nothing else serves a vulkan device). `upload_tensor` contract (v1): the source must be a HOST ndarray-backed `Device("cpu", 0)` tensor — anything else raises `core.DeviceError` suggesting the two-hop `t.to(cpu).to(target)`; it acquires the HAL device exactly like `load` (honoring `EVOXC_IREE_RUNTIME_ARGS`), performs a ONE-SHOT host→device copy, and returns a fresh `core.Tensor(IreeDevicePayload(da, device))` on the target device. Failures surface as `core.DeviceError`/`core.BackendError`, never a raw iree exception. A placed tensor lives on a fresh HAL device instance but is accepted by a separately loaded executable on the same physical device (iree allows same-device buffers across instances), so kind+index equality is the sufficient check.
- **Host→device staging machinery (`_staged_input`) — TWO TIERS, cuda/rocm ONLY — serves ONLY host-mode external-kernel boundaries and the placement provider (`upload_tensor`); plain GPU runs never stage.** Split at `_PINNED_DIRECT_MAX_BYTES = 4 * 1024`: **≤ 4 KB** writes a persistent mapped `DEVICE_LOCAL | HOST_VISIBLE` buffer with one `np.copyto` (no copy, no semaphore, no wait); **> 4 KB** copies per call (`queue_copy`) from a persistent `HOST_LOCAL | DEVICE_VISIBLE` source into a persistent `DEVICE_LOCAL` staging buffer.
  The tier is selected by an EXPLICIT normalized-kind dispatch (`device_kind`, a REQUIRED keyword-only argument on `_build_buffers` and always passed explicitly to `_staged_input` — no "defaults to cuda" fallthrough): **cuda** takes the pinned/DMA tiers above, **rocm** the host-local-source + `queue_copy` path (`_rocm_staged_input`), and **vulkan** returns `None` before any buffer work, so its uploads and segment boundaries use the plain `rt.asdevicearray` copy (the tiers' correctness rests on a CUDA-driver ordering guarantee that is unverified on the vulkan HAL driver).
  Buffers are cached per `(input index, shape, dtype)` (bounded `_STAGED_INPUT_CACHE_MAX = 64`, cleared on overflow — no per-call device alloc) while `upload_tensor` uses a fresh one-shot dict; inputs > 16 MB (`_STAGED_INPUT_MAX_BYTES`), unmappable dtypes, non-GPU paths and cache overflow fall back to `rt.asdevicearray`.
  **The tier-2 semaphore wait is LOAD-BEARING — do not remove it:** the cuda HAL does not reliably stream-order `queue_copy` ahead of invoke dispatches, so each call waits on a FRESH semaphore (reusing one ABORTS), query-first so an already-complete copy skips the fence wait.
  Byte-level buffer flags, the 4 KB-cutoff reasoning and the cuda `_pool_anchor`: `./PER-ADAPTER-NOTES.md`.
- **Iterative stateful workloads (DE/PSO-style steps) — the recommended pattern:** keep state ON the device; build once, then loop `evoxc.run(exe, key_dev, state_dev)` feeding each step's device-resident outputs back as the next inputs, with the seed placed once via `seed.to(Device(kind, N))`. Every later call costs zero `asdevicearray` calls and zero host round-trips. Anti-patterns: feeding fresh host state per step (rejected at the run boundary with `core.DeviceError`) and `.numpy()`-reading the whole state per step (a non-cpu output needs an explicit `.to(cpu)`).

### ROCm / HIP (`rocm`) — AMD GPU, device-resident

Same adapter and the same device-resident machinery as cuda — a third compile target and a third HAL driver.
- **Compile:** `target_backends=["rocm"]`. IREE has no ROCm target auto-detection, so the adapter injects a detected `--iree-rocm-target=<arch>` default (`_detect_rocm_target` reads `amdgpu-arch` then `rocm_agent_enumerator` under `$ROCM_PATH`/`$ROCM_HOME`//opt/rocm; a user flag of the same name wins; an undetectable arch with no user flag → actionable `BackendError` naming `iree_compile_args=['--iree-rocm-target=gfxNNN']`). `--iree-hal-target-device=rocm` is NOT needed. `Artifact.target == "rocm"`; a target/device mismatch is an explicit `BackendError`.
- **Device paths:** `rt.get_driver("hip")` + `create_device(device_id=index + 1)` (1-based, like cuda). `Device("rocm", N)` (canonical) and the alias `Device("hip", N)` both resolve (`_normalize_device_kind` folds `hip`→`rocm` for the driver call only; the `core.Device` label is never rewritten). Device-resident semantics are the cuda ones.
- **Placement/staging — THREAD-LOCAL caches (REQUIRED, not an optimisation):** rocm placement reuses ONE thread-local HAL device per `(index, runtime args)` (`_acquire_cached_rocm_device`, stored through the shared `_cached_hal_device` helper — the same thread-local cache the vulkan path uses) and a thread-local reusable `HOST_LOCAL|DEVICE_VISIBLE` source buffer keyed `(shape, dtype)` (`_rocm_source_buffer`, bounded `_ROCM_SOURCE_CACHE_MAX = 16`), then a per-call `queue_copy` with a fresh semaphore + query-first wait. Thread-locality is load-bearing because HAL devices are thread-affine (Known Issue 12): a process-global cache would hand the `evoxc.io` worker a foreign device. A one-shot `upload_tensor` returns a FRESH destination; segment executables keep a persistent destination per `(index, shape, dtype)`. Cuda placement instead uses a fresh-per-call device with its own pinned/DMA tiers; `_staged_input` selects the path from the NORMALIZED device kind.
- **Validated bit-exact vs numpy on rocm:** `cond`; sort/argsort with the default `sort_emission="auto"`; splitmix64 uniform/randint; threefry2x32 via the NATIVE `rng_bit_generator` path; philox inline; host-mode `external_call`; matmul+tanh. f32 `random.normal` differs from numpy only within the documented Box–Muller fast-path budget.
- **`while_loop`/`scan` were unreliable on rocm under iree 3.11** — upstream IREE HIP HAL; see Known Issue 13's sibling note in `./PER-ADAPTER-NOTES.md` and below in Known Issues. On **3.13.0** the three documented failing classes (scan with a constant init, while with a constant init, while whose condition reads a float carry) all ran 6/6 bit-exact vs numpy on this host's gfx942, and the `non_dominate_rank` while shape compiled 10/10 per target with the default options (Known Issue 10) — so the restriction is no longer reproducible, but it is reported rather than deleted: no adapter code depends on it, and removing the historical note would be a silent claim about a HAL nobody re-validated at scale.
- **A fully input-independent counted `while` fails to COMPILE on iree-base 3.13.0 — a clean compiler error, never a crash or a wrong result:** constant carry, constant condition bound and a constant-only body leave the whole `stablehlo.while` loop-invariant, and `iree-compile` stops with `error: maximum iteration count exceeded in fixed point pipeline` on llvm-cpu and on rocm. Nothing else in the counted-loop class is affected: a loop whose body consumes an input, and a loop whose bound is a static Python `int` (which specialises the graph at trace time), both compile and run — pinned as passing in `tests/backends/test_iree_rocm_while_scan.py`, with the MO-class loop pinned in `tests/backends/test_while_init_rewrite.py`; the rejected layout is documented in `tests/backends/test_iree_rocm_while_scan.py`'s module docstring and deliberately not pinned, because it must keep failing until upstream relaxes the bound.
- **Sugar (outside this node):** `evoxc/pipeline.py::_resolve_backend_device` infers `target_backends` from the resolved device when neither the option nor `EVOXC_TARGET_BACKENDS` is set (`cuda`→`["cuda"]`, `rocm`/`hip`→`["rocm"]`, `cpu`→`["llvm-cpu"]`), so `evoxc.build(fn, specs, backend="iree", device=Device("rocm", 0))` works end-to-end.

### Vulkan / SPIR-V (`vulkan`) — device-resident, queried device ids

Same adapter and the same device-resident machinery as cuda/rocm — a fourth compile target and a fourth HAL driver (`get_driver("vulkan")`).
- **Compile:** `target_backends=["vulkan-spirv"]` (`--iree-hal-target-backends=vulkan-spirv`; there is NO `--iree-hal-vulkan-target`). `_artifact_target` labels a vulkan-only target list `"vulkan"`; a mixed list (e.g. `["llvm-cpu","vulkan-spirv"]`) keeps the `"+"`-joined label, and the load-time target check (`_expected_target_for_kind`: `vulkan` → `"vulkan-spirv"`) accepts the artifact as long as the target is among them. No target flag is emitted by default; the optional `vulkan_target` compile option derives `--iree-vulkan-target=<profile>` (see the options table). `target_backends` is NOT inferred from a vulkan device (the pipeline sugar infers only `cuda`/`rocm`/`hip`/`cpu`), so pass `target_backends=["vulkan-spirv"]` (or `EVOXC_TARGET_BACKENDS`) explicitly — otherwise the artifact is an llvm-cpu one and `load()` rejects it with the target-mismatch `core.BackendError`.
- **Device paths — the ids are HASHES, not ordinals:** `Device("vulkan", N)` selects the N-th entry of `driver.query_available_devices()` (info dicts carrying `'device_id'` — a QUERIED PER-PROCESS HASH, e.g. `857002912` — plus `'path'` and `'name'`) and creates the HAL device with `driver.create_device(info_dict)` (`_acquire_vulkan_device`). The cuda/rocm `device_id = index + 1` ordinal convention does NOT apply and raises `ValueError`, wrapped as `core.BackendError`. An out-of-range or negative index raises a `core.BackendError` naming the requested index, the enumerated count and device names, and stating that vulkan ids are queried hashes; ZERO enumerated devices raises a `core.BackendError` whose text names the 3.11-era `llvmpipe` device-name denylist and hints at `VK_ICD_FILENAMES` (the adapter hard-codes no path) alongside `iree.runtime.get_driver("vulkan").query_available_devices()` as the diagnostic — 3.13 enumerates a software device with that variable unset, so the hint is historical guidance, not a requirement. Module load then takes the shared `rt.Config(device=...)` path.
- **HAL device caching:** the device is created ONCE per `(kind, index, tuple(runtime_args))` and held in the module THREAD-LOCAL cache through `_cached_hal_device` — thread affinity is required (HAL devices are thread-affine, Known Issue 12) and repeated `create_device` calls are costly; rocm uses the same helper. Because the lookup lives in `_acquire_vulkan_device`, `load()` and `upload_tensor` share ONE HAL device, so a placed tensor's buffer is accepted by the loaded executable's invoke.
- **`_GPU_DEVICE_KINDS` includes `vulkan`** — the set means "device-resident GPU-class kind": it selects the `rt.Config(device=...)` module-load path, the device-resident run branch and the placement gate. It is NOT "takes the cuda staging tier": `_pool_anchor`, `_configure_cuda_runtime_flags` and the pinned/DMA staging tier stay CUDA-ONLY.
- **Staging:** `_staged_input` returns `None` for vulkan (an explicit kind dispatch, before any buffer work), so uploads and segment boundaries use the plain `rt.asdevicearray` host-input fallback — there is no pinned/DMA tier, and the cuda tiers' ordering guarantee is unverified on this HAL driver. `_build_buffers`' `device_kind` is a REQUIRED keyword, so no kind can silently inherit the cuda tier; a vulkan segment executable keeps its `_staged_inputs = {}` dict unused and allocates no pool anchor.
- **Device-resident semantics are the cuda/rocm ones:** host inputs are rejected at the run boundary with `core.DeviceError`, `.numpy()` on a vulkan output raises (`core.DeviceError`), the readback is the explicit `.to(core.Device("cpu", 0)).numpy()`, and same-device inputs/outputs pass through with zero staging (`asdevicearray` = 0 in a warm same-device loop). `upload_tensor` and the download direction need no vulkan-specific code: the upload is a plain one-shot host→device copy on the shared cached device, and a download goes through the payload host copy (`IreeDevicePayload.to_host()`) → the adapter's own `_readback_device_array`, which on vulkan takes the explicit staging-`queue_copy` branch (the runtime's `DeviceArray.to_host()` fast path is the one that fails there; Known Issue 21).

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin** (user-provided; distribution OUT of scope): resolved in order (a) `plugin_path` (a compile AND load option), (b) env `EVOXC_PJRT_PLUGIN`, (c) well-known paths (`/usr/local/lib`, `/usr/lib`, `$HOME/.local/lib`, `./`). None found → `core.BackendError` with an actionable message (build e.g. `bazel build //xla/pjrt/c:pjrt_c_api_cpu_plugin` from OpenXLA, or any XLA build exporting `GetPjRtApi`). No pip hint — jaxlib is never imported by this adapter.
- **Device kinds:** serves `Device("cpu", 0)` (host-staged) and the device-resident accelerators in `_NON_CPU_KINDS = ("cuda", "rocm", "hip")` — kind-agnostic, any non-cpu kind is device-resident. `_check_kind_served` (a) rejects a kind outside `_NON_CPU_KINDS` (e.g. `"gpu"`) with a `core.BackendError` containing "supports CPU", and (b) once the plugin's platform is known, rejects a kind the platform does not physically serve when the platform is listed in `_PLATFORM_KINDS` (`"cuda"→("cuda",)`, `"rocm"→("rocm","hip")`, `"hip"→("rocm","hip")`, `"cpu"→()`), so `Device("cuda", N)` against a ROCm plugin is rejected rather than mislabelled. An UNLISTED platform (e.g. the fake plugin's `"fake"`) is PERMISSIVE.
- **compile:** `ctypes.CDLL(path)` → `GetPjRtApi()` (a lowercase-t `GetPjrtApi` fallback covers the shipped jax plugins' casing) → **version gate** (`PJRT_Api.version`/`struct_size` vs the bindings' minimum; too old → `BackendError`) → the process-global shared `PJRT_Client` (`acquire_client`, one per plugin path, created with empty options) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` (the plugin accepts MLIR text directly; NO MLIR python bindings anywhere in this adapter) → `PJRT_Executable_Serialize` → base64 bytes in the artifact payload (alongside `mlir_text` + `entry_functions`). The artifact stays device-agnostic (`target="cpu"`); the device is chosen at `load()`.
- **Static-shape gate:** `dynamic_shapes=False` — symbolic dims are rejected at compile via `_resolve_static_shape`/`_StaticShapeError`; the gate decision is recorded in the artifact (`static_input_shapes`/`static_output_shapes`) and enforced exactly at `run()`.
- **load/run — CPU:** deserialize via `PJRT_Executable_DeserializeAndLoad` on the refcounted shared client for the re-discovered plugin — never recompiles. Inputs staged via `PJRT_Client_BufferFromHostBuffer` (all 14 evoxc dtypes incl. complex64/128; dense row-major numpy with `np.asarray` + contiguity forced only for ndim ≥ 1, NOT `np.ascontiguousarray` whose hardcoded ndmin=1 promotes 0-d arrays; `kImmutableUntilTransferCompletes`; transfer event awaited and destroyed; host array kept alive on the buffer); execute via `PJRT_LoadedExecutable_Execute`; outputs copied via `PJRT_Buffer_ToHostBuffer` → writable numpy → `core.Tensor`.
- **load/run — device-resident (`Device("cuda"|"rocm"|"hip", N)`), iree-mirroring:** every input must already be an `XlaDevicePayload`-backed `core.Tensor` on the executable's device (host inputs raise `core.DeviceError` at the run boundary — never staged); payload buffers go to `PJRT_LoadedExecutable_Execute` DIRECTLY and outputs STAY on the device as `XlaDevicePayload` tensors (public class, like `IreeDevicePayload`; non-cpu `.numpy()` raises, explicit `t.to(cpu).numpy()` round-trips). The same-device loop places the seed once via `t.to(Device(kind, N))` (the module-level `upload_tensor`, a one-shot `BufferFromHostBuffer` on the shared client, registered by `register()` for every `_NON_CPU_KINDS` entry) and then feeds each step's outputs back as the next inputs, so the per-call staging/copy-back fixed cost is paid exactly once.
- **Device-resident `run` is ASYNCHRONOUS — `synchronize()` is the explicit completion boundary (Known Issue 17):** `PJRT_LoadedExecutable_Execute` returns once the work is ENQUEUED, so a device-resident `XlaExecutable.run` requests the plugin's per-device completion event (`events=` sink on `xla_util._LoadedExecutable.execute`, written through `PJRT_LoadedExecutable_Execute_Args.device_complete_events` into the 1-element `c_void_p` slot of the per-thread execute scaffolding) and commits the raw handle to `_pending_events` under `_events_lock` IMMEDIATELY after the execute returns — BEFORE the output-count/metadata checks, so a late validation failure can never leak a handle. `XlaExecutable.synchronize()` swaps the list out under the lock (work enqueued concurrently belongs to a later sync), then `PJRT_Event_Await`s and `PJRT_Event_Destroy`s every popped handle OUTSIDE the lock, re-raising the FIRST error after the remaining handles are cleaned up; it is reusable/idempotent and performs zero FFI when idle. A plugin that returns no event (0/None) makes `run` record a reason and `synchronize()` raise an explicit `core.BackendError` (never a silent claim of completion), and `close()` destroys pending handles WITHOUT awaiting. The CPU host-staging branch requests no event — its `PJRT_Buffer_ToHostBuffer` already awaits. Consequence for measurements: time `run` + `synchronize()` (or an explicit `.to(cpu)` readback), never a bare timed loop.
- **Per-call hot path:** a run on an accelerator executable re-derives nothing that is static for a loaded executable. `XlaExecutable` builds ONE `_XlaRunPlan` carrying everything static about a run — input/output arity, per-leaf `(dtype, shape)` contracts from the signature, output metadata from the recorded static output shapes, and the run MODE (`device_resident`, derived once from the load device). `run` then makes ONE plan-driven pass over the inputs that validates dtype/shape and performs the explicit-placement checks in the same loop (payload type -> device -> owning client, with identity fast paths ahead of the equality fallback), preserving the same exception types/messages/order; per-leaf metadata is read from a device payload's already-cached `_Buffer` `(shape, dtype)` rather than the generic `core.Tensor` property path (falling back to the properties when the cache is empty). Output leaves are built into a pre-sized list filled by index, and the same count/dtype/shape validation loop runs over it (the CPU host-staging branch is unchanged); `xla_util._LoadedExecutable` caches `num_outputs` and reuses per-thread ctypes scaffolding in `threading.local` (bounded by `_EXECUTE_SCAFFOLDING_MAX` — thread-local, not shared, so concurrent runs of one executable from different threads stay safe). Output buffers are created with the recorded static metadata PREFILLED (built into a pre-sized list; a tuple `output_meta` is consumed without a per-call copy), `_Buffer.__init__` assigns the handle fields inline instead of calling `_Handle.__init__`, and a destroy call resolves its entry point, args class and handle field ONCE per `api_name` from a per-plugin table while reusing a THREAD-LOCAL args struct (struct-class sizes come from a `_sizeof` cache) — so the per-output destroy churn is a field write plus the FFI call. Prefilled metadata is NEVER trusted blindly: `_Buffer._verify_metadata()` runs the real queries and raises a loud `core.BackendError` on a declared-vs-actual mismatch — every output is verified on an executable's FIRST device-resident run and `_Buffer.to_host()` re-verifies on every explicit readback. A run's whole output set shares ONE client reference and ONE `weakref.finalize` (`_XlaDeviceRunGroup` → `xla_util.release_payloads`); `release_payload` stays the single-buffer wrapper for `upload_tensor`/external payloads, and the public 4-arg `XlaDevicePayload` constructor keeps its own reference/finalizer. Design rationale + A/B medians: `./PER-ADAPTER-NOTES.md`.
- **Error contract (binding):** every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message`, destroys the error, and raises `core.BackendError` naming the failing step. All handles are destroyed via matching entry points (try/finally + `close()` helpers; the loaded-executable's inner unloaded twin from `PJRT_LoadedExecutable_GetExecutable` is destroyed first). Header-driven details: `PJRT_Program.format` is `"mlir"`; deserialize is `PJRT_Executable_DeserializeAndLoad`.
- **`check_available()`:** bindings integrity + plugin discovery + `GetPjRtApi` + version gate + a live client create/destroy round-trip. Artifact `runtime_dependencies` records numpy + the `pjrt_c_api` header commit + the plugin platform/version string — no jaxlib.

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- **translate:** `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (this API exists in 0.26; `tvm.relax.frontend.from_mlir` does NOT; build lives in `tvm.relax.vm_build`, re-exported as `tvm.relax.build`).
- **MLIR binding seam (`_mlir_bindings.py`):** ALL MLIR-binding access (context creation, `ir.Module.parse`, the `ir` re-export) routes through this one module, so a future standalone `mlir`/`stablehlo` PyPI package is a one-module swap.
- **jax shim (`tvm_util._install_jax_shim`):** the vendored translator's `from jaxlib import mlir` and `from jaxlib.mlir.dialects import stablehlo` imports work as-is; its single `from jax._src.interpreters import mlir` import (inside `from_stablehlo()`) is satisfied by injected `sys.modules` shims for `jax`, `jax._src`, `jax._src.interpreters` and `jax._src.interpreters.mlir` (the mlir shim provides `make_ir_context()` delegating to `_mlir_bindings.make_ir_context` and re-exports `jaxlib.mlir` as `ir`). Injection happens at the top of BOTH `check_available()` and `ensure_compat()` — before any `tvm.relax.frontend.stablehlo` import — and is idempotent (a real jax already imported in-process is left in place; `sys.modules["jax"] = None` is overwritten).
- **build/run:** `tvm.relax.vm_build.build(mod, target=tvm.target.Target("llvm"))` → `VMExecutable`; run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())["main"](...)`; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (the `tvm.nd` namespace does not exist in TVM 0.26); outputs `tvm.runtime.Tensor.numpy()` → `core.Tensor`.
- **persist:** `VMExecutable.export_library(path)` → host `.so`, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — no recompile at load. (`Module.save_to_file` does not exist in 0.26.)
- **Compatibility shim (REQUIRED):** the 0.26.0 vendored translator targets the OLD jax mlir bindings; `tvm_util.ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` decoding, float16 `np.asarray` constant decoding), each restoring exactly the semantics the vendored code assumed (no computation changes).
- **Op coverage gate:** `SUPPORTED_STABLEHLO_OPS` is checked at compile (`core.BackendError` naming the op otherwise) — arithmetic, unary math, compare, select, bitwise/logical, convert, `broadcast_in_dim`, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), `dot_general` (matmul), constant. Rejected: control flow (`stablehlo.if`/`while`), gather/scatter, remainder, conv/reduce_window (the vendored handlers hardcode NHWC/HWIO — silently wrong for evoxc's NCHW conv), multi-function modules, multi-output functions.
- **ROCm:** TVM is COMPILE-ONLY on ROCm — the `apache-tvm` 0.26.0 wheel is built `USE_ROCM=OFF`, so `tvm.runtime.device("rocm", 0).exist is False`. Do not include TVM in ROCm run matrices.

## Constraints (binding)

- **Heavy-import rule:** `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports are limited to stdlib, `evoxc.core`, and the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import evoxc` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`:** `import jax` / `from jax` is forbidden anywhere in `evoxc/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- **Errors:** capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never a silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`; shape mismatches `core.ShapeError`.
- **Staging never composes:** `load` never re-traces/lowers/compiles; device handles are never serialized.
- **Device kinds:** the tvm path is CPU only; the iree adapter accepts `core.Device("cpu"|"cuda"|"rocm"|"hip"|"vulkan", index)` and runs the non-cpu kinds device-resident, while the xla adapter accepts `core.Device("cpu"|"cuda"|"rocm"|"hip", index)` only (it does NOT serve `vulkan`). A device kind the adapter does not support — or a kind the resolved plugin's platform does not physically serve — raises `core.BackendError`; a non-`Device` object raises `core.DeviceError`.

## Design decisions

- **IREE cuda allocator flag — evoxc sets NO process-global `--cuda_async_allocations` value; iree's own default (`true`, stream-ordered) stands.** Forcing `false` measured ~2–3× slower per step on fused DE/PSO step graphs (numbers: companion). Users who need the classic allocator pool opt in per load via `iree_runtime_args=["--cuda_async_allocations=false"]` or `IREE_PY_RUNTIME_FLAGS`; `upload_tensor` honors the same `EVOXC_IREE_RUNTIME_ARGS`. Policy point: `_configure_cuda_runtime_flags` in `iree.py` is a deliberate no-op. The `_pool_anchor` is retained ONLY on cuda SEGMENT executables (the one plain-cuda path that still stages host tensors).
- **Adapter defaults are minimal and overridable** — a user flag with the same NAME drops the default (never both), and only the small documented DENY list is rejected. The rocm default flag set is already cost-free (no debug-info / executable-debug-level / truncate-floats flags); there is nothing to remove.

## Dispatch formation (merged-population graphs)

IREE forms dispatches AFTER lowering, so this knob is a compile-stage flag and the dispatch count is IDENTICAL on `llvm-cpu` and `rocm` for the same MLIR — measured on every configuration below (596/548 and 2191/2021 on both targets).
Only one flag moves it: `dispatch_formation="aggressive"` (options table) → `--iree-dispatch-creation-enable-aggressive-fusion`. It is OPT-IN; the adapter default stays flag-free.
Full sweep, per-chunk numbers and the probe: [`../../bench/dispatch_formation_findings.md`](../../bench/dispatch_formation_findings.md) + [`../../bench/probe_dispatch_formation.py`](../../bench/probe_dispatch_formation.py), raw records in `../../bench/dispatch_formation_results.json`.
**Every number and table below was measured on iree-base-compiler 3.11.0** — do not re-attribute them to a newer release.
On **3.13** the flag's own default became optimization-level-dependent (`--help`: "At optimization level O0 the default is false / At optimization level O2 the default is true"), so with evoxc's own plumbing unchanged the derived flag now produces a BYTE-IDENTICAL vmfb at `opt_level="O2"`/`"O3"` (verified on rocm and llvm-cpu); it only changes compilation at O0/O1 or with `opt_level` unset. `dispatch_formation="default"` still means exactly "evoxc derives NO flag" (byte-identical compile ARGS) and evoxc never emits the flag's `=false` form, so the option remains a semantically clean "let the compiler decide" default rather than an override.

**Fragmentation is NOT multi-use splitting.** `--iree-dispatch-creation-fuse-multi-use` is ON by DEFAULT in iree 3.11 (explicit `=false` on one 137-dispatch chunk WORSENS it to 222), and passing it explicitly changes nothing (596); neither does `--iree-dispatch-creation-enable-aggressive-reshape-movement` (596).
The ~1-executable-per-program fragmentation is ELEMENTWISE-FUSION GRANULARITY: each dispatch is one `linalg.generic` holding 37–69 arith/math ops, and the dispatcher breaks exactly where aggressive fusion will not merge two consumers.
So the lever is "fuse more of a program's op chain", not "stop splitting shared values".

## Known Issues

1. **Writer/export gaps surfaced by the adapters (sibling node `stablehlo/`):** (a) dynamic-shape support is per-op partial and exporter-gated — elementwise symbolic graphs (incl. scalar-constant broadcasts) compile and run on iree/tvm at multiple sizes, while symbolic `reshape`/`conv`/`slice`/`pad` (slice/pad: iree parses but the runtime aborts) and unemittable `dot` batch merges raise an explicit `core.BackendError` at `lower()` naming the op, shape and offending dims; (b) mixed-dtype binary ops with Python scalar constants can produce a dtype mismatch parse error (workaround: explicit `evoxc.cast`); (c) `stablehlo.add` on i1 is XOR, while numpy bool `+` is OR.
2. **IREE `rng_bit_generator` (empirical, iree 3.11, re-confirmed on 3.13.0):** the modern two-result syntax is REQUIRED (`%state_out, %out = stablehlo.rng_bit_generator %state, algorithm = THREE_FRY : …` — no shape operand, enum WITHOUT the `RNG_ALG_` prefix); the older shape-operand form is REJECTED. `THREE_FRY` legalizes and runs BIT-EXACT vs numpy with the key-first `[k0',k1',ctr0,ctr1]` state layout on llvm-cpu, cuda and rocm, so `{"threefry2x32"}` is the iree capability and native THREE_FRY is the default path for threefry graphs. `PHILOX` FAILS legalization on BOTH llvm-cpu and cuda (`failed to legalize operation 'stablehlo.rng_bit_generator' … explicitly marked illegal`; 6-word philox state) → philox graphs use the exporter's bit-exact inline expansion.   **3.13.0 re-check:** the same behaviour holds — the native THREE_FRY path is bit-exact vs numpy on llvm-cpu and rocm and the PHILOX inline expansion is used (pinned by `tests/backends/test_iree_random_algorithms_parity.py`, green on 3.13.0). 11. **iree 3.9.0's cuda runtime SIGSEGV on SO step graphs is superseded by the 3.11.0 record (Known Issue 8);** its measurement narrative stays in `./PER-ADAPTER-NOTES.md` (`## Known Issue 11`).
12. **CUDA HAL devices are thread-affine: any allocating HAL op from a thread with no prior CUDA activity fails `CUDA_ERROR_INVALID_CONTEXT`** (`to_host()`, `asdevicearray`, invoke output-alloc — even when the HAL device was created by another thread; the state is thread-local). Per-thread mitigation: the thread first creates its own unused cuda HAL device on the same GPU (`rt.get_driver("cuda").create_device(device_id=idx+1)`), making the shared primary context current; no iree-python API sets context-current directly, and llvm-cpu (local-task) has no such constraint. Implication: cuda/rocm FIFO-worker copies need this one-time bootstrap per worker thread — see `evoxc/io.py::_bootstrap_worker_context`.
13. **IREE GPU lowering of rank-0-result reductions is a single sequential workgroup — the dominant cost of monitor-style graphs, and NOT fixable with compiler flags.** On a 10000×100 evox SO-shaped step the `argmin`/`min`/i1 NaN-guard reductions are each lowered as ONE workgroup / ONE thread (sequential loop) while every data-parallel sibling dispatch gets a 64-thread workgroup, so three scalar reductions consume ~95 % of per-step time; the cost is constant per step, hence invisible at small population sizes (inside the launch floor) and dominant at large ones. The structural fix is EVOXC-side and numerically exact: split the reduced axis so the reduction is not rank-0 in one step (`reshape (n,) → (R,C)`, reduce `dim1`, then reduce the rows) — shipped as the `split_reduction` exporter option (default `True`, rank-0-result reductions over a large static dim) and worth ~8–10× on the affected ops; a keepdims reshape to `(n,1)` does NOT help (the split must yield ≥2 non-unit factors), and no compiler flag substitutes for it. RNG is not implicated (on rocm the inline SplitMix64 expansion is faster than the native threefry path for bulk draws). Profiling tables, subgraph attribution and the full flag sweep: companion (`## Known Issue 13`).
14. **Small-scale results are launch-overhead-bound, so iree and xla look equal there** (both sit inside the invoke floor plus wrapper cost); the cross-backend gap only appears once the population is large enough for the constant per-step scalar-reduction cost to dominate (Known Issue 13). The measured host-cost ladder — end-to-end vs pipeline vs bare-metal bounds, the ≈2–3.5 µs per-I/O-leaf / ≈0 per-op slope, the PJRT ENQUEUE caveat and the current plan-driven restatement — is in `./PER-ADAPTER-NOTES.md` (`## Known Issue 14`); don't re-derive it.
15. **Input-COUNT is unbounded, but per-call cost is per leaf and the CPU paths re-stage every input; compile-time scaling is UNMEASURED.** No adapter caps function arguments / buffers, and no adapter caches an input across calls: an llvm-cpu iree run calls `rt.asdevicearray` once per HOST input leaf (`iree.py` run loop, the `buffers[i] = rt.asdevicearray(...)` branch — the ONLY plain-run host-input path) and an xla `Device("cpu", 0)` run creates + closes one PJRT buffer per leaf (`xla.py`, the `buffers = [client.buffer_from_host(a) for a in arrays]` / `finally: buffer.close()` branch), while a DEVICE-RESIDENT run passes `IreeDevicePayload` / `XlaDevicePayload` buffers straight through (zero copies, zero staging). So a many-input graph is cheap only when every input is a device-resident tensor placed ONCE — and placement itself is per-call device acquisition on cuda (`upload_tensor` → `_acquire_runtime_device`, no cache; rocm avoids this with a thread-local device because hip `create_device` measured ~46 ms/call). Cost anchors: per-IO-leaf ≈2–3.5 µs pipeline+adapter (Known Issue 14) and the plugin's `PJRT_LoadedExecutable_Execute` FFI measured ~32 µs for 2 buffers vs ~59 µs for 8 (`PER-ADAPTER-NOTES.md`), i.e. arity grows the FFI cost. Compile-time scaling with graph size: the measured cost model is Known Issue 18 (large-graph probe, iree-base-compiler 3.11.0).
18. **Large-graph compile time ≈ #executables × ~30 ms + ~0.3 ms/op — NOT text size and NOT opt level (measured, llvm-cpu, adapter default flags).** `batch_functions`-merged population graphs (shape `(N, 32)`, `iree.compiler.compile_str(..., target_backends=["llvm-cpu"], input_type="stablehlo", extra_args=<adapter defaults>)`): 3450 ops → 5.9–6.3 s (230 executables), 9415 ops → 15.5 s (434), 12804 ops → 26.5 s (855); executables hold a median of only 16–19 ops, so cost is dominated by the per-executable fixed cost. `--compile-to=` split at 12804 ops: parse+ingest 1.3 s, → flow 6.6 s, → hal 27.5 s ≈ full 26.5 s (object emission + LLVM translation are the rest); `evoxc.lower` is 1.29 s of which `stablehlo.export` 1.10 s, and `evoxc.compile` adds 0 ms over raw `compile_str` (artifact base64 1.6 ms, `CompiledArtifact.save` 13 ms, `.load` 8 ms). A 2000-op elementwise CHAIN fuses into ONE dispatch and costs 11.1 s (9.5 s inside LLVM ISel/regalloc/encoding of one 14.5k-instruction function) while the SAME ops with an `optimization_barrier` every 100 ops (20 dispatches) compile in 2.3 s — mega-dispatches are the superlinear regime, many small dispatches are linear. Flags that do NOT help: `opt_level="O0"`/`"O1"` produce a BYTE-IDENTICAL vmfb (IREE 3.11's unflagged default behaves as O0/O1), `--iree-opt-const-eval=false` and `--iree-codegen-enable-default-tuning-specs=false` are no-ops, `--mlir-disable-threading` is 1.8× WORSE on many-executable graphs; `opt_level="O3"` buys −10 % (230-executable) / −6.4 % (855-executable) but O2/O3 is documented-broken for some cuda graphs (Known Issue 9); `--iree-hal-link-executables=false` is −26 % on the 230-executable graph and +22 % on the 855-executable one (unstable — measure per size). Frontend levers that do move wall clock: chunk-and-parallelize (a 64-program chunk = 895 ops compiles in 1.53 s, 128 = 3.0 s, 256 = 6.32 s — near-exact linearity, so 4 chunks on 4 cores ≈ 1.5 s instead of 6.3 s), `batch_functions(bands=32)` (−9 %, 230→169 executables; `switch_ops=True` is +22 %), and reuse (`CompiledArtifact.save`/`load`, `evoxc.build_cached` + `CompileCache`) — the adapter never caches a compile. Merged-graph TEXT is 86 % i1 select-mask literals (9.0 MB of 10.5 MB at N=1000, one `dense<[true, false, …]> : tensor<Nx1xi1>` per mux `select`, emitted by `evoxc/transforms/_emit.py::_row_mask` at :171-183 via the Writer's `_constant_text`, `../../../stablehlo/writer.py:4852`) yet that whole text costs ~1.3 s of parse/ingest, so compaction is worth <5 %; MLIR's compact `dense<"0x…">` hex form is NOT usable for i1 (`tensor<1000x1xi1>` rejects the 125-byte bit-packed payload, accepts 1000 bytes i.e. one byte per element).
16. **IREE 3.11 Vulkan runtime: software devices are hidden by NAME and the default target profile caps large graphs.** (a) **Device visibility** — the 3.11 vulkan driver hard-codes a device-name denylist in `iree_hal_vulkan_is_device_visible()` (`if (strstr(deviceName, "llvmpipe") == deviceName) return false;`) with NO flag/env override, so `query_available_devices()` returns `[]` on a host whose only Vulkan device is Mesa lavapipe while the loader's own log shows it enumerated. Making a SOFTWARE device enumerable requires `VK_ICD_FILENAMES` pointing at a RENAMED lavapipe ICD (a copy of `libvulkan_lvp.so` whose device-name string reads `lavapipe`) that is MACHINE-LOCAL under `$TMPDIR` — never a repo path, never a hard-coded dependency. **On 3.13.0 the denylist no longer hides lavapipe**: `query_available_devices()` enumerates the software device with `VK_ICD_FILENAMES` UNSET, so the renamed-ICD recipe is no longer required there (keep it only as a 3.11 fallback; the device-guarded Vulkan tests discover devices in a child process with a timeout, so they work either way). (b) **Hang** — with `VK_ICD_FILENAMES` unset this host's loader dlopens the wedged radeon ICD and `query_available_devices()` HANGS: wrap any Vulkan/DRM probe in `timeout`, and pinning the variable also keeps the loader away from that ICD. (c) lavapipe reports `deviceType=CPU` — a SOFTWARE device, so every vulkan number is provenance/correctness, never a GPU performance measurement. (d) **Default target profile** — without `vulkan_target`, codegen uses `vp_android_baseline_2022`: `max_workgroup_memory_bytes = 16384`, `max_thread_count_per_workgroup = 128`. The LayerNorm-shaped reductions of 124M-class transformer graphs exceed it at compile (`function 'main_dispatch_0_reduction_32x768_f32' uses 196864 bytes of shared memory; exceeded the limit of 16384 bytes`); raising the budget with `vulkan_target="<profile>"` (or the raw `--iree-vulkan-target=<profile>` flag — `rdna3`/`rdna4`/`gfx*` 64 KiB, `adreno`/`valhall*` 32 KiB, `sm_80`/`ampere` 166912 B) moves the wall to vector-dialect legalization (`vector.from_elements` marked illegal) instead of yielding a running module, so large transformer graphs do not compile under the default profile. (e) **This host's GPU-Vulkan verdict: no GPU Vulkan execution is possible** — RADV rejects CDNA3 by policy (`radv_is_gpu_supported`), AMDVLK's PAL has no CDNA IP path, and a binary-patched RADV enumerates but fails init on the wedged amdgpu DRM device; evidence, flags and the lavapipe measurements: `bench_logs/vulkan_findings.md`.
17. **xla's DEVICE-RESIDENT `run()` is ASYNCHRONOUS (dispatch overlap is intentional) — `XlaExecutable.synchronize()` is the only explicit completion boundary.** `PJRT_LoadedExecutable_Execute` returns after ENQUEUE, so a bare timed loop measures only host dispatch: on this host (MI300X VF / ROCm 7.1, real `jax_rocm7_pjrt` plugin, Qwen3-8B fp32 forward in a same-device loop) the loop reports best_ms **3.07 at seq_len 32 AND 3.07 at seq_len 128** — identical across a 4× work change, impossible for 32 GB of fp32 weights — while the same loop with ONE explicit `out.to(Device("cpu", 0))` readback per call measures **21.5 / 31.6 ms**; true execution latency is ~6–10× the reported dispatch time. Mechanism: a device-resident run passes `events=` to `xla_util._LoadedExecutable.execute`, which requests one per-device `PJRT_Event*` through `PJRT_LoadedExecutable_Execute_Args.device_complete_events` (1-element `c_void_p` slot in the per-thread execute scaffolding; `events=None`, the default, keeps the field NULL and costs no plugin work). `XlaExecutable.run` commits the raw handle (possibly `0`/`None`) to `_pending_events` under `_events_lock` the instant execute returns, BEFORE any output validation (so a late validation failure cannot leak a handle); `synchronize()` swaps the outstanding list out, then `PJRT_Event_Await` + `PJRT_Event_Destroy`s every popped handle OUTSIDE the lock (await then destroy, each guarded — the FIRST error is re-raised after the rest are cleaned up, and work enqueued concurrently belongs to a later sync), is reusable/idempotent and performs zero FFI when idle; a `0`/`None` handle means the plugin violated the contract, so `synchronize()` raises an explicit `core.BackendError` instead of claiming completion; `close()` destroys pending handles WITHOUT awaiting (close must never block). **Consequence (binding for benchmarks):** ANY wall-clock measurement of the xla leg must time `run` + `synchronize()` (or an explicit `.to(cpu)` readback) — a bare timed loop measures only host dispatch, since dispatch overlap is intentional; this is the general rule for GPU benchmarks of the xla path. iree (and numpy) `run` block on the device queue, so their `synchronize()` is a documented no-op. Real-plugin validation that a live plugin returns a usable event and that `PJRT_Event_Await` closes the 3.07 ms → 21.5/31.6 ms gap is still OPEN (GPU-only).
18. **IREE/ROCm is 5–10× behind XLA/ROCm on large-weight whole-model graphs, and the cause is IREE ROCm codegen — not host-backed buffers, not per-call staging, not dispatch overhead.** Weights are device buffers placed ONCE (`asdevicearray` = 0 in the warm loop), outputs stay device-resident, `evoxc_hf.run` does O(1) host work per call, and the exporter emits BYTE-IDENTICAL StableHLO for both adapters (`stablehlo_bytes` 669 881 on `qwen3_8b` s32) — so no evoxc-side difference exists to explain the gap. The residual is (a) per-dot kernel efficiency at the GEMV-ish `M≪N` shapes (260–711 GB/s on iree vs 1.3–2.5 TB/s on xla per isolated dot, same fp32 MFMA lowering) plus (b) a bimodal IREE HIP large-stream mode (a call streaming most of a 1–2.5 GB allocation runs 3–7× slow in most processes; a fixed 67 MB read is flat regardless of the owning allocation's size, so the packed layout is not the cause). `--iree-opt-data-tiling`, `opt_level=O3`, `--iree-opt-aggressively-propagate-transposes` and hand-written tuning specs are NOT remedies, and `--hip_async_allocations=false` is a placement-lottery artifact rather than a fix. Full decomposition, tables and reproduction: `bench_logs/iree_rocm_gap_findings.md` (+ `bench_logs/probe_iree_rocm_math_roofline.py`).
19. **The HIP and CUDA HALs cap ONE dispatch at 16 bindings, and the check runs at executable LOAD, not at compile.** `hip/native_executable.c:217-223` (inside `iree_hal_hip_native_executable_flatbuffer_verify`) rejects `exports[N] binding_flags count %zu exceeds maximum of %u` against `IREE_HAL_HIP_MAX_DISPATCH_BINDING_COUNT 16` (`hip/native_executable.h:21`; `constant_count` cap 64 at :25); CUDA is identical (`cuda/native_executable.c:224-230`, `cuda/native_executable.h:24`); the CPU local ABI allows 64 (`local/executable_library.h:380`, enforced `local/executable_library_util.c:48`) and Vulkan has no count cap (bindings become descriptor-set layouts). Pinned to the installed wheel: `iree.compiler.version.REVISIONS["IREE"] == e4a3b0405d7d23554da26403658d0e8c3c5ecf25`, `VERSION == 3.11.0rc20260316`.
  **3.13.0 re-check:** the 16-binding wall is still present and still load-time — the adapted `_binding_wall_fn` probe in `tests/backends/test_adapter_iree.py` (16 concatenate pieces → 17 bindings → `core.BackendError` at `load()`, naming the binding count, `native_executable.c` and the maximum of 16; 15 pieces → 16 bindings still loads and runs) behaves exactly as documented on 3.13.0/rocm.
   The counted vector is the export's `#hal.pipeline.layout` binding list (`HALAttrs.td:581-607` — a FLAT list in this version), one `BindingBits` per entry written by `compiler/plugins/target/ROCM/ROCMTarget.cpp:1102-1123` and copied into `iree_hal_hip_kernel_params_t.binding_count` at `native_executable.c:465-469` (the arg-chain length in `stream_command_buffer.c:550`): i.e. that ONE dispatch's input + output buffers. Tensor CONSTANTS never consume it — measured, 2 inputs + 20 distinct 4 KB tensor constants = 4 bindings (hoisted and subranged into ONE constant-pool binding) and 20 tiny constants = 2 bindings (inlined), while 22 tensor args + 1 result = 23 bindings in one dispatch; a static `stablehlo.concatenate` creates no dispatch of its own (host-side `flow.tensor.update` chain) unless its pieces' producers fuse into that chain,
   which is exactly the `batch_functions` combine case below.
   Nothing raises or splits it: the 23-binding graph compiles for `rocm`/`hip` with exit 0 (`rocm-hsaco-fb`, abi `hip` — no compiler-side gate), and `--iree-scheduling-optimize-bindings` (default ON, `FuseDispatchBindingsPass`), `--iree-stream-resource-alias-mutable-bindings` and `--iree-hal-indirect-command-buffers` leave the count unchanged (`--iree-hal-indirect-command-bindings` does not exist in 3.11). The only higher cap is the AMDGPU/HSA driver (`amdgpu/executable.h:51`, `UINT16_MAX`) behind `--iree-rocm-container-type=amdgpu`, unreachable in practice because the `iree-base-runtime` wheel ships no `amdgpu` driver.
   **`evoxc.batch_functions` boundary: the driver is the merge's OUTPUT combine, not the band count per se.** `evoxc/transforms/_bands.py::_combine_bands` emits ONE `stablehlo.concatenate` over all K per-band outputs; IREE rewrites it into a `flow.tensor.update` chain and fuses consecutive updates (plus each piece's trailing elementwise op) into ONE dispatch with one binding per piece.
   Measured worst case (evoxc-only synthetic, every piece an elementwise-terminated 1-element column): one dispatch with exactly K+1 bindings — K=15 (16 bindings) loads and runs bit-exact on `Device("rocm", 0)`, K=16 (17 bindings) raises the `core.BackendError` above.
   Measured downstream GP-loss shape (pop 256 / 199 merged functions, `axes=(None,None)`, `out_axes=0`, x `(128,8)`, y `(128,1)`, `per_row=False`, rocm/gfx942): max bindings 5 at K=32/64/100, 12 at K=105, 14 at K=106, 16 at K=107 (still loads), 18 at K=108 and 20–24 for K≥112 (do not load); band size 1 (K = n_functions) fails at every measured population (pop 64 K=49 → 22, pop 128 K=102 → 23, pop 256 K=199 → 23).
   The count is NOT monotone in K — IREE shares the pieces' source buffers, so a shared input costs ONE read binding — hence the reliable rule is K ≤ 15 unconditionally, and "band size ≥ 8" (K ≤ n/8) as the practical large-population policy; the default band size 32 (K = ceil(n/32)) measured 5 bindings at pop 256.
   Emission-side remedies were measured and do NOT work: a balanced pairwise concat tree, chunking into ≤16-operand concats, and a 2-D `(1,16)` axis-1 chunk all still produce ONE wide update dispatch (200 bindings for 199 pieces) because IREE re-associates same-axis concat chains; `--iree-opt-outer-dim-concat` leaves it unchanged and `--iree-scheduling-optimize-bindings=false` roughly doubles it.
   llvm-cpu is NOT immune, only wider, and it fails with two DIFFERENT (still raw) errors: the same K-piece combine loads at K=16 (local-task allows 64) but K=40 fails with `builtins.IndexError: … hal/module.c:1077: OUT_OF_RANGE; binding count 41 > 32` (the command-buffer dispatch cap 32) and K≥64 with `local/executable_library_util.c:52: … dispatch requiring 65 bindings exceeds limit of 64`; neither is converted by `_raise_if_dispatch_binding_limit` (different messages, and this node's scope is the HIP/CUDA verifier) — a caller batched on llvm-cpu caps at K=31 unconditionally.
   Merged graphs whose per-band pieces are NOT elementwise-terminated (e.g. the `out_axes=0` value variant, wide `(band_rows, N)` pieces) measured only 4–6 bindings per export for every K up to K=N — no wall; the wall appears only when the combine's pieces fuse.
   Consequence: keep ≤16 tensor I/O leaves per fused dispatch — the failure shape is a fused region (or a fused update chain) over 17+ tensors, e.g. a 20-input elementwise expression.
   `IreeBackend.load` (both the plain vmfb path and the segmented/`IreeExternalExecutable` path, which both go through `iree.py::_load_vm_module`) recognizes exactly that failure from the runtime text (`binding_flags count (\d+) exceeds maximum of (\d+)`, falling back to the `native_executable.c` source marker) in `iree.py::_raise_if_dispatch_binding_limit` and raises an explicit `core.BackendError` with the original `ValueError` as `__cause__`.
   The message names the HAL cap, the observed count, the backend/compile target, that constants never count and that `iree-compile`'s HAL layout assignment decides the count (so evoxc cannot detect it at `lower()`/`compile()`), and the remedies: (a) fewer `batch_functions` bands (larger band size) or `bands=None`, (b) split the graph so no fused region consumes >16 tensors, (c) `target_backends=['llvm-cpu']` or the `numpy` backend.
   Every other iree error keeps its previous behavior and wording (GPU kinds re-raise verbatim; the CPU `ValueError` keeps the mixed-install wrapper); `numpy`/`xla`/`tvm` paths are untouched.
   Vulkan has no count cap; llvm-cpu is wider but NOT safe at large K (see the two raw llvm-cpu classes above).
   Offline count: `iree-compile model.mlir --iree-input-type=stablehlo --iree-hal-target-backends=rocm --iree-rocm-target=gfx942 --compile-to=executable-configurations -o cfg.mlir`, then count `#hal.pipeline.binding<` per `hal.executable.export … layout(#hal.pipeline.layout<…>)`; per-executable variant `--iree-hal-dump-executable-sources-to=DIR` (one `module_<executable>.mlir`, count distinct `hal.interface.binding.subspan … binding(N)` ordinals — constant pool included) or `--iree-hal-dump-executable-configurations-to=DIR|=-`. `iree-dump-module` does NOT decode `HIP1` executable defs.

20. **Same-thread deadlock in the xla shared-client cache — a FINALIZER firing inside a plugin call (fixed; the discipline below is binding).** A `weakref` finalizer runs wherever the GC pass that freed its referent happens to be, including inside another critical section on the SAME thread; `xla_util.acquire_client` used to hold the non-reentrant `_shared_clients_lock` across `plugin.create_client()`, so a pending XLA payload finalizer (`release_payloads`, which takes that lock) collected during the create call re-entered and hung the thread permanently — observed as a full `pytest tests/backends` run stopping forever (faulthandler: `release_payloads` ← `weakref.__call__` ← `create_client` ← `acquire_client`), and a real user-facing hang since device-resident runs leave payload finalizers pending.
   Fix: creation moved OUT of the state lock — `acquire_client` double-checks the cache (fast path under `_shared_clients_lock`), then takes the dedicated `_client_create_lock` (which NO finalizer path touches) and calls `plugin.create_client()` while holding no state lock, then inserts under the state lock after re-checking.
   `_client_create_lock` still serializes creation process-wide, because real GPU plugins grab a large BFC pool per client and abort the process when one cannot be allocated — semantics are unchanged, only the lock boundaries moved.
   `_shared_clients_lock` and `_initialized_lock` are now `RLock` as a second line of defence (a same-thread re-entry can never hang), and every plugin call (`create_client`, `client.close`, `buffer.close`) happens OUTSIDE the state lock.
   Locking discipline (binding for anything added here): **never hold a shared lock across a plugin call or anything that can run a Python finalizer**; a finalizer path takes ONLY `_shared_clients_lock`, for refcount bookkeeping only, and closes buffers/clients outside it.
   The stale-client identity guard keeps a late finalizer from decrementing a re-created client for the same path.
   Validated with a deterministic throwaway repro (a pending cyclic-referent finalizer + `gc.collect()` forced inside `create_client()`; 50/50 iterations complete, the pre-fix code hangs on iteration 1 with that exact stack) and an 8-thread × 200-cycle acquire/release exercise (1600 created = 1600 closed exactly once, 1197 finalizers provably firing inside the create path, empty cache at the end, ~6.9 s); no committed test pins it yet (sibling `tests/backends/`).
21. **The device→host readback is ADAPTER-OWNED — iree 3.13.0's `DeviceArray.to_host()` fast path is unusable on the Vulkan HAL.** Every host materialization of an iree buffer (`IreeDevicePayload.to_host()` / `__array__`, hence `.numpy()` on a cpu-kind output, `t.to(cpu)`, `evoxc.io.sink` and host-mode external-kernel boundaries) goes through `iree.py::_readback_device_array`, which the adapter owns end to end. Two paths, chosen by `_buffer_is_host_mappable` (HOST_VISIBLE memory AND `BufferUsage.MAPPING_SCOPED` allowed): a **zero-copy mapping** for llvm-cpu/`local-task` allocations, and otherwise an explicit **staging `queue_copy`** — a `HOST_LOCAL | DEVICE_VISIBLE` staging buffer (reused per thread, capped at 4 sizes), `queue_copy`, the shared query-first `_wait_copy_semaphore`, `map()` + copy out, mapping released. Nothing in the adapter calls `DeviceArray.to_host()` on an iree buffer any more (only a duck-typed payload that satisfies the PUBLIC protocol without exposing the HAL buffer view — a test fake, never a `DeviceArray` — performs its own `to_host()`).
   Why: on 3.13.0 the runtime's `_copy_to_host` prefers `allocator.import_host_allocation` whenever `query_buffer_compatibility` reports `IMPORTABLE`, and the Vulkan allocator then rejects the very buffer it advertised — `ValueError: could not import host allocation: …/iree/hal/drivers/vulkan/allocator.c:1985: INVALID_ARGUMENT; host allocation import pointer does not satisfy Vulkan minImportedHostPointerAlignment 4096` (reproduced with PLAIN iree and no evoxc in the process: `IMPORTABLE` set in the compatibility flags, import then fails). The adapter therefore does not use that primitive at all: no iree-version branch, no `try: to_host() except: …` fallback (both would silently redefine what a readback is), and an upstream fix costs this adapter nothing. Host-memory IMPORT stays unused even where it works (HIP/CUDA), because one implementation serving every kind is what keeps the vulkan leg honest.
   Cost (IREE 3.13.0 on this host, MI300X VF / lavapipe; runtime path measured on the same buffer): 96 B rocm 43.6 → 37.6 µs, 4 KB rocm 44.4 → 39.3 µs (the explicit path is FASTER on small buffers), 16 MB rocm 0.37 → 1.51 ms (the runtime path hands back the imported host array itself, so it pays the DMA only; the explicit path additionally pays map + copy-out ≈ 0.95 ms and, on the first call per size, a ~5 ms host-visible allocation that the thread-local reuse then amortizes), 16 MB vulkan unavailable → 2.44 ms, llvm-cpu 16 MB 0.001 → 0.003 ms (zero-copy mapping either way; the delta is two nanobind compatibility queries per call).
   Re-tested on this host against iree 3.13.0: **vulkan** (lavapipe, `VK_ICD_FILENAMES` unset, all 6 device-guarded tests in `tests/backends/test_iree_vulkan_device_resident.py` green), **rocm** and **llvm-cpu** (device-resident / same-device-loop / dlpack / hot-path / host-input suites green; int32 readbacks bit-exact vs the numpy backend on all three kinds, fp32 within the documented budget). **CUDA could not be re-exercised here (no NVIDIA GPU)**: it takes the same single code path (its buffers are `DEVICE_LOCAL`, hence the explicit staging branch), but the claim stays scoped to what was measured.
- **ROCm `while_loop`/`scan` unreliability (same upstream family as 8f):** shapes build and compile, but at run the HIP HAL aborts with a RAW `RuntimeError: … hip/event_semaphore.c:786: ABORTED … hal.fence.await` (raised from `entry(*buffers)`, never wrapped in `core.BackendError`), and the process often hangs at teardown. It is deterministic per graph shape, and the same graphs are llvm-cpu-clean. Failing shapes: a loop carry initialized from a graph CONSTANT (`enp.zeros` — also why `evoxc.scan` fails) and a multi-carry loop whose condition reads the float carry; working bit-exact: condition on an i64 counter with input-derived carries.
  **3.13.0 status:** all three formerly-failing shapes above ran 6/6 bit-exact vs numpy on this host (gfx942, ROCm 7.1), and the `non_dominate_rank` while shape compiled 10/10 per target with the default options (Known Issue 10) — the failure is no longer reproducible on 3.13, though it is reported rather than assumed fixed (no scale matrix was re-run); the one counted-loop layout 3.13 still rejects is the fully input-independent loop, a compile error rather than a crash (ROCm/HIP section above).

## Scale & module-shape facts (large graphs)

- **No program-size limit exists anywhere in the adapter compile path.** No graph-size / op-count / MLIR-text-size / recursion-depth guard in `iree.py` / `xla.py` / `tvm.py` `compile()`. The only numeric caps are unrelated: run-path/staging caches (`_STAGED_INPUT_CACHE_MAX = 64`, `_ROCM_SOURCE_CACHE_MAX = 16`, `_EXECUTE_SCAFFOLDING_MAX = 64`), the `_STAGED_INPUT_MAX_BYTES = 16 MB` staging *fallback* (never a rejection), and the `inline_portables` 1000-expansion fixpoint cap (`../inline.py:321`, fires only on a recursive portable).
- **Function count:** tvm requires EXACTLY ONE `func.func` (`tvm_util.precheck_module`, `BackendError` naming the count) and rejects a multi-operand `func.return` (the vendored importer keeps only the first output). iree compiles whatever the module contains, but `IreeExecutable._entry_function` (`iree.py:2140`) resolves `"main"` first and otherwise requires exactly ONE recorded entry function. xla records `entry_functions` in the artifact but never consults it — PJRT compiles/executes the module's own entry.
- **tvm's op whitelist lacks `stablehlo.iota`** (so exporter compositions built on iota — `diag`/`eye`/`linspace`/count-sort/`eigh` — hit the compile-time gate), plus no `gather`/`scatter`/`if`/`while`/`remainder`/`conv`/`reduce_window`/`sort`. An embedding-gather transformer forward is therefore rejected on tvm before translation.

## Dependency surface

- **xla adapter:** ZERO pip dependencies. ## Test strategy

Committed adapter tests live in the SIBLING `tests/backends/` (read-only from here — test-related writes escalate to the repo root).
`test_options_override.py` (96) + `tests/test_pipeline_options.py` (61) pin the options-override semantics (keys, defaults, conflict rules, env precedence, the exporter-forwarded lower options).
`test_opt_level.py` (53), `test_split_reduction.py` (67), `test_iree_split_reduction_parity.py` (127) and `test_while_init_rewrite.py` (4) pin the evoxc-defined option translations and the exporter options' effects.
`test_xla_device_resident.py` (9, fake plugin) pins xla device-resident staging (zero-staging same-device loop, run-boundary host-input `DeviceError`, load-device validation, payload/client lifecycle) plus the rank-0 staging guard; `test_pjrt_ctypes_plugin.py` (10) pins the ABI checks + shared-client refcount; `test_adapter_xla.py` / `test_adapter_iree.py` / `test_adapter_tvm.py` hold the per-adapter end-to-end numerics.
iree E2E suites: `test_iree_emitters_parity.py`, `test_iree_random_algorithms_parity.py`, `test_iree_eigh_diag_parity.py`, `test_iree_device_resident.py`, `test_iree_same_device_loop.py`, `test_iree_hotpath_validation.py`, `test_iree_llvm_cpu_host_inputs.py`, `test_iree_rocm_device_resident.py` (rocm-guarded via `_rocm_guard.py`), `test_external_call_iree.py` (39), `test_external_batched_iree.py` (6), `test_build_cache_iree.py`, `test_nsga2_xla_route.py`.
CPU only, pytest, numpy-only deps; GPU suites are GPU-guarded.
Per-file assertions, the throwaway fake-plugin/TVM probe recipes, and the pytest note (`-q` suppresses the final "N passed" line — use `-v` or `-o addopts=`) live in the skill `evoxc-compiler-adapter-recipes`.
**Coverage gap:** the per-call hot-path machinery (per-thread execute-scaffolding cache, prefilled output metadata + `_verify_metadata`, the `_XlaDeviceRunGroup` shared client reference) has no direct assertion — it is exercised by every device-resident run, and the SEMANTICS it must preserve are pinned (zero-staging same-device loop, shared-client refcount, host-input `core.DeviceError`, non-cpu `.numpy()` raising, explicit `to(cpu)` round-trips).
Known Issue 20 (the finalizer-inside-`create_client` deadlock) is validated only by throwaway scripts; the committed pin belongs in the sibling `tests/backends/test_xla_device_resident.py` §5 and must force GC inside the critical section — a stub plugin whose `create_client` runs `gc.collect()` with a PENDING finalizer (cyclic referent + `gc.disable()`), run in a subprocess so a regression fails on a timeout instead of hanging the test process, asserting that the state lock is NOT held and the create lock IS held at that point. Under the current explicit-placement semantics, GPU tests written for host-input semantics fail with the intentional `DeviceError` pin category — a root-level follow-up converts them to explicit placement.
The `synchronize()`/device-complete-event lifecycle also has NO committed test: it is validated only by throwaway stub scripts (stub plugin, plus a stubbed `_LoadedExecutable.execute` checking the slot array/`_check`-failure cleanup) and by the fake C plugin end-to-end, whose `execute` ignores the event contract (so `run` records the reason and `synchronize` raises). Proving that a REAL plugin returns a live `PJRT_Event*` and that awaiting it closes the measured dispatch-vs-completion gap needs a GPU run (root-level test follow-up).
ROCM-specific gaps: rocm × `external_call`/segment staging, direct thread-locality of the staging caches (pinned only indirectly), and a real-rocm `upload_tensor` on the `evoxc.io` worker thread (`prefetch`) are not covered.
