# evoxc/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends: each adapter consumes the SHARED StableHLO lowering from `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half — `check_available` (a no-op by default), `compile` (drive the external compiler on the MLIR text) and `load` (rebuild the executable, never recompiling).
Activation is register-on-first-use: `evoxc.backends.registry.get(name)` imports the module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`, so `import evoxc` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** evoxc depends directly on the ML compilers and the `jax` frontend appears NOWHERE in `evoxc/` — see "Dependency surface" below for the per-adapter dependency facts.

Status: all three implemented and validated — iree end to end on llvm-cpu, CUDA, ROCm/HIP and Vulkan/SPIR-V, xla against the fake test plugin and the real `jax_cuda12_pjrt`/`jax-rocm7-pjrt` plugins, tvm on `apache-tvm` 0.26 + jaxlib (CPU; ROCm compile-only); CUDA is unverified on the pin (no NVIDIA GPU here).
**Adopted pin: iree-base 3.13.0** (`>=3.13.0,<3.14`, Known Issue 5), on which every emitted flag still exists and no runtime API drifted.

## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`/`"xla"`/`"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), the singleton `<name>_backend`, and an idempotent `register()` — iree/tvm probe their pip dependency there and raise `core.BackendError` with an actionable message when it is missing, while xla registers UNCONDITIONALLY (its plugin is a per-call artifact, probed in `compile`/`load`).
Every compiler executable exposes `synchronize() -> None`: iree's is a documented no-op (`run` already blocks), while `XlaExecutable.synchronize` awaits + destroys the pending `PJRT_Event*` handles (Known Issue 17) and `close` destroys them without awaiting.
`register()` installs the module-level `upload_tensor` into the PER-BACKEND device-transfer slots (`core.register_backend_device_transfer_provider`) — iree for `"cuda"`/`"rocm"`/`"hip"`/`"vulkan"`, xla for every `_NON_CPU_KINDS` entry — so `Tensor.to(Device(kind, N))` resolves to the activated adapter and activation order can never clobber another backend's provider or the flat DEFAULT slot; `"vulkan"` is the ONE exception, `register()` ALSO filling the FLAT DEFAULT slot (nothing else serves a vulkan device).
Helpers and their seams (`xla_util.py`, `tvm_util.py`, `_pjrt_c_api.py`, `_mlir_bindings.py`, the docstring-only `__init__.py`): routing table below.

| iree/xla/tvm | run | — (none in v1) | — | non-empty run options → loud `BackendError` (by design) |

**Exporter-option plumbing:** no adapter overrides `lower()` — the shared `CompilerBackend.lower` validates keys and builds the export dict in `_exporter_options`, forwarding exactly `rng_bit_generator`, `sort_emission`, `while_init_rewrite`, `dot_precision`, `eigh_algorithm`, `split_reduction`, `split_reduction_non_exact` and `split_reduction_threshold` (the last is passed through unvalidated; the Writer validates it); `eigh_early_exit` remains `stablehlo.export`-only (passing it to `evoxc.lower(..., backend="iree")` raises the unknown-key `BackendError`).
A NEW exporter option needs three touches: add it to `_exporter_options`, declare it in each adapter's `KNOWN_OPTIONS["lower"]`, and consume it in the stablehlo Writer (sibling node).

## Intel GPU route and portability boundaries

Intel GPUs use the existing vendor-neutral IREE `vulkan-spirv` target and `Device("vulkan", index)` path, not a new Intel device kind.
`iree.py::_acquire_vulkan_device` filters nothing by vendor and `_resolve_compile_options` forwards arbitrary target profiles, so an Intel claim must check the enumerated device name and ICD provenance (lavapipe can occupy an index too).
On NixOS the Intel ANV ICD can live outside `/usr/share/vulkan/icd.d` and the loader may need an explicit library search path for wheel runtimes (recipe → `../../bench/intel_vulkan_findings.md`).
No other adapter serves Intel: xla has no SYCL/XPU kind (`_NON_CPU_KINDS` is cuda/rocm/hip) and an unrecognized PJRT platform is permissive in `_check_kind_served`, so loading an Intel plugin as CPU is no honest-placement workaround; tvm rejects non-CPU execution in `tvm.py::load`.

**No Intel Xe / Panther-Lake `vulkan_target` profile exists.** iree-base-compiler 3.13.0 accepts 68 profiles (AMD `gfx*`/`cdna*`/`rdna*`, NVIDIA `sm_*`/`ampere..volta`, ARM/Qualcomm `mali-*`/`valhall*`/`adreno`, `llvmpipe`, the `vp_android_baseline_2022` default; full list → notes).
42 Intel candidates were rejected — among them `pantherlake`/`alderlake`/`meteorlake`/`arc`/`xe`/`xehp`/`dg2`/`gen9`/`gen12`, the lake names inside `libIREECompiler.so` being LLVM CPU `-mcpu` names rather than Vulkan profiles — so an Intel GPU runs the default profile (full probe list → notes).

**Measured on this Intel iGPU** (f32, interleaved medians, loadavg 5.5–9.5): naming a GPU-class profile is worth ~3× on a compute-bound matmul and ~6× on a large rank-0 reduction, uniformly across every real-GPU profile tried, so the residual is the reduction's own structure (`split_reduction=False` on the default changes nothing; the opt-in `split_reduction_non_exact=True` DOES split a rank-0 float `sum` — 648.5 → 10.9 ms on 16.8M f32, see the option table — because the default only splits the exact classes). Per-shape tables → notes.

**An ACCEPTED profile is not a correctness contract**: `llvmpipe` and `adreno` both compiled and gave a correct matmul yet returned exactly 2× and 0.5× on that reduction, and `gfx942` compiles then fails at LOAD (`pipelines[0] requires subgroup size 64 outside device range [16, 32]`).
So evoxc never validates option values (this is the evidence), never sets a profile by default, and the profile stays a user opt-in that needs a correctness check on the actual device.
A compile failure with the option set therefore appends an attribution note to the unchanged `BackendError` preface (byte-identical message when unset): it names the option and value, says the INSTALLED iree-compile rejected the value (evoxc forwards it verbatim and validates nothing), points at `iree-compile --help` for the installed compiler's list, and states the no-Intel-profile limitation.

Validated on real Panther Lake hardware (IREE 3.13.0, Python 3.14.10, numpy 2.5.2, ANV Mesa 26.3.0): `/dev/dri/renderD128` is `0x8086:0b0a0`, enumeration returns exactly `Intel(R) Graphics (PTL) (Intel open-source Mesa driver Mesa 26.3.0)`, and the claims here are correctness/residency only — never general Intel coverage or model readiness.
`../../bench/probe_intel_vulkan.py` (`python -m evoxc.bench.probe_intel_vulkan`; not imported by evoxc, not collected by pytest; record `../../bench/intel_vulkan_findings.md`, which also holds the NixOS loader recipe — subprocess-only env, never an evoxc default) runs five same-device iterations of a three-output `(4,6)`×`(6,5)` graph with zero `asdevicearray` calls, checked against numpy, and the Vulkan suites (acquisition/device-resident/`vulkan_target`/hotpath) pass, with the staging-tier dispatch pinned device-free in `test_iree_vulkan_acquisition.py`.

## Adapter designs

### IREE (`iree.py`) — llvm-cpu, CUDA, ROCm/HIP, Vulkan/SPIR-V

- **compile:** `iree.compiler.compile_str(mlir_text, target_backends=…, input_type="stablehlo", extra_args=resolved_args)` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"` + `mlir_text`/`entry_functions`/`target_backends`); diagnostics re-raise as `core.BackendError`.
- **Defaults (minimal, overridable):** `--iree-input-demote-f64-to-f32=false` ALWAYS, `--iree-llvmcpu-target-cpu=generic` + `--iree-llvmcpu-link-embedded=false` on llvm-cpu only, plus the detected `--iree-rocm-target` on rocm; no tiling/codegen flag and no `--iree-opt-level` unless set.
- **load + artifact gate:** CPU takes `get_driver("local-task")` + `create_default_device()` + `load_vm_flatbuffer` (never `rt.system_setup(config=…)`); every GPU kind binds through `rt.Config(device=…)` + `VmModule.copy_buffer` + `load_vm_module`, because the driver-name form always creates the DEFAULT device. ONE table (`_EXPECTED_TARGET_BY_KIND`, shared by `IreeBackend.load` and `_load_segments`) requires the artifact's `target_backends` to include the kind's target; absent = `["llvm-cpu"]`, mismatch names both.
- **Placement/outputs — no implicit transfers:** a same-device input (`IreeDevicePayload` matching kind+index, or a raw `DeviceArray`) passes through with ZERO host round-trips; anything else is rejected on cuda/rocm/vulkan (pipeline `DeviceError` first, plus a defensive one for direct `exe.run`), except llvm-cpu, which takes host ndarrays via `rt.asdevicearray`. Outputs wrap their `DeviceArray` in the PUBLIC `IreeDevicePayload` on the run device, never auto-copied: a cpu-kind `.numpy()` copies through `_readback_device_array`, a NON-cpu `.numpy()` raises `DeviceError` (`.to(cpu).numpy()` or `torch.from_dlpack(t)`), and wrappers never alias/pin HAL buffers (Known Issue 21).
- **Per-call cost is leaf-driven and `synchronize()` is a documented no-op:** ONE cached `_input_plan` drives ONE fused metadata-validation pass mirroring `_build_buffers`'s branch order (that helper now serves `_IreeSegmentExecutable` only — mirror any change), so cost tracks leaf COUNT, never leaf size and no validation is skipped.
- **External kernels** are SPLIT at `lower()` (`../compiler.py::_lower_external_segments` + `../external_split.py`) into ordered SEGMENTS (one vmfb each — payload `stablehlo-segments`, artifact `iree-vmfb-segments`) plus a JSON-safe PLAN; each boundary dispatches through `evoxc.external.get_external_kernel_entry(name, "iree")` (unknown at run → `BackendError`). HOST mode (default) stages to host numpy and back, warning ONCE per executable; DEVICE-RESIDENT mode (`device_resident=True`, explicit per-backend slot only) receives device tensors DIRECTLY and may return device tensors / duck payloads / raw `DeviceArray`s / DLPack objects / numpy arrays, validated METADATA-ONLY, so device results feed the next segment with zero round-trips. A `torch.Tensor` round-trips zero-copy both ways (device id = the 0-based `core.Device.index`, kind→code cuda 2 / rocm·hip 10 / vulkan 7), its `__dlpack_device__` MUST match, no fence is added, and `copy=True`/a different `dl_device` refuse with `DeviceError`. MODE-AWARE restrictions (`BackendError`): no calls inside cond/while/scan bodies, ≥1 tensor operand, single-function graphs, HOST mode STATIC integer result dims (device mode allows symbolic dims such as vmap batch `Dim`s); kernels are PURE and segments keep `callback` order.
- **`upload_tensor`** takes only a HOST ndarray-backed `Device("cpu", 0)` source (else `DeviceError` suggesting `t.to(cpu).to(target)`), acquires the HAL device like `load` (honoring `EVOXC_IREE_RUNTIME_ARGS`), stages the copy through the kind-dispatched tiers with the keyword-only `one_shot=True` (FRESH destinations the returned tensor owns) and returns a fresh `core.Tensor(IreeDevicePayload(da, device))`; kind+index equality suffices across HAL instances.
- **Staging (`_staged_input`) — TWO TIERS PER GPU KIND (`cuda`/`rocm`/`vulkan`), one shared shape — serves ONLY host-mode external-kernel boundaries and `upload_tensor`; plain GPU runs never stage.** `device_kind` is a REQUIRED keyword-only `_build_buffers` dispatch to the cuda leg (`_PINNED_DIRECT_MAX_BYTES = 4 KB` mapped cutoff, host-local source + `queue_copy` above it), `_rocm_staged_input`, or `_vulkan_staged_input` (see "Vulkan / SPIR-V"), and ANY OTHER kind returns `None` BEFORE any buffer work (plain `rt.asdevicearray`). `_STAGED_INPUT_MAX_BYTES = 16 MB` gates cuda/rocm ONLY, and segment executables cache per `(input index, shape, dtype)` (`_STAGED_INPUT_CACHE_MAX = 64`), while `one_shot=True` (`upload_tensor`) never reads or writes that cache, so an upload can never alias the caller's host memory or a later upload. **The copy tier's semaphore wait is LOAD-BEARING** — the cuda HAL does not reliably stream-order `queue_copy` ahead of dispatches, so each call waits on a FRESH semaphore (reuse ABORTS), query-first, and the rocm/vulkan copy tiers take the same discipline. Anything a selected path cannot take (oversized, unmappable dtype, full cache, any failure) returns `None` with identical semantics; byte-level mechanics → notes (`## IREE — host→device staging tiers`).

### ROCm / HIP (`rocm`) — AMD GPU, device-resident

Same adapter and machinery as cuda, driven by `rt.get_driver("hip")`.
- **Compile:** `target_backends=["rocm"]`; IREE has no ROCm auto-detection, so the adapter injects a DETECTED `--iree-rocm-target=<arch>` (`amdgpu-arch`, then `rocm_agent_enumerator`; a same-NAME user flag wins, and an undetectable arch without one is an actionable `BackendError`). `Artifact.target == "rocm"`; a target/device mismatch is explicit.
- **1-BASED device ids:** `create_device(device_id=index + 1)` (id 0 raises). `Device("rocm", N)` and the alias `Device("hip", N)` both resolve — `_normalize_device_kind` folds `hip`→`rocm` for the driver call only, never rewriting the `core.Device` label.
- **Placement/staging — THREAD-LOCAL caches (REQUIRED):** ONE thread-local HAL device per `(index, runtime args)` (`_acquire_cached_rocm_device`, via the shared `_cached_hal_device` helper) plus a thread-local reusable `HOST_LOCAL|DEVICE_VISIBLE` source buffer keyed `(shape, dtype)` (`_ROCM_SOURCE_CACHE_MAX = 16`), then a per-call `queue_copy` with a fresh semaphore + query-first wait. Thread-locality is load-bearing — HAL devices are thread-affine (Known Issue 12), so a global cache would hand the `evoxc.io` worker a foreign device.
- **A fully input-independent counted `while` still fails to COMPILE on 3.13.0 — a clean compiler error, never a crash or wrong result:** constant carry + bound + constant-only body leave the `stablehlo.while` loop-invariant and `iree-compile` stops with `error: maximum iteration count exceeded in fixed point pipeline`; a body consuming an input, or a static-`int` bound, compiles and runs (pinned in `tests/backends/test_iree_rocm_while_scan.py`, which records the rejected layout).
- **Sugar:** `evoxc/pipeline.py::_resolve_backend_device` infers `target_backends` from the resolved device when neither the option nor `EVOXC_TARGET_BACKENDS` is set (`cuda`→`["cuda"]`, `rocm`/`hip`→`["rocm"]`, `cpu`→`["llvm-cpu"]`).

### Vulkan / SPIR-V (`vulkan`) — device-resident, queried device ids

Same adapter and machinery, driven by `get_driver("vulkan")`.
- **Compile:** `target_backends=["vulkan-spirv"]` (there is NO `--iree-hal-vulkan-target`); a vulkan-only target list is labelled `"vulkan"` in the artifact, a mixed list keeps the `"+"`-joined label, and the load gate accepts the artifact when `vulkan-spirv` is among its targets. No target flag by default; `vulkan_target` derives `--iree-vulkan-target=<profile>`, and explicit stage users must pass the target to `compile()` themselves.
- **Device ids are QUERIED HASHES, not ordinals:** `Device("vulkan", N)` selects the N-th entry of `driver.query_available_devices()` (per-process hash ids) and creates the device with `driver.create_device(info_dict)`, so the cuda/rocm `index + 1` convention raises `ValueError` (wrapped as `BackendError`); an out-of-range/negative index names the index and the enumerated count, and ZERO devices names the cause and points at `query_available_devices()`/`VK_ICD_FILENAMES`. The HAL device is created ONCE per `(kind, index, tuple(runtime_args))` in the THREAD-LOCAL cache, so `load()` and `upload_tensor` share ONE device.
- **Upload takes the SAME two-tier shape as cuda/rocm, via `_vulkan_staged_input`:** `_GPU_DEVICE_KINDS` including `vulkan` means "device-resident GPU-class kind" (that load path, the run branch, the placement gate) AND a staging tier. MAPPED tier up to `_VULKAN_PINNED_MAX_BYTES = 16 MiB`: a persistent `DEVICE_LOCAL|HOST_VISIBLE` buffer mapped once, host values written with ONE `np.copyto`, dispatches reading it DIRECTLY (no copy, no semaphore, no wait), GATED on the allocation reporting `HOST_COHERENT` because the 3.13 python HAL exposes no flush/invalidate primitive at all (`_vulkan_pinned_buffer` returns `None` without coherence and the copy tier takes over). COPY tier above it: the reusable THREAD-LOCAL `HOST_LOCAL|DEVICE_VISIBLE` `_host_source_buffer` (shared with the rocm path) plus a per-call `queue_copy` into a `DEVICE_LOCAL` destination, waiting on a FRESH semaphore through the shared query-first `_wait_copy_semaphore`. The 16 MiB cutoff sits on the measured FRESH-destination crossover (16 MB: 1.38 ms mapped vs 3.09 ms via a host source) while the cached mapped tier wins at every size. Per-size tables → notes (`## IREE — Vulkan host->device upload tiers (measured)`).
- **Readback never maps a GPU output.** `_readback_device_array` keeps the ZERO-COPY mapping only on a HOST-MEMORY HAL (`_hal_is_host_memory` keys on iree's printable HAL id — `"local-task"` on CPU, `"vulkan"`/`"cuda:0"`/`"hip:0"` on the GPU HALs; unknown/unprintable counts as DEVICE memory, the safe side) because a small vulkan output IS host-visible + `MAPPING_SCOPED` (memory_type 62 at 1 MB) and mapping it would hand out a `Device("cpu", 0)` array whose bytes still live in device memory — a placement lie and a live alias. A GPU readback first tries `_readback_into_fresh_host_array`: a `_HOST_IMPORT_ALIGNMENT = 4096`-aligned over-allocation imported with `allocator.import_host_allocation` when `query_buffer_compatibility` reports `IMPORTABLE`, so ONE `queue_copy` writes straight into the array handed back; else the per-thread staging buffer with a PERSISTENT coherent mapping (a per-call scoped map costs ~60 µs/MB, more than the copy it precedes; a non-coherent allocation still maps per call). The returned array is ALWAYS a fresh allocation, never the staging memory and never the device buffer. 1 MB is COST-NEUTRAL (launch-bound at a ~0.7 ms floor, which is why the ~100× faster direct map is refused); per-size tables → notes (`## IREE — Vulkan readback paths (measured)`). Host inputs raise `DeviceError`, `.numpy()` on a vulkan output raises, and same-device inputs/outputs take zero staging (`asdevicearray` = 0 warm).

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin (4-step discovery):** `plugin_path` (a compile AND load option, validated as an existing file) → env `EVOXC_PJRT_PLUGIN` → the fixed `_DEFAULT_PLUGIN_PATHS` → an INSTALLED JAX PJRT plugin under `jax_plugins/<platform>/<name>_plugin.so`, so a pip-installed plugin needs no path or env var. Candidates are probed for `GetPjRtApi`/`GetPjrtApi` (a failed dlopen is skipped, the FIRST exporter wins) and the outcome is cached per process; `jax`/`jaxlib` are NEVER imported. Opt-out, error text and load-bearing details: Known Issue 3.
- **Placement has no option channel (documented, deliberate):** `core.Tensor.to(device)` calls `provider(tensor, device)`, so `upload_tensor` cannot receive `plugin_path` — placement resolves the env var → the fixed paths → the installed-plugin scan, so a `plugin_path`-only workflow keeps discovery enabled or exports `EVOXC_PJRT_PLUGIN` (the failure is explicit; `build` forwards its options to `load`).
- **Device kinds:** serves `Device("cpu", 0)` (host-staged) and the device-resident accelerators `_NON_CPU_KINDS = ("cuda", "rocm", "hip")`, kind-agnostic (`"vulkan"` is NOT served). `_check_kind_served` rejects any other kind (`BackendError` containing "supports CPU") and, once the plugin platform is known, a kind it does not physically serve when listed in `_PLATFORM_KINDS` (an UNLISTED platform is PERMISSIVE); it runs on BOTH `load()` paths, so an accelerator plugin with `Device("cpu", 0)`/`device=None` is refused rather than mislabelled.
- **compile:** `GetPjRtApi()` (lowercase-t fallback) → **version gate** → the process-global shared `PJRT_Client` (ONE per plugin path) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` (MLIR text directly, no MLIR python bindings) → `PJRT_Executable_Serialize` → base64 payload. The artifact stays device-agnostic (`target="cpu"`); the device is chosen at `load()`. `dynamic_shapes=False`: symbolic dims are rejected at compile, recorded as `static_input_shapes`/`static_output_shapes` and enforced exactly at `run()`.
- **load/run:** CPU deserializes via `PJRT_Executable_DeserializeAndLoad` on the shared client (never recompiles), stages inputs with `PJRT_Client_BufferFromHostBuffer` (dense row-major numpy via `np.asarray`, contiguity forced only for ndim ≥ 1 — never `np.ascontiguousarray`, whose `ndmin=1` promotes 0-d arrays) and copies outputs with `PJRT_Buffer_ToHostBuffer`. Device-resident runs require an `XlaDevicePayload`-backed `core.Tensor` on the executable's device (host inputs raise `DeviceError`), pass payload buffers to `PJRT_LoadedExecutable_Execute` DIRECTLY and leave outputs on the device (non-cpu `.numpy()` raises; explicit `t.to(cpu).numpy()` round-trips); the seed is placed once via `t.to(Device(kind, N))` and each step's outputs feed back.
- **Device-resident `run` is ASYNCHRONOUS — `synchronize()` is the explicit completion boundary (Known Issue 17):** execute returns once work is ENQUEUED, so `run` commits the raw `PJRT_Event*` handle to `_pending_events` under `_events_lock` IMMEDIATELY after the execute returns, BEFORE the output checks (a late validation failure therefore cannot leak a handle); `synchronize()` swaps the list out under the lock, then awaits + destroys every popped handle OUTSIDE it, re-raising the FIRST error after the rest are cleaned up (reusable, idempotent, zero FFI when idle). A missing handle raises an explicit `BackendError` (never a silent completion claim) and `close()` destroys pending handles WITHOUT awaiting.
- **Per-call hot path:** ONE `_XlaRunPlan` carries everything static (arity, per-leaf `(dtype, shape)` contracts, output metadata, the run MODE), so `run` makes ONE plan-driven validation pass. Prefilled metadata is NEVER trusted blindly — `_verify_metadata()` re-queries and raises on a declared-vs-actual mismatch, on an executable's FIRST device-resident run and on every explicit `to_host()`; outputs share ONE client reference and ONE `weakref.finalize` (`_XlaDeviceRunGroup` → `release_payloads`).
- **Error contract:** every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message`, destroys it, raises `BackendError` naming the failing step and destroys every handle through its matching entry point.
- **`check_available()`** is the OPTION-LESS probe (bindings integrity + discovery + `GetPjRtApi` + version gate + a live client round-trip); `register()` never runs it (it registers UNCONDITIONALLY, because `plugin_path` is a per-call option) — the stages call `_load_plugin(options)` and raise `_PLUGIN_MISSING_MESSAGE`. `runtime_dependencies` adds numpy + the header commit + the plugin platform/version (no jaxlib).

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- **translate/build/run:** `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (present in 0.26; `from_mlir` does NOT exist) → `tvm.relax.vm_build.build(...)` → `VMExecutable`, run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())` resolving `"main"` first; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (no `tvm.nd` namespace in 0.26), outputs `.numpy()` → `core.Tensor`.
- **Seams:** ALL MLIR-binding access routes through `_mlir_bindings.py` (a standalone `mlir` package is a one-module swap); the translator's `jaxlib` imports work as-is, while its single `from jax._src.interpreters import mlir` import is satisfied by `sys.modules` shims injected at the top of BOTH `check_available()` and `ensure_compat()` (idempotent).
- **persist:** `VMExecutable.export_library(path)` → host `.so`, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — never recompiles.
- **Compatibility shim (REQUIRED):** the 0.26.0 translator targets the OLD jax mlir bindings; `ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` and float16 constant decoding), each restoring the assumed semantics (no computation changes).
- **Op coverage gate:** `SUPPORTED_STABLEHLO_OPS` is checked at compile (`BackendError` naming the op otherwise) — arithmetic, unary math, compare, select, bitwise/logical, convert, `broadcast_in_dim`, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), `dot_general`, constant. Rejected: control flow, gather/scatter, remainder, conv/reduce_window (the vendored handlers hardcode NHWC/HWIO — silently wrong for NCHW conv), multi-function and multi-output modules.
- **ROCm:** TVM is COMPILE-ONLY there — the `apache-tvm` 0.26.0 wheel is built `USE_ROCM=OFF`, so `tvm.runtime.device("rocm", 0).exist is False`; never include TVM in a ROCm run matrix.

## Constraints (binding)

- **Heavy-import rule:** `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports are limited to stdlib, `evoxc.core`, the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import evoxc` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`:** `import jax` / `from jax` is forbidden anywhere in `evoxc/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- **Errors:** capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never a silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`; shape mismatches `core.ShapeError`.
- **Staging never composes:** `load` never re-traces/lowers/compiles; device handles are never serialized.
- **Device kinds:** the tvm path is CPU only; iree accepts `Device("cpu"|"cuda"|"rocm"|"hip"|"vulkan", index)` and runs the non-cpu kinds device-resident, while xla accepts `Device("cpu"|"cuda"|"rocm"|"hip", index)` only (it does NOT serve `vulkan`). A kind the adapter does not support — or a kind the resolved plugin's platform does not physically serve — raises `core.BackendError`; a non-`Device` object raises `core.DeviceError`.
- **Files stay small and single-purpose:** per-adapter modules under ~1000 lines; long narratives/measurements go to `./PER-ADAPTER-NOTES.md`, never back into this file.

## Dispatch formation (merged-population graphs)

`dispatch_formation` is the iree compile-stage knob for `evoxc.batch_functions` merged GP-population graphs (semantics in the options row above).
It ships OPT-IN (`../../bench/dispatch_formation_findings.md` + probe + JSON, `--seed 0`, one chunk body per compile) because on iree 3.11 it takes 596 → 548 dispatches on the reference merged graph (2191 → 2021 ops, i.e. −5 % compile at pop 4000 and −7…−9 % WARM on rocm) while llvm-cpu is flat-to-worse, and it is enabled for rocm merged plans with the band cap kept at 15 — a ONE-binding margin under the 16-binding wall (Known Issue 19) — so fusion cannot push a dispatch past the limit.

## Custom IREE builds (`iree_compiler_module` / `iree_runtime_module`)

A custom-built IREE whose Python packages are not named `iree.compiler` / `iree.runtime` plugs in through the two module options (table above; the published packages are used when unset).
`evoxc.backends.register(iree_backend, replace=True)` (a plain import from `evoxc.backends.adapters.iree`, no heavy compiler import) then one `evoxc.build(fn, spec, backend="iree", iree_compiler_module="my_iree.compiler", iree_runtime_module="my_iree.runtime")`.
`register(..., replace=True)` does NOT probe the default packages, so this works on a host with no default `iree` install, while `registry.get("iree")` and the module-level `register()` still probe them and fail loudly with the `pip install evoxc[iree]` hint, by design.
Every run-path cache is module-aware (the DEFAULT module keeps the `(kind, index, runtime_args)` keys, a custom module's entries are prefixed with the module object), so two builds can never share a HAL device, staging buffer or dtype memo.

## Known Issues

1. **The exporter is a name-based emitter — no layout folding, transpose elimination, constant folding or operand reordering, and every adapter lowers the SAME exported text.** So `dot(transpose(k), x)` reaches the compiler as separate SSA ops whose fusing is the CONSUMER's call, a cross-backend gap is downstream of evoxc, and `dot_precision` is the only evoxc-side `dot` knob (full statement: `../CONTEXT.md`).
   Dynamic shapes are per-op and EXPORTER-gated (the capabilities table above), and mixed-dtype binaries with Python scalar constants can hit a dtype-mismatch parse error (use `evoxc.cast`) → `../stablehlo/CONTEXT.md`.

2. **IREE `rng_bit_generator`:** the MODERN two-result syntax is REQUIRED (no shape operand, enum WITHOUT the `RNG_ALG_` prefix); `THREE_FRY` legalizes bit-exact vs numpy with the key-first `[k0',k1',ctr0,ctr1]` layout, so `{"threefry2x32"}` is the capability AND the threefry default, while `PHILOX` fails legalization on llvm-cpu and cuda → inline expansion (`collective_broadcast` cannot legalize either; `random_permutation` fails on iree-cuda).

3. **XLA needs a PJRT plugin `.so` exporting `GetPjRtApi` — pip-installable, dlopen-ed, never imported.** Discovery is the four-step order above (`EVOXC_PJRT_PLUGIN_DISCOVERY=0` opts out of the installed-`jax_plugins` scan only), so `pip install jax-rocm7-pjrt`/`jax-cuda12-pjrt` needs no plumbing; the missing-plugin error names all four steps plus the source build.
   Load-bearing: the `GetPjRtApi`→`GetPjrtApi` casing fallback and ONE process-global refcounted `PJRT_Client` per plugin path (a fresh client per load ABORTs GPU plugins on BFC-pool exhaustion); the non-NULL default `CompileOptionsProto` is owned by the options table above. Native `rng_bit_generator` is OFF by design (the plugin's u64-state importer rejects evoxc's u32-word state), though the per-call option still forces it. Plugin-edge facts + the ROCm command-buffer recipe → notes.

4. **TVM gate + jaxlib requirement:** the op whitelist and module-shape gate reject at compile (see "TVM (`tvm.py`)" and "Scale & module-shape facts"). The vendored translator needs **jaxlib** at adapter runtime (via `_mlir_bindings`); `jax` is NEVER imported, and a missing jaxlib makes `check_available()` raise `BackendError` with a pip hint, never a raw `ModuleNotFoundError`.

5. **Version floors and extras (edits live at the repo root — escalate):** `iree`/`compilers` pin `iree-base-compiler` and `iree-base-runtime` `>=3.13.0,<3.14`, which must MATCH (Known Issue 10); `tvm` pins `apache-tvm>=0.26` + `jaxlib>=0.10,<0.11`; there is NO `xla` extra. Artifacts record the ACTUAL installed distributions in `runtime_dependencies`, and 3.11-era numbers stay attributed to 3.11.

6. **nanobind refleak noise:** `iree-base-runtime` prints "nanobind: leaked N instances …" at shutdown — upstream diagnostics, harmless, NOT a test failure.

7. **Mixed-install trap:** the old `iree-compiler`/`iree-runtime` and the new `iree-base-*` distributions share the `iree` namespace and must not coexist — a residual install fails at `load` with `ValueError: … required module features [Ch] are not available in this runtime configuration` even for a trivial graph, which `load()` wraps into a `BackendError` with the original as `__cause__`. Purge ALL `iree*` distributions (incl. mangled residue), reinstall only the base pair and verify `iree.compiler.version.VERSION`.

8. **IREE CUDA facts (iree 3.11; UNVERIFIED on 3.13 — no NVIDIA GPU here).**
   (8a) Device ids are 1-BASED (`device_id = index + 1`), and the CUDA HAL driver is compiled INTO the runtime wheel.
   (8b) cuda/rocm modules bind via `rt.Config` + `rt.VmModule.copy_buffer` + `rt.load_vm_module` (the driver-name form always creates the DEFAULT device).
   (8c) Default codegen is sm_60 PTX (`+ptx76`), JIT'd by the driver, no arch flag needed.
   (8d) A cuda artifact cannot run on the cpu driver or vice versa (no recorded `target_backends` ⇒ `["llvm-cpu"]`), which is the load+artifact gate's job.
   (8e) While-loop crashes are SHAPE-SPECIFIC (upstream): `while_fib` SEGFAULTS at invoke and `while_cond_combo` ABORTs (`cuda/event_semaphore.c:354 … hal.device.queue.dealloca`), both llvm-cpu-clean, so exclude `while_fib` from iree/cuda runs; the evox `non_dominate_rank` shape needs `while_init_rewrite` (default ON), and loops hitting the T2 broadcast-shape class or non-zero vector-constant inits stay broken on both targets.
   (8f) The cuda 2-operand-sort bufferization bug (`error: failed to bufferize op` for a `stablehlo.sort` of value + i64 iota) hits whenever the SORTED AXIS SIZE ≥ 32 (≤ 24 passes; 1-operand `sort` and llvm-cpu unaffected) — avoided by `sort_emission="auto"` (bit-exact count composition, no `stablehlo.sort` emitted).
   (8g) Constant-in-while hoisting fails on BOTH targets: `'util.global.load' op undefined global: @__hoisted_*` when a CONSTANT tensor is used inside a while body.

9. **IREE opt-level cuda limits (upstream codegen — do NOT fix in evoxc):** `--iree-opt-level=O2`/`O3` on cuda silently produce WRONG `eigh` eigenvalues (cyclic-Jacobi) while O0/O1/default and every llvm-cpu level are correct, and the full NSGA2 tell graph FAILS TO COMPILE at O2/O3 (crowding-distance scatter); both reproduce on raw `iree-compile` of evoxc-dumped MLIR.

10. **IREE while-loop graphs (upstream, below the adopted pin):** 3.10.0/3.11.0 SIGSEGV in `IREE::Stream::AffinityAnalysis::run()` on `stablehlo.while` with ≥3 loop-carried values + `select`, NONDETERMINISTICALLY (~85–100 % of runs, so one successful compile proves nothing; no flag fixes it), and 3.9.0 compiles them but its cuda runtime crashes. **On 3.13.0 the class is not upstream-blocked** (the `non_dominate_rank` shape and a `while` nested in `cond` run on llvm-cpu and rocm on DEFAULT options) — evidence `../../bench/iree313_rocm_findings.md` + its probe.

11. **iree 3.9.0's cuda SIGSEGV on SO step graphs predates the 3.11.0 record (Known Issue 8)** — notes (`## Known Issue 11`).

12. **CUDA HAL devices are thread-affine:** any allocating HAL op from a thread with no prior CUDA activity fails `CUDA_ERROR_INVALID_CONTEXT` (`to_host()`, `asdevicearray`, invoke output-alloc). Per-thread mitigation: create an own unused cuda HAL device on the same GPU (`create_device(device_id=idx+1)`), which makes the shared primary context current; llvm-cpu is exempt, and the cuda/rocm `evoxc.io` worker needs this on its own thread (`evoxc/io.py::_bootstrap_worker_context`).

13. **IREE GPU lowering of rank-0-result reductions is ONE sequential workgroup — the dominant cost of monitor-style graphs, with no compiler flag substitute.** On a 10000×100 evox SO-shaped step each `argmin`/`min`/i1 NaN-guard reduction lowers as one workgroup / one thread, so three scalar reductions eat ~95 % of per-step time; the EVOXC-side exact fix is `split_reduction` (default `True`, ~8–10×), and a keepdims `(n,1)` reshape does NOT help. Tables → notes.

14. **Small-scale results are LAUNCH-bound, so iree and xla look equal there, and the vulkan launch floor is iree's own.** On a 64K-element `a*b+a` the warm per-call cost is 0.17–0.21 ms (a 1-element identity graph costs the same), ~97 % of it inside iree (`entry(*buffers)` takes 0.204 ms of the 0.220 ms call) while the evoxc wrapper adds ~2–3 µs typical (≤16 µs worst — option validation, the memoized runtime-module lookup, the fused validate+buffer pass, output wrapping and a pooled 0.6 µs allocation).
A device-buffer OUTPUT pool is REJECTED on ownership (outputs escape as device-resident `IreeDevicePayload`, so reuse would alias a live output), as are `--iree-vulkan-dispatch-abi=bda|all`, a `vulkan_target` profile on this workload, caching the `(np, rt)` pair and skipping option validation when `options is None`; the gap to xla appears once Known Issue 13's per-step cost dominates, and the host-cost ladder → notes.

15. **Input COUNT is unbounded, but per-call cost is per leaf and the CPU paths re-stage every input:** no adapter caps arguments or caches an input across calls — llvm-cpu iree calls `rt.asdevicearray` once per HOST leaf, an xla `Device("cpu", 0)` run creates + closes one PJRT buffer per leaf, and a DEVICE-RESIDENT run passes payload buffers through. Cheap only when every input is device-resident and placed ONCE; anchors → notes.

18. **Large-graph compile time ≈ #executables × ~30 ms + ~0.3 ms/op — NOT text size and NOT opt level (llvm-cpu, adapter defaults):** merged population graphs scale linearly with the number of executables (median 16–19 ops each), not op count; `evoxc.lower` is ~1.3 s (mostly `stablehlo.export`) and `evoxc.compile` adds 0 ms over raw `compile_str`, while a 2000-op elementwise CHAIN fuses into ONE dispatch = 11.1 s vs 2.3 s with an `optimization_barrier` every 100 ops. Flags that do NOT help: `opt_level="O0"`/`"O1"` emit a BYTE-IDENTICAL vmfb, `--mlir-disable-threading` is 1.8× WORSE, and O2/O3 is broken for some cuda graphs (Known Issue 9); the levers that work are chunk-and-parallelize (near-linear) and `batch_functions(bands=32)` (−9 %). Tables → notes.

16. **IREE Vulkan runtime: software devices were hidden by NAME below 3.13, and the unset target profile caps large graphs AND compute-bound kernels.**
   (16a) 3.11 hard-codes a name denylist in `iree_hal_vulkan_is_device_visible()` (strstr `"llvmpipe"`) with NO override; 3.13.0 no longer hides lavapipe, so the renamed-ICD workaround (`VK_ICD_FILENAMES`) is a 3.11-and-earlier fallback.
   (16b) With `VK_ICD_FILENAMES` unset this host's loader dlopens the wedged radeon ICD and enumeration HANGS: wrap any Vulkan/DRM probe in `timeout`, and treat lavapipe's `deviceType=CPU` as a SOFTWARE device (provenance/correctness numbers only).
   (16d) **Default target profile** — with `vulkan_target` unset, codegen uses `vp_android_baseline_2022` (16384-byte workgroup memory, 128 threads) and the vmfb is byte-identical to any other unset build; 124M-class graphs exceed its budget at compile, and on a compute-bound kernel the default is the measured outlier (figures → "Intel GPU route"), with NO 3.13 profile targeting an Intel GPU.
   (16e) On the recorded MI300X host no GPU Vulkan execution is possible (RADV policy-rejects CDNA3, AMDVLK has no CDNA IP path, the amdgpu DRM device is wedged), so lavapipe was the software device there — archived evoxc-bench artefact `vulkan_findings.md`.
   Narrative → notes (`## Known Issue 16`).

17. **xla's DEVICE-RESIDENT `run()` is ASYNCHRONOUS (dispatch overlap is intentional) — `synchronize()` is the only explicit completion boundary.** `PJRT_LoadedExecutable_Execute` returns after ENQUEUE, so a bare timed loop measures only host dispatch (a Qwen3-8B fp32 forward loop under-reported wall-clock ~6–10×), and **ANY wall-clock xla measurement must time `run` + `synchronize()`** (or an explicit `.to(cpu)` readback). Numbers → notes.

18. **IREE/ROCm is 5–10× behind XLA/ROCm on large-weight whole-model graphs, and the cause is IREE ROCm codegen, not staging or dispatch overhead.** Weights are device buffers placed ONCE (`asdevicearray` = 0 in the warm loop), outputs stay device-resident, `evoxc_hf.run` does O(1) host work per call, and both adapters get BYTE-IDENTICAL StableHLO (669 881 bytes on `qwen3_8b` s32); the residual is per-dot kernel efficiency at GEMV-ish `M≪N` shapes (260–711 GB/s on iree vs 1.3–2.5 TB/s on xla, same fp32 MFMA lowering) plus a bimodal IREE HIP large-stream mode (3–7× slow in most processes), and `--iree-opt-data-tiling`, `O3`, `--iree-opt-aggressively-propagate-transposes` and hand-written tuning specs are NOT remedies. Full decomposition: archived evoxc-bench artefact `iree_rocm_gap_findings.md`.

19. **The HIP and CUDA HALs cap ONE dispatch at 16 bindings, and the check runs at executable LOAD, not compile.** The HAL rejects a dispatch above the 16-binding cap (CUDA identical, the CPU local ABI allows 64, Vulkan has no cap), counting that ONE dispatch's input + output buffers: CONSTANTS never consume it (they hoist into one pool binding), a fused region over 17+ tensors does, and nothing raises or splits it at compile (a 23-binding graph compiles with exit 0).
   **The driver is the `batch_functions` OUTPUT combine:** `combine_bands` emits ONE `stablehlo.concatenate` over all K per-band outputs, which IREE rewrites into a `flow.tensor.update` chain fused into ONE dispatch with one binding per piece (K=15 → 16 loads bit-exactly, K=16 raises), and the count is NOT monotone in K — so the rules are **K ≤ 15 unconditionally** and **band size ≥ 8** for large populations; llvm-cpu caps at **K=31** (K=40 → `binding count 41 > 32`). `iree.py::_raise_if_dispatch_binding_limit` (both load paths) raises an explicit `BackendError` naming the HAL cap, the observed count, the target and the remedies (fewer bands / `bands=None`, split the graph so no fused region consumes >16 tensors, or `target_backends=['llvm-cpu']`/`numpy`), since `iree-compile`'s HAL layout assignment decides it and evoxc cannot detect it at `lower()`. K tables → notes (`## Known Issue 19`).

20. **Never hold the xla shared-client lock across a plugin call (binding) — a finalizer can run there on the SAME thread.** A `weakref` finalizer runs wherever the GC pass freeing its referent happens to be, so releasing a payload inside `plugin.create_client()` re-entered the non-reentrant state lock and hung the thread. Creation therefore runs OUTSIDE the state lock: double-check under `_shared_clients_lock`, take the dedicated `_client_create_lock` (which NO finalizer path touches), call `create_client()` holding no state lock, then insert under the state lock after re-checking (the create lock still serializes creation process-wide — real GPU plugins grab a large BFC pool and abort when one cannot be allocated); both state locks are `RLock`.
   A finalizer path takes ONLY `_shared_clients_lock` for refcount bookkeeping, closes buffers/clients outside it and keeps a stale-client identity guard so a late finalizer cannot decrement a re-created client. No committed test pins it yet (post-mortem → notes).

21. **The device→host readback is ADAPTER-OWNED — iree 3.13.0's `DeviceArray.to_host()` fast path passes an arbitrary pointer the Vulkan HAL rejects.** Every host materialization of an iree buffer (`.numpy()` on a cpu-kind output, `t.to(cpu)`, `evoxc.io.sink`, host-mode external-kernel boundaries) goes through `iree.py::_readback_device_array`, which keeps the zero-copy mapping only on a HOST-MEMORY HAL and otherwise takes ONE aligned HAL copy ("Vulkan / SPIR-V").
`_copy_to_host` hands `import_host_allocation` whatever pointer it holds, so the Vulkan allocator rejects the very buffer it advertised (`allocator.c:1985`, `minImportedHostPointerAlignment 4096`) — hence no version branch and no `try: to_host() except:` fallback; the READBACK direction DOES use `import_host_allocation` (over-allocated and offset to the alignment) once that alignment is satisfied. Re-tested bit-exact on vulkan (Panther Lake ANV and lavapipe), rocm and llvm-cpu; costs → notes (`## Known Issue 21`).

22. **An unknown `stablehlo.custom_call` target PARSES but fails IREE legalization — IREE only legalizes its own known target set.** `custom_ops=True` means evoxc forwards the op verbatim, so the compiler's diagnostic is the verdict, surfaced inside the unchanged `core.BackendError`.
Measured on 3.13.0/llvm-cpu, it parses (IREE reads `call_target_name`) then dies in legalization with `error: failed to legalize operation 'stablehlo.custom_call' that was explicitly marked illegal` — a target-set verdict, not a syntax error; the workarounds are `evoxc.inline_stablehlo` or `evoxc.external_call`, never teaching IREE an arbitrary target.
- **ROCm `while_loop`/`scan` unreliability (same upstream family as 8e):** shapes build and compile, but on older iree releases the HIP HAL aborts at run with a RAW `RuntimeError: … hip/event_semaphore.c:786: ABORTED … hal.fence.await` (from `entry(*buffers)`, unwrapped) and the process often hangs at teardown — deterministic per shape, llvm-cpu-clean; the failing shapes were a loop carry initialized from a graph CONSTANT (`enp.zeros` — also why `evoxc.scan` failed) and a multi-carry loop whose condition reads the float carry. **3.13.0 status:** all three ran 6/6 bit-exact vs numpy here (gfx942, ROCm 7.1) and `non_dominate_rank` compiled 10/10 per target — no longer reproducible, reported rather than assumed fixed, and only the fully input-independent counted loop is still rejected, as a compile error.

## Scale & module-shape facts (large graphs)
- **No program-size limit exists anywhere in the adapter compile path** — no graph-size / op-count / MLIR-text-size / recursion-depth guard in `iree.py`/`xla.py`/`tvm.py` `compile()`. The only numeric caps are unrelated: staging/run caches (`_STAGED_INPUT_CACHE_MAX = 64`, `_ROCM_SOURCE_CACHE_MAX = 16`, `_EXECUTE_SCAFFOLDING_MAX = 64`), the staging ceilings (`_STAGED_INPUT_MAX_BYTES = 16 MB` cuda/rocm-only, `_VULKAN_PINNED_MAX_BYTES = 16 MiB` — both fall back to `asdevicearray`, never a rejection), and the `inline_portables` 1000-expansion fixpoint cap (`../inline.py:321`).
- **Function count:** tvm requires EXACTLY ONE `func.func` (`tvm_util.precheck_module`, `BackendError` naming the count) and rejects a multi-operand `func.return` (the vendored importer keeps only the first output). iree compiles whatever the module contains, but `IreeExecutable._entry_function` (`iree.py:2244`) resolves `"main"` first and otherwise requires exactly ONE recorded entry function. xla records `entry_functions` but never consults it.
- **tvm's op whitelist lacks `stablehlo.iota`** (so iota-based compositions — `diag`/`eye`/`linspace`/count-sort/`eigh` — hit the compile gate), so an embedding-gather transformer forward is rejected before translation.

## Native-host portability boundary
Only XLA drives a native C ABI directly — `_pjrt_c_api.py` defines the PJRT function table and `xla_util.py` calls it through ctypes — so a Rust host is a direct driver translation rather than a compiler rewrite, while IREE's native handoff is its VMFB bytes (its bindings stay Python) and TVM needs Python Relax translation/build plus a monkey-patched `StableHLOImporter` and jaxlib dialect registration, its exported `.so` being a VM-wrapped TVM module, not a tensor-function C ABI.
`IreeDevicePayload` exports/imports through IREE HAL capsules while `XlaDevicePayload` has readback but no DLPack — buffer residency does not imply cross-backend DLPack interchange.

## Dependency surface

No adapter fetches anything at run time (no HTTP client, no cache directory): the only `subprocess` call is `iree.py::_detect_rocm_target`'s local `amdgpu-arch`/`rocm_agent_enumerator` probe and the only filesystem write is `tvm_util`'s temp `.so`.
`_pjrt_c_api.HEADER_URL`/`HEADER_COMMIT`/`HEADER_SIZE_BYTES` are provenance METADATA only — never opened or fetched; the module is hand-written, stdlib-only ctypes.
So xla needs ZERO pip dependencies (no xla extra; the plugin `.so` is dlopen-ed, never imported) and tvm needs `apache-tvm` + `jaxlib`, the latter ONLY for its bundled LLVM MLIR python bindings behind the `_mlir_bindings` seam, with `check_available()` probing `jaxlib.mlir` under the `pip install evoxc[tvm]` hint — the binding rules are in "Constraints (binding)", Known Issues 3/4 and the options table.
**Legitimately long files — do not split without a plan:** `iree.py` (4355 lines) holds the whole iree adapter surface (custom-module resolvers, options/defaults, backend + executable + cached run plans, staging tiers, upload and readback, device acquisition, segments/external dispatch, `IreeDevicePayload`, `register()`), and `xla.py` (1479) + `xla_util.py` (1680) split xla the same way; all three are cohesive and tightly coupled.

## Test strategy
Committed adapter tests live in the SIBLING `tests/backends/` (read-only here; writes escalate to the repo root), whose own CONTEXT.md owns the per-file inventory.
Option semantics are pinned by `test_options_override.py` + `tests/test_pipeline_options.py` (keys, defaults, conflict rules, env precedence, the exporter-forwarded lower options), with `test_opt_level.py`, `test_split_reduction.py` + `test_iree_split_reduction_parity.py` and `test_while_init_rewrite.py` pinning the translations and effects.
`test_adapter_iree.py`/`test_adapter_xla.py`/`test_adapter_tvm.py` hold the per-adapter end-to-end numerics, `test_xla_device_resident.py` (fake plugin) the device-resident staging contract (zero-staging same-device loop, run-boundary host-input `DeviceError`, load-device validation, payload/client lifecycle, the rank-0 staging guard) and `test_pjrt_ctypes_plugin.py` the ABI checks + shared-client refcount; the iree E2E suites (`test_iree_*` emitters/random/device-resident/same-device-loop/hotpath/llvm-cpu/rocm, `test_external_call_iree.py`, `test_build_cache_iree.py`, `test_nsga2_xla_route.py`) pin the numerics per path, and `test_iree_vulkan_device_resident.py` is the only cover for the `t.to(vulkan)` upload tiers where a device enumerates.
**Coverage gaps:** the per-call hot-path machinery has no direct assertion (every device-resident run exercises it; the SEMANTICS are pinned), the `synchronize()`/event lifecycle none (throwaway stubs and the fake C plugin only — a real `PJRT_Event*` needs a GPU run), the `vulkan_target` attribution note none (it fires only inside a real iree-compile failure, verified by hand with `vulkan_target="xe"`), and rocm × `external_call`/segment staging, thread-locality of the staging caches and a real-rocm `upload_tensor` on the `evoxc.io` worker thread (`prefetch`) are unexercised.
Known Issue 20's committed pin belongs in the sibling `test_xla_device_resident.py` §5 and must force GC inside the critical section (a stub plugin running `gc.collect()` with a PENDING finalizer, in a subprocess so a regression fails on a timeout, asserting the state lock is NOT held and the create lock IS).
