# evoxc/backends/adapters — optional compiler adapters (IREE, XLA via PJRT, TVM)

## Intent

Pluggable compiler backends: each adapter consumes the SHARED StableHLO lowering from `CompilerBackend.lower` (`../compiler.py` — verify, capability pre-check, block-portable inlining, StableHLO export, Signature recording) and implements only the compiler-specific half — `check_available` (a no-op by default), `compile` (drive the external compiler on the MLIR text) and `load` (rebuild the executable, never recompiling).
Activation is register-on-first-use: `evoxc.backends.registry.get(name)` imports the module via `registry.OPTIONAL_ADAPTERS` and calls its `register()`, so `import evoxc` never imports an adapter or its compiler dependency.

**Dependency posture (binding):** evoxc depends directly on the ML compilers and the `jax` frontend appears NOWHERE in `evoxc/` — see "Dependency surface" below for the per-adapter dependency facts.

Status: all three implemented and validated — iree end to end on llvm-cpu, CUDA, ROCm/HIP and Vulkan/SPIR-V, xla against the fake test plugin and the real `jax_cuda12_pjrt`/`jax-rocm7-pjrt` plugins, tvm on `apache-tvm` 0.26 + jaxlib (CPU; ROCm compile-only).
**Adopted pin: iree-base 3.13.0** (`>=3.13.0,<3.14`, Known Issue 5) — re-run on it: every emitted flag still exists, none deprecated, no runtime API drifted, the default paths warning-free (Known Issues 2, 10, 13, 16, 21); CUDA unverified (no NVIDIA GPU).


## API Surface

Each adapter module (`iree.py`, `xla.py`, `tvm.py`) exposes `<Name>Backend` (a `CompilerBackend` subclass; names `"iree"`/`"xla"`/`"tvm"`), `<Name>Executable` (a `CompilerExecutable` subclass), the singleton `<name>_backend`, and an idempotent `register()` — iree/tvm probe their pip dependency there and raise `core.BackendError` with an actionable message when it is missing, while xla registers UNCONDITIONALLY (its plugin is a per-call artifact, probed in `compile`/`load`).
Every compiler executable exposes `synchronize() -> None`: iree's is a documented no-op (`run` already blocks; numpy's executable omits the method), while `XlaExecutable.synchronize` awaits + destroys the `PJRT_Event*` handles of every earlier DEVICE-RESIDENT `run` (which returns after ENQUEUE — Known Issue 17) and `close` destroys them without awaiting.
`register()` installs the module-level `upload_tensor` into the PER-BACKEND device-transfer slots (`core.register_backend_device_transfer_provider`) — iree for `"cuda"`/`"rocm"`/`"hip"`/`"vulkan"`, xla for every `_NON_CPU_KINDS` entry — so `Tensor.to(Device(kind, N))` resolves to the activated adapter and activation order can never clobber another backend's provider or the flat DEFAULT slot; `"vulkan"` is the ONE exception, `register()` ALSO filling the FLAT DEFAULT slot (nothing else serves a vulkan device).
Helpers: `xla_util.py` (PJRT driver), `tvm_util.py` (compat shim, jax `sys.modules` injection, op whitelist gate, translate/build/run/persist), `_pjrt_c_api.py` (vendored ctypes translation of the Apache-2.0 header — URL + commit recorded), `_mlir_bindings.py` (binding seam) and a docstring-only `__init__.py`.

The shared mechanism — per-stage `KNOWN_OPTIONS`, union-of-stages key validation, `validate_options`, `normalize_opt_level`/`normalize_bool_option`, the env table and explicit > env > default precedence — is specified in `../CONTEXT.md` ("Backend options override") and implemented in `../options.py` + `evoxc/pipeline_options.py`; this file owns only the per-adapter keys, defaults and conflict rules.

| iree | compile | `iree_compile_args` (list of flags) | `EVOXC_IREE_COMPILE_ARGS` | appended AFTER the defaults; a user flag whose NAME (text before `=`) collides with a default DROPS the default. | xla | compile AND load | `plugin_path` (str) | `EVOXC_PJRT_PLUGIN` | plugin discovery — the FIRST of four steps (then the env var, the fixed well-known paths, then the installed `jax_plugins/*/*.so` scan, which takes no option); honored at load too, so a persisted artifact loads without re-passing it |

Unset → `bytes.fromhex("1a0420012801")` (num_replicas=1/num_partitions=1 — a NULL one CHECK-crashes real plugins). Non-bytes → `core.BackendError` |
| xla | compile | `opt_level` (str\|int) | `EVOXC_OPT_LEVEL` | injected into `executable_build_options` (wire-format field 24) by `xla_util.set_opt_level`; a level already present in `xla_compile_options` wins unchanged; unset → bytes untouched |
| tvm | compile | `tvm_target` (str) | `EVOXC_TVM_TARGET` | default `"llvm"`; non-str → `core.BackendError` |

| tvm | compile | `opt_level` (str\|int) | `EVOXC_OPT_LEVEL` | forwarded to `tvm_util.build_vm_executable(..., opt_level=N)` as a version-adaptive kwarg. Unset → byte-identical default |
| iree/xla/tvm | lower | `rng_bit_generator` (bool\|collection) | — | reserved StableHLO-export override of the adapter's native-RNG capability set |
| all (iree/xla/tvm) | lower | `dot_precision` (str) | — | reserved exporter option `"DEFAULT"`\|`"HIGH"`\|`"HIGHEST"` (case-insensitive); default `"DEFAULT"` emits NO `precision_config` (byte-identical export); only `"HIGHEST"` disables XLA/ROCm's TF32-class fp32 `dot` (`"HIGH"` does not on this XLA version). iree/llvm-cpu and tvm/llvm results are BIT-IDENTICAL to `"DEFAULT"`. Invalid value → exporter `core.BackendError` |
| all (iree/xla/tvm) | lower | `eigh_algorithm` (str) | `EVOXC_EIGH_ALGORITHM` | `"jacobi"`\|`"jacobi_batched"` (case-insensitive, whitespace-stripped), default = `CompilerBackend.default_eigh_algorithm` = `"jacobi_batched"` (one odd-even round-robin round of mutually disjoint rotations per `stablehlo.while` iteration; `"jacobi"` = one (p,q) rotation). The Writer validates the value, so the env value is NOT raw pass-through. Batched is default: far faster, and it avoids an iree llvm-cpu compile crash at n ∈ {4,8,12,16} (→ notes) |
| all (iree/xla/tvm) | lower | `split_reduction` (bool) | `EVOXC_SPLIT_REDUCTION` | default `CompilerBackend.default_split_reduction = True`: two-stage split reductions for rank-0-result reductions (split the reduced axis into ≥2 non-unit factors, reduce per row, then the rows — numerically exact; min/argmin keep the first-occurrence tie-break). `False` emits the byte-identical single-stage text. Normalized by `options.normalize_bool_option` |
| iree | lower | `sort_emission` (str) | — | `"pair"`\|`"count"`\|`"auto"`; iree `default_sort_emission = "auto"` (= `"count"` iff the sorted-axis extent ≥ 32, since iree-cuda cannot bufferize that multi-operand `stablehlo.sort` and the count composition is bit-exact). The upgrade resolves at `lower()` time from the LOWER-stage options, so pass `target_backends` to `lower()` too (or use `evoxc.build`/`evaluate`) — a later `compile(..., target_backends=["cuda"])` keeps the pair emission. `CompilerBackend.default_sort_emission` is `"pair"` |
| iree | lower | `while_init_rewrite` (bool) | — | default ON at export (hardcoded in `../compiler.py::_exporter_options`, NOT a ClassVar) — the computed-zeros init rewrite that keeps `non_dominate_rank` compilable (Known Issue 8f) |
| iree/xla/tvm | run | — (none in v1) | — | non-empty run options → loud `BackendError` (by design) |

**Exporter-option plumbing:** no adapter overrides `lower()` — the shared `CompilerBackend.lower` validates keys and builds the export dict in `_exporter_options`, forwarding exactly `rng_bit_generator`, `sort_emission`, `while_init_rewrite`, `dot_precision`, `eigh_algorithm`, `split_reduction`; `eigh_early_exit`, `split_reduction_threshold` and `split_reduction_non_exact` are writer-only and NOT plumbed (passing them to `evoxc.lower(..., backend="iree")` raises the unknown-key `BackendError`).
Env spellings exist only for the backend-agnostic lower options `eigh_algorithm` (`EVOXC_EIGH_ALGORITHM`) and `split_reduction` (`EVOXC_SPLIT_REDUCTION`), registered for all three adapters at the lower stage.
A NEW exporter option needs three touches: add it to `_exporter_options`, declare it in each adapter's `KNOWN_OPTIONS["lower"]` (all three declare `rng_bit_generator`/`dot_precision`/`eigh_algorithm`/`split_reduction`; iree additionally `sort_emission`/`while_init_rewrite`), and consume it in the stablehlo Writer (sibling node).

## Intel GPU route and portability boundaries

Intel GPUs use the existing vendor-neutral IREE `vulkan-spirv` target and `Device("vulkan", index)` path, not a new Intel device kind.
`iree.py::_acquire_vulkan_device` filters nothing by vendor and `_resolve_compile_options` forwards arbitrary target profiles, so an Intel claim must check the enumerated device name and ICD provenance (lavapipe can occupy an index too).
On NixOS the Intel ANV ICD can live under `/run/opengl-driver/share/vulkan/icd.d/intel_icd.x86_64.json` rather than `/usr/share/vulkan/icd.d`, and the loader may need an explicit library search path for wheel runtimes.
No other adapter serves Intel: xla has no SYCL/XPU kind (`_NON_CPU_KINDS` is cuda/rocm/hip) and an unrecognized PJRT platform is permissive in `_check_kind_served`, so loading an Intel plugin as CPU is no honest-placement workaround; tvm rejects non-CPU execution in `tvm.py::load`.
Validated on real Panther Lake hardware (IREE 3.13.0, Python 3.14.10, numpy 2.5.2, ANV Mesa 26.3.0) — correctness/residency only, never a performance or general Intel-model claim: `/dev/dri/renderD128` is `0x8086:0b0a0` and enumeration returns exactly `Intel(R) Graphics (PTL) (Intel open-source Mesa driver Mesa 26.3.0)`.
`../../bench/probe_intel_vulkan.py` (`python -m evoxc.bench.probe_intel_vulkan`; not imported by evoxc, not collected by pytest; record `../../bench/intel_vulkan_findings.md`) runs five same-device iterations of a three-output `(4,6)`×`(6,5)` graph with zero `asdevicearray` calls, checked against numpy.
`test_iree_vulkan_device_resident.py`, `test_iree_vulkan_acquisition.py` and `test_vulkan_target.py` pass **101/101, no skips** under the same Intel-scoped environment; no adapter blocker and no environment/ICD/driver/pin/test was modified.
Reproduce from the repository root with these machine-local Nix store paths (re-discover after a Nix upgrade; never persist this environment globally):
```bash

LIBS=/nix/store/1l0a4cq8ahhpgwx0byq2zcsi316mlzm1-vulkan-loader-1.4.363.0/lib
```

## Adapter designs

### IREE (`iree.py`) — llvm-cpu, CUDA, ROCm/HIP, Vulkan/SPIR-V

- **compile:** `iree.compiler.compile_str(mlir_text, target_backends=…, input_type="stablehlo", extra_args=resolved_args)` → VM flatbuffer, base64'd into the payload (`format="iree-vmfb"` + `mlir_text`/`entry_functions`/`target_backends`); diagnostics re-raise as `core.BackendError`.
- **Defaults (minimal, overridable):** `--iree-input-demote-f64-to-f32=false` ALWAYS, `--iree-llvmcpu-target-cpu=generic` + `--iree-llvmcpu-link-embedded=false` on llvm-cpu only, plus the detected `--iree-rocm-target` on rocm; no tiling/codegen flag and no `--iree-opt-level` unless set.
- **load + artifact gate:** CPU takes `get_driver("local-task")` + `create_default_device()` + `load_vm_flatbuffer` (never `rt.system_setup(config=…)`); every GPU kind binds through `rt.Config(device=…)` + `VmModule.copy_buffer` + `load_vm_module`, because the driver-name form always creates the DEFAULT device. ONE table (`_EXPECTED_TARGET_BY_KIND`, shared by `IreeBackend.load` and `_load_segments`) requires the artifact's `target_backends` to include the kind's target; absent = `["llvm-cpu"]`, mismatch names both.
- **Placement/outputs — no implicit transfers:** a same-device input (`IreeDevicePayload` matching kind+index, or a raw `DeviceArray`) passes through with ZERO host round-trips; anything else is rejected on cuda/rocm/vulkan (pipeline `DeviceError` first, plus a defensive one for direct `exe.run`), except llvm-cpu, which takes host ndarrays via `rt.asdevicearray`. Outputs wrap their `DeviceArray` in the PUBLIC `IreeDevicePayload` on the run device, never auto-copied: a cpu-kind `.numpy()` copies through `_readback_device_array`, a NON-cpu `.numpy()` raises `DeviceError` (`.to(cpu).numpy()` or `torch.from_dlpack(t)`), and wrappers never alias/pin HAL buffers (Known Issue 21).
- **Per-call cost is leaf-driven and `synchronize()` is a documented no-op** (`run` already blocks): ONE cached `_input_plan` drives ONE fused metadata-validation pass mirroring `_build_buffers`'s branch order (that helper now serves `_IreeSegmentExecutable` only — mirror any change), so cost tracks leaf COUNT, never leaf size and no validation is skipped.
- **External kernels** are SPLIT at `lower()` (`../compiler.py::_lower_external_segments` + `../external_split.py`) into ordered SEGMENTS (one vmfb each — payload `stablehlo-segments`, artifact `iree-vmfb-segments`) plus a JSON-safe PLAN; each boundary dispatches through `evoxc.external.get_external_kernel_entry(name, "iree")` (unknown at run → `BackendError`). HOST mode (default) stages to host numpy and back, warning ONCE per executable; DEVICE-RESIDENT mode (`device_resident=True`, explicit per-backend slot only) receives device tensors DIRECTLY and may return device tensors / duck payloads / raw `DeviceArray`s / DLPack objects / numpy arrays, validated METADATA-ONLY, so device results feed the next segment with zero round-trips. A `torch.Tensor` round-trips zero-copy both ways (device id = the 0-based `core.Device.index`, kind→code cuda 2 / rocm·hip 10 / vulkan 7), its `__dlpack_device__` MUST match, no fence is added, and `copy=True`/a different `dl_device` refuse with `DeviceError`. MODE-AWARE restrictions (`BackendError`): no calls inside cond/while/scan bodies, ≥1 tensor operand, single-function graphs, HOST mode STATIC integer result dims (device mode allows symbolic dims such as vmap batch `Dim`s); kernels are PURE and segments keep `callback` order.
- **`upload_tensor`** takes only a HOST ndarray-backed `Device("cpu", 0)` source (else `DeviceError` suggesting `t.to(cpu).to(target)`), acquires the HAL device like `load` (honoring `EVOXC_IREE_RUNTIME_ARGS`), makes ONE copy and returns a fresh `core.Tensor(IreeDevicePayload(da, device))`; kind+index equality suffices across HAL instances.
- **Staging (`_staged_input`) — TWO TIERS, cuda/rocm ONLY — serves ONLY host-mode external-kernel boundaries and `upload_tensor`; plain GPU runs never stage.** Split at `_PINNED_DIRECT_MAX_BYTES = 4 * 1024`: **≤ 4 KB** writes a persistent mapped `DEVICE_LOCAL | HOST_VISIBLE` buffer with one `np.copyto`; **> 4 KB** `queue_copy`s per call from a persistent `HOST_LOCAL | DEVICE_VISIBLE` source into a persistent `DEVICE_LOCAL` buffer. `device_kind` is a REQUIRED keyword-only `_build_buffers` dispatch: cuda the tiers, rocm the host-local source + `queue_copy`, vulkan `None` BEFORE any buffer work; buffers cache per `(input index, shape, dtype)` (`_STAGED_INPUT_CACHE_MAX = 64`), > 16 MB / unmappable dtypes / overflow fall back to `asdevicearray`. **The tier-2 semaphore wait is LOAD-BEARING** — the cuda HAL does not reliably stream-order `queue_copy` ahead of dispatches, so each call waits on a FRESH semaphore (reuse ABORTS), query-first.

### ROCm / HIP (`rocm`) — AMD GPU, device-resident

Same adapter and machinery as cuda, driven by `rt.get_driver("hip")`.
- **Compile:** `target_backends=["rocm"]`; IREE has no ROCm auto-detection, so the adapter injects a DETECTED `--iree-rocm-target=<arch>` (`amdgpu-arch`, then `rocm_agent_enumerator`; a same-NAME user flag wins, and an undetectable arch without one is an actionable `BackendError`). `Artifact.target == "rocm"`; a target/device mismatch is explicit.
- **1-BASED device ids:** `create_device(device_id=index + 1)` (id 0 raises). `Device("rocm", N)` and the alias `Device("hip", N)` both resolve — `_normalize_device_kind` folds `hip`→`rocm` for the driver call only, never rewriting the `core.Device` label.
- **Placement/staging — THREAD-LOCAL caches (REQUIRED):** ONE thread-local HAL device per `(index, runtime args)` (`_acquire_cached_rocm_device`, via the shared `_cached_hal_device` helper) plus a thread-local reusable `HOST_LOCAL|DEVICE_VISIBLE` source buffer keyed `(shape, dtype)` (`_ROCM_SOURCE_CACHE_MAX = 16`), then a per-call `queue_copy` with a fresh semaphore + query-first wait. Thread-locality is load-bearing — HAL devices are thread-affine (Known Issue 12), so a global cache would hand the `evoxc.io` worker a foreign device.
- **A fully input-independent counted `while` still fails to COMPILE on 3.13.0 — a clean compiler error, never a crash or wrong result:** constant carry + bound + constant-only body leave the `stablehlo.while` loop-invariant and `iree-compile` stops with `error: maximum iteration count exceeded in fixed point pipeline`; a body consuming an input, or a static-`int` bound, compiles and runs (pinned in `tests/backends/test_iree_rocm_while_scan.py`, which records the rejected layout, and `test_while_init_rewrite.py`).
- **Sugar:** `evoxc/pipeline.py::_resolve_backend_device` infers `target_backends` from the resolved device when neither the option nor `EVOXC_TARGET_BACKENDS` is set (`cuda`→`["cuda"]`, `rocm`/`hip`→`["rocm"]`, `cpu`→`["llvm-cpu"]`).

### Vulkan / SPIR-V (`vulkan`) — device-resident, queried device ids

Same adapter and machinery, driven by `get_driver("vulkan")`.
- **Compile:** `target_backends=["vulkan-spirv"]` (there is NO `--iree-hal-vulkan-target`); a vulkan-only target list is labelled `"vulkan"` in the artifact, a mixed list keeps the `"+"`-joined label, and the load gate accepts the artifact when `vulkan-spirv` is among its targets. No target flag by default; `vulkan_target` derives `--iree-vulkan-target=<profile>`, and explicit stage users must pass the target to `compile()` themselves.
- **Device ids are QUERIED HASHES, not ordinals:** `Device("vulkan", N)` selects the N-th entry of `driver.query_available_devices()` (per-process hash ids) and creates the device with `driver.create_device(info_dict)`, so the cuda/rocm `index + 1` convention raises `ValueError` (wrapped as `BackendError`); an out-of-range/negative index names the index and the enumerated count, and ZERO devices names the cause and points at `query_available_devices()`/`VK_ICD_FILENAMES`. The HAL device is created ONCE per `(kind, index, tuple(runtime_args))` in the THREAD-LOCAL cache, so `load()` and `upload_tensor` share ONE device.
- **Staging and residency are the cuda/rocm ones minus the tiers:** `_GPU_DEVICE_KINDS` including `vulkan` means "device-resident GPU-class kind" (that load path, the run branch, the placement gate) — NOT "takes the cuda staging tier": `_staged_input` returns `None` for vulkan, so uploads and segment boundaries take the plain `rt.asdevicearray` host→device copy. Host inputs raise `DeviceError`, `.numpy()` on a vulkan output raises, readback is explicit `.to(cpu).numpy()`, and same-device inputs/outputs take zero staging (`asdevicearray` = 0 warm); a download goes payload host copy → `_readback_device_array`'s staging `queue_copy` (Known Issue 21).

### XLA via the PJRT C API (`xla.py`) — no jaxlib

- **Plugin (4-step discovery):** `plugin_path` (a compile AND load option, validated as an existing file) → env `EVOXC_PJRT_PLUGIN` → the fixed `_DEFAULT_PLUGIN_PATHS` → an INSTALLED JAX PJRT plugin under `jax_plugins/<platform>/<name>_plugin.so`, so a pip-installed plugin needs no path or env var. Candidates are probed for `GetPjRtApi`/`GetPjrtApi` (a failed dlopen is skipped, the FIRST exporter wins) and the outcome is cached per process; `jax`/`jaxlib` are NEVER imported. Opt-out `EVOXC_PJRT_PLUGIN_DISCOVERY` (`0`/`false`/`no`/`off`, empty = unset, other spellings a loud `BackendError`) skips ONLY that scan; nothing found → `BackendError` listing all four steps, the pip-installable plugins and the source build.
- **Placement has no option channel (documented, deliberate):** `core.Tensor.to(device)` calls `provider(tensor, device)`, so `upload_tensor` cannot receive `plugin_path` — placement resolves the env var → the fixed paths → the installed-plugin scan, so a `plugin_path`-only workflow keeps discovery enabled or exports `EVOXC_PJRT_PLUGIN` (the failure is explicit; `build` forwards its options to `load`).
- **Device kinds:** serves `Device("cpu", 0)` (host-staged) and the device-resident accelerators `_NON_CPU_KINDS = ("cuda", "rocm", "hip")`, kind-agnostic (`"vulkan"` is NOT served). `_check_kind_served` rejects any other kind (`BackendError` containing "supports CPU") and, once the plugin platform is known, a kind it does not physically serve when listed in `_PLATFORM_KINDS` (an UNLISTED platform is PERMISSIVE); it runs on BOTH `load()` paths, so an accelerator plugin with `Device("cpu", 0)`/`device=None` is refused rather than mislabelled.
- **compile:** `GetPjRtApi()` (lowercase-t fallback) → **version gate** → the process-global shared `PJRT_Client` (ONE per plugin path) → `PJRT_Client_Compile` with `PJRT_Program{code=mlir_text, format="mlir"}` (MLIR text directly, no MLIR python bindings) → `PJRT_Executable_Serialize` → base64 payload. The artifact stays device-agnostic (`target="cpu"`); the device is chosen at `load()`. `dynamic_shapes=False`: symbolic dims are rejected at compile, recorded as `static_input_shapes`/`static_output_shapes` and enforced exactly at `run()`.
- **load/run:** CPU deserializes via `PJRT_Executable_DeserializeAndLoad` on the shared client (never recompiles), stages inputs with `PJRT_Client_BufferFromHostBuffer` (dense row-major numpy via `np.asarray`, contiguity forced only for ndim ≥ 1 — never `np.ascontiguousarray`, whose `ndmin=1` promotes 0-d arrays) and copies outputs with `PJRT_Buffer_ToHostBuffer`. Device-resident runs require an `XlaDevicePayload`-backed `core.Tensor` on the executable's device (host inputs raise `DeviceError`), pass payload buffers to `PJRT_LoadedExecutable_Execute` DIRECTLY and leave outputs on the device (non-cpu `.numpy()` raises; explicit `t.to(cpu).numpy()` round-trips); the seed is placed once via `t.to(Device(kind, N))` and each step's outputs feed back.
- **Device-resident `run` is ASYNCHRONOUS — `synchronize()` is the explicit completion boundary (Known Issue 17):** execute returns once work is ENQUEUED, so `run` commits the raw `PJRT_Event*` handle to `_pending_events` under `_events_lock` IMMEDIATELY after the execute returns, BEFORE the output checks (a late validation failure therefore cannot leak a handle); `synchronize()` swaps the list out under the lock, then awaits + destroys every popped handle OUTSIDE it, re-raising the FIRST error after the rest are cleaned up (reusable, idempotent, zero FFI when idle). A missing handle raises an explicit `BackendError` (never a silent completion claim) and `close()` destroys pending handles WITHOUT awaiting.
- **Per-call hot path:** ONE `_XlaRunPlan` carries everything static (arity, per-leaf `(dtype, shape)` contracts, output metadata, the run MODE), so `run` makes ONE plan-driven validation pass. Prefilled metadata is NEVER trusted blindly — `_verify_metadata()` re-queries and raises on a declared-vs-actual mismatch, on an executable's FIRST device-resident run and on every explicit `to_host()`; outputs share ONE client reference and ONE `weakref.finalize` (`_XlaDeviceRunGroup` → `release_payloads`).
- **Error contract:** every PJRT call returns `PJRT_Error*` (NULL = success); the driver checks EVERY call, extracts `PJRT_Error_Message`, destroys it, raises `BackendError` naming the failing step and destroys every handle through its matching entry point.
- **`check_available()`** is the OPTION-LESS probe (bindings integrity + discovery + `GetPjRtApi` + version gate + a live client round-trip); `register()` never runs it (it registers UNCONDITIONALLY, because `plugin_path` is a per-call option) — the stages call `_load_plugin(options)` and raise `_PLUGIN_MISSING_MESSAGE`. `runtime_dependencies` adds numpy + the header commit + the plugin platform/version (no jaxlib).

### TVM (`tvm.py`) — jax-free, jaxlib MLIR bindings only

- **translate/build/run:** `tvm.relax.frontend.stablehlo.from_stablehlo(mlir_text)` (present in 0.26; `from_mlir` does NOT exist) → `tvm.relax.vm_build.build(...)` → `VMExecutable`, run via `tvm.runtime.vm.VirtualMachine(ex, tvm.runtime.cpu())` resolving `"main"` first; inputs `tvm.runtime.tensor(np_array, tvm.runtime.cpu())` (no `tvm.nd` namespace in 0.26), outputs `.numpy()` → `core.Tensor`.
- **Seams:** ALL MLIR-binding access routes through `_mlir_bindings.py` (a standalone `mlir` package is a one-module swap); the translator's `jaxlib` imports work as-is, while its single `from jax._src.interpreters import mlir` import is satisfied by `sys.modules` shims injected at the top of BOTH `check_available()` and `ensure_compat()` (idempotent).
- **persist:** `VMExecutable.export_library(path)` → host `.so`, base64'd into the payload (`format="tvm-vm-library"`); load decodes to a temp file and `tvm.runtime.load_module(path)` — never recompiles.
- **Compatibility shim (REQUIRED):** the 0.26.0 translator targets the OLD jax mlir bindings; `ensure_compat()` patches five gaps (type-check classmethods, OpView/Operation key normalization, `broadcast_to` ShapeExpr, `DenseI64ArrayAttr` and float16 constant decoding), each restoring the assumed semantics (no computation changes).
- **Op coverage gate:** `SUPPORTED_STABLEHLO_OPS` is checked at compile (`BackendError` naming the op otherwise) — arithmetic, unary math, compare, select, bitwise/logical, convert, `broadcast_in_dim`, reshape, transpose, concatenate, slice (unit strides), pad (zero interior), reduce (add/max/min/mul), `dot_general`, constant. Rejected: control flow, gather/scatter, remainder, conv/reduce_window (the vendored handlers hardcode NHWC/HWIO — silently wrong for NCHW conv), multi-function and multi-output modules.
- **ROCm:** TVM is COMPILE-ONLY there — the `apache-tvm` 0.26.0 wheel is built `USE_ROCM=OFF`, so `tvm.runtime.device("rocm", 0).exist is False`; never include TVM in a ROCm run matrix.

## Constraints (binding)

- **Heavy-import rule:** `iree`/`jaxlib`/`tvm` imports live ONLY inside function bodies; top-level imports are limited to stdlib, `evoxc.core`, the `..compiler`/`..program`/`..registry` siblings (plus this package's `_pjrt_c_api.py`/`_mlir_bindings.py` for the xla/tvm adapters). Verified: `import evoxc` leaves `sys.modules` free of iree/jax/jaxlib/tvm.
- **No `jax`:** `import jax` / `from jax` is forbidden anywhere in `evoxc/` (grep-proof; the TVM shim satisfies the vendored translator's `jax._src` import). `jaxlib` may appear ONLY inside function bodies, ideally only via `_mlir_bindings.py`, and NEVER in the xla adapter (`_pjrt_c_api.py`/`xla_util.py`/`xla.py` are jaxlib-free).
- **Errors:** capability violations and compiler/translator failures raise `core.BackendError` naming the op/feature — never a silent fallback to numpy or partial semantics; load-time mismatches raise `core.PersistenceError`; dtype mismatches `core.DTypeError`; shape mismatches `core.ShapeError`.
- **Staging never composes:** `load` never re-traces/lowers/compiles; device handles are never serialized.
- **Device kinds:** the tvm path is CPU only; iree accepts `Device("cpu"|"cuda"|"rocm"|"hip"|"vulkan", index)` and runs the non-cpu kinds device-resident, while xla accepts `Device("cpu"|"cuda"|"rocm"|"hip", index)` only (it does NOT serve `vulkan`). A kind the adapter does not support — or a kind the resolved plugin's platform does not physically serve — raises `core.BackendError`; a non-`Device` object raises `core.DeviceError`.
- **Files stay small and single-purpose:** per-adapter modules under ~1000 lines; long narratives/measurements go to `./PER-ADAPTER-NOTES.md`, never back into this file.

`dispatch_formation` is the iree compile-stage knob for `evoxc.batch_functions` merged GP-population graphs (evidence `../../bench/dispatch_formation_findings.md` + `../../bench/probe_dispatch_formation.py` + `../../bench/dispatch_formation_results.json`, `--seed 0`; the probe compiles ONE chunk body per compile, as the downstream engine does).

## Known Issues

1. **The exporter is a name-based emitter — no layout folding, transpose elimination, constant folding or operand reordering.** It never reads `defining_op`, so `dot(transpose(k), x)` reaches the compiler as separate SSA ops and fusing it is the CONSUMER's call; every adapter lowers the SAME text, so a cross-backend gap is downstream of evoxc, and `dot_precision` is the only evoxc-side `dot` knob.
   Dynamic shapes are per-op and EXPORTER-gated (symbolic `reshape`/`conv`/`slice`/`pad` and unemittable `dot` batch merges → `core.BackendError` at `lower()`); mixed-dtype binaries with Python scalar constants can hit a dtype-mismatch parse error (use `evoxc.cast`), and `stablehlo.add` on i1 is XOR vs numpy bool `+` = OR → `../stablehlo/CONTEXT.md`.

2. **IREE `rng_bit_generator`:** the MODERN two-result syntax is REQUIRED (no shape operand, enum WITHOUT the `RNG_ALG_` prefix) and the shape-operand form is rejected. `THREE_FRY` legalizes bit-exact vs numpy with the key-first `[k0',k1',ctr0,ctr1]` layout, so `{"threefry2x32"}` is the capability AND the threefry default; `PHILOX` fails legalization on llvm-cpu and cuda → inline expansion; `collective_broadcast` cannot legalize; u32/u64 excluded; `random_permutation` fails on iree-cuda. Pinned by `tests/backends/test_iree_random_algorithms_parity.py`.

3. **XLA needs a PJRT plugin `.so` exporting `GetPjRtApi` — pip-installable, dlopen-ed, never imported.** Discovery is the four-step order above (`EVOXC_PJRT_PLUGIN_DISCOVERY=0` opts out of the installed-`jax_plugins` scan only), so `pip install jax-rocm7-pjrt`/`jax-cuda12-pjrt` needs no plumbing; the missing-plugin error names all four steps plus the source build, and a `_PLATFORM_KINDS` platform must physically serve the kind on BOTH `load()` paths.
   Load-bearing: the `GetPjRtApi`→`GetPjrtApi` casing fallback, a NON-NULL default `CompileOptionsProto` (a NULL one CHECK-crashes real plugins) and ONE process-global refcounted `PJRT_Client` per plugin path (a fresh client per load ABORTs GPU plugins on BFC-pool exhaustion). Native `rng_bit_generator` is OFF by design — the plugin's u64-state importer rejects evoxc's u32-word state and XLA's ciphers differ, though the per-call option still forces it. Plugin-edge facts + the ROCm command-buffer recipe → notes.

4. **TVM gate + jaxlib requirement:** control flow, conv, gather/scatter, remainder, multi-function and multi-output modules are rejected at compile. The vendored translator needs **jaxlib** at adapter runtime (via `_mlir_bindings`); `jax` is NEVER imported, and a missing jaxlib makes `check_available()` raise `BackendError` with a pip hint, never a raw `ModuleNotFoundError`.

5. **Version floors and extras (edits live at the repo root — escalate):** `iree`/`compilers` pin `iree-base-compiler>=3.13.0,<3.14` and `iree-base-runtime>=3.13.0,<3.14`, which must MATCH (Known Issue 10); `tvm` pins `apache-tvm>=0.26` + `jaxlib>=0.10,<0.11`; there is NO `xla` extra. Artifacts record the ACTUAL installed distributions in `runtime_dependencies`; 3.11-era numbers stay attributed to 3.11.

6. **nanobind refleak noise:** `iree-base-runtime` prints "nanobind: leaked N instances/functions/keep_alive records …" at shutdown — upstream diagnostics, harmless, NOT a test failure.

7. **Mixed-install trap:** the old `iree-compiler`/`iree-runtime` and the new `iree-base-*` distributions share the `iree` namespace and must not coexist — a residual install fails at `load` with `ValueError: … required module features [Ch] are not available in this runtime configuration` even for a trivial graph. Purge ALL `iree*` distributions (incl. mangled residue), reinstall only the base pair, verify `iree.compiler.version.VERSION`; `load()` wraps that `ValueError` into a `BackendError` with the original as `__cause__`.

15. **Input COUNT is unbounded, but per-call cost is per leaf and the CPU paths re-stage every input:** no adapter caps arguments or caches an input across calls — llvm-cpu iree calls `rt.asdevicearray` once per HOST leaf, an xla `Device("cpu", 0)` run creates + closes one PJRT buffer per leaf, a DEVICE-RESIDENT run passes payload buffers through. Cheap only when every input is device-resident and placed ONCE; anchors → notes (`## Known Issue 15`).

18. **Large-graph compile time ≈ #executables × ~30 ms + ~0.3 ms/op — NOT text size and NOT opt level (measured, llvm-cpu, adapter defaults):** merged population graphs (shape `(N,32)`) scale linearly with the number of executables, not op count, at a median of 16–19 ops per executable; `evoxc.lower` is ~1.3 s (mostly `stablehlo.export`) and `evoxc.compile` adds 0 ms over raw `compile_str`; a 2000-op elementwise CHAIN fuses into ONE dispatch = 11.1 s vs 2.3 s with an `optimization_barrier` every 100 ops (per-size table → notes `## Known Issue 18`).
   Flags that do NOT help: `opt_level="O0"`/`"O1"` emit a BYTE-IDENTICAL vmfb, `--mlir-disable-threading` is 1.8× WORSE, O2/O3 is broken for some cuda graphs (Known Issue 9). Levers that work: chunk-and-parallelize (near-linear) and `batch_functions(bands=32)` (−9 %). Table → notes (`## Known Issue 18`).

16. **IREE 3.11 Vulkan runtime: software devices were hidden by NAME and the default target profile caps large graphs.**

   Narrative → notes (`## Known Issue 16`).

17. **xla's DEVICE-RESIDENT `run()` is ASYNCHRONOUS (dispatch overlap is intentional) — `synchronize()` is the only explicit completion boundary.** `PJRT_LoadedExecutable_Execute` returns after ENQUEUE, so a bare timed loop measures only host dispatch: a Qwen3-8B fp32 forward loop under-reported wall-clock ~6–10× (numbers → notes). The `PJRT_Event*` lifecycle is the design section's; a `0`/`None` handle makes `synchronize()` raise an explicit `BackendError` rather than claim completion, and `close()` destroys pending handles WITHOUT awaiting. **Binding for benchmarks:** ANY wall-clock xla measurement must time `run` + `synchronize()` (or an explicit `.to(cpu)` readback). Numbers → notes.

18. **IREE/ROCm is 5–10× behind XLA/ROCm on large-weight whole-model graphs, and the cause is IREE ROCm codegen, not staging or dispatch overhead.** Weights are device buffers placed ONCE (`asdevicearray` = 0 in the warm loop), outputs stay device-resident, `evoxc_hf.run` does O(1) host work per call, and the exporter emits BYTE-IDENTICAL StableHLO for both adapters (669 881 bytes on `qwen3_8b` s32). The residual is per-dot kernel efficiency at GEMV-ish `M≪N` shapes (260–711 GB/s on iree vs 1.3–2.5 TB/s on xla, same fp32 MFMA lowering) plus a bimodal IREE HIP large-stream mode (3–7× slow in most processes); `--iree-opt-data-tiling`, `O3`, `--iree-opt-aggressively-propagate-transposes` and hand-written tuning specs are NOT remedies. Full decomposition: archived evoxc-bench artefact `iree_rocm_gap_findings.md` (+ `probe_iree_rocm_math_roofline.py`).

19. **The HIP and CUDA HALs cap ONE dispatch at 16 bindings, and the check runs at executable LOAD, not compile.** The HAL rejects a dispatch above the 16-binding cap (CUDA identical, the CPU local ABI allows 64, Vulkan has no cap), counting that ONE dispatch's input + output buffers: CONSTANTS never consume it (they hoist into one pool binding), a fused region over 17+ tensors does, and nothing raises or splits it at compile (a 23-binding graph compiles with exit 0).
   **The driver is the `batch_functions` OUTPUT combine:** `combine_bands` emits ONE `stablehlo.concatenate` over all K per-band outputs, which IREE rewrites into a `flow.tensor.update` chain fused into ONE dispatch with one binding per piece (K=15 → 16 loads bit-exactly, K=16 raises), and the count is NOT monotone in K — so the rules are **K ≤ 15 unconditionally** and **band size ≥ 8** for large populations. llvm-cpu is NOT immune, only wider (K=40 → `OUT_OF_RANGE; binding count 41 > 32`; K≥64 → `… exceeds limit of 64`), so it caps at **K=31**. `iree.py::_raise_if_dispatch_binding_limit` (both load paths) raises an explicit `BackendError` naming the HAL cap, the observed count, the target, that constants never count and that `iree-compile`'s HAL layout assignment decides it (so evoxc cannot detect it at `lower()`), with the remedies: fewer bands / `bands=None`, split the graph so no fused region consumes >16 tensors, or `target_backends=['llvm-cpu']`/`numpy`. K tables → notes (`## Known Issue 19`).

20. **Same-thread deadlock in the xla shared-client cache — a FINALIZER inside a plugin call (FIXED; the discipline below is binding).** A `weakref` finalizer runs wherever the GC pass freeing its referent happens to be, including inside another critical section on the SAME thread; `acquire_client` used to hold the non-reentrant `_shared_clients_lock` across `plugin.create_client()`, so a pending payload finalizer collected there re-entered and hung the thread. Creation now happens OUTSIDE the state lock: double-check under `_shared_clients_lock`, take the dedicated `_client_create_lock` (which NO finalizer path touches), call `create_client()` holding no state lock, then insert under the state lock after re-checking (the create lock still serializes creation process-wide — real GPU plugins grab a large BFC pool and abort when one cannot be allocated); both state locks are `RLock`.
   **Locking discipline (binding): never hold a shared lock across a plugin call or anything that can run a Python finalizer**; a finalizer path takes ONLY `_shared_clients_lock` for refcount bookkeeping and closes buffers/clients outside it, with a stale-client identity guard so a late finalizer cannot decrement a re-created client. No committed test pins it yet (post-mortem → notes).

21. **The device→host readback is ADAPTER-OWNED — iree 3.13.0's `DeviceArray.to_host()` fast path is unusable on the Vulkan HAL.** Every host materialization of an iree buffer (hence `.numpy()` on a cpu-kind output, `t.to(cpu)`, `evoxc.io.sink`, host-mode external-kernel boundaries) goes through `iree.py::_readback_device_array`: a **zero-copy mapping** for host-mappable llvm-cpu/`local-task` allocations, else an explicit **staging `queue_copy`** with the shared query-first semaphore, `map()` + copy out.
   Cause: `_copy_to_host` prefers `allocator.import_host_allocation` whenever `query_buffer_compatibility` reports `IMPORTABLE`, and the Vulkan allocator then rejects the very buffer it advertised (`allocator.c:1985`, `minImportedHostPointerAlignment 4096`) — so the adapter never uses that primitive, has no version branch or `try: to_host() except:` fallback, and leaves host-memory IMPORT unused even where it works so ONE implementation serves every kind. Re-tested bit-exact on vulkan (lavapipe), rocm and llvm-cpu. Cost table → notes (`## Known Issue 21`).

- **ROCm `while_loop`/`scan` unreliability (same upstream family as 8f):** shapes build and compile, but at run the HIP HAL aborts with a RAW `RuntimeError: … hip/event_semaphore.c:786: ABORTED … hal.fence.await` (from `entry(*buffers)`, unwrapped) and the process often hangs at teardown; deterministic per shape and the same graphs are llvm-cpu-clean. ## Scale & module-shape facts (large graphs)
- **No program-size limit exists anywhere in the adapter compile path** — no graph-size / op-count / MLIR-text-size / recursion-depth guard in `iree.py`/`xla.py`/`tvm.py` `compile()`. The only numeric caps are unrelated: staging/run caches (`_STAGED_INPUT_CACHE_MAX = 64`, `_ROCM_SOURCE_CACHE_MAX = 16`, `_EXECUTE_SCAFFOLDING_MAX = 64`), the `_STAGED_INPUT_MAX_BYTES = 16 MB` staging *fallback* (never a rejection), and the `inline_portables` 1000-expansion fixpoint cap (`../inline.py:321`).
- **Function count:** tvm requires EXACTLY ONE `func.func` (`tvm_util.precheck_module`, `BackendError` naming the count) and rejects a multi-operand `func.return` (the vendored importer keeps only the first output). iree compiles whatever the module contains, but `IreeExecutable._entry_function` (`iree.py:2140`) resolves `"main"` first and otherwise requires exactly ONE recorded entry function. xla records `entry_functions` but never consults it.
- **tvm's op whitelist lacks `stablehlo.iota`** (so iota-based compositions — `diag`/`eye`/`linspace`/count-sort/`eigh` — hit the compile gate), plus no `gather`/`scatter`/`if`/`while`/`remainder`/`conv`/`reduce_window`/`sort`: an embedding-gather transformer forward is rejected on tvm before translation.

## Native-host portability boundary
Only XLA drives a native C ABI directly: `_pjrt_c_api.py` defines the PJRT function table and argument structs and `xla_util.py` calls it through ctypes, so a Rust host is a direct driver translation rather than a compiler rewrite.
IREE uses Python compiler/runtime bindings, including private `DeviceArray._buffer_view`/`_device`/`_override_dtype`; its VMFB bytes are the natural native handoff, but no IREE C-ABI host exists here.
TVM compilation needs Python Relax translation/build plus a monkey-patched `StableHLOImporter` and private jaxlib `_jax_mlir_ext` dialect registration, so swapping `_mlir_bindings` alone does not remove Python; its exported `.so` is a TVM runtime module wrapped in a VM, not a standalone tensor-function C ABI.
`XlaDevicePayload` has host readback but no DLPack, while `IreeDevicePayload` exports/imports through IREE HAL capsules — buffer residency does not imply cross-backend DLPack interchange; native IREE bindings, native TVM VM/FFI hosting and native DLPack ownership bridges are plausible paths, not implemented interfaces in this tree.

## Dependency surface

No adapter fetches anything at run time: there is no urllib/requests/curl/wget, no `XDG_CACHE_HOME`/`HOME` cache directory, and no software download anywhere in this node (the only `subprocess` call is `iree.py::_detect_rocm_target`'s local `amdgpu-arch`/`rocm_agent_enumerator` probe; the only filesystem writes are `tvm_util`'s temp `.so` for `export_library`/`load_module`).
`_pjrt_c_api.HEADER_URL`/`HEADER_COMMIT`/`HEADER_SIZE_BYTES` are provenance METADATA only — never opened or fetched; the module is a hand-written ctypes translation, stdlib-only.
xla needs ZERO pip dependencies: the PJRT C API is driven over pure-stdlib ctypes against a `GetPjRtApi`-exporting plugin `.so`, required at compile/load time, discovered as documented above and dlopen-ed never imported (no xla extra); provenance (header URL + commit) is recorded in `_pjrt_c_api.py` and the artifact `runtime_dependencies`.
tvm needs `apache-tvm` + `jaxlib`, the latter ONLY for its bundled LLVM MLIR python bindings (not the jax API) behind the `_mlir_bindings` seam; `jax` is never imported anywhere in `evoxc/`, and `check_available()` probes `jaxlib.mlir` + `jaxlib.mlir.ir` with the `pip install evoxc[tvm]` hint.
**Legitimately long files — do not split without a plan:** `iree.py` (3828 lines) holds the whole iree adapter surface (options/defaults, backend + executable + cached run plans, staging tiers, adapter readback, device acquisition, segments/external dispatch, `IreeDevicePayload`, `upload_tensor`, `register()`).
`xla.py` (1479) and `xla_util.py` (1680) are the same split for xla (backend/executable surface incl. the static-shape gate, `_XlaRunPlan`, the device-complete-event lifecycle; PJRT C API driver).
All three are cohesive and tightly coupled, so splitting would only spread one adapter across files.
