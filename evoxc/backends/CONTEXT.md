# evoxc/backends — backend abstraction, numpy reference backend, StableHLO exporter

## Intent

Turn verified frontend Graphs into executable programs. Four responsibilities:

1. **Backend contract** — `Capabilities`, `Backend` ABC, backend `Executable` protocol, registry.
   This is the plug-in seam for compilers.
2. **Shared pluggable-compiler framework** (`compiler.py`, `inline.py`, `external_split.py`, `external_validate.py`, `adapters/`) — `CompilerBackend` / `CompilerExecutable` plus the shared inlining/splitting machinery, so every compiler adapter reuses the exact same lowering logic as the numpy backend.
   Three adapters are IMPLEMENTED in `adapters/`: `"iree"`, `"xla"` (PJRT C API driven with ctypes — a plugin `.so` DISCOVERED at run time: `plugin_path` > `EVOXC_PJRT_PLUGIN` > fixed well-known paths > an installed `jax_plugins/<platform>/<name>_plugin.so`; no jax/jaxlib import), `"tvm"` — each does lower (shared) → compile (native compiler on the StableHLO text) → load → run.
3. **Reference numpy CPU backend** (`numpy_backend`, default) — a pure-Python numpy interpreter proving the IR semantics; the only concrete-computation path besides `core`'s concrete creators.
4. **StableHLO export utility** (`stablehlo`) — emits StableHLO MLIR text so external compilers (`iree-compile model.mlir -o model.vmfb`) can take over compilation.
   Export-only, NOT a compilable backend.

**Ownership (binding):** `LoweredProgram` and `CompiledArtifact` are owned by THIS package, not by `pipeline`; `pipeline` orchestrates staging and re-exports them.

**Authority split (do not restate subordinate files here):** adapter contracts, per-adapter capabilities and known issues live in `./adapters/CONTEXT.md` (with narratives/measurements in `./adapters/PER-ADAPTER-NOTES.md`); the exporter's per-op mapping, emitters, deferral list, dynamic-dims matrix, dtype map and option values live in `./stablehlo/CONTEXT.md` (measurement evidence in `./stablehlo/EMISSION-NOTES.md`); the numpy interpreter's internals live in `./numpy/CONTEXT.md`; test coverage per file lives in `../../tests/backends/CONTEXT.md`.

See `../../CONTEXT.md` (principles, staging pipeline, error strategy) and `../CONTEXT.md` (cross-module contracts) — both binding.

### Staged-object inspection (pure, `program.py`)

`LoweredProgram` and `CompiledArtifact` expose pure-inspection methods — reads of already-recorded attributes plus an optional payload rendering; no tracing, lowering, compiling, verifying or caching, and a lazy `evoxc.persist`/`evoxc.ir` import inside the rendering body only.

- `__repr__` — one line: backend, target (`CompiledArtifact` only), payload kind + byte size (`payload=None` for an absent payload, `?` when the size is not computable), input/output leaf counts. Never raises.
- `summary() -> dict` — exactly these keys, in order: `backend`, `target` (`None` for a `LoweredProgram`), `payload_kind` (`None` for an absent payload, else `"serialized-ir"`, `"mlir"`, a known payload `format` such as `"stablehlo"`/`"stablehlo-segments"`, `"json"` for any other dict, else the payload type name), `payload_bytes` (UTF-8 length for `str`, canonical-JSON length for `dict`, `None` when not computable — never raises), `input_count`/`output_count`, `input_shapes`/`output_shapes` (per leaf `[str(dim), …]`), `input_dtypes` (per leaf `str(dtype)`), `static_value_count`, `required_custom_ops` (`[]` for a `LoweredProgram`), `runtime_dependencies` (`{}` for a `LoweredProgram`).
- `source_text() -> str | None` — the human-readable payload text, implemented ON TOP of the `text()` rendering (`program.py::_render_payload_text`, shared by both classes so `CompiledArtifact.source_text()` and `LoweredProgram.text()` agree): MLIR text verbatim, a payload's `mlir_text`, or the pretty-printed serialized IR; `text()` keeps its raising contract and exact `BackendError` wording, while `source_text()` returns `None` instead of raising.
- `NumpyExecutable.plan_text() -> str` renders the interpreter's per-block execution plan (see `./numpy/CONTEXT.md`).
- `save()`/`load()` are unchanged: the persisted container carries the same payload/metadata bytes and none of the runtime-only private attributes.

## Constraints (binding)

- **Import acyclicity** (from `../CONTEXT.md`): top-level imports restricted to `evoxc.core` and `evoxc.ir`.
  `evoxc.ops` may be imported ONLY inside function bodies (block-impl registration).
  `evoxc.persist` may be imported ONLY inside function bodies (persist sits ABOVE backends in the DAG — a top-level import would be a cycle).
  NEVER import `evoxc.pipeline` (pipeline imports backends).
- **Errors**: capability violations and unsupported ops raise `core.BackendError` — always naming the op/feature.
  Load-time mismatches (backend/device/ABI/custom-op availability) raise `core.PersistenceError` — never silently re-lower/re-compile.
  `lower()` surfaces `core.VerificationError` from `graph.verify()`.
  Runtime shape failures raise `core.ShapeError`.
  No silent fallbacks or partial semantics.
- **No hidden staging**: `load()` never traces/lowers/compiles.
  Artifacts are self-describing (backend name/version, target, signature, required custom ops, IR format version).
- **Files < ~1000 lines** — kernel modules are pre-split by category (`numpy/kernels/`); stablehlo mapping data lives separately from the writer (the writer itself is the known exception — see `./stablehlo/CONTEXT.md`).
- **CPU only in v1**: the numpy backend never requires or touches GPU.

## Numpy backend design (reference CPU interpreter)

**Capabilities**: name `"numpy"`; `dynamic_shapes=True`; `dtypes=` all numpy dtypes; `collectives=True` (single-process simulation); `runtime_calls=True`; `external_calls=True` (host-mode slots only — a resolved numpy slot registered `device_resident=True` raises `BackendError`); `custom_blocks=True`; `async_collectives=False` (simulation is synchronous); `sparse_ops=True` (the ONLY backend with sparse support in v1 — the 16 `sparse_*`/`dense_dot_sparse` ops are numpy-implemented only).

**Staging flow** (see `numpy/__init__.py`):
- `lower(graph, options=None)`: (1) `graph.verify()`; (2) `kernels.register_all()` (idempotent) + capability flags pre-check on the current module state (kernel-table membership is checked AFTER inlining as the drift net); (3) inline `block_call` portable decompositions as a graph→graph expansion via the SHARED fixpoint `inline.py::inline_portables(module, keep_backend_impls="numpy")` (a block with neither portable nor registered numpy impl ⇒ `BackendError` naming the block); (4) ONE post-inline capability walk that also COLLECTS the sorted `required_custom_ops` names (`block_call` block names + `external_call` kernel names) in the same `iter_ops` loop, plus the defensive post-inline `graph.verify()` ONLY when `inline_portables` reported a non-zero expansion count (a zero count means the module is byte-for-byte the one already verified — same proof as `compiler.py`); (5) record `Signature` from the Graph's LIVE attributes; (6) `payload` = versioned self-describing `ir.Module` serialization (`ir.serialize_module`).
  The LIVE module, the exact payload object and the collected names are attached to the returned `LoweredProgram` as PRIVATE runtime-only attributes (`_numpy_module`/`_numpy_payload`/`_numpy_required_custom_ops`) — never dataclass fields, never persisted, so the container stays byte-identical.
- `compile(lowered, options=None)`: validate `lowered.backend == "numpy"`; then either reuse the in-process attachments (identity test `_numpy_payload is lowered.payload` — no decode, no rescan) or, for a `LoweredProgram.load`ed from disk, deserialize ONCE + scan ONCE; wrap into a `CompiledArtifact` (`target="cpu"`, records required custom ops + `runtime_dependencies={"numpy": <version>}`), which also carries the module as `_numpy_module`.
  No machine code exists — the artifact IS serialized IR.
- `load(artifact, device=None)`: validate backend/device (None or CPU; else `BackendError`/`DeviceError`); take the attached module when `_numpy_payload is artifact.payload`, else deserialize ONCE; run the unchanged `block_call`-impl validation; build a `NumpyExecutable` around that SAME module object (mutating a `Graph.module` after `lower` is therefore unsupported — the persisted payload is the snapshot of record; see `./numpy/CONTEXT.md` "Single-decode staging").
  Never re-compiles.
- **Single-decode property (measurable):** `trace → lower → compile → load` deserializes **zero** times in one process (the module `lower` verified is the module the interpreter runs), `evoxc.build` likewise zero, and an object loaded from disk exactly once.
  `numpy.decode_stats()`/`reset_decode_stats()` (module-level, exported) count `ir.deserialize_module` calls through the single `_decode_payload` helper — a TEST SEAM, deliberately not re-exported from `evoxc`/`evoxc.backends`.
- **Measured staging cost** (1700-op `tanh` chain, (64,) f32, min/median ms on this host, shared loadavg ≈1.4): `lower` 16.0/16.5 → 13.2/13.9 (one `ir.verify` walk dropped), `compile` 15.4/16.3 → 0.009/0.010, `load` 15.4/16.1 → 0.09/0.09 (the removed double `ir.deserialize_module` + rescans), `run` 3.02/3.05 unchanged, `trace` ≈11.2/11.7 unchanged.

**Interpreter execution model** (`NumpyExecutable.run(flat_input_tensors)`):
- **Execution order = block op order.** This IS the effect ordering (write/read/collective/callback ops anchor order); pure ops could be reordered but program order is kept for determinism.
- **Shape inference: reuse, don't duplicate.** Runtime shapes are computed from concrete input shapes using the SAME ops-level inference rules with symbolic dims bound to concrete values (`numpy/shapes.py` evaluates `DimExpr` against name→int bindings).
  The backend carries NO second copy of shape rules.
  Free symbolic dims at run time ⇒ `ShapeError`.
- **dtypes**: numpy dtype ↔ evoxc dtype is 1:1; kernels validate support; no promotion beyond what ops define.
- **Control flow**: `cond`/`while_loop`/`scan` region ops are interpreted by recursively running region blocks — genuinely dynamic runtime control flow (the graph is NOT specialized per iteration).
- **`runtime_call`**: executes the Python callback synchronously at the op's position — a documented sync point (no async execution in v1).
- **`block_call` dispatch**: portable decompositions are inlined at `lower()` time, so the interpreter only ever dispatches blocks that have a registered numpy impl (`kernels/custom.py`); otherwise `BackendError`.
- **`external_call` dispatch**: resolved by name at the op's position via `evoxc.external.get_external_kernel_entry(name, "numpy")`; all matching/validation rules are in the frontend contract (`../CONTEXT.md`, "External kernels").
- **Collectives**: ALL collective ops dispatch through the canonical `CollectiveExecutor` hook in `evoxc.dist.context` (`set_collective_executor`/`get_collective_executor`); the numpy backend installs its default `SingleRankCollectiveExecutor` (identity semantics on one rank) into that slot at import, and tests simulate multi-rank in-process by installing a custom executor.
  `numpy/collectives.py` only defines the default executor class.
  Group semantics are simulation-only in v1.
- **rank/world_size**: resolved at RUN time from a per-execution `dist.context.RankContext` (default rank 0 / world_size 1; overridable per run via `numpy/exec_context.py`'s thread-local `set_rank_context` or the `run(..., rank_context=...)` kwarg) — never constant-folded at lower/compile time.
- **`NumpyExecutable` persistence**: `.save(path)` saves the underlying `CompiledArtifact` — the executable is reconstructed explicitly at `load`; device handles are never serialized.

**Kernel split** (`numpy/kernels/`): `elementwise.py` (arith/activations/comparisons/select/cast/broadcast), `reductions.py` (reduce_*, argmax/argmin), `indexing.py` (reshape/transpose/slice/concat/pad/gather/scatter/tril/triu/cumsum), `linalg.py` (dot/conv/solve), `sorting.py` (sort/argsort), `structural.py` (tile/flip/roll/diag/nan_to_num), `control_flow.py` (if/while/call region execution), `collective.py` (collective dispatch via the hook + rank/world_size), `custom.py` (`runtime_call`, `block_call`, `external_call`, `constant`), `sparse.py` (the 16 sparse kernels: from_dense/to_dense, coo↔csr/csc conversions, add/multiply/negate/multiply_dense, reduce_sum, transpose, reshape, concatenate, sparse_dot_dense/dense_dot_sparse), `random.py` (the 6 random kernels over all 3 algorithms). `kernels/__init__.py` assembles the dispatch table from every category module's `register_kernels(table)` (`register_all()` is idempotent, duplicate registrations raise); `dispatch(op_name)` maps op name → kernel and raises `BackendError` naming the op for an unknown name (capability-drift safety net). The kernel contract (`kernel(ctx, op, operands)` + `KernelContext`) and the interpreter loop live in `numpy/interpreter.py`; per-category semantics in `numpy/kernels/`; details in `./numpy/CONTEXT.md`.

## StableHLO exporter — scope & ownership

`stablehlo.export(graph_or_module, options=None) -> str` emits StableHLO MLIR text (module + `func.func` + `return` shell) from a verified module, and is used BOTH as standalone compiler input (`iree-compile model.mlir -o model.vmfb`) and as the LOWERING PAYLOAD of every compiler adapter — `CompilerBackend.lower` calls the module-private `stablehlo._emit_verified(module, options)` on the module it already verified (byte-identical text; `export` keeps its own verify-first contract and is used for segment modules). It is an export utility, NOT a `Backend`: no compile/load/run, no runtime.

- **Authoritative detail lives in `./stablehlo/CONTEXT.md`**: the per-op mapping table (direct mnemonics, decompositions, `SPECIAL_EMITTERS` compositions for gather/scatter/sort/argsort/arg-reduce/tile/eigh/diag/random), the v1 DEFERRED list, the per-op dynamic-dims allow/reject matrix, the dtype→MLIR `DTYPE_MAP`, and every exporter option with its accepted values.
  Measurement evidence (what each composition costs and why) is in `./stablehlo/EMISSION-NOTES.md`.
  Mapping data: `./stablehlo/ops.py`; text emission: `./stablehlo/writer.py`.
- Anything unmapped or deferred raises `core.BackendError` naming the op at export/`lower()` time — never invalid MLIR reaching a compiler, never a silent approximation.
- `scan` has no IR OpDef: `evoxc.scan` desugars at trace time into `while` + `gather` + `scatter`, so scan graphs export and run.
- Adapter-side dynamic-shape support is per-op PARTIAL; the exporter is the gate (allow/reject lists in `./stablehlo/CONTEXT.md`).

## Serialization compliance

`LoweredProgram.save`/`CompiledArtifact.save` delegate to the `evoxc.persist` container format (lazy import): magic header + format version + JSON metadata + payload + SHA-256 integrity. Metadata is self-describing: backend name/version, target, signature (TreeSpecs + specs + static values), required custom ops, IR format version. `load()` validates the recorded backend against the registry (numpy reconstruction handled by `NumpyBackend`) — mismatch or missing custom op ⇒ `PersistenceError`. Never silently re-traces/re-compiles.

## Compiler adapter framework (design)

`compiler.py` is the pluggability seam: a new StableHLO-consuming compiler backend is a `CompilerBackend` subclass declaring `name`/`capabilities`, implementing `check_available()` (dependency probe with a `pip install evoxc[...]` hint), `compile()` (invoke the native compiler on the payload's `mlir_text`; JSON-safe artifact payload), and `load()` (rebuild the executable — never recompiling), plus a `CompilerExecutable` subclass implementing `run()`. The shared `lower()` does everything else: `options.validate_options` (key validation first, so an unrecognized option fails before any graph work) → `graph.verify()` → capability pre-check (incl. dynamic dims in function signatures when `dynamic_shapes=False`) → `inline_portables` (expansion count) → `graph.verify()` only when that count is non-zero → `stablehlo._emit_verified` (the already-verified private export entry point, so the required `ir.verify` walk runs exactly once per `lower()`) — the per-op dynamic-dims gate for `dynamic_shapes=True` backends → Signature → MLIR payload. The "How to add a new adapter" recipe lives in `compiler.py`'s docstring.

**The three implemented adapters** (`./adapters/`) are optional and lazily activated. iree/tvm probe their pip-installable dependency in `register()` and raise an explicit `core.BackendError` with a pip hint there. xla's `register()` never raises: its dependency is a per-call plugin `.so` (`plugin_path` / `EVOXC_PJRT_PLUGIN` / the fixed well-known paths / a discovered artifact), so the actionable plugin-discovery error is raised by `compile`/`load` — it lists the four discovery steps ending in a pip-installed JAX PJRT plugin under `jax_plugins/<platform>/<name>_plugin.so`, so `pip install jax-rocm7-pjrt` / `jax-cuda12-pjrt` needs no hand-wiring; the plugin is dlopen-ed, never imported, and no jax/jaxlib is required — while `XlaBackend.check_available()` stays the explicit option-less preflight for callers with no stage context. Shared capability floor: `collectives=False`, `runtime_calls=False` (rejected at `lower()`), `custom_blocks=False` (portable-only inlining), `async_collectives=False`, `sparse_ops=False`; `dynamic_shapes` is per-op partial; `external_calls=True` for iree (segment split + host/device dispatch) and `False` for xla/tvm (portable inline at `lower()`, else explicit `BackendError`).

**Per-adapter capabilities, compile targets/drivers, supported dtypes, device kinds, persistence and validated hardware are owned by `./adapters/CONTEXT.md`** (narratives + measurements in `./adapters/PER-ADAPTER-NOTES.md`). Adapters never silently fall back to the numpy backend.
The adopted compiler generation is **iree-base 3.13.0** (the `iree`/`compilers` extras pin `iree-base-compiler`/`iree-base-runtime` `>=3.13.0,<3.14`, which must match; the pin itself lives in the repo-root `pyproject.toml`); the 3.13.0 re-validation of the llvm-cpu and ROCm/HIP legs, the loop/scan/cond-while/MO retest and the measured cells are in `./adapters/PER-ADAPTER-NOTES.md` ("IREE 3.13.0 — the adopted pin"), with the committed records under `../bench/iree313_rocm_findings.md`.

## Native CPU-engine backend (`native`)

`NativeBackend` (`name = "native"`, package `./native/`) executes a verified `Graph` on the in-process Rust CPU execution engine (`evoxc-cpu` under `native/`) through the `evoxc._evoxc_native` extension's `native_compile` entry point.
It is OPTIONAL and lazily activated exactly like the compiler adapters (`registry.OPTIONAL_ADAPTERS`), so `import evoxc` never imports the extension; `register()` probes `native_compile` and raises an actionable `core.BackendError` (build with `scripts/build-native.sh`) when the extension or that entry point is missing — never a silent fallback to numpy.
Staging mirrors `numpy` step for step: `graph.verify()` → capability pre-check (effects, sparse, dtypes) → `inline_portables(..., keep_backend_impls="native")` (shared `./inline.py`) → conditional re-verify → **engine capability gate** (`native_compile` + `stats()`; any op the engine reports as unsupported raises `BackendError` naming the ops and pointing at `backend="numpy"`) → `Signature` from the Graph's live attributes → payload = the serialized EvoXIR module (savable/portable, like numpy — no machine code).
`compile()` records `target="cpu"`, the custom-op names scanned from the module and `runtime_dependencies = {"numpy": …, "evoxc-native": …}`; `load()` accepts only a CPU `Device`, requires a registered `native` impl for every surviving `block_call` (`PersistenceError` naming the block) and rebuilds the engine program from the payload (never re-lowering) — external kernels and `runtime_call` callbacks stay LAZY at run time per the binding persistence contract.
`NativeExecutable` adds `plan_text()` / `stats()` / `required_ops()` (the user-facing `Executable.summary()` inspection API in `../pipeline.py` delegates to them) and a documented no-op `synchronize()` (`run` blocks).
Capabilities: `dynamic_shapes=True`, the 14 evoxc dtypes, `collectives=True` (single-rank identity), `runtime_calls=True`, `external_calls=True` (host-mode kernels via the resolver), `custom_blocks=True`, `async_collectives=False`, `sparse_ops=False`.
v1 deferrals, all explicit: sparse ops (numpy-only by contract), non-CPU devices, `device_resident=True` external slots, any engine-unsupported op, and pipeline options (all four `KNOWN_OPTIONS` stage sets are empty — a compiler option passed here fails loudly instead of being ignored).
Callback boundaries (`block_call` / `external_call` / `runtime_call`) reach Python through `NativeCallbackResolver` — `call_block(name, args, static_args=None)` / `call_external(name, args)` / `call_runtime(name, args)` returning host numpy arrays; `static_args` is the `block_call` op's static-kwarg dict and MUST be passed by the engine (see `./native/CONTEXT.md`).
The FFI contract, the resolver protocol, the staging order and the in-process compile-reuse rule are owned by `./native/CONTEXT.md`.

## Lower-stage cost model
Scope: `CompilerBackend.lower()` — `NumpyBackend.lower` keeps its unconditional post-inline `graph.verify()` and serializes the module instead of exporting text.

`lower()` on `batch_functions`-merged population graphs, measured on an AMD MI300X-era box with iree-base 3.11.0, `EVOXC_DISABLE_LOCATIONS=1`, iree backend, one shared `(1024,)` f32 input, random expression programs, median of 3.
The `verify walks` column counts the `ir.verify` passes `lower()` performs: the two `lower()` columns are the same code path with three walks (explicit verify + post-inline verify + the export's own verify) and with the current single walk.

| graph | emitted ops | text | `lower()` ms, 3 walks | `lower()` ms, 1 walk (current) | gain |
|---|---|---|---|---|---|
| 64 programs flat | 522 | 0.09 MB | 18.2 | 7.6 | 2.4× |
| 64 programs, switch_ops | 739 | 0.18 MB | 30.1 | 10.6 | 2.8× |
| 256 programs flat | 2008 | 0.72 MB | 94.5 | 30.9 | 3.1× |
| 256 programs, switch_ops | 2656 | 1.54 MB | 204.9 | 52.6 | 3.9× |
| 256 programs, bands=32 + switch | 3376 | 0.46 MB | 123.6 | 50.1 | 2.5× |
| 1000 programs flat | 7291 | 7.81 MB | 699.9 | 142.3 | 4.9× |
| 1000 programs, bands=32 | 8944 | 1.38 MB | 354.0 | 137.1 | 2.6× |
| 1000 programs, bands=32 + switch | 12310 | 2.24 MB | 567.8 | 204.5 | 2.8× |
| one 64-program chunk | 568 | 0.10 MB | 19.4 | 7.4 | 2.6× |
| single 7-op graph (fixed cost) | 7 | ~0 | 0.3 | 0.2 | — |

The model behind those numbers:

- **Fixed cost ≈0.2 ms per `lower()` call** (a 7-op graph), independent of graph size.
- **One `ir.verify` walk is required and is the largest single share of `lower()` at scale** — 55 ms of 142 ms on the 7291-op graph, 80 of 137 on the banded one, 116 of 204 on the switch one (32–57 %) — because `ir.verify`'s `_verify_uses` is superlinear in use count.
  That code lives in `evoxc/ir`, not here; the only in-node lever is the walk COUNT, and `lower()` is at one (post-inline verify only when `inline_portables` expanded something, export through `stablehlo._emit_verified`).
- **The writer's per-op emission costs ≈11 µs/op** (the second-largest share).
- **Constant payload text is O(elements)** and bulk-rendered (see `./stablehlo/CONTEXT.md`), so it tracks payload size rather than op count — the reason the banded graphs are cheaper per op than the flat ones.

`lower()` is safe to call CONCURRENTLY on DIFFERENT graphs: verified with 4 threads × 4 graphs × 50 iterations, byte-identical text versus serial execution.
The writer's caches are per-`Writer` (one per export call), and the only process-global tables are the `_EMITTERS` dispatch dict (built once at import, immutable afterwards) and the locked payload→text LRU in `constants.py`; the pre-existing adapter first-use registration race documented in `./adapters/CONTEXT.md` is unchanged.

## Backend options override (binding)

Every pipeline stage — `lower`, `compile`, `load`, `run` (plus the `build`/`evaluate` sugar and `evoxc.bind`-ed executables) — accepts backend options via the existing `**options` kwargs. The mechanism (design doc: "we only took care of the graph, provide a clean pipeline, and everything else should be hack-able") is general: users can override ANY compiler flag or related option without evoxc hardcoding them.

- **Option NAMES are validated; option VALUES never are** — the exceptions are `opt_level` (evoxc-defined: evoxc translates its value per backend, so evoxc validates it — see the `opt_level` bullet below) and the reserved StableHLO-exporter lower options, whose values the Writer validates (see the reserved-keys bullet below).
  Each backend/executable declares `KNOWN_OPTIONS: dict[str, frozenset[str]]` (stage → key set).
  `evoxc/backends/options.py::validate_options(options, known, backend_name, stage)` validates a stage's options against the **union of all stages' sets** (a key valid for any stage passes, accepted-and-ignored elsewhere — `build`/`evaluate` forward one dict to every stage).
  A key in no stage's set raises `core.BackendError`: "the {backend} backend does not recognize the {stage} option '{key}' — known options by stage: lower: …, compile: …, load: …, run: …".
  Flag/option VALUES always pass through — the compiler validates them (evoxc never parses compiler flags).
  `STAGES = ("lower", "compile", "load", "run")`.
- **Precedence (binding): explicit kwarg > env var (`EVOXC_<BACKEND>_*`) > evoxc default.** Env vars are read lazily at call time by `evoxc.pipeline_options.apply_env_options` (table in `evoxc/pipeline_options.py::ENV_OPTION_TABLE`); empty/whitespace env = unset; malformed env values raise `core.BackendError` naming the variable and value.
  Env application is stage-scoped (e.g. `EVOXC_IREE_RUNTIME_ARGS` applies only at the load stage).
  Value formats (parsers in `evoxc/pipeline_options.py`): the flag-list rows `EVOXC_IREE_COMPILE_ARGS`/`EVOXC_IREE_RUNTIME_ARGS` are split with `shlex.split` — QUOTING IS PROCESSED, so a quoted flag survives as one entry — and must yield ≥1 flag; `EVOXC_XLA_COMPILE_OPTIONS` is base64 of the serialized proto bytes; `EVOXC_TVM_PASS_CONFIGS` is a JSON object; `EVOXC_OPT_LEVEL`/`EVOXC_EIGH_ALGORITHM`/`EVOXC_SPLIT_REDUCTION` are backend-agnostic spellings (ONE row per compiler adapter, same option key).
  Full env-name table + precedence doc: `evoxc/pipeline_options.py` and `../CONTEXT.md` ("Backend options override").
- **Backend defaults are minimal, documented, and OVERRIDABLE.** A user flag with the same NAME as an evoxc default drops the default (never both) — evoxc must never force flags users cannot override.
  The numpy reference backend documents-ignores unknown options (`run(..., rank_context=...)` still flows through the options dict; the caller's dict is never mutated).
- **Per-adapter `KNOWN_OPTIONS` key ownership** (semantics + values in `./adapters/CONTEXT.md`): iree — lower `rng_bit_generator`/`sort_emission`/`while_init_rewrite`/`dot_precision`/`eigh_algorithm`/`split_reduction`, compile `target_backends`/`iree_compile_args`/`opt_level`, load `iree_runtime_args`; xla — lower `rng_bit_generator`/`dot_precision`/`eigh_algorithm`/`split_reduction`, compile `plugin_path`/`xla_compile_options`/`opt_level`, load `plugin_path`; tvm — the same four lower keys, compile `tvm_target`/`tvm_pass_configs`/`opt_level`, no load key.
  Run-stage sets are v1-empty for all three (non-empty → loud `BackendError`), by design.
- **Reserved exporter lower options** (forwarded by `CompilerBackend._exporter_options` to `evoxc.backends.stablehlo`; declared in each consuming adapter's `KNOWN_OPTIONS["lower"]`; KEY validation is the framework's, VALUE validation is the Writer's with a loud `core.BackendError` naming the accepted forms): `rng_bit_generator` (bool or a collection of algorithm names, default = the adapter's `Capabilities.rng_bit_generator` — per-call override of the native-emission capability), `sort_emission` (`"pair"` | `"count"` | `"auto"`, default = `default_sort_emission`, whose class default is `"pair"` while the iree adapter sets `"auto"` and upgrades to `"count"` for cuda targets), `while_init_rewrite` (bool, default `True`), `dot_precision` (`"DEFAULT"` | `"HIGH"` | `"HIGHEST"`, default `"DEFAULT"` = no `precision_config` emitted; only `"HIGHEST"` disables XLA/ROCm's TF32-class fp32 `dot`), `eigh_algorithm` (`"jacobi"` | `"jacobi_batched"`, case-insensitive, whitespace-stripped, default = `default_eigh_algorithm` = `"jacobi_batched"`), `split_reduction` (bool, default = `default_split_reduction` = `True`).
  The BOOL-valued ones (`split_reduction`, `while_init_rewrite`) are coerced to a real `bool` by `options.normalize_bool_option` inside `_exporter_options`, so env-style strings (`"0"`/`"false"`/`" off "`) cannot fall into the `bool("0") is True` trap.
  `eigh_early_exit` (and `split_reduction_threshold`/`split_reduction_non_exact`) are EXPORT-ONLY — no adapter declares them, so `evoxc.build(..., eigh_early_exit=...)` raises the unrecognized-option `BackendError`; entry point is `stablehlo.export(graph, options={...})`.
- **DENY list (iree)**: a small documented set of flags is rejected with actionable reasons (`--iree-hal-target-backends` → use `target_backends`; `--iree-input-type` → StableHLO is always the input; `--iree-vm-bytecode-module-output-format` → the adapter requires the default VM flatbuffer output).
  Everything else in `iree_compile_args`/`iree_runtime_args` passes through to the compiler/loader.
  Details: `./adapters/CONTEXT.md`.
- **`opt_level` — the first evoxc-defined, evoxc-validated option** (compile stage, all three compiler adapters; `normalize_opt_level` + the `OPT_LEVEL` key constant live in `evoxc/backends/options.py`, exported in `__all__`, also consumed by the pipeline env-var resolution for `EVOXC_OPT_LEVEL`): accepted values `"O0"`..`"O3"` (case-insensitive, whitespace-stripped), `"0"`..`"3"`, or ints 0..3 (bool rejected) — anything else raises a loud `core.BackendError` naming the option and the accepted forms, never silently swallowed.
  Per-backend translation: iree → the derived flag `--iree-opt-level=O{N}` (O-form REQUIRED — iree-base-compiler 3.13.0, the adopted pin, rejects numeric levels), which joins evoxc's defaults in the name-collision machinery: a user `--iree-opt-level=…` in `iree_compile_args`/`EVOXC_IREE_COMPILE_ARGS` wins and the derived flag is dropped — never both (the conflict rule); xla → injected into the serialized `CompileOptionsProto`'s `executable_build_options` (wire-format field 24, `c0 01 <N>`) by `xla_util.set_opt_level`, and an optimization level already present in the user's `xla_compile_options` bytes wins unchanged (never override, never both); tvm → forwarded to `build_vm_executable(..., opt_level=N)` as a version-adaptive kwarg (installed TVM 0.26 has no `opt_level` kwarg and PassContext provably does not reach the LLVM codegen, so a build without the kwarg gets a loud `BackendError` naming `opt_level` and the installed TVM; never silently dropped); numpy documents-ignores it.
  Unset `opt_level` = byte-for-byte unchanged behavior on every backend.
- **Lower-stage backend-agnostic env spellings.** The two reserved exporter lower options have per-backend env rows in `evoxc/pipeline_options.py::ENV_OPTION_TABLE` — `EVOXC_EIGH_ALGORITHM` (`eigh_algorithm`: `"jacobi"` | `"jacobi_batched"`, case-insensitive, whitespace-stripped, default `"jacobi_batched"`) and `EVOXC_SPLIT_REDUCTION` (`split_reduction`: bool — `1`/`0`, `true`/`false`, `yes`/`no`, `on`/`off`, case-insensitive, default `True`) — registered for all three compiler adapters with ONE option key each.
  These are not raw pass-through values: `eigh_algorithm` is validated by the Writer (`stablehlo/writer.py::_normalize_eigh_algorithm`) and `split_reduction` is coerced by `options.normalize_bool_option`, so a malformed env/pipeline value raises a loud `core.BackendError` naming the option, the value and the accepted forms (precedence unchanged: explicit kwarg > env var > adapter class default).
- **`normalize_bool_option(option, value) -> bool`** is the shared coercion for BOOL-valued options: real bools, ints 0/1, and case-insensitive `"true"`/`"false"`/`"yes"`/`"no"`/`"on"`/`"off"`/`"1"`/`"0"`; anything else raises a loud `BackendError` naming the option, the value and the accepted forms.
  It is a TYPE COERCION, not a per-backend semantic mapping.

## Known Issues

- **The exporter is a name-based emitter — it does NO layout folding, transpose elimination, constant folding, or operand reordering** (`stablehlo/writer.py::_emit_transpose` always emits `stablehlo.transpose` + `permutation`; `::_emit_dot` always emits `stablehlo.dot_general` contracting lhs-last × rhs-second-to-last, and neither looks at the operand's `defining_op` — `defining_op` is consulted only by `render_constant`, the gather constant-index fast path, and `_rewrite_while_init`).
  A `dot(transpose(k), …)`, `dot(x, transpose(w))` or `dot(slice(packed_w, …), x)` therefore reaches the compiler as SEPARATE SSA ops; whether the transpose/slice is materialized (a real device copy per call) or fused into the matmul's layout is entirely the CONSUMER compiler's decision — not observable from this repo and not something any evoxc option influences.
  Consequence for cross-backend A/B diagnosis: every compiler adapter lowers from the SAME exported text (`compiler.py` `lower()` stores `mlir_text`; no adapter rewrites/canonicalizes it), so two adapters fed one graph compile byte-identical MLIR and any runtime gap is downstream of evoxc; the only evoxc-side `dot` knob is `dot_precision` (a `precision_config` attribute, no `DEFAULT` attr), and no adapter emits a tiling/layout/codegen flag (agent-added flags go through `iree_compile_args` passthrough).
  Diagnose a matmul/bandwidth gap with `iree_compile_args=["--iree-hal-dump-executable-configurations-to=-"]` (per-dispatch `workgroup_size`/`lowering_config`), dispatch statistics, `--iree-opt-data-tiling` both ways, and `--mlir-print-ir-after-all`-class flags — see `./adapters/CONTEXT.md` (`./adapters/PER-ADAPTER-NOTES.md` has the flag recipes).
- **StableHLO writer semantics surfaced by adapters** (in this package's `stablehlo/`): mixed-dtype elementwise/compare/select operands (including Python scalar constants) are equalized by the writer with `stablehlo.convert` (see `stablehlo/CONTEXT.md`), and `stablehlo.add` on i1 is XOR (XLA semantics) vs numpy bool+ = OR.
  Dynamic-shape broadcasts are supported — the writer emits `stablehlo.dynamic_broadcast_in_dim` (output_dimensions built via `get_dimension_size` chains) whenever a broadcast's result has dynamic dims, validated end-to-end through iree and tvm at multiple concrete sizes; broadcasts with no full-shape source raise `BackendError` naming "dynamic broadcast" (see `stablehlo/CONTEXT.md`).
- **Sparse ops (v1, numpy-backend-only):** the 16 `sparse_*`/`dense_dot_sparse` ops (evoxc.sparse family) are implemented ONLY by the numpy backend; compiler backends (stablehlo export, iree/xla/tvm adapters) defer with an explicit `BackendError` naming the op and suggesting densification via `evoxc.sparse.to_dense` — never silent.
- **External kernels on compiler backends (v1 dispatch/fallback semantics):** the iree adapter splits `external_call` graphs at lower() into segments (see `external_split.py`) and dispatches each boundary through `get_external_kernel_entry(name, "iree")`: HOST-mode kernels (default registration) stage the boundary tensors device→host→device (a `UserWarning` is emitted ONCE per executable at the first boundary that actually stages), while DEVICE-RESIDENT kernels (`device_resident=True`, explicit per-backend slot only) receive device tensors directly and return device tensors / duck payloads — kernel authors may isinstance-check the PUBLIC `evoxc.backends.adapters.iree.IreeDevicePayload` (`.device_array` HAL handle, `.shape`, `.dtype`, `.to_host()`, `.device`) and e.g. run additional vmfb modules on the SAME HAL device; results are validated metadata-only (never a forced host copy), so fully device-resident boundaries never warn (numpy-returning device kernels stage back — boundary marked staged).
  Lower-time restrictions (MODE-AWARE): no control-flow bodies around calls, ≥1 operand, kernels assumed pure, sequential plan order, and — for HOST-mode boundaries only — STATIC (integer) result dims (host staging needs concrete shapes); DEVICE-RESIDENT boundaries allow symbolic / runtime-dynamic result dims (e.g. vmap/vectorize batch dims on a batched-variant kernel), validated metadata-only at run time with the ACTUAL runtime shapes — the stablehlo exporter's per-op symbolic-shape support decides what compiles (unsupported segment ops still raise explicit `BackendError`, never silent). xla/tvm have no host-dispatch: an `external_call` op with a registered portable decomposition (`evoxc.external.get_portable`) is INLINED at lower() through the shared portable-splicing machinery with a `UserWarning` per kernel name (the original call's effect/callback ordering is replaced by the inlined graph's op order); an op WITHOUT a portable raises an explicit `BackendError` naming the op/backend and listing the options (iree/numpy backends, or `evoxc.register_external_kernel(name, fn).portable(decomp)`).
  The stablehlo exporter itself still defers `external_call` (pure export utility — direct-export users see the deferral).
  Never silent.
- **No program-size limit anywhere in the compiler path** — the shared `CompilerBackend.lower()` and every adapter `compile()` impose NO graph-size / op-count / MLIR-text-size / recursion-depth cap; a several-hundred-op graph is structurally fine and compile wall-clock belongs entirely to the external compiler.
  The only numeric caps in this package bound per-call RUNTIME caches (`--iree` staging caches, `xla_util._EXECUTE_SCAFFOLDING_MAX`) and the `inline.py:321` 1000-expansion portable-decomposition fixpoint.
  The real gates are FUNCTION-SHAPE, not size: the iree executable needs a `main` function or exactly ONE entry function (`adapters/iree.py:1781-1789`), the tvm translator requires exactly one `func.func` with a single-operand `return` (one output), and external-call splitting requires a single-function graph (`external_split.py:272`).
- **Compile-time cost of a large graph is the consumer compiler's, and it is NOT text size, export time, or `opt_level`** — measured on iree-base-compiler 3.11.0/llvm-cpu: `stablehlo.export` + the whole `lower()` is 0.05–1.3 s (≤5 % of a 6–27 s compile) and `evoxc.compile` adds 0 ms over a raw `iree.compiler.compile_str`; the cost is ~30 ms per IREE executable (a merged population graph fragments into ~1 executable per program, median 16–19 ops) plus ~0.3 ms/op, with a superlinear spike when one dispatch mega-fuses (a 2000-op elementwise chain = one dispatch = 11.1 s vs the same ops in 20 dispatches = 2.3 s); `opt_level="O0"`/`"O1"` provably emit a byte-identical vmfb, so no compile-time flag is a free win. Full numbers, the flag sweep and the levers that do work (chunked parallel compile, `batch_functions(bands=…)`, artifact/`build_cached` reuse) are Known Issue 18 in `./adapters/CONTEXT.md`; the merged-graph text composition (86 % i1 select-mask literals) is measured there too — do not re-derive either.
- **The `native` backend (v1) is host-only and engine-gated:** `sparse_ops=False`, CPU devices only, no pipeline options, and `lower()` compiles once as its capability gate (the engine, not this package, decides which ops it implements) — `load()` reuses that program only through an in-process hint carried on the artifact payload object, so a saved/reloaded `native` artifact recompiles from its serialized IR. External kernels and `runtime_call` callbacks are NOT required at load (binding persistence contract: registries are never serialized and resolve lazily at RUN time). `NativeExecutable.run` is synchronous, so `synchronize()` is a no-op. Details: `./native/CONTEXT.md`.
- **Adapter-specific known issues live in `./adapters/CONTEXT.md` (authoritative; per-probe measurements in `./adapters/PER-ADAPTER-NOTES.md`)** — iree legalization limits (native `rng_bit_generator` PHILOX, `collective_broadcast`, u32/u64 reduce) and target/driver quirks, the ROCm/HIP loop/`scan` run-time aborts recorded on older iree releases (on iree-base 3.13.0, the adopted pin, the retested constant-init-carry `while`, float-carry-condition `while` and plain `evoxc.scan` all run device-resident bit-exactly — the retest table is in `./adapters/PER-ADAPTER-NOTES.md`), the XLA PJRT-plugin requirement (auto-discovered from an installed `jax_plugins` wheel, with `plugin_path`/`EVOXC_PJRT_PLUGIN` to pin a different one and `EVOXC_PJRT_PLUGIN_DISCOVERY=0` to opt out) plus its interpreter-exit abort caveat, TVM's jaxlib-bindings dependency and compile-time op gate, and the pyproject extras (repo root — escalated).

## Native-host integration boundary

The backend ABC, executable protocol, signatures and artifact containers are Python interfaces, not an exported evoxc C ABI or Rust API.
A non-Python consumer can target the shared StableHLO text or backend-native artifact boundary, but must separately implement tensor ownership, placement, synchronization, signature validation and any structured/static I/O reconstruction (`program.py` encodes signatures using the evoxc persistence codec).
StableHLO construction dependency and serialization boundaries are documented in `./stablehlo/CONTEXT.md`, and the actual native-versus-Python adapter seams and DLPack gaps are documented in `./adapters/CONTEXT.md`.

## Notes for agents

- **Implementation status: complete.** All behavioral bodies in `backend.py`, `program.py`, `compiler.py`, `inline.py`, `registry.py`, `numpy/`, `stablehlo/`, and `adapters/` (iree/xla/tvm) are implemented; no `NotImplementedError` stubs remain in this node (the abstract `compile`/`load`/`run` methods of `CompilerBackend`/`CompilerExecutable` are adapter contracts, by design; `check_available` is a concrete default no-op).
  `evoxc.pipeline` (orchestration above this package) and sibling test suites are handled elsewhere.
- Optional adapters are NEVER imported at `evoxc`/`evoxc.backends` import time — `registry.get("iree"|"xla"|"tvm")` imports + registers them on first use (`import evoxc` leaves `sys.modules` free of iree/jax/jaxlib/tvm).
  `program.py._require_registered_backend` routes through `get()`, so persisted adapter artifacts auto-activate on load.
- The IR op names for control flow are `if`/`while` (trace lowers `cond`/`while_loop`/`scan` into them) and the dist broadcast collective is `broadcast_collective` — frontend names differ from IR names; kernels and the stablehlo writer dispatch on IR names.
- `runtime_call` carries its callback as a STRING registry id (resolved via `evoxc.ops.constant._get_callback` at run time) — artifacts with `runtime_call` require the same callback registrations at load time; callbacks are never serialized.
- Block-impl convention (finalized with `evoxc.block`): the interpreter invokes registered numpy impls as `impl(*numpy_arrays, **static_args) -> ndarray | tuple[ndarray]`; portable decompositions are spliced into the graph at `lower()` time via `evoxc.block.registry`.
- Collective protocol limitation: `dist.context.CollectiveExecutor` has a single `axis` param for `all_to_all` (kernel forwards `split_axis`) and no `reduce_op` for `reduce_scatter` — documented in `numpy/kernels/collective.py`.
- `../../tests/` is a sibling: read-only, escalate writes to root.
