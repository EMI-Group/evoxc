# evoxc/transforms — graph-to-graph transformations

## Intent

Frontend graph transformations: `vectorize` (the batching primitive), `vmap` (transparent function-side sugar over vectorize), `batch_functions` (merging N same-signature programs onto one static function axis), and automatic differentiation (`grad` / `jvp` / `vjp`). Everything here is **graph → graph**: the result of any transform is an ordinary `Graph` of ordinary `evoxc.ops` ops — backends need NO vectorize/autodiff runtime support (binding: `../../CONTEXT.md` design principle 7, `../CONTEXT.md` transforms bullet).

There is deliberately **no execution here**: transforms never import `evoxc.backends` / `evoxc.pipeline` and never run tensors. When a transform is given a plain function or `Defn` (rather than a `Graph`), it cannot know input shapes without specs, so it returns a `TransformCallable` mapping `TensorSpec`s → transformed `Graph` (see **Spec-callable convention** below). Calling that callable with concrete `Tensor`s raises `TraceError` — explicit staging applies here as everywhere.

## API surface (public — re-exported from `__init__.py`)

- `vectorize(graph, axes) -> Graph` — THE primitive. `graph` must be a traced `Graph` (a callable/`Defn` raises `TypeError` pointing at `evoxc.vmap`). `axes`: an `int`, `None`, or a pytree thereof matching the graph's input structure; an `int` maps that input's leading axis (v1: only 0), `None` leaves it unmapped (mandatory for static inputs). Every op is rewritten via its batching rule; mapped values carry an explicit leading batch dim. No rule ⇒ `core.TransformError` naming the op — never a Python-loop fallback.
- `vmap(fn_or_graph, in_axes=0, out_axes=0) -> Graph | TransformCallable` — function-side sugar over the same machinery. Graph input: `vectorize(graph, in_axes)` + output-axis rearrangement per `out_axes`. Callable/`Defn` input: returns a `TransformCallable` `(*batched_specs) -> Graph` that strips the leading mapped dim from each mapped spec, traces the function exactly ONCE via `evoxc.trace`, then vectorizes + rearranges.
- `grad(fn_or_graph, argnums=None) -> Graph | TransformCallable` — reverse-mode gradients via the shared VJP machinery. Graph output must be exactly one scalar tensor (`ShapeError` otherwise). `argnums`: int or tuple/list of ints indexing the flattened **tensor** inputs (static values excluded); `None` = all tensor inputs. Selected inputs must be floating/complex (`TransformError` otherwise). Result graph: same inputs → one gradient tensor (int argnum) or a tuple of gradient tensors.
- `jvp(fn_or_graph, tangents) -> Graph | TransformCallable` — forward-mode. `tangents`: pytree of `TensorSpec` (or `None` = zero tangent) matching the **input** structure; shapes/dtypes must match the primal specs. Result graph inputs = primal inputs followed by tangent inputs (in flattened order); outputs = `(primal_outputs, tangent_outputs)`. With exactly one tensor input, a bare `TensorSpec`/`None` and a 1-tuple are also accepted (vectorize/vmap bare-axes precedent; static positions default to `None`).
- `vjp(fn_or_graph, cotangents=None) -> Graph | TransformCallable` — reverse-mode. `cotangents`: pytree of `TensorSpec` (or `None`) matching the **output** structure; `None` default = scalar-one cotangent `TensorSpec((), out_dtype)`, valid only for a single scalar output. With exactly one tensor output, a bare `TensorSpec`/`None` and a 1-tuple are also accepted (same normalization as `jvp`). Result graph inputs = primal inputs followed by cotangent inputs; outputs = `(primal_outputs, input_cotangents)`. Shares VJP rules with `grad`.
- Rule registries (public mutable dicts + register functions): `batching_rules` / `register_batching_rule(name, fn)`, `jvp_rules` / `register_jvp_rule(name, fn)`, `vjp_rules` / `register_vjp_rule(name, fn)`. Custom blocks register under the namespace **`block:<block_name>`** — that is exactly what `BlockOp.batching_rule/jvp_rule/vjp_rule(fn)` in `../block/` do (block imports transforms for registration; transforms never imports block, keeping the import graph acyclic).
- `register_batched_aux_remap(node_type, fn)` — batched-output aux remap registry for registered pytree output nodes with static-leaf children (e.g. a future sparse-tensor node). `fn(node: core.TreeSpec, static_values: tuple, batch_dim: core.Dim) -> tuple` receives the node's spec, its direct static-leaf child values (in child order), and the current pass's fresh batch `Dim`, and returns the REMAPPED static leaf values (the count may change); unregistered node types keep the current verbatim behavior (static leaves pass through unchanged with recomputed indices). Rejects `node_type is object` with a `TypeError` (mirror of `core.register_pytree_node`'s MRO-hijack guard).
- `batch_functions(fns, axes=0, out_axes=0, *, switch_ops=None, bands=None) -> Graph | TransformCallable` — merge N traced `Graph`s **or** N callables/`Defn`s (never mixed) that share IDENTICAL input/output signatures but differ in implementation into ONE `Graph` whose leading axis is a STATIC "function axis" of length N (row i evaluates function i). `bands` (keyword-only) selects the merge strategy: `None` = the flat merge, `int K` in `1..N` = K contiguous bands, `"auto"` = the cost model's partition. See **Batch functions** below.
- `BatchReport` / `SwitchRecord` — the merge report types (`graph.batch_report` on every `batch_functions` result; frozen `SwitchRecord` per switched position, `BatchReport` with `n_functions`, `value_classes`, `shared_classes`, `switched`, `stacked_constants`, `output_muxes`, `emitted_ops`, `bands`, `band_sizes`, `band_strategy`, `cost_estimate`, `flat_cost_estimate` + `as_dict()`).
- `TransformCallable` — the object returned for fn/`Defn` inputs; `__call__(*specs) -> Graph` (fresh graph per call); `kind` attribute (`"vmap" | "batch_functions" | "grad" | "jvp" | "vjp"`).

## The vectorize core (design, binding for implementation)

`vectorize(graph, axes)` walks the graph's function blocks in **topological order** and builds a **new** module/function (never mutates the input graph; `Graph`'s prebuilt-module constructor is used). Per value, the rewriting env records batching metadata (see **MappedAxes** below); per op, the machinery:

1. Looks up the operand metadata from the env (`ValueEnv`).
2. Fetches the op's rule: `batching_rules[op.def.name]`; for `block_call` ops the key is `block:<name>` taken from the op's block-name attribute, and for `external_call` ops `external:<name>` taken from the op's name attribute. A `block_call` with NO registered rule raises `TransformError` naming the block (the built-in pass-through rule for `elementwise`/`map_over_batch` blocks is pre-registered under `block:<name>` by `../block/` at declaration time — the rule channel; the `block_call` op carries no `batching_policy` attribute); an `external_call` with NO registered rule raises `TransformError` naming the op and hinting the external-kernel handle (`evoxc.register_external_kernel`). A registered rule always wins.
3. Pushes its own `ir.Builder` onto the trace builder stack and invokes the rule; rules build replacement ops with ordinary `evoxc.ops.*` functions (resolved via `trace.current_builder()`).
4. Records the returned values + metadata; seeds input metadata from `axes` (all mapped input specs share ONE fresh symbolic `Dim` as the leading dim — one pass = one batch axis; the dim is named from the active pass depth, `batch` at depth 0 / `batch_1` at depth 1 / ..., see `batching._batch_dim`; rank stays known).

The result `Graph` preserves `output_tree` and `static_values`; mapped outputs carry the leading batch dim; unmapped outputs are unchanged. Source locations of original ops are attached to replacement ops.

**Batched-output aux remap (registered pytree output nodes):** registered pytree nodes whose children include STATIC leaves (e.g. a future sparse-tensor node: children = [tensor leaves..., dense_shape ints, dtype, format]) get their OUTPUT static leaves remapped at the vectorize boundary via `register_batched_aux_remap` — the output tree's static leaves go stale when vectorize prepends a batch dim to the tensor outputs (the sparse value's dense_shape must gain the batch dim as a leading symbolic `Dim`). The rebuild (`batching._remap_output_aux`, step 6 of `vectorize_graph`) walks the output tree with two leaf counters (OLD-tree indices classify leaves against the recorded static records — registered nodes may change leaf counts, so old/new indices diverge; NEW-tree indices assign the rebuilt records), calls each registered node's fn with its direct static-leaf child values + the pass's batch `Dim` (the SAME object the mapped tensor specs carry, so the remapped dense_shape shares the batch Dim identity), and rebuilds the node's children as non-static children in original order + fresh plain-leaf `TreeSpec(type(None))` specs for the returned statics (the canonical normalized leaf — a `type=None` FIELD would classify as a TENSOR position in the pipeline's `_is_tensor_leaf_spec`, grad/vjp output-tree convention). INPUT-side static values stay unchanged — the batch lives in the flat tensor-leaf specs only, and dense_shape at the I/O boundary excludes the batch. Unregistered trees return the ORIGINAL `output_tree`/`output_static_values` objects (zero regression).

## The vmap ⇔ vectorize equivalence contract (binding, tested)

1. **Graph case**: `vmap(graph, in_axes, out_axes=0)` must produce the **same IR** as `vectorize(graph, in_axes)` — same ops, same input/output specs. Tests compare `ir.serialize_module` / `pretty_print` output for exact equality.
2. **Function case**: `vmap(f)(*batched_specs)` must produce the same IR as `vectorize(evoxc.trace(f, *stripped_specs), in_axes)` with `out_axes=0`, where `stripped_specs` removes the leading mapped dim from each mapped spec (dtype/device/name preserved).
3. **Rearrangement is post-processing**: `out_axes` handling (transpose of a mapped axis, insertion of a size-one axis) happens AFTER vectorize, as ordinary ops added to the already-vectorized graph — never inside batching rules. With `out_axes=0` there is no extra op at all.
4. **Once-only tracing**: the wrapped function is traced exactly once per `TransformCallable` invocation (tested with a call counter in `f`).
5. **Numerical check**: building + running the vmap graph on a batch equals running the unvectorized graph per row and stacking, for a fixed set of inputs.

`out_axes` semantics (v1): entry `0` ⇒ output must be mapped — its mapped axis stays leading; if the output is unmapped, a size-one axis is inserted at 0 (explicitly requested, allowed). Entry `None` ⇒ output must be unmapped; a mapped output raises `TransformError` (axis mismatch — a batch axis can never be silently dropped). Non-zero entries are deferred (see v1 scope).

## Batch functions (design, binding for implementation)

`batch_functions(fns, axes=0, out_axes=0, *, switch_ops=None)` merges a LIST of N programs with identical input AND output signatures but DIFFERENT implementations into ONE `Graph` whose leading axis is a **static "function axis"** of length N: row i evaluates function i. Binding semantics: for any run-time inputs, `run(merged, *inputs)` row i equals `run(graphs[i], *rowwise_inputs_i)` (a mapped input supplies row i of its leading axis, an unmapped input is shared by every function, static leaves are shared and validated).
`fns` must be a non-empty `collections.abc.Sequence` (`str`/`bytes` rejected) of traced `Graph`s **or** of callables/`Defn`s — never mixed; anything else is a `TypeError` naming `fns` and the offending element index.
Graph path → `Graph`; callable path → `TransformCallable` with `kind="batch_functions"` (its existing concrete-`Tensor` guard raises the `TraceError`), whose `build(*specs)` strips the leading mapped dim per spec, traces EVERY function exactly once with the SAME stripped specs, then runs the graph path with those pre-normalized entries.
`axes`: `0`/`None` or a pytree thereof, normalized EXACTLY like `vectorize` (bare int/None only for a one-tensor-input graph or a registered-node tree; recorded static positions must be `None`; entries must be `{0, None}`; non-zero ints are a v1 `TransformError`); `0` makes that input leaf's leading axis the function axis, `None` shares the input unmapped.
`out_axes`: one `0`/`None` per TENSOR output leaf (bare form only for ≤1 tensor output or a registered-node tree; static output positions must be `None`); `0` keeps the function axis, `None` requires the merged output to be unmapped (`TransformError`: a batch axis is never silently dropped); non-zero entries are a v1 `TransformError`.
`switch_ops`: `None`/`False` = no op switching (exact-structure sharing + value muxing only); `True` = the default merge groups `("elementwise", "comparison")`; any other non-`str` iterable = explicit groups, each a category name (validated against `{o.category for o in ir.all_opdefs()}`) or an iterable of IR op names (validated against the registry; empty or unknown → `TransformError`); anything else → `TypeError`.
Called callable-path with specs: the BATCHED args are normalized and stripped with `vmap._derive_unvectorized_args_and_entries` (shared with `vmap`; the same `_broadcast_registered_axes` / `_normalize_axis_entries` rules) and the traced graphs carry the STRIPPED specs — never re-normalize `axes` against the traced graph (an `axes=0` on a scalar-per-function input would mis-rank-check).
**The function axis is a static Python `int` (N), never a symbolic `Dim`** — the merged graph stays fully static so compiler backends can lower it, and every mask is a static bool constant.

### Phase 1 — class DAG (`_merge.py`, pure bookkeeping, no IR)

`variant_id(op) = (op.name, canonical_attributes(op.attributes))` with `canonical_attributes` deeply canonicalizing every leaf into something hashable and order-insensitive (dict → sorted key/`canon` items, ndarray → `(dtype, shape, bytes)`, `np.dtype` → `str`, `core.Dim`/`DimExpr` → structural tuples, `ir.ValueType` → itself, scalars tagged by type so `True`/`1`/`1.0` stay distinct).
`identity(op)` = `variant_id(op)` normally, `("constant",)` for constants (an ALWAYS-ON type-based merge: the payload is deliberately NOT part of the identity), or `("group", group_key)` when a merge group covers the op (first matching group in `switch_ops` declaration order wins).
`skeleton = (identity, operand_slots, result_types)`, where a slot is `(class_id, result_index)` for a program-op value or `("input", tensor_leaf_index)` for a function block argument.
`occurrence` = per `(program, skeleton)` the 0-based index of the distinct `variant_id`s seen for that skeleton in that program, in insertion order, so `class_key = (skeleton, occurrence)`: two DIFFERENT same-skeleton ops (or two different constants) inside ONE program land in SEPARATE classes while an exact repeat reuses one class, and every `(program, class)` pair holds at most one op.
Each class records its `(program_index, op, variant)` contributors (the op's `variant_id` is computed ONCE per op in `build_merge_dag` and carried) plus its distinct variants (first-appearance order) and result count; classes are numbered by a monotonically increasing int.
`ClassInfo.program_indices` returns the distinct contributor program indices in first-appearance order in ONE pass; `ClassInfo.representative_for(variant)` resolves a variant through a lazily built `{variant: (program_index, op)}` map, never by recomputing `variant_id`.
`_merge._opdef(name)` memoizes the IR op-def lookup (module-level cache) because `Op.opdef`/`Op.is_terminator` re-run the lazy `evoxc.ir.op_defs` import per op; the per-op hot path (`build_merge_dag`'s terminator skip, `MergeGroup.matches`, `batch_functions._check_ops`) goes through it.
Reachability is seeded from the output slots (each program's `return` operands) and walks operand slots transitively — unreachable classes (dead or function-local-only values) are dropped; emission order = first appearance scanning programs in order, each program's ops in program order, filtered to reachable classes (a valid topological order that reduces to the original program order for identical programs).

### Phase 2 — emission (`_emit.py`)

The new module/function is built exactly like `vectorize_graph` (same `ir.Builder`/`build_function`/`set_terminator` shape, all rule invocation inside `with trace.with_builder(builder):`), with the merged input specs computed from function 0's `TensorSpec` (name/device preserved; a mapped leaf just gains a leading `N`).
Emission runs inside `ops._utils._suppress_location_capture()` (a PRIVATE, re-entrant `contextlib.contextmanager` — not public API) because no location is taken from emission time: `_stamp_locations` re-assigns every rule-emitted op the contributing ORIGINAL op's location and `graph.source_locations` is carried from the original graphs, so skipping the per-op `inspect.stack()` capture is semantics-preserving.
The ONE location emission needs is the mux/broadcast helper call site, captured once into `_Merged.call_site` from `get_location()` before the suppression block opens.
`_stamp_locations(new_block, start, location)` stamps only `new_block.ops[start:]` — the tail produced by the current rule/constant — so stamping is linear in the newly emitted ops, not quadratic in the block.
Per class, in emission order: **constant class** → built directly with `ops.constant` (never through a rule): all payloads `np.array_equal` ⇒ ONE shared UNMAPPED constant, otherwise ONE stacked constant of shape `(N, *payload_shape)` where row i is function i's payload and every non-contributing row repeats the LOWEST contributing function's payload (never NaN; `stacked_constants += 1`) as a MAPPED value; **single-variant class** → the op is rebuilt ONCE through its registered batching rule, exactly as `vectorize` does (this is the zero-overhead path: identical programs emit no `select` at all); **switch class** (≥2 variants of one merge group) → every variant is emitted through its own rule over the SAME operand stack, the variants' `ir.ValueType` tuples must agree (else `TransformError` naming the group and suggesting dropping the op from `switch_ops`), then each result is muxed as `acc = variant_0; acc = select(mask_v, variant_v, acc)` with `mask_v` a static `(N,) + (1,)*row_rank` bool constant True exactly on that variant's function rows (variant 0 needs no mask); a `SwitchRecord` is appended in emission order.
**A switch class is ALWAYS MAPPED** — its value genuinely depends on the function row, so before the mux every candidate is aligned to the mapped `(N,) + (1,)*(target_row_rank - row_rank) + row_shape` shape (`_align_switch_candidate`): an UNMAPPED candidate (shared `axes=None` inputs ⇒ unmapped variants) is broadcast along a fresh leading axis, a MAPPED one keeps its values, and `target_row_rank` is the largest per-row rank among the candidates (identical variant result types make it the unbatched rank, so the padding term is normally zero); the mux result is recorded as `MappedAxes((0,))` so downstream rules and `_operand_axes` see consistent metadata, the mask rank follows the aligned rank (`1 + target_row_rank`), and a candidate that cannot be aligned raises an explicit `TransformError` naming the group and op instead of letting a raw `ShapeError` escape.
Operand axes come from the strict `ValueEnv` (every emitted value — including masks/selects/broadcasts — is recorded there, `MappedAxes((0,))` / `UNMAPPED`), masks and branches use TRAILING alignment (never leading-1s-only), and every directly-built op carries the contributing op's `ir.Location` while `graph.source_locations` is carried per merged value from the contributing op's result id (falling back to `op.location`).
Outputs, one value per tensor output leaf in output-leaf order: one distinct producing class → pass through, inserting `ops.broadcast(value, (N,) + value.type.shape)` only when the value is UNMAPPED and the `out_axes` entry is `0`; ≥2 distinct classes → `output_muxes += 1`, each class value is broadcast to the mapped `(N, *per_row_shape)` when unmapped and muxed by the same mask cascade (so a muxed output is ALWAYS mapped); a mapped value with `out_axes=None` (single-class or muxed) raises `TransformError`.
Cost model: identical programs cost exactly one `vectorize` pass (no selects, `emitted_ops` == the original op count); a switched position costs one op per variant plus one `select` (+ one mask constant) per extra variant per result, plus one `broadcast` per unmapped candidate (zero when the candidates are already mapped); a divergent output costs one broadcast per unmapped class plus one `select`/mask per extra class — nothing is ever evaluated per row.

### Bands — clustered merge (`bands=`, `_bands.py`)

`bands` splits the function axis into bands and merges each band INDEPENDENTLY with LOCAL program indices, then concatenates the per-band outputs along the function axis in band order — trading dispatch count for wasted work (the flat merge computes every variant of a divergent position on ALL N rows; a band computes only its OWN variants, on its own rows).
Values: `None` (default — the flat merge, graph BYTE-IDENTICAL to the pre-`bands` behaviour), `int K` with `1 <= K <= N` (`_bands.even_partition`, sizes as even as possible, LARGER bands first: N=10, K=3 → (4,3,3)), or `"auto"`.
`bands` is validated at the PUBLIC entry (`_bands.normalize_bands`) BEFORE `switch_ops` parsing and before any tracing, so the callable path rejects a bad `bands` without tracing a single function: a `bool` is a `TypeError` (never a band count), a non-`None`/`int`/`str` a `TypeError`, an out-of-range K or an unknown string a `core.TransformError` naming the accepted forms.
A partition is always a permutation of `0..N-1`: `K` bands are CONTIGUOUS, `"auto"` may be non-contiguous (fingerprint grouping) — row order is restored by ONE static inverse-permutation `gather` after the concatenation, emitted only when the band order is not `0..N-1`.
Single-band delegation (binding): `bands=1` — and an `"auto"` resolution that keeps every function together — delegate to the FLAT emitter, so their graph is byte-identical to `bands=None` and only the report's band fields differ.
Auto candidates (`_bands.plan_auto_partition`): (0) the flat partition, (1) the FINGERPRINT partition — programs grouped by `program_fingerprint` (per-op identity + operand refs + result types + terminator refs; constants fingerprint as one type-level class and switch-group ops as `("group", key)`, so "same structure, different weights" groups together) — and (2) the fingerprint partition with all SINGLETON groups coalesced into one trailing misc band; flat is candidate 0, so the chosen `cost_estimate` can never exceed `flat_cost_estimate` and the model never silently picks a pricier partition.
Cost model (`_bands.band_cost`/`partition_cost`/`op_work`, units "element-equivalents"): `cost(partition) = Σ over the classes each band emits (DISPATCH_COST + work(op) · rows) + BAND_OVERHEAD per band`, where `work(op) = static result elements × category weight` (`CATEGORY_WEIGHTS = {"linalg": 12, "reduction": 2, "sorting": 2, "sparse": 4}`, `DEFAULT_CATEGORY_WEIGHT = 1`, symbolic/`None` dims fall back to `SYMBOLIC_DIM_FALLBACK = 1`) and `rows` is the band size for a ROW-DEPENDENT class (one that reads a mapped input) and 1 otherwise; a switch class costs one op per distinct VARIANT plus its `select` mux, and constants cost `CONSTANT_COST`.
Each band is costed from its OWN class DAG (`_merge.build_merge_dag` over the band's graphs), so a position shared by two fingerprints is correctly charged once per band — the per-band overlap that makes banding pay off only when the saved rows outweigh the re-emission.
`DISPATCH_COST = 512.0` is the measured dispatcher/arithmetic crossover (one dispatch ≈ what 512 element-ops cost) and `BAND_OVERHEAD = 1024.0` covers the per-band input slice/gather plus the output concatenation; both are documented constants tuned on CPU, and the model is STATIC program metadata — never a measurement, never used for the explicit `K` path.
Per band the emitter reuses the flat machinery: `_emit.new_merged_module` builds the full block ARGS once, `_bands._BandInputs` materializes a band's view of each MAPPED input once per used input (`ops.slice` when the band's rows are contiguous and every trailing dim is a static int, else `ops.gather` with one cached int32 index constant), `_Merged` runs with `band_args` + `n = band_size` + `row_map`, and `_bands._combine_bands` broadcasts an UNMAPPED per-band value to `(band_size, *shape)`, concatenates the bands in partition order and applies the shared inverse-permutation `gather` when needed.
Masks use BAND-LOCAL row indices and the band size, while `SwitchRecord.rows_per_variant` stays in GLOBAL function indices (mapped through the partition) — a band with no switched position contributes no record.
Constants stack exactly as in the flat path (`(band_size, …)` payloads for that band's rows), so nothing changes semantically.
v1 restriction (`core.TransformError`, checked before the partition so `bands=1` obeys it too): `out_axes=None` is rejected whenever `bands` is not `None` — a per-band value cannot be one unmapped output; `bands=None` keeps today's `out_axes=None` behaviour exactly.
Everything stays STATIC (the function axis and every band size are Python ints, no symbolic `Dim` is introduced), so a banded merge is an ordinary graph that every backend lowers unchanged — validated end-to-end on iree/llvm-cpu (max abs error 8.8e-07 vs numpy).

Measured guidance (N=100, two `(64,)` f32 mapped inputs, depth-10 chains, best-of-N, numpy + iree-llvm-cpu + iree-ROCm/MI300X): banding is a large win exactly where programs DIVERGE and pure overhead where they agree.
`identical` → flat/auto (`bands="auto"` resolves to `bands=1`); any K>1 is a loss (up to 78× at K=100 on numpy).
`two_groups` (50+50 contiguous) → auto's 2 fingerprint bands: numpy 0.154 → 0.144 ms, llvm-cpu 1.171 → 0.624 ms (1.87×), ROCm neutral.
`random_trees` (100 unrelated chains with transcendentals) → numpy 3.32 → 2.24 ms, llvm-cpu 18.73 → 0.386 ms — a FLAT merge there is 4× SLOWER than not merging at all, banding makes it 12.3× vs the separate programs and 48× vs flat.
Compile cost grows with the band count (llvm-cpu, divergent population: flat 1.37 s, auto 1.84 s, K=100 1.85 s) but ONE merged compile always beats N separate compiles (1.8 s vs 19.8 s).
`bands="auto"` matched the measured argmin on 5 of 6 measured populations on numpy and llvm-cpu and never lost to flat there; it can be wrong on an accelerator (see Known Issues) — the data-supported rule is **`bands="auto"` on CPU, `bands=16` (or `bands=None`) on GPU**.
`switch_ops=True` should not be combined with banding: once the population is banded there is no cross-row position left to switch, and it measured 13–66 % slower in every configuration.

### Report (`graph.batch_report`)

A plain instance attribute (never part of the persisted payload — `Graph.save` ignores it, so a loaded graph has no `batch_report`). `BatchReport` fields: `n_functions`, `value_classes` (REACHABLE classes), `shared_classes` (classes contributed by ≥2 functions), `switched` (`SwitchRecord`s in emission order), `stacked_constants`, `output_muxes`, `emitted_ops` (`len(entry_block.ops) - 1`), plus the band fields `bands` (number of merge bands — 1 for the flat merge and for a single-band resolution), `band_sizes` (`(N,)` for a single band), `band_strategy` (`"flat"` / `"explicit"` / `"auto"`), `cost_estimate` and `flat_cost_estimate` (`None` unless the model ran, i.e. `bands="auto"`); `as_dict()` expands `SwitchRecord`s to plain dicts and `band_sizes` to a list and carries EXACTLY these 12 keys.
With several bands the per-class counters are TOTALS across bands: `value_classes`/`emitted_ops`/`stacked_constants`/`output_muxes` sum the bands (`emitted_ops` also counts the band input slices and the output concatenation), while `shared_classes` sums a band's classes contributed by ≥2 of THAT BAND's functions — the logical per-partition definition, because a class is "shared" when it saves work inside its band.
`SwitchRecord` is a frozen dataclass `(group, variants, rows_per_variant)`: `group` is the category name or `",".join(sorted(names))` for an explicit set, `variants` are the op names in first-appearance order, and `rows_per_variant` are the GLOBAL function indices using each variant (aligned with `variants`) — also under banding.

### Validation & errors (binding)

Across functions (function 0 against every k ≥ 1, paths rendered with `core.first_mismatch_path`/`core.format_path`): identical input tree structure (`TraceError`), tensor-leaf count, per-leaf dtype (`DTypeError`), shape (`ShapeError`) and device (`DeviceError`), recorded static input leaves by type+value (`TraceError`; ndarrays via `np.array_equal`), and the same for the output tree + output static values.
Program shape: single-function/single-block with a `return` terminator (`_entry_function`'s `TransformError` is re-raised with a `batch_functions: ` prefix) and block-arg count == `len(graph.tensor_specs)`.
Per op: any op without a batching rule (region-bearing `if`/`while`/`scan`, `runtime_call`, collectives, `sparse_*`/`random_*`, `sort`/`argsort`/`tile`/`flip`/`roll`/`diag`/`cumprod`/`nan_to_num`, the linalg factorizations, bitwise shifts, `block_call`/`external_call` without their namespaced rules, …) raises `TransformError` naming the op, the function index and (for region-bearing ops) that control flow is unsupported — rules resolve through `batching._rule_key(op)` + `batching.batching_rules` so the `block:<name>`/`external:<name>` namespacing works. A registered pytree output node carrying static leaves (`batching._lookup_batched_aux_remap(spec)` non-None anywhere in the output tree) is a v1 `TransformError` — no batched-aux remapping is attempted. `batch_report` is set only after the graph is fully emitted; `ir.verify` is NOT called here (`Graph.verify()` is the caller's job).

## Rule-call signatures (binding)

Rules are **pure graph builders**: they emit ops into the active transform builder (the machinery has pushed its `ir.Builder` onto the trace builder stack while a rule runs) and must never loop over batch elements or swallow errors.

**Proxy-op convention (implemented in `autodiff.py`, binding for JVP/VJP rules)**: the AD machinery rebuilds the full primal computation into a new module, so the ORIGINAL op's values are NOT the values rules must build on. Rules therefore receive a **proxy `ir.Op`** — a fresh dataclass instance never inserted into any block — carrying the original op's `name`/`id`/`attributes` (shallow-copied dict; leaf objects shared, read-only) and `location`, but whose `operands` and `results` are the RECREATED SSA values of the transformed graph (same types as the originals). `op.opdef`/`op.effect`/`op.result` resolve normally by name. Rules must treat the proxy as read-only and must NOT follow `value.owner`/`value.defining_op` off proxy values (those still point at the original op). The `constant` op is handled by the machinery itself (fixed data: output tangent = `ZeroTangent`; zero operands propagate nothing) — it has NO registry entry.

- **Batching**: `rule(op, operands, axes) -> (new_values, new_axes)` — `operands: tuple[ir.Value, ...]` are the **REWRITTEN** new-module operand values (NOT the originals — rules must build replacement ops over the values they receive; the originals stay accessible via `op.operands` and belong to the old module), `axes: tuple[MappedAxes, ...]` their metadata (aligned). Returns replacement SSA values aligned with `op.results` plus their metadata (real `MappedAxes` instances, leading-contiguous — the machinery validates both). A rule may emit any number of ops (e.g. a reduction rule shifts its axis argument; a dot rule builds a batched matmul).
- **JVP**: `rule(op, tangents) -> output_tangents` — `tangents` is a tuple of `ir.Value | None | ZeroTangent` aligned with `op.operands`; primal values are available as `op.operands` / `op.results`. Returns a tuple aligned with `op.results`.
- **VJP**: `rule(op, cotangents, primals) -> input_cotangents` — `cotangents` aligned with `op.results`; `primals` = the op's operand values. Returns a tuple of `ir.Value | None | ZeroTangent` aligned with `op.operands`; `None`/`ZeroTangent` mean zero gradient, materialized (as a zeros op) only when a real tensor is required (e.g. cotangent accumulation), keeping transformed graphs free of dead zero ops.

## Axis metadata (MappedAxes)

Per-value batching metadata in a transformed graph: a tuple of **leading** mapped axis indices — `(0,)` after one vectorization, `(0, 1)` after nesting two, `()` = unmapped (`UNMAPPED`). A value of shape `(a, b, c)` with axes `(0,)` has batch extent `a` and per-row dims `b, c`. Metadata lives in a `ValueEnv` keyed by value identity; rules receive operand metadata as arguments and never touch the env. Static operands (attributes) carry no metadata — they specialize, they don't batch.

## AD semantics (binding)

- `grad`: exactly one scalar output (`ShapeError` otherwise). Reverse mode = one backward sweep: per-op VJP rules applied in reverse topological order; cotangents of multiply-used values accumulate via `add`. The sweep is seeded with a scalar-one cotangent of the output dtype. `vjp` returns primal outputs + input cotangents; `grad` returns only the selected input gradients. `jvp` is a forward sweep seeded with the tangent inputs.
- `stop_gradient`: gradient/tangent = zero (`ZeroTangent`) in both directions.
- Boolean/int-producing ops (`equal`, `less`, `greater`, `argmax`, `argmin`, …) have builtin rules yielding `ZeroTangent` — their outputs cannot backpropagate, which is NOT an error.
- Ops with **no rule** — `runtime_call`, collectives, `external_call`, `block_call` of a block without a registered rule — raise `TransformError` naming the op/block (external-call keys `external:<name>` also name the `external_call` op and hint the external-kernel handle). No silent fallback, ever.
- **JVP derived from VJP**: when an op has a registered VJP rule but no JVP rule, the JVP sweep derives the JVP via the adjoint (double-vjp) trick instead of raising: the VJP rule's linear map L: c ↦ Jᵀc is instantiated with c = the op's primal results (any well-typed c works — L's adjoint is independent of the concrete c), then a second reverse sweep over L's emitted ops applies L's transpose (J) to the input tangents, propagating cotangents only along paths reaching a ct slot (paths to primals are second-order terms and are dropped — the decomposition's own vjp rules never run, keeping the graph free of dead second-order ops). All-zero tangents short-circuit to `ZeroTangent` without calling the rule.

## Spec-callable convention (design decision)

Transforms are graph→graph, but `vmap(f)/batch_functions(fns)/grad(f)/jvp(f)/vjp(f)` on bare functions cannot know input shapes at transform time, and importing pipeline/backends is forbidden. Therefore fn/`Defn` inputs return a `TransformCallable`: `tf(*specs) -> Graph`. Each public module's docstring states the exact expansion (trace → transform → rearrange), keeping every composition transparent — no hidden staging, no hidden execution. `evoxc.build(tf(*specs))` is the documented way to run the result.

## v1 scope vs deferred

- **v1 supported**: straight-line op graphs (all ops with registered rules); nested vmap via composition (rule support permitting); `stop_gradient`; custom blocks via `block:<name>` rules; `batch_functions` over any program whose ops ALL have batching rules (identical programs, switched positions and output muxes included) with any merge strategy — flat (`bands=None`), `bands=K` and `bands="auto"`.
- **Deferred → `TransformError`**: vectorizing region-bearing control-flow ops (`cond`/`while_loop`/`scan`) — no batching rules are registered for them in v1; non-zero `in_axes`/`out_axes` entries (mapped axes must be leading; transpose-based normalization is planned); vectorizing `runtime_call` (callbacks are per-value Python); `external_call` with NO `external:<name>` rules and no registered portable (the external-kernel rule surface — `ExternalKernel.batching_rule/jvp_rule/vjp_rule` + portable decomposition fallbacks — is live; see "Notes for agents").
- **`batch_functions`-specific deferrals (same rule)**: any op in any program without a batching rule (named with its function index), region-bearing control flow, a registered pytree OUTPUT node carrying static leaves (no batched-aux remapping), non-zero `axes`/`out_axes` entries, and `out_axes=None` on an output that ends up mapped (single mapped value or a mux).
- **Non-goals here**: no caching of transformed graphs (design principle 3), no backend awareness, no lowering.

## Constraints

- **Imports (binding)**: only `evoxc.core`, `evoxc.ir`, `evoxc.trace`, `evoxc.ops`, and this package's own submodules. NEVER `evoxc.backends` / `evoxc.pipeline` / `evoxc.dist` / `evoxc.block`. Block rules arrive through the registries (key `block:<name>`), keeping `block → transforms` one-directional.
- Files < ~1000 lines: machinery in `batching.py`/`autodiff.py`, builtin rules in `rules.py` (split per op category if it grows), entry points one file each.
- **Errors**: `TransformError` (missing rule, axis mismatch, bad out_axes, non-differentiable argnums), `ShapeError` (grad of non-scalar output), `TraceError` (concrete tensors passed to a `TransformCallable`), `TypeError` (wrong argument kinds). Messages name the offending op/block and include source locations where available.

## Known Issues

- **Rule-level v1 deferrals (raise `TransformError`, never silent)**: `gather` batching with mapped data + unmapped indices; multi-axis gather/scatter transforms; `solve` batching/AD with `left_side=False`; `conv` VJP (the IR has no transposed-convolution op — needs an opdef addition to close); `mean` VJP, `concatenate` VJP segment splits, and `pad` VJP inverses over symbolic dims (static dims work); `vmap(vjp(f))`/`vmap(jvp(f))` composition (their callables produce extended input trees the outer axes normalization cannot address yet — plain `vmap(vmap(f))` and `vmap(grad(f))` compose fine).
- **Mapped inputs of one pass share one runtime batch extent (intended)**: the per-pass shared `Dim` (named from the active pass depth — `batch` at depth 0, `batch_1` at depth 1, ... — see `batching._batch_dim`) makes the numpy interpreter's name-keyed input binding the within-level guard — a mismatched mapped extent raises a clear `ShapeError` ("dimension 'batch' is already bound to 4, got 1") instead of the silent numpy-style broadcasting that distinct per-input dims (`batch`/`batch_1`) used to allow.
- **Pointwise batching alignment**: every operand is reshaped to `own_batch_dims + (1,)*(max_row_rank − row_rank) + per_row_shape` before the op rebuild — do NOT regress to leading-1s-only insertion (that misaligns mapped rows against unmapped leading dims, e.g. `(batch,3)×(4,3)` would become `max(batch,4)` instead of `(batch,4,3)`).
- **`broadcast` batching edge (non-issue)**: an unvectorized `broadcast` whose operand rank is smaller than its target rank without expandable dims is statically invalid at trace time, so the batched rebuild `broadcast(x, batch_dims + original_target)` is always reachable/semantically correct.
- **Mapped `slice` is lowered, not shifted**: the IR slice op needs static int limits, so the batching rule lowers to `reshape → constant(arange) → gather → reshape` (batch dims folded through one symbolic-product reshape). `slice` VJP uses scatter into `primal·0` with static arange indices for strided axes.
- **Splicing ops into an existing module** (needed by `_rearrange_outputs`/`grad`): `ir.Builder` has no public API to position an insertion point at a block's end — use `InsertionPoint(block, len(block.ops))` pushed onto the private `builder._insertion_stack`; when replacing a `return` op's operands, first clear the stale `Use` records of its old operands (`value.uses[:] = [u for u in value.uses if u.owner is not ret]`) or `ir.verify` fails — the Use-check runs both directions.
- **No generic pass machinery exists here (no DCE, no CSE, no region rewriting).** The only graph rewrites are fixed-purpose: `vectorize_graph` (batching), the AD `_sweep` (autodiff), and `_insert_size_one_axes` (vmap out_axes). Region-bearing ops (`cond`/`while_loop`/`scan`) are hard-REJECTED, not walked: `vectorize` raises `TransformError` on any `op.regions` (`batching._rewrite_block`, batching.py:751-756) and the AD sweeps have no rules for control flow (rules.py:903 → `TransformError`). A graph-level transform that needs to inspect/rewrite `while`-loop carried values (e.g. packing/eliminating carries to shrink `stablehlo.while` carry counts) would be the FIRST region-walking transform and must build its own region-rewrite utilities — none of the existing machinery (batching env/remap, AD dual sweeps) can be reused for it.

## Notes for agents

- **Registered pytree nodes in axes normalization**: public `vmap`/`vectorize` axes normalization (in_axes, callable-path args, and out_axes) supports registered pytree nodes (e.g. the sparse-tensor node): a LEAF axes entry (int/None) at a registered-node position broadcasts across the node's leaves — every TENSOR leaf gets the entry, every STATIC leaf gets None (one axes leaf per node). A bare int/None works for any tree containing a registered node (applies to ALL tensor leaves); for plain dense trees the single-tensor-input restriction and its error message are unchanged. A CONTAINER axes entry at a registered-node position raises `core.TransformError` (v1: per-leaf axes for a registered node are deferred). Implemented in `vectorize._normalize_axes`/`_broadcast_registered_axes` (shared by `vmap._derive_unvectorized_args` and `vmap._rearrange_outputs`).
- **Batch dim names are level-distinct by design**: one `vectorize` pass creates ONE fresh `Dim` shared by all its mapped inputs, named from the active pass depth (`batching._batch_dim` — a contextvars counter, the builder-context pattern): depth 0 → `batch`, depth 1 → `batch_1`, depth 2 → `batch_2`, ... `vmap._vmap_fn` increments the depth (`batching.with_batch_depth`) around the invocation of a nested `TransformCallable`, so in `vmap(vmap(f))` the INNER pass names its dim `batch_1` and the OUTER pass `batch` — all names match `_BATCH_DIM_NAME`, so output-mappedness detection (identity-based) is unaffected. Rationale: the numpy interpreter binds symbolic dims BY NAME, so distinct nesting levels must never share a name (equal extents would accidentally pass; unequal extents would raise a misleading ShapeError on a valid graph). Scope: the depth covers TransformCallable composition only — vectorizing a graph that already carries batch dims via the Graph path (`vectorize(vectorize(g))`, `vmap(graph)`, no composition; both passes run at depth 0) still yields same-named dims and remains a documented v1 fail-explicit ShapeError for unequal extents.
- **AD registration is table-driven — a category-tuple op without a table entry is a latent bug**: every op in `ELEMENTWISE_OPS` (and the other category tuples) is auto-registered to the generic `_pointwise_jvp`/`_pointwise_vjp` handlers, which raise `TransformError` at TRACE time unless the op also appears in `_UNARY_DERIV` or `_POINTWISE_JVP`/`_POINTWISE_VJP` — the registry then advertises a rule that can never succeed (`sign` was exactly this; fixed via a `_UNARY_DERIV` entry with zero derivative). When adding an op to a category tuple, add its rule-table entry in the same change.
- `batching.block_call_pass_through_rule()` is the reusable built-in batching rule for elementwise/map_over_batch block calls — `../block/` pre-registers its product under `block:<name>` for blocks declared with those policies (the rule channel; the `block_call` op carries no `batching_policy` attribute — transforms never imports block). It rebuilds the `block_call` with `result_specs` == result types exactly (both must be the same `ir.ValueType` tuple — `ir.verify` enforces this), batch dims taken from the operand with the most mapped axes.
- **Rebuilding exactly ONE op has no public entry point**: the reusable pieces are `batching._resolve_batching_rule(op)` (key lookup incl. the `block:`/`external:` namespacing), the rule call `rule(op, rewritten_operands, operand_axes)`, and `batching._validate_rule_result(op, values, axes)`; the full `batching._rewrite_op(op, env, builder, remap, source_locations, graph)` only fits a straight old→new value remap (it derives the rewritten operands from `remap` itself), so a transform that merges or muxes several op variants must call the three pieces and replicate `_rewrite_op`'s ~6-line location/env bookkeeping (batching.py:788-801).
- `batching._operand_axes` is STRICT (`batching.py:805`): every operand value it is handed must already be recorded in the `ValueEnv` or the machinery raises `TransformError` — a new pass must seed the env for every value it emits, including values it muxed itself.
- External-kernel rule keys: `external_call` ops resolve via `external:<name>` (mirroring `block:<name>`), so a parallel package can register batching/vjp/jvp rules for external kernels under that namespace; the missing-rule `TransformError`s name the `external_call` op, show the key, and hint the external-kernel handle (`evoxc.register_external_kernel`).
- **Portable-decomposition VJP fallback seeding (binding)**: `../block/`'s fallback (`../block/rules.py::_portable_vjp_rule`) seeds its local reverse sweep on the decomposition's OUTPUTS — the post-inline values — NOT on the block_call's own result ids (which are never inserted into the builder; seeding on them would yield all-zero gradients). The AD sweeps rely on this contract; there is no repair layer in transforms.
- Rules must NEVER fall back to Python loops or silently no-op. If a cotangent is `None`/`ZeroTangent`, every returned input cotangent may be zero.
- `evoxc.trace` the ATTRIBUTE is the trace function (shadows the submodule) — inside scripts use `from evoxc.trace import trace as trace_fn`.
- `ir.verify` does NOT detect foreign-module value references — a rule that builds ops over `op.operands` (originals) can pass verify via id collisions while producing a semantically broken graph. Always build over the values the machinery passes.
- Zero-materialization is `ops.multiply(primal, 0)` + `ops.cast` when needed — an int `0` is weak toward float dtypes per the NEP-50 rules in `ops`.
- The mini IR interpreter used for numerical validation lives at `$TMPDIR/evoxc_numval/interp.py` (throwaway, not in the repo) — reuse it for numerical checks until the numpy backend lands.
- **Pytree handling is strictly LEAF-LEVEL (relevant to any structured-tensor design, e.g. sparse)**: transforms flatten axes/tangent/cotangent pytrees with `core.flatten` and validate structure via `core.first_mismatch_path`, but the graph's `input_specs`/`output_tree` TreeSpecs — including a registered node's `context`/aux — are preserved VERBATIM by `vectorize_graph`/the AD sweeps; nothing recomputes node-level aux when vectorize prepends batch dims or `_rearrange_outputs` inserts size-one axes (static values are likewise reused unchanged). `vmap._derive_unvectorized_args` is the only place that rebuilds a user pytree via `core.unflatten` (aux preserved but unmodified). Per-op rules never see pytrees: they receive flat `ir.Value` tuples + a static attributes dict, so a structured representation must carry shape data in operand value types or op attributes, and rules must prepend batch dims to result types themselves — `_rearrange_outputs`' mapped-output detection is by batch-`Dim` identity in the result shape (an unmapped-shaped result under `out_axes=0` silently gets a size-one axis inserted).
- `vmap._derive_unvectorized_args_and_entries(args, in_axes, what)` is the shared normalization/strip helper (`vmap` = `..._and_entries(..., "vmap")[0]`; `batch_functions` uses the full `(stripped_args, entries)` pair and must NOT re-normalize `axes` against the traced graphs, whose specs are already stripped/possibly rank-0).
- **`evoxc.transforms.vectorize` the NAME is shadowed by the re-exported function** inside the package: `from evoxc.transforms import vectorize` (or `import evoxc.transforms.vectorize as m`) binds the FUNCTION, not the module — import private helpers explicitly (`from evoxc.transforms.vectorize import _normalize_axes, _normalize_axis_entries, _is_int`).
- **`batch_functions` reuses the batching machinery, not `vectorize_graph`**: it calls `batching._rule_key(op)` + `batching.batching_rules[...]` (own error wording, names the function index), `batching._validate_rule_result`, `batching._tensor_input_axes`, `batching._entry_function`, and records EVERY emitted value in the strict `ValueEnv` (masks/selects/broadcasts included) — a value the machinery muxes itself but forgets to record breaks the next operand lookup.
- `_emit._broadcast` falls back to a raw `builder.create("broadcast", ...)` when the target shape contains `None`, because the frontend `ops.broadcast` rejects wildcard dims while the IR shape inference accepts them.
- A muxed `batch_functions` output is ALWAYS mapped (mapping is what makes row i take function i's value), so `out_axes=None` on a mux raises; the only legitimate `out_axes=None` merge is one whose output leaf is produced by a single class (typically identical programs, or a shared-input computation all functions agree on).
- When adding a public name here, update `__init__.py`, this CONTEXT.md, and the parent contract `../CONTEXT.md` together.
- `evoxc/__init__.py` (parent-owned) must re-export this surface: `vectorize`, `vmap`, `batch_functions`, `BatchReport`, `SwitchRecord`, `grad`, `jvp`, `vjp`, the three registries + register functions, `TransformCallable`.
