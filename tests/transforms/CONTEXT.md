# tests/transforms — graph-transform test suite

## Intent

Tests for `evoxc.transforms` (sibling binding contract: `../../evoxc/transforms/CONTEXT.md` — read it before changing anything). Transforms are **graph→graph and never execute**: every numerical check builds the transformed `Graph` from `TensorSpec`s, verifies it (`graph.verify()`), and runs it through the explicit staging pipeline (`lower → compile → load → run`), comparing against numpy finite-difference or per-row references. Error-path tests assert `TransformError`/`ShapeError`/`TraceError`/`TypeError` per the v1 restrictions (mapped axes ∈ {None, 0} with leading-only mapping; control flow not vectorizable; ruleless ops fail loudly — never a silent fallback).

## Structure

- `_fd_utils.py` — shared helpers (leading underscore keeps pytest from collecting it): `run_graph` (explicit staging), `to_np` (Tensor→numpy), `central_directional` / `central_jacobian` / `central_grad` (float64 numpy central differences), and `run_jvp` / `run_vjp` / `run_grad` (transform → verify → run).
- `test_vectorize.py` — the batching primitive: per-op numerics vs stacked per-row runs (add/mul/dot/sum), dict/tuple `in_axes` with unmapped broadcast, result contains NO `vectorize` op, input graph not mutated, ONE shared `Dim('batch')` per pass (object identity across mapped inputs and the mapped output; no `batch_1` dims / DimExprs), vectorize on already-symbolic row specs (`(B, 16)`) preserving the row dim by identity with correct numpy-backend numerics, validation errors (bare callable → TypeError pointing at `evoxc.vmap`; non-leading/out-of-range axes; pytree mismatch; bare axes with multiple tensor inputs).
- `test_vmap.py` — sugar equivalence: vmap⇔vectorize IR equality (serialize_module + pretty_print, fn and Graph cases), `TransformCallable` kind/Graph return, once-only tracing, numerics, default `in_axes=0` + unmapped-arg broadcast, `out_axes` semantics (None-on-mapped → TransformError, size-one insertion for unmapped, non-zero deferred); external-kernel rule channel (batching half): vmap/vectorize over `external_call` with an explicit `external:<name>` batching rule (registered via the `evoxc.register_external_kernel` handle), the portable-decomposition fallback (`@handle.portable` — re-traces the decomposition over batched operands, no `external_call` left in the graph), and explicit-rule-wins-over-portable (a rule registered after the fallback overwrites it — registry lookup + vmap semantics; kernels/rules registered at module scope under unique `tx_ext_*` names).
- `test_grad.py` — reverse mode: analytic checks (x²+3x → 2x+3), argnums int/tuple/None (incl. static inputs excluded from numbering), non-scalar/multi-output → `ShapeError`, documented ZeroTangent zeros (argmax/equal), sign's implemented zero-derivative rule (`sum(sign(x))` → all-zeros gradient; `sum(x*sign(x))` = `sum(abs(x))` → gradient `sign(x)` vs analytic + central difference), `runtime_call` → `TransformError`, Graph-form ≡ callable-form, argnums validation errors.
- `test_jvp.py` — forward mode vs central directional differences, tangent normalization (bare spec / 1-tuple / bare None spellings; None = zero tangent), structure/shape/dtype mismatch → `TransformError`, Graph-form ≡ callable-form, concrete Tensor → `TraceError`, `runtime_call` → `TransformError`, zero-tangent rules (argmax/equal, sign).
- `test_vjp.py` — reverse mode: default scalar-one cotangent equals `grad` result, pullback == ct @ finite-difference Jacobian, multi-output cotangent pytrees, cotangent mismatch errors, non-scalar/multi-output with cotangents=None → `ShapeError`, stop_gradient → zero cotangent, sign's zero-derivative rule → all-zeros input cotangent.
- `test_autodiff_rules.py` — chain rule through composites vs finite differences: grad of dot (2D×2D; `evoxc.dot` requires rank ≥ 2 by design — 1D·1D inner product is composed as multiply+sum), sigmoid, reduce_sum(x²), reshape, transpose, broadcast; jvp AND vjp through dot/sigmoid/reshape/transpose; stop_gradient blocks gradient flow; chained elementwise ops; deferred conv VJP → `TransformError`; external-kernel rule channel (AD half): grad/vjp over `external_call` with an explicit `external:<name>` vjp rule, jvp derived from that vjp rule (adjoint) AND via an explicit `external:<name>` jvp rule, grad/vjp through the portable-decomposition fallback (incl. a REAL non-scalar cotangent on the vjp — exercises the post-inline cotangent seeding), and grad through a block portable whose body contains a nested `external_call` resolving its own `external:<name>` vjp rule during the block fallback sweep.
- `test_errors.py` — TransformError paths: axis errors (non-zero/out-of-range/mismatch/mapped-static), ruleless ops (`runtime_call`, collectives like `all_reduce`, control flow) under vmap/grad/jvp/vjp, argnums/tangent/cotangent validation, concrete-Tensor rejection for all four `TransformCallable` kinds, plus the documented zero-gradient behavior of argmax/equal (NOT errors); `external_call` with NO rule and NO portable → `TransformError` naming the op AND the `external:<name>` key (`no VJP/JVP/batching rule for op 'external_call' (key 'external:…')`) with the `evoxc.register_external_kernel` hint (the namespaced message format) for grad/vjp/jvp/vmap/vectorize.
- `test_equivalence_meta.py` — transformed graphs are ordinary graphs: `verify()` passes, no banned transform op names anywhere in the module (walk all blocks/regions), every op resolves to a registered opdef, `main` has a `return` terminator; `TransformCallable.kind` values; input-graph non-mutation (serialize before == after) for all five graph-form transforms.
- `test_vmap_control_flow.py` — v1 restriction behavior: vmap/vectorize over `cond`/`while_loop`/`scan` → `TransformError` ("cannot batch op 'if'/'while' … not vectorizable in v1"), grad/jvp/vjp over control flow → "no VJP/JVP rule for op 'if'"; plain `evoxc.trace` of the same functions still succeeds (restriction is transform-only).

## Conventions

- Finite-difference references are computed in **float64**; float32 tests use a coarser step (a 1e-6 step would be dominated by float32 rounding). Settings: f64 → eps 1e-6, rtol 1e-7; f32 → eps 1e-3, rtol 1e-5; atol 1e-6 both.
- Runtime args mirror the transformed graph's input tree: jvp/vjp graphs take `(primal input tree, flat tangent/cotangent tuple)`; `None` tangent/cotangent entries are passed as `None` leaves at runtime; `grad` graphs keep the original input tree (static leaves included).
- `grad` with an int argnum returns a bare tensor; `argnums=None`/tuple returns a tuple (even a 1-tuple).
- Small shapes (≤ 5×4×4), CPU only, each file <2s; parametrize fns × dtypes instead of looping. The `batch_functions` families are the exception: they need elementwise populations on `(4,)`–`(1024,)` vectors (and 32-program chains) to exercise sharing/switch/band structure — still cheap, still CPU only.

## Notes for agents

- The traced input tree wraps EACH argument (root tuple → one child per argument); a dict-taking fn therefore needs axes as a 1-tuple wrapping the dict, e.g. `vectorize(g, ({"a": 0, "b": None},))`.
- `evoxc.run` returns a bare `Tensor` for single outputs and a tuple for structured outputs; `Tensor` has no `__array__` protocol — convert via `.numpy()` (the `to_np` helper).
- `evoxc.sum` axes must be an int/tuple (lists raise TypeError); `evoxc.evaluate` rejects static (non-tensor) args — use numpy references there.
- `evoxc.scan` lowers a step-0 `gather` into the entry block, so vectorizing it raises the gather deferral ("cannot batch op 'gather' with mapped data but unmapped indices") before the `while` op is reached — still a TransformError per contract (use `in_axes=(0, None)` on the scan state to reach the `while` path).
- When a test exposes behavior contradicting the evoxc contract, do NOT fix evoxc (sibling, read-only) and do NOT weaken the test: mark it with `# BUG(evoxc): <description>` and keep it failing, with the repro recorded in this file's Known Issues.
- `evoxc.build`/`evoxc.evaluate` do NOT accept a `TransformCallable` or a transformed `Graph` (they trace a callable; vmap/grad/batch_functions all raise the same way) — stage the graph with the explicit `lower → compile → load → run` chain instead, and call the spec-callable (`transform(*specs)`) to obtain the graph.
- A merge's own mask `constant`s and `select`s carry the `batch_functions` CALL-SITE `Location`, so two `serialize_module` comparisons are byte-identical only when both merges are invoked from the same source line.
- **The `alignment` default is `"variant"`** (`_merge.DEFAULT_ALIGNMENT = ALIGNMENT_VARIANT`, so `inspect.signature(evoxc.batch_functions).parameters["alignment"].default == "variant"`); `"occurrence"` remains an accepted explicit value — the byte-stable legacy policy, so any pin stating occurrence counts passes `alignment="occurrence"` explicitly. `test_batch_functions_alignment.py` is the authority on that default — do not restate it elsewhere; any count/op-sequence assertion whose value depends on alignment belongs here or passes `alignment=` explicitly.
- Measured `alignment` effect at this HEAD on the branchy `(x + c) * (x - c)` population with a shared reduction: `"occurrence"` emits 19 ops with 3 `select`s, `"variant"` 7 ops with 0 (`"auto"` picks `"variant"`); without the shared reduction 17/3 vs 6/0. Constants always stack by OCCURRENCE, so `"variant"` never splits a shared constant.
- `bands=1` (and an auto-resolved single band) delegates to the flat emitter and only rewrites the report's band fields — the graph is byte-identical to `bands=None`, which is what the export-text AND entry-block op-name pins assert.
- `bands="auto"`'s partition is population-dependent (`_bands.plan_auto_partition` candidates, in priority order: flat, structural-fingerprint, fingerprint-with-a-trailing-misc-band, then the geometric ladder `ladder_partitions` — `k` in `AUTO_BAND_LADDER = (2, 4, 8, 16, 32, 64)` clipped to `2..N-1` plus `k = N`; earlier wins a tie, so `cost_estimate <= flat_cost_estimate` always).
  Cost model: `DISPATCH_COST=512`, `BAND_OVERHEAD=8192`, `CONSTANT_COST=128`, and ROW-DEPENDENCE PROPAGATES through the class DAG (mapped inputs, switch classes and stacked constants seed it), so a switched class is priced per row (one op per variant + a per-row `select` mux) and a shared-input (`axes=None`) chain whose only per-program difference is a stacked constant is per-row too.
  Pin only MEASURED partitions: the two-group length-1024 population (`(x + c) + c` ×5 vs `(x * c) - c` ×5) gives 2 fingerprint bands `(5,5)` both plain and under `switch_ops=True` — the switched case costing `39168.0` against a flat `64640.0` (the unswitched flat estimate is `43136.0`); a seeded 16-program GP population over a shared `(1024,)` spec gives 8 bands of 2 (`225280.0 < 727040.0`, the ladder's win).
- The one-call-site pin must target the DRIVERS' `get_location` SEAM, not `inspect.stack`: `evoxc.transforms._emit` and `evoxc.transforms._bands` each bind `get_location` by value (`from evoxc.ops._utils import get_location`), so a delegating wrapper around each binding intercepts exactly the ONE capture a merge makes outside its suppression block — exactly one of the two paths fires per merge, and the captured value is a REAL location.
  `inspect.stack` is pinned separately, at ZERO calls: location capture is a `sys._getframe` walk (`get_location` + the memoized `_inside_evoxc_package`), and a raising `inspect.stack` stand-in must never be reached.
  Do NOT pin `_inside_evoxc_package` per merge — it is called once per candidate FRAME (4 today: three evoxc frames plus the user frame) and drifts whenever an internal helper frame is added; pin it only for the direct mechanism test (0 while suppressed, exactly 1 for one real capture from a test body).
- Banded merged graphs replay the same per-op numpy kernels as per-program runs, so row comparisons are bit-exact (`np.array_equal`); none of the `batch_functions` files assert timing — the speed hooks are pinned structurally (`emitted_ops`, the captured-call-site count).
