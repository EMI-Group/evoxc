# evoxc — EvoX Compiler

## Intent

A **minimal, explicit, compiler-neutral tensor graph compiler and runtime** (Python-first), named **EvoX Compiler**. evoxc provides an ergonomic tensor-graph language — its input language — for constructing, transforming, inspecting, caching, loading, and executing computational graphs, and it owns everything above the runtime boundary: the frontend language and its ops, EvoXIR, the graph transforms, explicit staging, and the backend-adapter contract. It deliberately does **not** own optimization, kernel scheduling, memory planning, or hardware code generation — those belong to external compilers (IREE, XLA via PJRT, TVM).

**Defining principle: Make computation explicit, require large tensors to be explicit inputs, keep `vmap` as transparent function-side sugar over `vectorize`, keep binding as transparent argument-passing sugar, keep communication, multi-device tensor preparation, and tensor placement/transfer explicit, expose and persist the graph, and let compilers do the compilation.**

evoxc learns from Nx (explicit numerical language, `block`, `vectorize`, `runtime_call`, backend abstraction), early JAX (NumPy ergonomics, `vmap`/`grad`/`jvp`/`vjp`), PyTorch (interop), and tinygrad (small inspectable IR). The Python API stays semantically close to Elixir Nx so a future Elixir implementation can extend Nx rather than duplicate it.

## Design principles (binding for all submodules)

1. **The graph is the program.** `@evoxc.defn` marks a numerical graph definition — it is NOT JIT or eager execution. There is no implicit tracing and no eager/graph mode switching.
2. **Explicit staging.** Pipeline: `defn → trace → Graph → transform → Graph → lower → LoweredProgram → compile → CompiledArtifact → load → Executable → run → Tensor`. Every stage has an explicit public function. Convenience APIs (`evoxc.build`, `evoxc.evaluate`) are *documented shorthand* compositions only — no additional hidden semantics.
3. **Minimal magic.** No API silently traces, compiles, specializes, moves/reshards tensors, inserts collectives, executes Python callbacks, or switches semantics. Caching/binding are explicit operations. Sugar is allowed only as transparent composition of explicit primitives.
4. **Python value → Python semantics; SymbolicTensor → graph semantics.** `if evoxc.sum(x) > 0:` must fail clearly; runtime tensor control flow is `evoxc.cond` / `evoxc.while_loop` / `evoxc.scan`.
5. **Local tensors + explicit communication.** A tensor is always a local physical tensor. Collectives (`evoxc.dist.*`) appear explicitly in the program; the compiler may optimize but never invent communication. Multi-device helpers (`split_tensor`, `replicate_tensor`) are explicit data-preparation utilities, not sharding transformations. **Placement is physical and explicit:** a `Tensor`'s `device` always says where its data actually lives — numpy host data can only be `Device('cpu', 0)`, and device payloads carry their real device (no label-only "virtual" devices, no relabeling). The ONLY device↔host movement primitive is `Tensor.to(device)`; run outputs stay on the device they ran on (never auto-copied to host); no API silently moves/copies tensor data, and data that is not where an API needs it raises `DeviceError` (`split_tensor`/`replicate_tensor` are v1 cpu-only host-memory utilities; `evoxc.constant` and graph embedding accept host data only).
6. **Large tensors must be explicit inputs.** Capturing a concrete `Tensor` from a closure into a graph is an error. `evoxc.constant(w)` is the only (explicit, warned) way to embed tensors. `evoxc.bind` is argument-passing sugar only.
7. **Frontend transformations are graph→graph.** `vectorize`/`vmap`/`grad`/`jvp`/`vjp` produce ordinary graphs of ordinary ops. Backends never need to understand `vmap` or Python containers.
8. **Compiler-neutral IR.** EvoXIR (region-based SSA) is the frontend IR. StableHLO is an important export target but not the definition of the IR. Backend limitations fail explicitly.
9. **No eager numerical implementation duplication.** Concrete creators (`evoxc.zeros`, `evoxc.tensor`, `evoxc.from_numpy`, …) and a reference CPU backend are the only concrete-computation paths; random generation, `linspace`, etc. go through compiled graphs.

## Value model (four distinct concepts)

| Concept | Meaning | Has storage? | Key capabilities |
|---|---|---|---|
| Python/static value | `None`, bool, int, float, complex, str, Enum, dtype, slice, config objects | n/a | Evaluated at trace time; specializes the graph. Changing it = new graph. No hidden guards/recompile. |
| `TensorSpec` | Describes a future runtime tensor | No | `shape` (symbolic dims allowed), `dtype`, optional `device`. Lifecycle: spec → trace → SymbolicTensor → run → Tensor. |
| `SymbolicTensor` | SSA value inside a graph | **No** | dtype, symbolic shape, source location, SSA identity. `x.numpy()`, `data_ptr()`, `__dlpack__` must NOT exist on it. |
| `Tensor` | Materialized runtime tensor | Yes | dtype, concrete shape, **physical** device (numpy host data ⇒ `Device('cpu', 0)`; device payloads carry their real device), explicit `Tensor.to(device)` transfers, DLPack interop (`from_dlpack` / `__dlpack__`; device payloads that implement the optional payload protocol export their buffer zero-copy — `torch.from_dlpack(t)` on a rocm/cuda tensor shares the device memory), `.numpy()` — host data only: on a non-cpu tensor it raises `DeviceError` (`.to(cpu)` first; cpu-kind payloads like llvm-cpu map lazily). Wraps numpy host memory (v1) or device buffers (iree, v1). |

## Architecture overview

```
                         evoxc  (package)
        tensor-graph frontend (ops core, numpy namespace, trace, block)
        graph transforms (transforms: vectorize/vmap/grad/jvp/vjp)
        explicit collectives (dist)
                         │
                         ▼
                      EvoXIR (ir)
                         │
              ┌──────────┼───────────┐
              ▼          ▼           ▼
          StableHLO     native     (future: Relax/TVM, PJRT/XLA)
          (export)      numpy interpreter backend
────────────────── runtime boundary ──────────────────
                     Tensor  +  DLPack
```

**Pipeline objects (public types):** `Defn`, `Graph`, `LoweredProgram`, `CompiledArtifact`, `Executable`, `Tensor`. Each is a distinct public type; functions never silently consume an earlier-stage object and perform missing steps.

## Cross-module contracts (binding)

**Import acyclicity (strict):** dependency layers, each importing only lower layers:
`core` ← `ir` ← `ops` ← {`trace`, `numpy`(enp)} ← {`block`, `transforms`, `backends`, `dist`, `sparse`, `pipeline`, `persist`}.
Details: `core` imports nothing from evoxc (numpy only). `ir` imports `core`. `ops` imports `core`, `ir`, `trace` (for the active-builder hook — `trace` must NOT import `ops`). `trace` imports `core`, `ir`. `block` imports `core`, `ir`, `ops`, `trace` (lazily for portable tracing). `transforms` imports `core`, `ir`, `ops`, `trace`. `backends` imports `core`, `ir` (plus lazy `ops`/`block` access for block-impl registration). `dist` imports `core`, `ir`, `trace`. `sparse` imports `core`, `ir`, `trace`, `ops`, `transforms` (rules register one-way into `transforms`' public registries; never imports `pipeline`/`backends` — `evoxc.evaluate` lazy-imports sparse inside the function). `pipeline` imports `trace`, `backends`, `core`. `persist` imports `core` only. `io` imports `core` only (stdlib at module top; numpy/iree lazy inside functions). `build_cache` imports `core` and `persist` (its `cache`/`codec` submodules — `Cache`/`compute_key`/`encode_value`), with `pipeline`/`trace` imported lazily inside `build_cached`.

**`evoxc_hf` (the `evoxc-hf` distribution, a `uv`-workspace member — not an evoxc submodule)** imports `evoxc` only — the dependency direction is one-way and `evoxc` must NEVER import `evoxc_hf`.
It may only use evoxc's public API; evoxc-core gaps are worked around inside `evoxc_hf` and documented in `./evoxc_hf/CONTEXT.md` (a missing op or exporter deferral is never patched by editing `./evoxc/`).
The two distributions share one repository and one root `uv.lock` but publish separately, with one version per project: `[tool.uv.workspace] members = ["evoxc_hf"]` in `./pyproject.toml` makes the member its own `uv_build` project (src layout `evoxc_hf/src/evoxc_hf/`, own `pyproject.toml`/`README.md`/`LICENSE`, version, extras `hf`/`dev`, release tag `evoxc-hf-v<version>`), and `[tool.uv.sources] evoxc = { workspace = true }` resolves its `evoxc>=0.1.0` dependency from that root project rather than PyPI.
Each distribution ships exactly ONE module — `evoxc` from the repository root (`module-name = "evoxc"`), `evoxc_hf` from the member's `src/` (`module-name = "evoxc_hf"`) — so no `evoxc` wheel/sdist contains `evoxc_hf` and no `evoxc-hf` wheel/sdist contains `evoxc`.
Development and CI install both with `uv sync --all-packages` (a plain `uv sync` installs the root project only and uninstalls the member, leaving an importable-looking namespace package behind).
`evoxc-hf`'s `hf` extra (`torch` + `transformers`) is oracle-only — the reference implementations used to validate and benchmark it, never runtime requirements; evoxc's own extras carry no torch/transformers, and `pip install evoxc[iree]` enables the compiled path.
`./tests/test_packaging.py` pins all of this.

**Key shared contracts** (defined in `./evoxc/CONTEXT.md` and owned by the listed module):
- `core`: dtypes, `Dim`/`DimExpr` (symbolic shapes), `TensorSpec`, `Tensor`, `SymbolicTensor`, `Device`, TreeSpec + pytree utilities (`flatten`/`unflatten`, `tree_map`, `tree_leaves`, `tree_structure`, `tree_flatten`/`tree_unflatten` aliases, `register_pytree_node`), structure-mismatch contract (`first_mismatch_path`/`format_path`/`describe_node` — internal, used by trace/pipeline/transforms), device helpers (`devices` — enumerates `cpu` plus any present cuda/rocm devices, probing ROCm via the iree HIP driver so it lazy-imports iree; `split_tensor`/`replicate_tensor` — v1 cpu-only), the explicit-transfer primitive `Tensor.to(device)` + the dual device-transfer provider registry (per-backend `register_backend_device_transfer_provider(kind, backend, provider)` slots — each adapter registers its own `upload_tensor`, order-independent — and the legacy flat `register_device_transfer_provider(kind, provider)` DEFAULT slot where `evoxc.backends` installs the lazy iree cuda thunk at import; `Tensor.to` resolves the owning backend's slot then the flat default; `evoxc.constant`/graph embedding accept host data only), plus a **registration hook** so `ops` can install `SymbolicTensor` operator handlers without import cycles.
- `ir`: `Value`, `Op`, `Block`, `Region`, `Function`, `Module`, `Builder`, `Location`, effect annotations, `verify()`, IR serialization.
- `ops`: frontend op functions (`add`, `dot`, `sum`, `reshape`, …) + `runtime_call`. Top-level op exports not enumerated in the deferral/status lists: `arange` (graph Constant), stats compositions `median`/`nansum`/`std`/`var`, `norm` (vector norms only, ord ∈ {1,2,±inf}), `diagonal`; `Capabilities` and `__version__` are also top-level exports. Called with `SymbolicTensor` → builds IR into the active builder; called with concrete `Tensor` → `TraceError` (no eager mode, clear message suggesting `evoxc.constant` / explicit inputs / `evoxc.evaluate`); called outside a trace → `TraceError`.
- `trace`: `defn`, `trace`, `Graph`, `cond`, `while_loop`, `scan`, current-builder context, static-value snapshotting.
- `block`: custom ops — declaration, portable impl, per-backend impl registry, batching rules, derivative rules.
- `transforms`: `vectorize`, `vmap`, `grad`, `jvp`, `vjp` — graph→graph.
- `backends`: `Backend` interface (`lower`/`compile`/`load`/capabilities), registry (lazy activation of optional adapters), numpy interpreter backend (default, CPU), stablehlo exporter (MLIR text — also the shared lowering input for compiler backends), and pluggable compiler adapters `iree` / `xla` (PJRT C API via ctypes over a plugin `.so` it DISCOVERS — the `plugin_path` option, `EVOXC_PJRT_PLUGIN`, the fixed well-known paths, then an installed JAX `jax_plugins/<platform>/<name>_plugin.so`; `EVOXC_PJRT_PLUGIN_DISCOVERY=0` opts out of that last step; no jax/jaxlib import) / `tvm` (jaxlib only for its bundled MLIR bindings — the `jax` package is never imported) in `evoxc.backends.adapters` — optional, activated by `lower(..., backend="iree"|"xla"|"tvm")`, explicit errors when absent: iree/tvm probe their pip package in `register()` and raise there with a pip-install hint, while `xla` registers UNCONDITIONALLY (its plugin is a per-call `plugin_path`/env/discovered artifact, so the four-step discovery message — naming the pip-installable `jax-rocm7-pjrt`/`jax-cuda12-pjrt` plugins and the OpenXLA source build — comes from `compile`/`load`, with `XlaBackend.check_available()` as the explicit option-less preflight). Every stage takes options and `build`/`evaluate`/`build_cached` forward ONE resolved options dict to `lower`, `compile` AND `load` (a load-stage option such as `plugin_path` therefore reaches the load hop through the sugar too). Compile/lower options are first-class and env-aware (`./evoxc/backends/options.py` + `./evoxc/pipeline_options.py`: `EVOXC_<OPTION>` defaults, precedence explicit > env > default, and a raw same-name flag in a backend's own args wins — never both): `opt_level` (`"O0"`–`"O3"` / `0`–`3`, env `EVOXC_OPT_LEVEL`; iree → the derived `--iree-opt-level=O{N}` flag, xla → `executable_build_options` wire-format field 24, tvm → the `opt_level=` build kwarg, numpy documented-ignored) and `dispatch_formation` (iree: `"default"`/unset emits no flag — byte-identical compile args — `"aggressive"` emits `--iree-dispatch-creation-enable-aggressive-fusion`, env `EVOXC_DISPATCH_FORMATION`, an unknown value a loud `BackendError`; measured on a merged GP-population graph it takes 596 → 548 dispatches, −5 % compile at pop 4000 and −7…−9 % warm on rocm while llvm-cpu is flat-to-worse, so it ships OPT-IN and is enabled for rocm merged plans — evidence `./evoxc/bench/dispatch_formation_findings.md` + its probe and JSON records). The rest of the per-call option surface (`rng_bit_generator`, `dot_precision`, `eigh_algorithm`, `split_reduction`, `sort_emission`, `while_init_rewrite`, `vulkan_target`, `plugin_path`) is owned by `./evoxc/backends/adapters/CONTEXT.md`.
`remainder` is numpy floormod on every backend: the op contract takes the sign of the divisor, the numpy kernel is `np.remainder`, and the StableHLO exporter emits `stablehlo.remainder` (fmod) plus the inline sign correction (unsigned dtypes need none), so one graph gives the same values on the numpy interpreter and on iree.
- `dist`: `group`, collectives (`all_reduce`, `all_gather`, `reduce_scatter`, `all_to_all`, `broadcast`, `collective_permute`), `rank`/`world_size` graph scalars.
- `sparse`: sparse tensor value model + 16 graph ops + per-op batching/vjp/jvp rules — full surface in `./evoxc/CONTEXT.md`; numpy-backend-only in v1 (compiler backends defer explicitly).
- `pipeline`: `LoweredProgram`, `CompiledArtifact`, `lower`, `compile`, `load`, `run`, `bind`, `build`, `evaluate`, and the explicit `Executable.synchronize()` (waits for device work submitted by earlier `run()` calls; `BoundExecutable` delegates; a no-op where the backend's `run` already blocks — iree/numpy — because the xla device-resident `run` only ENQUEUES, so a wall-clock measurement must timestamp `run` + `synchronize`).
- `persist`: versioned/self-describing/integrity-checked save-load container, explicit `Cache`.
- `io`: explicit async host↔device copy sugar over the explicit `Tensor.to` transfer — `prefetch(host_tensor, device)`/`sink(device_tensor)` → `AsyncCopy` handles (`.device`, `.direction` `"host_to_device"`/`"device_to_host"`, `.done`, `.wait(timeout=None)`, `.result(timeout=None)`), `wait_all(timeout=None)`; one process-global FIFO daemon worker executes the copies — schedule-time validation synchronous, transfer errors surface verbatim at wait/result, wait timeouts never cancel.
- `build_cache`: memoized-build shorthand for meta-level loops — `build_cached(fn, *specs, backend=None, device=None, cache=None, **options)` → `Executable`, keyed BEFORE tracing (fn identity + keepalive, full specs tree, resolved backend/device, canonicalized options); `CompileCache` (in-memory LRU `Cache`, maxsize 128, `hits`/`misses`).

## Error strategy (binding)

All public errors derive from `EVOXCError` (in `core`): `TraceError`, `ShapeError`, `TransformError` (axis mismatch, unsupported batching/diff — never silent fallback), `BackendError`, `PersistenceError`, `DeviceError`, `DTypeError`, `VerificationError`. No API silently swallows or works around errors. Error messages include source location (e.g. `model.py:83`) whenever a graph location exists.

## Dependencies, testing, and hardware policy

- **Deps:** `numpy` is the only hard runtime dependency of `evoxc` (`dependencies = ["numpy>=1.24"]`).
  Pure Python — no native C/Rust code in the library.
  `evoxc`'s optional extras, each enabling only its own capability: `interop` (torch, DLPack interop tests), `dev` (pytest), `iree` (IREE compiler+runtime adapters), `tvm` (apache-tvm + jaxlib for its bundled MLIR bindings), `compilers` (both), `bench` (torch, only for `evoxc.bench` PyTorch comparisons) — no `hf` extra; the `xla` adapter has no pip extra (it auto-discovers an installed JAX PJRT plugin — `pip install jax-rocm7-pjrt` / `jax-cuda12-pjrt` — or a plugin `.so` given by `plugin_path`/`EVOXC_PJRT_PLUGIN`).
  The oracle-only `hf` extra (`torch` + `transformers`, **reference implementations used to validate/benchmark, never runtime requirements**) belongs to the separate `evoxc-hf` distribution (`pip install "evoxc-hf[hf]"`), whose other hard dependency is `evoxc` itself.
  Neither distribution can contain the other: each ships exactly ONE module through `uv_build` (`evoxc` from the root, `evoxc_hf` from `evoxc_hf/src/evoxc_hf/`), and `import evoxc` never imports `evoxc_hf`, torch or transformers.
  `./tests/test_packaging.py` pins the boundary (one module per distribution on both sides, numpy-only runtime deps for `evoxc`, `evoxc-hf`'s `hf`/`dev` extras, `import evoxc` pulling neither `evoxc_hf` nor torch/transformers).
- **Python floor & uv env:** `requires-python = ">=3.11"` — the `compilers` extra's `jaxlib>=0.10,<0.11` needs Python ≥3.11.
  The uv-managed environment is pinned by `.python-version` to **3.14** (latest stable supported by the full dependency set; 3.15 is RC); the single root `uv.lock` covers the whole workspace, and the documented dev/CI install is `uv lock` + `uv sync --locked --all-packages --extra dev` (`--all-packages` is mandatory — a plain `uv sync` installs only the root project and uninstalls the `evoxc_hf` member).
  Builds are `uv build --all-packages` (both distributions) or `uv build --package evoxc-hf` (one).
- **Testing:** pytest, CPU only. Tests mirror package structure under `./tests/`. torch interop tests use `pytest.importorskip("torch")`. Spec-compliance tests live in `./tests/test_spec_compliance.py` (closure capture errors, SymbolicTensor has no `.numpy()`, staging explicitness, bind is sugar, vmap=vectorize sugar, etc.).
- **GPU policy:** v1 never requires GPU — the reference backend is a CPU numpy interpreter. GPU is only considered later for optional adapters; if ever used, scan for an empty GPU first and do not occupy it for long.

## Non-goals (evoxc core must NOT contain)

NN modules, layers, optimizers, datasets, loaders, training loops, model zoo; automatic global sharding/resharding/implicit collectives; CUDA allocator / GPU runtime / kernel scheduler; compiler optimization passes; Triton compiler; distributed job scheduler, checkpoint manager, model serving. Separate libraries build those on top.

## Status

Implemented and tested. The full explicit pipeline (`trace → lower → compile → load → run` plus `bind`/`build`/`evaluate` sugar), graph transforms (`vectorize`/`vmap`/`grad`/`jvp`/`vjp`), explicit collectives (`dist`), custom blocks (`block`), the `evoxc.numpy` graph namespace, the numpy interpreter backend (default, CPU), the StableHLO exporter, the pluggable compiler adapters and persistence/caching (`persist`, Graph save/load) are in place. The public API contract is `./evoxc/CONTEXT.md`; the adapter semantics, the per-option tables and every Known Issue are `./evoxc/backends/adapters/CONTEXT.md`. Adapter state: **iree** is validated end-to-end on llvm-cpu, CUDA, ROCm/HIP and Vulkan/SPIR-V (Vulkan on Mesa lavapipe, a software device) with **device-resident execution** — adapter outputs are device `Tensor`s wrapping the iree buffers and STAY on the device, same-device input `Tensor`s pass through with zero host round-trips, and a host input to a non-cpu executable raises `core.DeviceError` at the run boundary (placement is always explicit via `Tensor.to(device)`, and `.numpy()` on a non-cpu tensor raises). The `iree`/`compilers` extras pin `iree-base` 3.13.0, on which the llvm-cpu and ROCm/HIP legs (plus the lavapipe Vulkan suite) were re-validated: `while_loop`, `scan`, `while` nested in `cond` and the MO/NSGA2-class `non_dominate_rank` loop all compile and run with numpy parity — 0 crashes in 30 compiles, where iree 3.10/3.11 aborted at run on the HIP HAL or SIGSEGV'd `iree-compile` nondeterministically (`./evoxc/bench/iree313_rocm_findings.md`) — and the device→host readback is the adapter's own (`_readback_device_array`: zero-copy mapping for host-mappable buffers, a staging `queue_copy` on device memory) because 3.13's `DeviceArray.to_host()` is unusable on the Vulkan HAL. **CUDA** is validated on iree 3.11 (`target_backends=["cuda"]` compile option + `Device("cuda", N)` load) and was NOT re-exercised on 3.13 (the validating host has no NVIDIA GPU); **xla** runs through the PJRT C API — a ctypes driver over a plugin `.so` it discovers with no hand-wiring (the `plugin_path` option, `EVOXC_PJRT_PLUGIN`, the fixed well-known paths, then an installed JAX `jax_plugins/*/*.so`; no jax/jaxlib import) — validated against the real `jax_cuda12_pjrt` CUDA plugin and, with no env var and no `plugin_path`, against the pip-installed `jax-rocm7-pjrt` 0.10.2 ROCm plugin (rank-0 staging, PSO/DE/OpenES-shaped steps, threefry2x32 + philox4x32_10 bit-exactness, a non-domination-rank while_loop; env recipe = Known Issue #3 there); **tvm** runs with the `jax` package removed (jaxlib only for its bundled MLIR bindings), CPU end-to-end with numpy parity. The xla device-resident `run` only ENQUEUES, so a wall-clock measurement timestamps `run` + the explicit `Executable.synchronize()` (a no-op on iree/numpy). The conformance/benchmark harness (`evoxc.bench`: 98 curated examples staged through the explicit pipeline, `python -m evoxc.bench`) and the campaigns built on it are archived in the separate `evoxc-bench` repository — this tree keeps the dispatch-formation evidence under `./evoxc/bench/`.

**Sparse tensor support** (`evoxc.sparse`, numpy-backend-complete): three-phase value model — `SparseTensor`/`CSRTensor`/`CSCTensor` (concrete), `SparseTensorSpec` (trace inputs) and symbolic instances inside graphs — all ONE registered pytree node (tensor leaves + `dense_shape`/dtype/format static leaves, polymorphic unflatten, canonical-form validation); polymorphic creators/converters (`coo`/`csr`/`csc`/`from_dense`, `to_dense`/`to_csr`/`to_csc`/`to_coo`); 16 graph ops (`sparse_from_dense`/`to_dense`, COO↔CSR/CSC, `negate`, union `add`, intersection `multiply`, `multiply_dense`, `reduce_sum` → dense, `transpose`, static `reshape`, `concatenate` axes 0/1, `matmul` sparse@dense + dense@sparse) with native batch-aware numpy kernels (runtime structure validation, explicit `ShapeError`/`VerificationError`); per-op batching and vjp rules (13 ops; 3 documented `TransformError` deferrals) plus jvp rules for the bilinear ops, so `vmap`/`vectorize`/`grad`/`jvp`/`vjp` all work on sparse values, which also flow through `cond`/`while_loop`/`scan`, derive their specs in `evoxc.evaluate`, bind at the leaf level and survive Graph save/load. Numpy-backend-only in v1 — compiler backends defer explicitly. Surface: `./evoxc/sparse/CONTEXT.md`.

**Key-based functional RNG** (`evoxc.random`, numpy-backend-complete, three algorithms): `key(seed, algorithm="splitmix64"|"threefry2x32"|"philox4x32_10")` encodes the algorithm in the key's static shape/dtype and stamps it as an `algorithm` attr on all 6 `random_*` OpDefs, so `key()` is the only API that names an algorithm and the sampling ops (`split`/`split_n`/`uniform`/`normal`/`randint`/`permutation`/`multinomial`) infer it from the key operand at trace time. Deterministic and stateless: same key + operands ⇒ bit-identical values across runs; no op consumes or mutates a key; `split`/`split_n` are sugar over `random_key_mix`. Lowering is algorithm-aware (`./evoxc/backends/stablehlo/random_export.py`): splitmix64 → an inline SplitMix64 i64 expansion; threefry2x32/philox4x32_10 → `stablehlo.rng_bit_generator` per the adapter's per-algorithm `Capabilities.rng_bit_generator` set (iree declares threefry — native THREE_FRY is bit-exact on llvm-cpu and cuda while native PHILOX fails iree legalization; xla and tvm declare none, because XLA's threefry2x64 / 2-word philox4x32-10 ciphers differ from evoxc's by design), else a bit-exact inline i32 cipher expansion; the reserved per-call `rng_bit_generator` option overrides the capability. Both paths are bit-exact against numpy (f32 `normal` within the documented Box–Muller fast-path budget), never `stablehlo.rng`. **splitmix64 remains the default** on benchmark evidence (fastest on both CPU targets, tied on cuda, lowest compile times; threefry2x32 wins only the small-sample cuda cells). Only `random_multinomial` defers on compiler backends, and transforms have no rules for random ops (`TransformError`). Contract: `./evoxc/CONTEXT.md`.

**15-op batch** (`sort`/`argsort`/`topk`/`tile`/`stack`/`flip`/`roll`/`clamp`/`eye`/`matmul`/`cumprod`/`diag`/`isnan`/`nan_to_num`/`linspace`, numpy-reference end-to-end): 8 new IR ops (`sort`, `argsort`, `tile`, `flip`, `roll`, `diag`, `cumprod`, `nan_to_num` — the registry holds 119 op defs incl. `return`) and 7 frontend compositions (`topk` = sort/argsort + gather, `stack` = reshape + concatenate, `clamp` = maximum/minimum, `eye`/`linspace` = Constant compositions, `matmul` = dot sugar, `isnan` = comparison). Compiler backends export `sort`/`argsort`/`tile`/`diag` as v1 StableHLO and defer `flip`/`roll`/`cumprod`/`nan_to_num` with explicit `BackendError` (compositions run via their components); there are no vjp/batching rules for the 8 new IR ops + `eye`/`linspace` (`TransformError`, the random-op pattern). Notes: `./evoxc/CONTEXT.md`, `./evoxc/ops/CONTEXT.md`, `./evoxc/ir/CONTEXT.md`.

**External kernels (kernel-agnostic custom-kernel escape hatch — graph side + numpy backend + iree host/device dispatch):** `evoxc.external_call(name, *operands, result=TensorSpec...)` declares an opaque named call with declared output specs inside `defn` graphs (IR op `external_call`, effect `callback`); `evoxc.register_external_kernel(name, callable, backend=None, device_resident=False)` / `unregister_external_kernel` / `get_external_kernel{,_entry}` form the process-global, never-serialized **per-backend-slot** registry (`evoxc/external.py`, stdlib-only, lazy; resolution: exact backend slot → default slot → `None`). `register_external_kernel` returns the `ExternalKernel` handle: `impl(backend, fn)`, `portable(decomp)` (an `@evoxc.defn` decomposition that pre-registers batching/vjp fallback rules), the `batching_rule`/`vjp_rule`/`jvp_rule` decorators (rules land under `external:<name>`), and declarative batched-variant sugar — `batch_invariant()` (mapped ops are rebuilt with the prepended batch dims and the full batched operand stack passes through AS-IS) and `batch_variant(fn=None, *, backend=None, device_resident=False)` (registers a reserved `f"{name}__evoxc_batched"` kernel and installs the rule under both keys). No kernel code ships in evoxc: a triton kernel is written in another repo against this interface. The numpy interpreter dispatches by name and validates count/dtype/shape against the declared specs (`BackendError`/`ShapeError`, never silent; an unknown name or a `device_resident=True` slot raises explicitly). The **iree** adapter (`Capabilities.external_calls=True`) splits the graph at `lower()` into segment programs + a kernel-call plan (`stablehlo-segments` payload, `iree-vmfb-segments` artifact) and dispatches each boundary either HOST (numpy in/out, explicit `Tensor.to(cpu)` staging, static result dims required) or **DEVICE-RESIDENT** (operands passed as device `core.Tensor`s whose payload is the public `IreeDevicePayload`; results validated metadata-only, never host-copied, so the boundary costs zero round-trips, and symbolic result dims are allowed); **the device boundary is a zero-copy DLPack round trip** — the operand tensors are DLPack exporters (payload-`__dlpack__` delegation) so a kernel does `torch.from_dlpack(tensor)` and returns a `torch.Tensor`, which the adapter imports back through `HalDevice.from_dlpack_capsule` onto the run's device (device mismatch → explicit `BackendError`); the adapter adds NO fence, so a kernel whose work is still pending on torch's stream must synchronize before returning (iree's HAL has its own stream), while the export direction is safe because `run` blocks. Backends without host-dispatch (xla/tvm) fall back to the registered portable decomposition with a `UserWarning`, else raise a `BackendError` naming the op, the backend and the options, and the stablehlo exporter still defers direct export. `vmap`/`grad`/`jvp`/`vjp` compose through the rules or the portable fallbacks (neither → `TransformError`), kernels work inside `cond`/`while_loop`/`scan` bodies, and `Graph.save`/`load` round-trips with the kernel re-registered in the running process. Binding contract: `./evoxc/CONTEXT.md` "External kernels"; suites: `tests/backends/test_external_*.py` + `tests/ops/test_external_*.py`.

**Host data IO (`evoxc.io` — explicit async host↔device copy sugar):** `evoxc.io.prefetch(host_tensor, device)` / `evoxc.io.sink(device_tensor)` schedule the explicit `Tensor.to` transfers (host→device through the registered device-transfer provider, device→host through the payload host-copy path) on ONE process-global FIFO daemon worker and return `AsyncCopy` handles — `.device`, `.direction` (`"host_to_device"`/`"device_to_host"`), non-blocking `.done`, `.wait(timeout=None)`, `.result(timeout=None)` — while `evoxc.io.wait_all(timeout=None)` waits for every copy outstanding at call time. Schedule-time validation is synchronous on the calling thread; transfer errors (a missing provider, the copy's own `DeviceError`) surface VERBATIM at `wait`/`result`/`wait_all`; wait timeouts raise `TimeoutError` and never cancel copies; GC never auto-waits, the atexit drain is best-effort and the daemon dies with the interpreter; submitting from — or blocking on — the worker thread raises `RuntimeError`. Non-cpu-kind copies trigger a lazy, best-effort, one-time CUDA/ROCm primary-context bootstrap on the worker (a throwaway iree HAL device kept alive in `_bootstrap_devices`) because iree-python 3.11 exposes no real async host-copy API — the worker thread is the v1 design (adapter Known Issue #12). Module-top imports: stdlib + `core` only. Pins: `tests/io/` + `tests/backends/test_iree_host_io_parity.py`.

**Memoized-build sugar for meta-level loops (`build_cached` + `CompileCache`):** `build_cached(fn, *specs, backend=None, device=None, cache=None, **options) -> Executable` is documented shorthand for a cache-guarded `evoxc.build` — the exact `trace → lower → compile → load` composition runs AT MOST ONCE per distinct key, computed BEFORE any tracing from fn identity (`id(fn)`, pinned as the entry's keepalive), the full `*specs` tree including static-leaf content, the resolved backend name and device, and the canonicalized options. It exists for NAS/genetic-programming outer loops that produce a different static program per iteration: each distinct static value is a distinct graph and a distinct cache entry, while runtime tensors stay ordinary graph inputs validated at the run boundary like any executable (the returned object is a NORMAL executable — same-device inner loops work unchanged). Per-call env defaults (`EVOXC_BACKEND`/`EVOXC_DEVICE`/`EVOXC_TARGET_BACKENDS`) participate in the key and resolution failures count no miss; post-key trace/lower/compile/load failures count a miss, insert nothing and re-raise untouched; an unencodable static leaf raises a pre-cache `TypeError` naming the component. `CompileCache` is the in-memory LRU table (default `maxsize=128`, thread-safe first-insert-wins, `hits`/`misses`, never persisted) and there is deliberately no `cache=False` escape — plain `evoxc.build` is the no-cache path. Contract: `./evoxc/CONTEXT.md`; pins: `tests/test_build_cache.py`, `tests/test_meta_programming.py`, `tests/backends/test_build_cache_iree.py`.

**Batch transformation of a list of functions (`evoxc.batch_functions` — the "one graph for a whole population" trick):** `batch_functions(fns, axes=0, out_axes=0, *, switch_ops=None, bands=None, alignment="variant")` merges a non-empty list of N `Graph`s (or N callables/`Defn`s — never mixed) that share their input AND output specs but have different bodies into ONE ordinary graph whose leading axis is a STATIC length-N function axis: row i evaluates function i (a mapped input supplies its row, a `None`-axes input is shared). It is `vectorize`'s analogue for a *family* of functions: values are aligned across programs by an occurrence-indexed structural skeleton signature into congruence classes, so positions where every program has the same op collapse into ONE batched op rebuilt through the existing per-op batching rule (identical programs emit ZERO `select`s), same-skeleton positions whose op differs merge — when the user opts in via `switch_ops` (`True` = the `elementwise` + `comparison` IR categories) — into one class value computed as one op per variant plus a static per-row `select` cascade, and constants always collapse into a shared or one stacked `(N, …)` constant. All remaining divergence (different topology, different arity, op switching declined) is `select`-muxed at the consumers/outputs, so ANY same-signature program list merges correctly.
Two strategy arguments select among merge implementations — both pure performance heuristics, so neither changes semantics: `bands` (`None` = one flat merge; `int K` = K contiguous bands merged independently and concatenated along the function axis; `"auto"` = a static cost model over flat, fingerprint groups, groups + a coalesced "misc" band and a geometric ladder, priced with a per-dispatch constant, per-band overhead and per-category op weights) and `alignment` (`"variant"` default = a switched op joins an existing class of that skeleton already holding its variant, collapsing sibling branches; `"occurrence"` = the byte-stable legacy alignment; `"auto"` = variant-first with occurrence fallback). `bands != None` rejects `out_axes=None` tensor outputs, `bands=1` is byte-identical to `bands=None`, and constants always stack by occurrence. The merge is reported on `graph.batch_report` (the documented 12-key `BatchReport` — function/class/switch/constant/mux/op counts, the band fields and the two cost estimates — never persisted), uses static shapes throughout and needs no new backend support: merged graphs compile on iree/llvm-cpu and export to StableHLO unchanged. v1 deferrals (`TransformError`, never silent): any op without a batching rule (control flow, `runtime_call`/`external_call` without their namespaced rules, collectives, `random_*`, the 8 new IR ops of the 15-op batch, unruled block calls), a registered pytree OUTPUT node with static leaves, non-zero `axes`/`out_axes` entries and `out_axes=None` on a mapped/switched output — `sparse_*` ops DO merge. The data-supported band rule is `bands="auto"` on CPU and `bands=16` (or `bands=None`) on an accelerator, where a caller must cap k because the HIP/CUDA HAL allows 16 bindings per exported dispatch (explicit `BackendError`). Semantics, cost model and measured payoffs: `./evoxc/transforms/CONTEXT.md`.

**Merged-population / many-small-graphs cost (measured):** the Python half of a merged-population build is cheap — trace-time location capture is a `sys._getframe` frame walk with a per-filename package-classification memo (~0.018 ms/node, ~6 % over the `EVOXC_DISABLE_LOCATIONS=1` floor; `./evoxc/ops/CONTEXT.md`, contract pinned in `tests/transforms/test_batch_functions_speed_pins.py`), `ir.verify` is linear in use-count (`./evoxc/ir/CONTEXT.md` "Verification cost model"), and `lower()` costs ~0.2 ms fixed + ~13 µs/op (`./evoxc/backends/CONTEXT.md` "Lower-stage cost model"). What remains is device code. On the downstream EvoGP `EVOGP_EVAL_MODE=batch` route the warm call is dispatch-bound — `run` is 84–90 % of the per-call time and IREE forms roughly one dispatch chain per program, a count only `dispatch_formation="aggressive"` materially reduces (596 → 548; `./evoxc/bench/`). On that route `batch_functions` beats the dense padded-template route on the row axis (6.2× at 256 trees × 16384 rows, 3.0–3.2× at 1000 trees) and past dense's 64-node trace cap (4.2–5.2× against a raised-cap dense, ~23–44× against per-tree specialization), winning 7 of 8 large-scale cells and losing the pop-2048 / rows-1024 cell. It is nonetheless disqualified as a GP-loop evaluator by population-specific compile, which is ~quadratic in emitted ops — pop 2048 ≈ 44 s, pop 4096 ≈ 154 s, pop 8192 ≈ 800 s for one plan, paid per generation — an architectural blocker, not a tuning gap; a persistent on-disk artifact cache turns a repeat into 4.1 s at pop 2048 (10.8×) and leaves only the host-side decode/trace/merge. So the `dense` fixed-template route remains the GP-loop winner, while `batch_functions` is the fixed-population evaluator (a trained population re-evaluated over many row sets). Report of record: `test/benchmark/evoxc/LARGE_SCALE.md` + `LARGE_SCALE_ROUND2.md` in the EvoGP repository.

**Tree/pytree UX:** `core` ships the complete tree utility API at top level — `tree_map` (single- and multi-tree, strict structure validation with first-mismatch-path errors), `tree_leaves`, `tree_structure`, and `tree_flatten`/`tree_unflatten` (literal aliases of `flatten`/`unflatten`) — over list/tuple/dict/namedtuple/dataclass (plus `defaultdict`/`Counter` roundtrips preserving `default_factory`, and custom containers via `register_pytree_node`, which rejects `object`). Structure-mismatch errors from `evoxc.run`/`evoxc.bind`/graph input validation report the first diverging pytree path with node descriptions (`expected dict with keys ['b', 'w'], got dict with keys ['b', 'w2']`); unorderable dict keys, dataclass `InitVar`/`init=False` rebuild failures and unpreservable `default_factory` raise explicit actionable `TypeError`s; `Dim`/`DimExpr`/`Device` are single static leaves; block portable impls may return namedtuple/dataclass pytrees. The duplicated structure-walkers in graph/pipeline/vectorize/grad were consolidated onto `core.first_mismatch_path` + `core.format_path` (+ `core.describe_node` for message rendering).

**Numpy reference interpreter (measured, TensorNEAT 0.2.0 workload):** the interpreter executes a cached per-block dispatch plan (kernel resolved once at plan build, operand/result value ids, liveness free list, static-result `(dtype, shape)` fast path) over one flat SSA-id value store, releases each value at its last use instead of retaining every intermediate until the block returns, and its kernels skip the broadcast pre-check on the happy path; ndarray-backed `core.Tensor`s share one immutable `Device('cpu', 0)` (construction 0.55 → 0.18 µs).

**v1 deferrals (intentional, explicit errors — never silent fallback):** control-flow vectorization; `conv` VJP (no transposed-conv op); symbolic-length `scan`; `linalg.inv` / `norm` / `det`; non-constant pad modes; symbolic-bound `arange` / `linspace`; a few StableHLO op exports (`cumsum`, `diagonal`, `erf`/`gelu`, the linalg factorizations `cholesky`/`qr`/`matrix_rank`/`svd`/`matrix_exp`, `random_multinomial`, … — `eigh` is v1 via a while-loop cyclic-Jacobi composition). Sparse-specific v1 deferrals (explicit errors, never silent): **sparse ops are numpy-backend-only** — all 16 `sparse_*` ops defer on compiler backends (stablehlo `export` and adapter `lower()`) with an explicit `BackendError` naming the op and suggesting densify via `evoxc.sparse.to_dense`; `sparse@sparse` matmul, sparse constants, whole-sparse `bind`, and `sparse_concatenate`/`sparse_coo_to_csc`/`sparse_csc_to_coo` vjps are also v1 deferrals. Random-specific v1 deferrals (explicit errors, never silent): only `random_multinomial` defers on compiler backends with an explicit `BackendError` naming the op; the other 5 `random_*` ops export as v1 StableHLO with the algorithm-aware lowering described above. `vmap`/`grad`/`jvp`/`vjp` have no rules for random ops or for the 8 new IR ops → `TransformError` (never a silent Python-loop fallback). Vectorize/vmap batch dims are level-distinct (`batch`, `batch_1`, … — nested vmap with unequal extents works) and mapped inputs of one pass share one `Dim`. Adapters are validated on CPU, IREE additionally on CUDA (that leg on the 3.11 release — not re-exercised on the 3.13 pin, no NVIDIA GPU) and on ROCm/HIP (re-validated device-resident on 3.13.0), XLA on CUDA (the `jax_cuda12_pjrt` plugin) and on ROCm (the auto-discovered pip-installed `jax-rocm7-pjrt` plugin), and TVM CPU end-to-end (TVM on ROCm is compile-only — its wheel is built `USE_ROCM=OFF`).

## ROCm / AMD MI300X (validated on hardware)

The compiler adapters are validated end-to-end on an **AMD Instinct MI300X (gfx942, ROCm 7.1.0)**, the iree legs on `iree-base` 3.13.0. `"rocm"` is the canonical device kind (`"hip"` is an accepted alias, preserved as spelled on `Device` values; only compile-target derivation canonicalizes hip→`["rocm"]`). iree ROCm device ids are **1-based** (`Device("rocm", N)` → HAL `device_id = N+1`), and the IREE ROCm HAL has **no target auto-detection**, so the adapter supplies `--iree-rocm-target=gfxNNN` (detected via `amdgpu-arch` / `rocm_agent_enumerator`) unless the user overrides it. Recipes and traps: `./evoxc/backends/adapters/CONTEXT.md` + the `.agents/skills/evoxc-compiler-adapter-recipes.md` skill.

- **IREE / ROCm (HIP HAL) — working, device-resident.** Host→device staging uses a thread-local cached HAL device + a reusable `HOST_LOCAL|DEVICE_VISIBLE` source buffer + per-call `queue_copy` (no per-call device-creation tax), so per-call execution is not staging-dominated. On the pinned `iree-base` 3.13.0 the shapes that failed under 3.11 now work: a loop carry initialized from a graph constant (also the shape every `evoxc.scan` desugars to), a multi-carry loop whose condition reads the float carry, `cond`-nested `while`, and the MO/NSGA2-class `non_dominate_rank` while all compile and run device-resident with numpy parity (integers bit-exact, fp32 reduction-order deltas ≤ 1e-4 abs), where 3.10/3.11 aborted in the HIP HAL (`hip/event_semaphore.c` `hal.fence.await`) and `iree-compile` SIGSEGV'd nondeterministically on while-heavy MO graphs; the `while_fib` SIGSEGV recorded under 3.11 was not re-exercised. Evidence: `./evoxc/bench/iree313_rocm_findings.md`. Device→host readback is adapter-owned — a zero-copy mapping for host-mappable buffers and a staging `queue_copy` for device memory, so a large ROCm readback is a real DMA copy-out (16 MB 0.37 ms → 1.51 ms) while llvm-cpu readback stays zero-copy — and a fully input-independent counted `while` (constant carry, constant bound, constant-only body) fails to COMPILE on 3.13 with `maximum iteration count exceeded in fixed point pipeline`, while an input-consuming body or a static Python `int` bound compiles and runs (Known Issues #10 and #21 in `./evoxc/backends/adapters/CONTEXT.md`).
- **XLA / ROCm** via the pip-installed `jax-rocm7-pjrt` PJRT plugin, which the adapter auto-discovers under `jax_plugins/xla_rocm7/xla_rocm_plugin.so` — no env var and no `plugin_path` needed (`jax-rocm7-pjrt==0.10.2` validated) — device-resident, bit-exact vs numpy. The plugin's platform must physically serve the requested device kind, so a ROCm/CUDA plugin with `Device('cpu', 0)` (or `device=None`) is refused and accelerator use is `backend="xla", device="rocm"` with explicit `Tensor.to(...)` placement. The plugin aborts at interpreter exit AFTER all work completes (`os._exit(0)` is clean). fp32 `dot` runs at reduced (TF32-class) precision by DEFAULT — opt into true fp32 with the explicit `dot_precision="HIGHEST"` lower option (iree/tvm parse-and-ignore it, bit-identical; the default emits no `precision_config`). Device-resident `run` is **asynchronous** — it enqueues and returns; result reads await, timing does not — so any wall-clock measurement must call the explicit `Executable.synchronize()` after `run` (a no-op on iree/numpy; pinned by `tests/backends/test_xla_synchronize.py` + `tests/pipeline_test.py`).
- **TVM / ROCm** — compile-only: the wheel is built `USE_ROCM=OFF`, so lowering succeeds while execution raises explicitly. TVM runs CPU (llvm) end-to-end with numpy parity.


## Vulkan (`vulkan-spirv`, IREE HAL driver `vulkan`)

`vulkan` is a **first-class device kind**: `Device("vulkan", N)` derives `target_backends=["vulkan-spirv"]` (artifact label `vulkan`), executes device-resident (outputs stay on `Device('vulkan', N)`, `.numpy()` raises, `.to(cpu)` is the only readback, host inputs raise `DeviceError` at the run boundary) and uploads through a registered provider. Unlike cuda/rocm: IREE vulkan HAL device ids are **queried per-process UUID hashes**, so an evoxc index maps onto `get_driver("vulkan").query_available_devices()[index]` (never `index+1`) with one HAL device cached per `(kind, index, runtime_args)`; vulkan does **not** inherit the CUDA pinned/DMA staging tier; an out-of-range index raises an explicit `BackendError` naming the enumerated count. The compile option `vulkan_target` derives `--iree-vulkan-target=<profile>` (env `EVOXC_IREE_VULKAN_TARGET`, explicit > env > default, a raw same-name flag in `iree_compile_args` wins) — needed because IREE's default profile allows only 16384 bytes of workgroup shared memory. `core.devices("vulkan")` enumerates (an empty list — never an invented device — when nothing is usable) and `evoxc.bench` accepts the kind. Contract: `./evoxc/CONTEXT.md` "Device kinds"; recipes/traps in `./evoxc/backends/adapters/CONTEXT.md` (Known Issue 16) and `.agents/skills/evoxc-vulkan-device-recipe.md`.

Validation device on this host is **lavapipe** (Mesa software Vulkan, `deviceType=CPU`): IREE 3.11 hard-denylisted device names beginning `llvmpipe`, while IREE 3.13.0 (the pinned release) enumerates the software device with `VK_ICD_FILENAMES` unset, so the renamed-lavapipe ICD recipe is only a 3.11 fallback — it is still used here to keep this host's loader away from its wedged radeon ICD. Device→host readback on every iree kind is the adapter's own (`_readback_device_array`: a zero-copy mapping for host-mappable buffers, an explicit staging `queue_copy` on device memory), because iree 3.13's `DeviceArray.to_host()` is unusable on the Vulkan HAL. Pinned by `./tests/backends/test_iree_vulkan_device_resident.py` (6 device-guarded tests — parity, residency, `.numpy()` refusal, host-input rejection, zero-`asdevicearray` same-device loop, out-of-range index) plus device-less unit suites for the target/option/device-acquisition/env paths. **No AMD-GPU Vulkan execution is possible on the MI300X-VF host**: Mesa RADV policy-rejects CDNA3, AMDVLK/PAL has no `FAMILY_AI` IP level, and the amdgpu DRM device is wedged in a never-completing reset.

## HuggingFace models (`evoxc_hf`)

HuggingFace checkpoint support is the **separate `evoxc-hf` distribution** (`pip install evoxc-hf`; workspace member `./evoxc_hf/`), published independently from this repo and **never part of the `evoxc` distribution**: its hard dependencies are `numpy` + `evoxc`, and its optional deps are its own `hf` extra — `torch`/`transformers` reference oracles for validation/benchmarking only (`pip install "evoxc-hf[hf]"`; `evoxc[iree]`, `evoxc[tvm]` or an installed JAX PJRT plugin (`pip install jax-rocm7-pjrt` / `jax-cuda12-pjrt`, auto-discovered) for `xla` enables the compiled path). It loads a real checkpoint (`config.json` + `model.safetensors`/`pytorch_model.bin`, pure-numpy readers) and runs the whole model forward as ONE evoxc graph through the normal explicit pipeline — weights as explicit graph inputs, static `(config, seq_len, batch)` shapes.

The API is **functional**, split along evoxc's value model: `load_config(ckpt)` → a frozen static `ModelConfig`, `load_params(ckpt, cfg)` → a canonical host `dict[str, np.ndarray]`, `load_hf(ckpt)` → both as a plain `LoadedModel(config, params, family, model_dir)` record (the **data** half); `forward_fn(cfg, seq_len=...)` is the **compute function** — a pure, memoised `@evoxc.defn` `(params, input_ids) -> logits` capturing **no** weights, with `param_specs(config)` giving its specs tree; **staging** is `build(fwd, cfg, backend=..., device=...)` (the `evoxc.build_cached` trace → lower → compile → load composition, memoised per static specialisation), `run(exe, params, ids)` (→ `evoxc.Tensor` on the executable's device, never auto-copied to the host), the one host-facing shorthand `predict(loaded, ids, ...)` (→ `np.ndarray`), and the explicit placement primitives `place_params`/`place_ids` for the device-resident recipe. `reference_logits(cfg, params, ids)` is the independent pure-numpy oracle and `pack_plan`/`pack_params`/`PackPlan` the opt-in packing surface; there is no loaded-model class (`HFModel`/`build_model`/`run_model` do not exist, and `evoxc_hf.build` is a function, not a submodule). Families: `llama` (+`mistral`/`qwen2`/`qwen3` — Qwen3 adds per-head QK-Norm, a static `qk_norm` config field applied to q/k after the head split and before RoPE) and `gpt2` (+`distilgpt2`). Validated against real `torch`/`transformers` logits on eight checkpoints (`tiny_llama`, `tiny_mistral`, `tiny_gpt2`, `distilgpt2`, `gpt2`, `qwen3_0_6b`, `qwen3_1_7b`, `qwen3_8b`) plus `qwen3_14b` (14.77B params) against the independent pure-numpy oracle, and end-to-end through the compiled adapters (`iree` on llvm-cpu, `iree` and `xla` device-resident on ROCm/MI300X). `pack_weights=True` collapses the weight tree into ~4 inputs via host-side concatenation + static in-graph slices (bit-identical) and also sidesteps IREE's llvm-cpu runtime SIGSEGV above ~161 consumed inputs. `erf`-GELU configs, dynamic shapes, kv-cache and generation are explicit v1 deferrals, and `tvm` remains unvalidated for `evoxc_hf`. Binding contract: `./evoxc_hf/CONTEXT.md`.

**Benchmark verdict (HF-vs-PyTorch campaign; its harness, per-cell records and reports are part of the archived bench material):** every device leg is timed as `run` + `Executable.synchronize()` (`torch.cuda.synchronize()` on the torch legs) in the device-resident same-device loop, one leg per subprocess run strictly sequentially, so the comparison against eager and compiled `torch-rocm` is apples-to-apples. `xla`/rocm wins 13 of 14 cells against eager torch — decisively on mid-size prefill-shaped work, converging to parity and then losing at the top of the range; `torch.compile` is carried as its own baseline and is the strongest one, winning the 8–14B short-sequence (`seq_len` 32) regime while xla wins at `seq_len` 128, so the honest summary stays "evoxc-xla leads on prefill-shaped mid-size work and torch.compile leads at 8–14B with 32 tokens". `iree`/rocm is fine up to ~1.7B and then degrades hard with model size — an open iree-ROCm codegen gap, reported rather than patched, and not a host-side one: weights are placed once, outputs stay device-resident, `evoxc_hf.run` does O(1) host work per call, and the exporter emits byte-identical StableHLO for the iree and xla legs. On CPU the numpy/OpenBLAS interpreter still wins the large matmuls (`gpt2` at `seq_len` 32 is faster interpreted than on llvm-cpu), so the CPU and GPU stories are never conflated. Precision: `xla`'s default fp32 `dot` is TF32-class, so the opt-in `dot_precision="HIGHEST"` leg is the bit-accurate one; `iree`/numpy/torch agree with the golden fixtures and the numpy reference. Static footprint: `xla`'s allocator reserves the pool regardless of model size (~150 GB of a 196 GB card at 14B), so it is the leg that hits the ceiling first, while the iree leg's host cost is a one-time footprint, not a per-call cost. Legs that cannot run fail explicitly, never silently: `tiny_mistral` on `iree`/`xla` (its `gelu` needs `evoxc.erf`, a StableHLO export v1 deferral), the `iree-rocm` `O3` legs for `distilgpt2`/`gpt2` (an upstream iree-compile distribute failure on a LayerNorm-shaped reduce) and their `seq_len=128` llvm-cpu legs (an upstream `iree-compile` stack-allocation limit).
