# evoxc — EvoX Compiler

## Intent

A **minimal, explicit, compiler-neutral tensor graph compiler and runtime** (Python-first), named **EvoX Compiler**. evoxc provides an ergonomic tensor-graph language — its input language — for constructing, transforming, inspecting, caching, loading, and executing computational graphs, and it owns everything above the runtime boundary: the frontend language and its ops, EvoXIR, the graph transforms, explicit staging, and the backend-adapter contract. It deliberately does **not** own optimization, kernel scheduling, memory planning, or hardware code generation — those belong to external compilers (IREE, XLA via PJRT, TVM).

**Defining principle: Make computation explicit, require large tensors to be explicit inputs, keep `vmap` as transparent function-side sugar over `vectorize`, keep binding as transparent argument-passing sugar, keep communication, multi-device tensor preparation, and tensor placement/transfer explicit, expose and persist the graph, and let compilers do the compilation.**

evoxc learns from Nx (explicit numerical language, `block`, `vectorize`, `runtime_call`, backend abstraction), early JAX (NumPy ergonomics, `vmap`/`grad`/`jvp`/`vjp`), PyTorch (interop), and tinygrad (small inspectable IR). The Python API stays semantically close to Elixir Nx so a future Elixir implementation can extend Nx rather than duplicate it.

## Design principles (binding for all submodules)

1. **The graph is the program.** `@evoxc.defn` marks a numerical graph definition — it is NOT JIT or eager execution. There is no implicit tracing and no eager/graph mode switching.
2. **Explicit staging.** Pipeline: `defn → trace → Graph → transform → Graph → lower → LoweredProgram → compile → CompiledArtifact → load → Executable → run → Tensor`. Every stage has an explicit public function. Convenience APIs (`evoxc.build`, `evoxc.evaluate`) are *documented shorthand* compositions only — no additional hidden semantics.
3. **Minimal magic.** No API silently traces, compiles, specializes, moves/reshards tensors, inserts collectives, executes Python callbacks, or switches semantics. Caching/binding are explicit operations. Sugar is allowed only as transparent composition of explicit primitives.
4. **Python value → Python semantics; SymbolicTensor → graph semantics.** `if evoxc.sum(x) > 0:` must fail clearly; runtime tensor control flow is `evoxc.cond` / `evoxc.while_loop` / `evoxc.scan`.
5. **Local tensors + explicit communication.** A tensor is always a local physical tensor. Collectives (`evoxc.dist.*`) appear explicitly in the program; the compiler may optimize but never invent communication. Multi-device helpers (`split_tensor`, `replicate_tensor`) are explicit data-preparation utilities, not sharding transformations. **Placement is physical and explicit:** a `Tensor`'s `device` always says where its data actually lives — numpy host data can only be `Device('cpu', 0)`, and device payloads carry their real device (no label-only "virtual" devices, no relabeling). The ONLY device↔host movement primitive is `Tensor.to(device)`; run outputs stay on the device they ran on (never auto-copied to host); no API silently moves/copies tensor data, and data that is not where an API needs it raises `DeviceError` (`split_tensor`/`replicate_tensor` are v1 cpu-only host-memory utilities; `evoxc.constant` and graph embedding accept host data only).
6. **Large tensors must be explicit inputs.** Capturing a concrete `Tensor` from a closure into a graph is an error. `evoxc.constant(w)` is the only (explicit, warned) way to embed tensors. `evoxc.bind` is argument-passing sugar only.
7. **Frontend transformations are graph→graph.** `vectorize`/`vmap`/`grad`/`jvp`/`vjp` produce ordinary graphs of ordinary ops. Backends never need to understand `vmap` or Python containers.
8. **Compiler-neutral IR.** EvoXIR (region-based SSA) is the frontend IR. StableHLO is an important export target but not the definition of the IR. Backend limitations fail explicitly.
9. **No eager numerical implementation duplication.** Concrete creators (`evoxc.zeros`, `evoxc.tensor`, `evoxc.from_numpy`, …) and a reference CPU backend are the only concrete-computation paths; random generation, `linspace`, etc. go through compiled graphs.

## Value model (four distinct concepts)

| Concept | Meaning | Has storage? | Key capabilities |
|---|---|---|---|
| Python/static value | `None`, bool, int, float, complex, str, Enum, dtype, slice, config objects | n/a | Evaluated at trace time; specializes the graph. Changing it = new graph. No hidden guards/recompile. |
| `TensorSpec` | Describes a future runtime tensor | No | `shape` (symbolic dims allowed), `dtype`, optional `device`. Lifecycle: spec → trace → SymbolicTensor → run → Tensor. |
| `SymbolicTensor` | SSA value inside a graph | **No** | dtype, symbolic shape, source location, SSA identity. `x.numpy()`, `data_ptr()`, `__dlpack__` must NOT exist on it. |
| `Tensor` | Materialized runtime tensor | Yes | dtype, concrete shape, **physical** device (numpy host data ⇒ `Device('cpu', 0)`; device payloads carry their real device), explicit `Tensor.to(device)` transfers, DLPack interop (`from_dlpack` / `__dlpack__`; device payloads that implement the optional payload protocol export their buffer zero-copy — `torch.from_dlpack(t)` on a rocm/cuda tensor shares the device memory), `.numpy()` — host data only: on a non-cpu tensor it raises `DeviceError` (`.to(cpu)` first; cpu-kind payloads like llvm-cpu map lazily). Wraps numpy host memory (v1) or device buffers (iree, v1). |

## Architecture overview

```
                    evoxc  (package: Python frontend)
        tensor-graph frontend (ops core, numpy namespace, trace, block)
        function-side sugar (vmap/grad over the native transforms), explicit collectives (dist)
                         │
                         ▼
                      EvoXIR (ir)
                         │
        ┌────────────────┴──────────────────┐
        ▼                                   ▼
  native Rust core (in-process)      trace-time inference (Python)
  schemas · promotion                backends (Python)
  vectorize/vmap · AD · batch_       StableHLO export · numpy interpreter
  functions · CPU engine             iree / xla / tvm adapters
  →  evoxc._evoxc_native             (+ the "native" backend over that engine)
────────────────── runtime boundary ──────────────────
                     Tensor  +  DLPack
```
Builtin graph transformations and the optional CPU execution engine are one Rust implementation, reached through the `evoxc._evoxc_native` PyO3 extension (built by maturin, shipped in the `evoxc` wheel).

**Pipeline objects (public types):** `Defn`, `Graph`, `LoweredProgram`, `CompiledArtifact`, `Executable`, `Tensor`. Each is a distinct public type; functions never silently consume an earlier-stage object and perform missing steps.

## Cross-module contracts (binding)

**Import acyclicity (strict):** dependency layers, each importing only lower layers:
`core` ← `ir` ← `ops` ← {`trace`, `numpy`(enp)} ← {`block`, `transforms`, `backends`, `dist`, `sparse`, `pipeline`, `persist`}.
Details: `core` imports nothing from evoxc (numpy only). `ir` imports `core`. `ops` imports `core`, `ir`, `trace` (for the active-builder hook — `trace` must NOT import `ops`). `trace` imports `core`, `ir`. `block` imports `core`, `ir`, `ops`, `trace` (lazily for portable tracing). `transforms` imports `core`, `ir`, `ops`, `trace`. `backends` imports `core`, `ir` (plus lazy `ops`/`block` access for block-impl registration) and, in the numpy interpreter only, `dist` — the ONE documented `backends → dist` edge (`numpy/{__init__,collectives,exec_context}.py` import `dist.context` for single-process collective emulation; `dist` imports only `core`/`ir`/`trace` and must NEVER import `backends`). `dist` imports `core`, `ir`, `trace`. `sparse` imports `core`, `ir`, `trace`, `ops`, `transforms` (rules register one-way into `transforms`' public registries; never imports `pipeline`/`backends` — `evoxc.evaluate` lazy-imports sparse inside the function). `pipeline` imports `trace`, `backends`, `core`. `persist` imports `core` only. `io` imports `core` only (stdlib at module top; numpy/iree lazy inside functions). `build_cache` imports `core` and `persist` (its `cache`/`codec` submodules — `Cache`/`compute_key`/`encode_value`), with `pipeline`/`trace` imported lazily inside `build_cached`.

**`evoxc_hf` (the `evoxc-hf` distribution, a `uv`-workspace member — not an evoxc submodule)** imports `evoxc` only — the dependency direction is one-way and `evoxc` must NEVER import `evoxc_hf`.
It may only use evoxc's public API; evoxc-core gaps are worked around inside `evoxc_hf` and documented in `./evoxc_hf/CONTEXT.md` (a missing op or exporter deferral is never patched by editing `./evoxc/`).
The two distributions share one repository and one root `uv.lock` but publish separately, with one version per project: the root `evoxc` project is a MIXED `maturin` project (the flat `./evoxc/` package plus the Rust/PyO3 abi3 extension from `./native/`), while `[tool.uv.workspace] members = ["evoxc_hf"]` in `./pyproject.toml` makes the member its own pure-Python `uv_build` project (src layout `evoxc_hf/src/evoxc_hf/`, own `pyproject.toml`/`README.md`/`LICENSE`, version, extras `hf`/`dev`, release tag `evoxc-hf-v<version>`), and `[tool.uv.sources] evoxc = { workspace = true }` resolves its `evoxc>=0.1.0` dependency from that root project rather than PyPI.
Each distribution ships exactly ONE module — `evoxc` from the repository root (`module-name = "evoxc._evoxc_native"` installs the extension inside the `evoxc` package, so the wheel is `evoxc/` plus `evoxc/_evoxc_native.abi3.so`), `evoxc_hf` from the member's `src/` (`module-name = "evoxc_hf"`, pure `py3-none-any`) — so no `evoxc` wheel/sdist contains `evoxc_hf` and no `evoxc-hf` wheel/sdist contains `evoxc`.
Development and CI install both with `uv sync --all-packages` (a plain `uv sync` installs the root project only and uninstalls the member, leaving an importable-looking namespace package behind).
`evoxc-hf`'s `hf` extra (`torch` + `transformers`) is oracle-only — the reference implementations used to validate and benchmark it, never runtime requirements; evoxc's own extras carry no torch/transformers, and `pip install evoxc[iree]` enables the compiled path.
`./tests/test_packaging.py` pins all of this.

**Key shared contracts** (defined in `./evoxc/CONTEXT.md` and owned by the listed module):
- `core`: dtypes, `Dim`/`DimExpr` (symbolic shapes), `TensorSpec`, `Tensor`, `SymbolicTensor`, `Device`, TreeSpec + pytree utilities (`flatten`/`unflatten`, `tree_map`, `tree_leaves`, `tree_structure`, `tree_flatten`/`tree_unflatten` aliases, `register_pytree_node`), structure-mismatch contract (`first_mismatch_path`/`format_path`/`describe_node` — internal, used by trace/pipeline/transforms), device helpers (`devices` — enumerates `cpu` plus any present cuda/rocm devices, probing ROCm via the iree HIP driver so it lazy-imports iree; `split_tensor`/`replicate_tensor` — v1 cpu-only), the explicit-transfer primitive `Tensor.to(device)` + the dual device-transfer provider registry (per-backend `register_backend_device_transfer_provider(kind, backend, provider)` slots — each adapter registers its own `upload_tensor`, order-independent — and the legacy flat `register_device_transfer_provider(kind, provider)` DEFAULT slot where `evoxc.backends` installs the lazy iree cuda thunk at import; `Tensor.to` resolves the owning backend's slot then the flat default; `evoxc.constant`/graph embedding accept host data only), plus a **registration hook** so `ops` can install `SymbolicTensor` operator handlers without import cycles.
- `ir`: `Value`, `Op`, `Block`, `Region`, `Function`, `Module`, `Builder`, `Location`, effect annotations, `verify()`, IR serialization.
- `ops`: frontend op functions (`add`, `dot`, `sum`, `reshape`, …) + `runtime_call`, plus the two compiler-only escape hatches `custom_call(call_target_name, *operands, result, backend_config="", api_version=1, has_side_effect=False)` (emits `stablehlo.custom_call @target`) and `inline_stablehlo(body, *operands, result, has_side_effect=False)` (raises an opaque StableHLO snippet into the graph; contract: operand *i* is `%in<i>`, result *i* must be assigned as `%out<i>` exactly once). Both are gated per backend by `Capabilities.custom_ops`, so numpy/native reject them with an explicit `BackendError` while iree/xla/tvm forward the text verbatim and let the compiler decide validity. Top-level op exports not enumerated in the deferral/status lists: `arange` (graph Constant), stats compositions `median`/`nansum`/`std`/`var`, `norm` (vector norms only, ord ∈ {1,2,±inf}), `diagonal`; `Capabilities` and `__version__` are also top-level exports. Called with `SymbolicTensor` → builds IR into the active builder; called with concrete `Tensor` → `TraceError` (no eager mode, clear message suggesting `evoxc.constant` / explicit inputs / `evoxc.evaluate`); called outside a trace → `TraceError`.
- `trace`: `defn`, `trace`, `Graph`, `cond`, `while_loop`, `scan`, current-builder context, static-value snapshotting.
- `block`: custom ops — declaration, portable impl, per-backend impl registry, batching rules, derivative rules.
- `transforms`: `vectorize`, `vmap`, `grad`, `jvp`, `vjp` — graph→graph.
- `backends`: `Backend` interface (`lower`/`compile`/`load`/capabilities), registry (lazy activation of optional adapters), numpy interpreter backend (default, CPU), stablehlo exporter (MLIR text — also the shared lowering input for compiler backends), and pluggable compiler adapters `iree` / `xla` (PJRT C API via ctypes over a plugin `.so` it DISCOVERS — the `plugin_path` option, `EVOXC_PJRT_PLUGIN`, the fixed well-known paths, then an installed JAX `jax_plugins/<platform>/<name>_plugin.so`; `EVOXC_PJRT_PLUGIN_DISCOVERY=0` opts out of that last step; no jax/jaxlib import) / `tvm` (jaxlib only for its bundled MLIR bindings — the `jax` package is never imported) in `evoxc.backends.adapters` — optional, activated by `lower(..., backend="iree"|"xla"|"tvm")`, explicit errors when absent: iree/tvm probe their pip package in `register()` and raise there with a pip-install hint, while `xla` registers UNCONDITIONALLY (its plugin is a per-call `plugin_path`/env/discovered artifact, so the four-step discovery message — naming the pip-installable `jax-rocm7-pjrt`/`jax-cuda12-pjrt` plugins and the OpenXLA source build — comes from `compile`/`load`, with `XlaBackend.check_available()` as the explicit option-less preflight). Every stage takes options and `build`/`evaluate`/`build_cached` forward ONE resolved options dict to `lower`, `compile` AND `load` (a load-stage option such as `plugin_path` therefore reaches the load hop through the sugar too). Compile/lower options are first-class and env-aware (`./evoxc/backends/options.py` + `./evoxc/pipeline_options.py`: `EVOXC_<OPTION>` defaults, precedence explicit > env > default, and a raw same-name flag in a backend's own args wins — never both): `opt_level` (`"O0"`–`"O3"` / `0`–`3`, env `EVOXC_OPT_LEVEL`; iree → the derived `--iree-opt-level=O{N}` flag, xla → `executable_build_options` wire-format field 24, tvm → the `opt_level=` build kwarg, numpy documented-ignored) and `dispatch_formation` (iree: `"default"`/unset emits no flag — byte-identical compile args — `"aggressive"` emits `--iree-dispatch-creation-enable-aggressive-fusion`, env `EVOXC_DISPATCH_FORMATION`, an unknown value a loud `BackendError`; measured on a merged GP-population graph it takes 596 → 548 dispatches, −5 % compile at pop 4000 and −7…−9 % warm on rocm while llvm-cpu is flat-to-worse, so it ships OPT-IN and is enabled for rocm merged plans — evidence `./evoxc/bench/dispatch_formation_findings.md` + its probe and JSON records). The rest of the per-call option surface (`rng_bit_generator`, `dot_precision`, `eigh_algorithm`, `split_reduction`, `sort_emission`, `while_init_rewrite`, `vulkan_target`, `plugin_path`) is owned by `./evoxc/backends/adapters/CONTEXT.md`. The registry is extensible out of tree — `register(backend, *, replace=False)`/`unregister(name)` plus the `evoxc.backends` entry-point group probed on a `get()` miss — and iree additionally accepts `iree_compiler_module`/`iree_runtime_module` (a module object or dotted path, env `EVOXC_IREE_COMPILER_MODULE`/`EVOXC_IREE_RUNTIME_MODULE`) to drive a custom IREE build; compiler adapters DO inline portable `block` decompositions (`inline_portables`) even though their `capabilities.custom_blocks` is `False`.
`remainder` is numpy floormod on every backend: the op contract takes the sign of the divisor, the numpy kernel is `np.remainder`, and the StableHLO exporter emits `stablehlo.remainder` (fmod) plus the inline sign correction (unsigned dtypes need none), so one graph gives the same values on the numpy interpreter and on iree.
- `dist`: `group`, collectives (`all_reduce`, `all_gather`, `reduce_scatter`, `all_to_all`, `broadcast`, `collective_permute`), `rank`/`world_size` graph scalars.
- `sparse`: sparse tensor value model + 16 graph ops + per-op batching/vjp/jvp rules — full surface in `./evoxc/CONTEXT.md`; numpy-backend-only in v1 (compiler backends defer explicitly).
- `pipeline`: `LoweredProgram`, `CompiledArtifact`, `lower`, `compile`, `load`, `run`, `bind`, `build`, `evaluate`, `compile_text(mlir_text, input_specs, output_specs, *, backend=None, device=None, entry_functions=("main",), **options)` (the raw-StableHLO entry point: bypasses `lower()` entirely, so hand-written or third-party StableHLO runs through the same compile/load/run pipeline), and the explicit `Executable.synchronize()` (waits for device work submitted by earlier `run()` calls; `BoundExecutable` delegates; a no-op where the backend's `run` already blocks — iree/numpy — because the xla device-resident `run` only ENQUEUES, so a wall-clock measurement must timestamp `run` + `synchronize`). `compile` and `load` accept a `Backend` instance as well as a name, and `build`/`build_cached` forward the instance they were given through both hops.
- `persist`: versioned/self-describing/integrity-checked save-load container, explicit `Cache`.
- `io`: explicit async host↔device copy sugar over the explicit `Tensor.to` transfer — `prefetch(host_tensor, device)`/`sink(device_tensor)` → `AsyncCopy` handles (`.device`, `.direction` `"host_to_device"`/`"device_to_host"`, `.done`, `.wait(timeout=None)`, `.result(timeout=None)`), `wait_all(timeout=None)`; one process-global FIFO daemon worker executes the copies — schedule-time validation synchronous, transfer errors surface verbatim at wait/result, wait timeouts never cancel.
- `build_cache`: memoized-build shorthand for meta-level loops — `build_cached(fn, *specs, backend=None, device=None, cache=None, **options)` → `Executable`, keyed BEFORE tracing (fn identity + keepalive, full specs tree, resolved backend/device, canonicalized options); `CompileCache` (in-memory LRU `Cache`, maxsize 128, `hits`/`misses`).

## Error strategy (binding)

All public errors derive from `EVOXCError` (in `core`): `TraceError`, `ShapeError`, `TransformError` (axis mismatch, unsupported batching/diff — never silent fallback), `BackendError`, `PersistenceError`, `DeviceError`, `DTypeError`, `VerificationError`. No API silently swallows or works around errors. Error messages include source location (e.g. `model.py:83`) whenever a graph location exists.

## Dependencies, testing, and hardware policy

- **Deps:** `numpy` is the only hard runtime dependency of `evoxc` (`dependencies = ["numpy>=1.24"]`).
  The distribution is a mixed Python/Rust build: maturin compiles the in-repo Rust/PyO3 `abi3-py311` extension (`./native/`) into the wheel as `evoxc/_evoxc_native.abi3.so`, so published artifacts are per-platform wheels and a source install needs a Rust toolchain and a C compiler.
  `evoxc`'s optional extras, each enabling only its own capability: `interop` (torch, DLPack interop tests), `dev` (pytest), `iree` (IREE compiler+runtime adapters), `tvm` (apache-tvm + jaxlib for its bundled MLIR bindings), `compilers` (both), `bench` (torch, only for `evoxc.bench` PyTorch comparisons) — no `hf` extra; the `xla` adapter has no pip extra (it auto-discovers an installed JAX PJRT plugin — `pip install jax-rocm7-pjrt` / `jax-cuda12-pjrt` — or a plugin `.so` given by `plugin_path`/`EVOXC_PJRT_PLUGIN`).
  Compilers are never vendored, downloaded or linked into the extension: the wheel ships only the `evoxc` package plus the abi3 CPU-engine extension, and every adapter module is pure Python behind `OPTIONAL_ADAPTERS` lazy activation (`evoxc/backends/registry.py` imports and probes only on `get()`).
  The lone `HEADER_URL` constant in `adapters/_pjrt_c_api.py` is provenance metadata and is never fetched; a missing compiler fails at activation with a pip-install hint.
  The oracle-only `hf` extra (`torch` + `transformers`, **reference implementations used to validate/benchmark, never runtime requirements**) belongs to the separate `evoxc-hf` distribution (`pip install "evoxc-hf[hf]"`), whose other hard dependency is `evoxc` itself.
  Neither distribution can contain the other: the root `evoxc` project ships its flat `evoxc` package plus the compiled extension (maturin), the member `evoxc_hf` ships `evoxc_hf/src/evoxc_hf/` through `uv_build`, and `import evoxc` never imports `evoxc_hf`, torch or transformers.
  `./tests/test_packaging.py` pins the boundary (one module per distribution on both sides, `evoxc`'s wheel carrying the abi3 extension while the member stays pure `py3-none-any`, numpy-only runtime deps for `evoxc`, `evoxc-hf`'s `hf`/`dev` extras, `import evoxc` pulling neither `evoxc_hf` nor torch/transformers).
- **Python floor & uv env:** `requires-python = ">=3.11"` — the `compilers` extra's `jaxlib>=0.10,<0.11` needs Python ≥3.11.
  The uv-managed environment is pinned by `.python-version` to **3.14** (latest stable supported by the full dependency set; 3.15 is RC); the single root `uv.lock` covers the whole workspace, and the documented dev/CI install is `uv lock` + `uv sync --locked --all-packages --extra dev` (`--all-packages` is mandatory — a plain `uv sync` installs only the root project and uninstalls the `evoxc_hf` member).
  Builds are `uv build --all-packages` (both distributions) or `uv build --package evoxc-hf` (one); building or `uv sync`-ing the root project compiles the extension, so it needs a Rust toolchain and a C compiler. The `evoxc` wheel is a per-platform abi3 wheel (`maturin`, e.g. `evoxc-0.1.0-cp311-abi3-linux_x86_64.whl`) and its sdist carries the `native/` Rust workspace, so a source install builds the extension; the `evoxc-hf` wheel stays `py3-none-any`.
- **Testing:** pytest, CPU only. Tests mirror package structure under `./tests/`. torch interop tests use `pytest.importorskip("torch")`. Spec-compliance tests live in `./tests/test_spec_compliance.py` (closure capture errors, SymbolicTensor has no `.numpy()`, staging explicitness, bind is sugar, vmap=vectorize sugar, etc.).
- **GPU policy:** v1 never requires GPU — the reference backend is a CPU numpy interpreter. GPU is only considered later for optional adapters; if ever used, scan for an empty GPU first and do not occupy it for long.

### Native core (Rust + PyO3)

`./native/` is a Cargo workspace: `evoxc-core` (dtypes + promotion table, `Dim`/`DimExpr`, `ValueType`, attrs, the 121-op schema table, graph IR, envelope codec, per-category inference/verification), `evoxc-compiler` (builder, `vectorize`/`vmap`, `jvp`/`vjp`/`grad`, the `batch_functions` merge, extension-rule inlining), `evoxc-cpu` (the CPU execution engine: compile to an immutable plan, run on typed host buffers, all 94 dense op defs), `evoxc-runtime` (session/buffer/executable skeleton with real ownership invariants but no drivers), `evoxc` (the reusable, publishable facade crate re-exporting `core`/`compiler`/`cpu`/`runtime` behind the `cpu`/`runtime`/`full` features for non-Python frontends) and `evoxc-python` (the only PyO3 crate, depending only on the facade: `version`, `infer`, `transform`, `batch_functions`, `batching_rule_keys`, `native_compile`).
The engine builds on mature crates rather than its own N-d machinery: `ndarray` 0.17 for typed N-d views/iteration and `faer` 0.24 for parallel `dot` (no `blas`, no `matrixmultiply`/`nalgebra`); the few kernels that stay hand-written (`cholesky`, `qr`, `svd`, `eigh`, `matrix_exp`, the sorting segment walk) are documented with their measured reason in `./native/evoxc-cpu/CONTEXT.md`.
The six builtin transforms are one Rust implementation; Python keeps validation with pinned wording, pytree/spec adaptation, `Graph` reconstruction and the extension-rule bridge (`block:*`/`external:*`/`sparse_*`). There is no Python fallback — a missing extension raises an actionable `ImportError`.
The CPU engine is reached only through the OPTIONAL `"native"` backend (`evoxc/backends/native/`, registered in `registry.OPTIONAL_ADAPTERS`, numpy-mirroring staging, host-data `run`, explicit `sparse_ops=False`); the numpy interpreter stays the DEFAULT backend, so `evoxc.evaluate(...)` without `backend=` is unchanged.
Gates: `cargo test --workspace` **907 passed, 19 ignored**; `cargo clippy --workspace --all-targets --no-deps -- -D warnings` clean; `native/tools/parity_cpu.py` **73/73** (exact bool/int, `allclose` floats, bit-exact only where a case opts in; 4 rows reported `PASS~`: `dot_f32_large` at `atol 1e-5` and the three f32 `normal` 1-ulp cells); transform parity harnesses 61 cases/122 mode-runs and 25 populations/87 checks, 0 mismatches.

**Python↔numpy hand-off (binding):** payloads cross the FFI as typed numpy views and typed Rust allocations — inputs are read straight through `PyReadonlyArrayDyn<T>::as_array()` after dtype and byte-order validation and copied once into the engine's owned `Storage`, while outputs are moved out zero-copy by handing the Rust `Vec` to numpy (`ArrayD::from_shape_vec` + `into_pyarray`); there is no byte-slice reinterpretation and no element-at-a-time conversion through Python objects. An array returned by a native `run` is a fresh, C-contiguous, writeable numpy array that shares no memory with any input (`tests/backends/test_native_numpy_interop.py`). Measured: **0.592 ms per 8 MB in+out round trip** (0.296 ms/direction) and **0.43 ms end to end for an identity `evoxc.run`** at that size (`./native/evoxc-python/CONTEXT.md`).

**Measured (shared host, medians, evidence in `./native/CONTEXT.md` cost note, `./native/evoxc-cpu/CONTEXT.md`, `./evoxc/transforms/CONTEXT.md` "Measured cost", `./evoxc/bench/native_architecture_findings.md`):** whole-graph `grad`/`vjp` cost 1.22× (752 ops) and 1.27× (2252 ops) the deleted pure-Python sweep end to end — the residual gap is the Python-side envelope decode, not the Rust work.
Native run vs numpy on synthetic graphs (`native/tools/bench_cpu.py`, release, low load): `ew_chain_1e6` 1.62×, `ew_transcendental_1e6` 9.13×, `tf_softmax_8x128x384` 8.93×, `chain_2000` 0.117 ms ≈ 10.9× (6.3 ms full `native_compile`, 0.89 ms engine plan compile), `gp_gather_4096` 1.81× isolated (1.39× inside a busy eight-row sequence), `tn_step_pop500` 1.05×.
Still slower than numpy: unblocked `dot` (0.38× in the eight-row sequence — numpy uses threaded OpenBLAS, while `faer`'s parallel path is 4.8× faster when measured in isolation), `sort`/`argsort` (0.58× vs AVX2), `random_normal` (correctly-rounded libm floor).
**Real-workload check (tensorneat 0.2.0 `Pipeline.step`, one build + one run per generation):** native is FASTER than numpy — `xor_p500` 40.4–41.0 vs 49.0–49.6 ms/gen, `cartpole_p100` 24.1 vs 68.5–69.6 ms/gen, A/B-interleaved against the pre-`ndarray` engine on the same host (`cartpole_p100` 23.9 → 24.1, `xor_p500` 40.9–41.4 → 40.4–41.0, i.e. within noise; the numpy legs are identical across builds, which is the control that the harness did not move).

**Cross-backend numerics (binding, measured; full table in `./evoxc/backends/native/CONTEXT.md`):** bool/integer paths and every float op built from one-rounding primitives — including `power`, which reproduces numpy's 0/1/2/3/0.5/−1 special table and calls one libm `powf`/`pow` for every other exponent — are bit-identical between numpy and native.
Transcendentals follow the platform libm while numpy uses its own CPU-dispatched SIMD kernels (≤2 ulp in f32, 1 ulp in f64), and f32 `dot` reassociates differently through `faer` than through OpenBLAS `sgemm` (≤1e-6 relative near cancellation, `atol 1e-5` in the parity harness); a graph that branches on float comparisons can amplify those windows, so a numpy-vs-native trajectory difference is diagnosed op by op, never assumed to be a staging bug.
Measured end to end, evox's NSGA2 quickstart (f64 DTLZ2, 50 generations) is output-identical on both backends (`339` Pareto points, `max |f|` deviation `0.005165`).
**Compile/staging performance (evidence `./evoxc/bench/compile_perf_findings.md` + probe + JSON, `--seed 0 --reps 7`, numpy backend):** in-process staging decodes the serialized module at most once (`LoweredProgram` → `CompiledArtifact` → `load`), so `compile`/`load` cost ~5 µs/20 µs instead of re-decoding: 200-op graph staging total 6.29 → 1.99 ms (3.16×), `build` 8.65 → 3.68 ms (2.35×); 1700-op graph staging 52.0 → 16.7 ms (3.11×), `build` 66.2 → 30.8 ms (2.15×); 5000-op trace 65.6 → 36.4 ms (1.8×). `build_cached` hits stay ~0.04 ms. The native backend stages through the same single-decode pattern (100-op graph 3.46 → 1.51 ms).

### Backends and adapters

`numpy` (default, CPU reference), `native` (in-process Rust CPU engine), and the optional compiler adapters `iree` / `xla` / `tvm` (activated by `lower(..., backend=...)`; explicit errors when absent).
**iree** is validated on llvm-cpu, CUDA (3.11 release; not re-exercised on the 3.13 pin — no NVIDIA GPU here), ROCm/HIP and Vulkan/SPIR-V with device-resident execution: outputs stay on the device, same-device inputs pass through with zero host round-trips, a host input to a non-cpu executable raises `DeviceError`, `.numpy()` on a non-cpu tensor raises, `.to(cpu)` is the only readback.
The pinned `iree-base` 3.13.0 re-validated the llvm-cpu and ROCm/HIP legs (plus the lavapipe Vulkan suite) — `while_loop`, `scan`, `while` nested in `cond` and the MO/NSGA2-class loop compile and run with numpy parity, 0 crashes in 30 compiles (`./evoxc/bench/iree313_rocm_findings.md`); device→host readback is the adapter's own (`_readback_device_array`).

**tvm** runs CPU end-to-end with numpy parity (its wheel is built `USE_ROCM=OFF`, so ROCm lowering succeeds while execution raises explicitly).
The generated program is unchanged by the native work: nothing under `./evoxc/backends/stablehlo/` or `./evoxc/ir/serialize.py` changed, so `.lower()` output is byte-identical and compiled-backend performance is unchanged.

### ROCm / AMD MI300X (validated on hardware)

`"rocm"` is the canonical device kind (`"hip"` accepted as an alias, preserved on `Device` values); iree ROCm device ids are **1-based** and the IREE ROCm HAL has no target auto-detection, so the adapter supplies `--iree-rocm-target=gfxNNN` (via `amdgpu-arch`/`rocm_agent_enumerator`) unless overridden.
IREE/HIP is device-resident with a thread-local cached HAL device + reusable `DEVICE_VISIBLE` source buffer + per-call `queue_copy`; on the 3.13 pin the loop shapes that failed under 3.10/3.11 (constant-initialised carry, multi-carry float-conditioned `while`, `cond`-nested `while`, the MO/NSGA2 non-domination loop) compile and run with numpy parity, while a fully input-independent counted `while` still fails to compile (Known Issues #10/#21 in `./evoxc/backends/adapters/CONTEXT.md`).
XLA/ROCm runs through the auto-discovered `jax-rocm7-pjrt` plugin (device-resident, bit-exact; the plugin's platform must physically serve the requested kind, so accelerator use is `backend="xla", device="rocm"`); fp32 `dot` is TF32-class by default, opt in with `dot_precision="HIGHEST"`.
TVM/ROCm is compile-only. Recipes and every trap: `./evoxc/backends/adapters/CONTEXT.md` + the `.agents/skills/evoxc-compiler-adapter-recipes.md` skill.

### Vulkan (`vulkan-spirv`, IREE HAL driver `vulkan`)

`vulkan` is a first-class device kind: `Device("vulkan", N)` derives `target_backends=["vulkan-spirv"]`, executes device-resident, and uploads through a registered provider.
IREE vulkan HAL device ids are per-process UUID hashes, so an evoxc index maps onto `query_available_devices()[index]` (never `index+1`), with one cached HAL device per `(kind, index, runtime_args)`; an out-of-range index raises an explicit `BackendError`.
`vulkan_target` derives `--iree-vulkan-target=<profile>` (env `EVOXC_IREE_VULKAN_TARGET`, explicit > env > default; a raw same-name flag wins) because IREE's default profile allows only 16384 bytes of workgroup shared memory; readback is the adapter's own (`_readback_device_array`), since `DeviceArray.to_host()` is unusable on the Vulkan HAL.
Intel Panther Lake (`8086:b0a0`, xe) is validated on physical hardware through Mesa ANV + the pinned IREE 3.13.0: numpy parity over five same-device resident iterations with zero `asdevicearray` calls, and the Vulkan suites **101/101 with no skips**. Evidence: `./evoxc/bench/intel_vulkan_findings.md`. No AMD-GPU Vulkan execution is possible on the MI300X-VF host (RADV policy-rejects CDNA3, AMDVLK has no `FAMILY_AI` IP level, the amdgpu DRM device is wedged), so lavapipe is the software device there.

### HuggingFace models (`evoxc_hf`)

HuggingFace checkpoint support is the **separate `evoxc-hf` distribution** (workspace member `./evoxc_hf/`, `pip install evoxc-hf`), never part of the `evoxc` distribution: hard deps `numpy` + `evoxc`; the `hf` extra (`torch`/`transformers`) is an oracle for validation/benchmarking only. It loads a real checkpoint (`config.json` + `model.safetensors`/`pytorch_model.bin`) and runs the whole forward as ONE evoxc graph through the normal pipeline (weights as explicit inputs, static `(config, seq_len, batch)` shapes).
The API is functional: `load_config`/`load_params`/`load_hf` (data) → `forward_fn`/`param_specs` (compute, capturing no weights) → `build` (a memoised `evoxc.build_cached` composition) → `run`/`predict` (staging), plus `place_params`/`place_ids`, the `reference_logits` numpy oracle and the opt-in `pack_plan`/`pack_params`. ### v1 deferrals (intentional, explicit errors — never silent fallback)

Control-flow vectorization; `conv` VJP; symbolic-length `scan`; `linalg.inv`/`norm`/`det`; non-constant pad modes; symbolic-bound `arange`/`linspace`; a few StableHLO op exports (`cumsum`, `diagonal`, `erf`/`gelu`, the linalg factorizations `cholesky`/`qr`/`matrix_rank`/`svd`/`matrix_exp`, `random_multinomial`, … — `eigh` is v1 via a while-loop cyclic-Jacobi composition).
Sparse: all 16 `sparse_*` ops are numpy-backend-only (compiler backends defer with an explicit `BackendError` suggesting `evoxc.sparse.to_dense`); `sparse@sparse` matmul, sparse constants, whole-sparse `bind`, and three sparse vjps are v1 deferrals.
Random: only `random_multinomial` defers on compiler backends; the other five `random_*` ops export as StableHLO with algorithm-aware lowering.
`vmap`/`grad`/`jvp`/`vjp` have no rules for random ops or for the 8 new IR ops → `TransformError` (never a silent Python-loop fallback).
Compiler adapters: collectives and `runtime_call` are not compiled in v1 (multi-rank runtime channels not wired); symbolic dims are supported PER-OP by the exporter — elementwise/cast/select/reductions-over-static-dims/transpose/concat/dot work, while reshape/conv/slice/pad/reduce_mean-over-a-dynamic-reduced-dim are rejected with a clear `BackendError` at `lower()` (this is why vmap of softmax/layernorm/attention-style per-sample functions defers on compiler backends; numpy and native handle all symbolic shapes).
Vectorize/vmap batch dims are level-distinct (`batch`, `batch_1`, …) and mapped inputs of one pass share one `Dim`.
Adapter validation state: CPU, IREE additionally CUDA (3.11 release) and ROCm/HIP (re-validated on 3.13), XLA on CUDA and ROCm, TVM CPU end-to-end (TVM on ROCm compile-only).

## Notes for Agents

**Native architecture proposal:** `./NATIVE_ARCHITECTURE_PROPOSAL.md` is the approved target design.
Its numerical-authority rule is implemented for the graph transformations: `vectorize`, `vmap`, `grad`, `jvp`, `vjp` and `batch_functions` are one Rust implementation in `./native/`, reached through the `evoxc._evoxc_native` PyO3 extension.
Python keeps only frontend duties — executing `defn` bodies, adapting trees/specs, and serving extension rules (`block:*`, `external:*`, `sparse_*`) through the native extension-rule bridge.
Python shape inference/verification at trace time, lowering/StableHLO export, and the backend adapters remain Python; the native ports of inference/verification exist and are parity-tested but are not yet on the Python hot path, and the native runtime crate is a skeleton.
Do not reintroduce a builtin batching/AD/merge implementation in Python: extend the native engine and expose it through the bridge.
Do not reintroduce a second CPU kernel implementation either: the numpy interpreter (`./evoxc/backends/numpy/`) is the *reference behaviour*, `./native/evoxc-cpu` is the fast engine, and the two must agree wherever the contract says so (`native/tools/parity_cpu.py` is the gate — exact bool/integer paths, `allclose` floats with case-declared tolerances; the documented residuals are the 3 f32-`normal` 1-ulp cells and f32 `dot`, where `faer`'s blocking differs from OpenBLAS `sgemm`).
New op work lands in three places in this order: the op schema/inference, the numpy reference kernel, and the native kernel — a native-only op or a numpy-only op is a bug.

**README (`./README.md`) is the front page and a derived document.**
